### 12.7 Target-order and fork gates

One read-only research worker traced how a target order and an exported
instance are gated today, citing sources. It found three things.

**A target order is judged against the launchpad, never the target.**
`requireGateClaims` (`scripts/lib/handoff-ledger.mjs`) needs a passing
launchpad `npm test` row at the launchpad's code identity whenever a met
criterion names `npm test`. The target's bytes enter no identity. In the
operator's fork, that launchpad gate is the kit's own: in the exported
fixture, `npm test` ran fresh in 41.7 s and `npm run test:docs` in 14.0 s,
with 45 core-only rows skipped (`docs/evidence/WO-201/gate-in-kit.json`). So
Angular orders do not pay core's 25-minute gate today.

**The gap runs the other way: DotLn-Angular's own tests are never run or
recorded by the lifecycle.** A target class's `checks` reach only the
resident path. There, named test commands run with a 30-second limit, too
short for Playwright or integration suites. Worse, a criterion that names
the target's own `npm test` would wrongly demand a launchpad row, because the
claim check matches any `npm test`.

**In the fork, gate reuse is keyed by the whole code identity.** That
identity includes `dotln.config.json` and any instance code. Inference:
registering a target or editing the fork's own code reruns every carried kit
suite. No rule covers tests of the fork's own additions. The suite table is
a kit file, and WO-208 names a review burden for extension code but no suite.

The operator's direction (2026-10-13) lands in two orders:

- **Target orders pay the target's own tests, plus the launchpad's document
  gate. WO-210 gains:**
  - a `gate` declaration on each registered repository: its commands and

### 12.8 Where a repository's knowledge lives

The operator named the crux. DotLn carries much machinery that a target
repository never needs, and much knowledge it does need: the repository's
product documents, its planning passes, and its orders' records and audit
trails. At work, several people will share one work fork, or use their own
forks for different repositories. So that knowledge must live with the
repository, not in any one fork.

The 2026-10-11 route recorded the opposite: targets receive only branches
and pull requests, and the launchpad holds their orders and evidence
(products 03, 06 and 12). Asked three questions, the operator chose:
- **Timing:** before the real run. WO-210 gains the change, so the UI shell's
  first planning pass and records land in DotLn-Angular from the start.
- **Packaging:** the same pull request, with a records-only commit after the
  reviewed code commit on the order's branch.
- **Contents:** the repository's product documents, its planning passes, and
  each order's file with its decisions, verification and final-review
  reports. Raw evidence (transcripts, logs and captures) stays in the fork.

The fork keeps the machinery, the control state, cross-repository
workstreams, its own planning, raw evidence and requests to core. It is
never ignorant of a sibling repository: for each one it holds its own data
or a link to where the source of truth lives there (the repository, the
commit and the path of each order's records and of the repository's planning
passes and product documents), and its index shows them (operator direction,
2026-10-13). Products 03, 06 and 12 now say so.

WO-210 carries the design:
- a documentation root that each registered repository declares, which the
  roles read as repo-native authority;
- the records-only commit, and the publication check that it touches only
  that root;
- target-scoped planning documents written into that root.

WO-083's real run is the first use. WO-192's role text follows, and WO-213's
private-path screen covers records bound for a target. The root's default
name is open for the operator at review.
