## 6. The live qualification: the answer to the fork's question

**Where the hook's decision is written.** The emitted hook's
`registeredTargetAdmission` (`packages/skeleton/src/harness-host.ts`)
journals every admission it carries as a row in the session's host
observation log, `docs/control/local/harness/<digest>.jsonl` under the
launchpad root, where the digest is the SHA-256 hex of the Claude Code
session id (`sessionKey`); the file is ignored, mode 0600, appended by
`record`. The row is `{recordedAt, event: "PreToolUse", tool,
registeredTargetAdmission: {workOrder, repositoryId, kind}}`, and the
hook's reply to the host carries the reason text (`DotLn's
registered-target admission: repository <id> (<identity>); recorded target
worktree of <order> on <branch>; main's committed operator grant admits
repo.push and pr.open; <phase> makes <command> legal. Host deny and ask
rules still apply.`). A withholding is journaled as an `advisory` row with
the reason (an unreadable registration, a phase that does not make the
command legal, an origin that is not the recorded one). A session reads
the file as a file, with no host prompt: it is inside the repository under
the ignored control lane, and the session knows its own id from its
dispatch banner (`harness usage <session>` prints token counters from the
transcript, not these rows). So: yes, the hook's own decision is readable
without a prompt, and `scripts/test-harness.mjs` reads the same rows in
core's fixtures.

**What the journal cannot show.** The hook does not observe what the host
does after its `allow`. A prompt the operator answers leaves no hook row
(the tool then runs; the next row is the ordinary PostToolUse
observation). A denial does: the `PermissionDenied` hook appends
`{event: "PermissionDenied", advisory, delegated: true}` to the same file
and the host handler records a typed `HostPermissionDenied` row with the
tool, the input digest and byte count and the bracketed rule the host
named. Claude Code's published hooks reference, as FINAL-002 read it,
says a hook's allow skips the permission prompt except for actions no mode
auto-approves, and that deny and ask rules are still evaluated regardless
of the hook's reply. Whether the auto-mode classifier still asks after the
hook's allow is the open question of core's qualification row (WO-221's
`host-qualification.md`), and only the fork's episode answers it. With the
operator's interim trust entries present, a prompt that does not appear
proves nothing about the hook (the entry admits the same command); the
fork's D6 reads this right: WO-005 shows the hook's decision in the
journal, and WO-006 without the entries is the test of the host honoring
it.
