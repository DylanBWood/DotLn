### 3. A criterion

A criterion names one behavior where its user meets it, the supported inputs, the public command and the observable result, and takes one of three closed forms:

1. scenarios, each with a control that fails at the base, or under a planted fault where the base already passes;
2. an invariant held by construction (one choke point, and a check that bans the raw call), which one counterexample on supported input disproves;
3. a list frozen at a named revision, built before the implementation from a source independent of the code under judgment. A discovery step may build it. Where the refuter cannot establish the population, discovery is its own order first.

At filing a refuter predicts each outcome without seeing the planner's, and a lint checks the fields and references. The executor's first step makes each control fail by its command; one that cannot be told apart returns to planning at once.

### 4. What returns an order, what is read again, and when it stops

- **Supported input** is what a kit writer produces or a documented command's contract admits, and a faithful fixture of either counts whoever typed it. Where a command takes free text, that is text a writer actually produced or a form its contract names.
- **A criterion is met** when its named evidence holds at the tree's identity and no ground below applies.
- **An order returns to repair on:** a listed scenario or a required suite failing at that identity, reproduced alone where possible and under the recorded concurrency and limits where the failure depends on them; a retained reproduction of an earlier blocking finding that still shows a violation; on supported input, in what the change adds or alters, a counterexample to an invariant a criterion states, a wrong result accepted or a record lost or misfiled; a regression against `main` on supported input; a breach of the clean-room floor or of an authority or credential boundary. A reproduction is judged by its input and its observed result, whoever found it. A refusal that names its remedy returns nothing where the contract permits that refusal. Wording returns an order only where a criterion requires an emitted text. Anything else is recorded with a reopening condition.
- **A check that did not run** neither passes nor returns. The judge gets it run through the host's permission flow; where only the owner can supply what it needs, the judge states that block once with the line that clears it, and waits.
- **Evidence.** One passing product gate at each code identity, reused across roles, and document evidence on the exact tree. After a repair the blockers are reproduced and the affected claims and consumers judged again; unknown impact widens the read, and a reviewer may read a whole component where a repair's effect is uncertain. Nothing else is re-read. The first verification attacks the whole change. The final review judges integration, release surfaces and any interaction verification names as unread.
- **To his question.** A change invalidates every earlier test result, so the gate runs at each new code identity. A reading is a search, not a test: repeating it over code the change cannot reach revalidates nothing, and on a large change it never comes back empty.
- **The bound.** Failed verifications and failed final reviews count together for one activation. At the second, a planner and a refuter change how the returned criterion is evidenced, with the Objective still true as written, or propose a cut. A smaller promise is the owner's, and he may give it in advance in the order's text. At the third the order is held, attended or driven, and nobody is asked. The lifecycle has no such action today and the router counts the two kinds apart: until the termination order ships, the bound is run by attended dispatch and a hold the planner records under Not now.

### 5. What programs read

A machine decision is taken from a record that has a validator, and prose is never read for a fact. The form follows the writer:

1. **A worker's result**: one whole versioned JSON payload, bound to its launch and tree independently of the payload, validated before filing. A missing, malformed or second result leaves the review incomplete and files nothing; an identical retry files once.
2. **What a command records** (a verdict, criterion judgments, findings, attestation, cost): JSON given to that command, validated there, kept as an immutable record the lifecycle event names by digest. The Markdown beside it is prose no program reads.
3. **What a person authors and reviews as a diff** (an order's fields and criteria): one versioned JSON block between exact reserved marker lines, read with no Markdown grammar and refused whole on a duplicate marker or a failed validation. If an example can change what is extracted, the record becomes a file of its own.

The moves come in that order, each a small delivery that removes the reader it replaces. The linter and the readers share validators; the checker the console's tests hold is a seed to promote, and the strict extractor has to be written. The pinned Markdown parser stays for the document check. Closed records keep their readers. There is no repository-wide rewrite.
