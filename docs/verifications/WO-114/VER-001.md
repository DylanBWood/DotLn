## VER-001-F1 — Per-event publication times out an existing gate test

**Severity:** major. **Criterion:** 5. **Status:** requires repair.

**Expected:** `npm test` green on the subject without spending an existing
test's timing margin.

**Observed:** `npm test` run 1: 26 passed, 1 failed, 406.02 s, 71
fresh tasks. The skeleton suite ran 433 tests, 432 passed and 1 was
cancelled with `test timed out after 60000ms`. Run 2 on the unchanged
subject: 27 passed, 0 failed, 352.62 s. The executor recorded one passing
run (344.96 s). The failure is intermittent, and the subject causes it. The failing test is `WO-143 thirty
consecutive kill/restart rounds remain openable on once and loop paths`
(`packages/skeleton/test/resident.test.ts:864`, 60 s timeout at line 865);
its once path finished and its loop path was cut off.

**Reproduction and attribution:**

1. Build HEAD in scratch: `git archive HEAD packages tsconfig.json
   package.json`, link `typescript` and `@types`, `tsc -b --force`.
2. Alternate isolated runs of
   `node --test --test-name-pattern="thirty consecutive"
   packages/skeleton/dist/test/resident.test.js`: HEAD 31.8 s and 32.4 s;
   WO-114 subject 48.0 s, 39.3 s and 41.3 s (+23% to +51%).
3. A preload counting renames onto `runtime-status-v1.json`, run on the same
   test with `NODE_OPTIONS=--import`, observed 777 publications.
4. A micro-benchmark on this host measured 8.97 ms per atomic write with file
   and directory fsync, and 0.12 ms and 0.81 ms to read and parse the 391 KB
   index. A reviewer measured 14.2 ms and 0.88 ms. At 9-14 ms, 777
   publications take 7-11 s, which matches the isolated slowdown. The
   inference is that per-event fsync, not index parsing, spends the margin.
   Gate concurrency then pushes the test past 60 s.

**Required repair:** restore the gate's margin without weakening the WO-143
test or dropping per-event publication. The file is disposable and is rebuilt
on restart, which bears on how much durability each publication needs. The
executor chooses the method. The measurement reopens
[WO-114-D002](../../evidence/WO-114/decisions.md), recorded in D008.

## VER-001-F2 — The order section depends on which writer published last

**Severity:** major. **Criteria:** objective, 1 and 4. **Status:** requires
repair.

**Expected:** every writer of a store projects the same generated index, so
the file carries every Active or Open order, and a restart rebuilds the last
published bytes.

**Observed:** `ResidentStore` defaults its index to
`new URL("../../../../docs/work-orders/README.md", import.meta.url)`
(`packages/skeleton/src/resident-store.ts:122-124`). Only the host passes an
override (`resident-host.ts:103-107`).

- The generated presence hooks import skeleton from the harness snapshot
  (`.claude/hooks/presence-pretooluse.mjs:5`, `.runtime/harness/68c6cb9c738d03a0`).
  Its `resident-store.js` is byte-identical to the current build, but the
  snapshot has no `docs/`. Reproduced here: a host published `available 54`,
  then one `recordHarnessHeartbeat` call from the snapshot published
  `unavailable 0`. Resident-launched workers set `DOTLN_RESIDENT_STORE`
  (`worker-transport.ts:100`, `script-episode.ts:85`), so this happens on
  every hook event during a live worker episode.
- `recordPresenceObservation`, `answerHandoff` and `clearMissionHold` build
  `new ResidentStore(directory)` (`resident-store.ts:302`, `255`, `280`),
  ignoring a host's configured index. A reviewer reproduced 4 of 32
  publications that differ from the rebuild from the same log prefix. The
  executor fixture appends through its own store with the fixture index
  (`runtime-status.test.ts:117`), so it does not exercise this path.
- `dotln resident` passes no index (`dotln.ts:124-127`), so the tool
  checkout's index is used whatever `DOTLN_LAUNCHPAD` selects. A reviewer's
  temporary launchpad held a derived `WO-999`. The projection reported the tool
  repository's 54 orders as `available`, without `WO-999`.

**Required repair:** one index source per store for every writer, including
heartbeats through the harness snapshot. Add a fixture that publishes through
a helper and a snapshot-hosted heartbeat.

## VER-001-F3 — A projection failure aborts durable resident work

**Severity:** major. **Criterion:** design ("The file is a projection, never
authority"). **Status:** requires repair.

**Expected:** a failed disposable publication neither aborts nor truncates the
log-authoritative operation. The next publication rebuilds the file, as the
store's own comment says.

**Observed:** `publish()` runs unguarded inside `append()` after the event's
fsync (`resident-store.ts:95-105`), and again at the end of each transaction
(line 197). With the index path made unreadable at the dispatch append,
reproduced here:

- `tick` rejected with `EISDIR` after `ScriptEpisodeDispatched` was durable.
  `adapter.run` was called 0 times, the next tick skipped the dispatched id,
  and a restart recorded `ScriptEpisodeLost`.
- `start` rejected and left the lifetime lock held in-process; a second host
  got `worker store already has a live host`.
- A presence command threw after `OperatorPresenceObserved` was durable and
  skipped its `ClockSampled` (log 1 to 2 events).

The triggers are synthetic: a directory in place of the index or status file,
and a read-only store directory. By code inference, ENOSPC or EACCES take the
same path. The finding also contradicts the implementation evidence ("Missing
or malformed index data is marked unavailable"): read errors throw. It also
contradicts the premise of the `scripts/lib/evidence-sources.mjs:358`
exclusion, because the excluded module can change what the registered
resident store appends.

**Required repair:** contain publication failures, so the operation completes
and a later publication rebuilds the file. Add regressions at dispatch, start
and presence.
