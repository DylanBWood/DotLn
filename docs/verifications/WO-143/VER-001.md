## Findings

### F1 — minor — the README says the refusal names `host-lock-recovery`; the operator CLI never prints it

- **Criterion:** 5, with criterion 3's operator reading. Boarded up in
  [D003](../../evidence/WO-143/decisions.md#wo-143-d003--board-up-ver-001-f1-the-readme-says-the-refusal-names-the-guard-but-the-cli-prints-its-redacted-line).
- **Observed:** `packages/skeleton/README.md:6` says refusing guards "name the
  inspection path". `:279` says, in the `dotln resident` runbook, "the
  diagnostic names `host-lock-recovery`". Running the built CLI against a
  legacy append guard, a legacy lifetime guard, a live-owner guard and a
  malformed-owner guard gave exit 1 each time. Stderr was only
  `worker host refused; inspect the store and declared environment before
  retrying` (`dotln.ts:267`, redaction since WO-009 `eddce52e`). The guard path
  exists only in the store-level `Error` (`worker-store.ts` `refuse()`).
- **Expected:** operator documentation that states what the operator sees.
- **Reproduction:** `cli-legacy.mjs` in this session's scratchpad. It writes a
  real store with `--once`, plants each guard state and runs `resident --once`
  and `presence away`.
- **Severity and route:** minor. Documentation on a surface final review may
  edit. The CLI behavior is unchanged from released v0.32.0 (the race baseline
  printed the same line). Product 03's "refuse with the inspection path"
  (`03-architecture.md:1702`) is accurate for the store and should be checked
  for the same ambiguity. Criterion 3 stays met: it is a fixture criterion at
  the store boundary. If final review reads it as requiring the command to
  print the path, that is a code change and routes to repair.

### F2 — minor — the delayed-claimant fixture does not detect removal of the claim-time canonical fence

- **Criterion:** 2 (serialization), evidence strength only. Boarded up in
  [D005](../../evidence/WO-143/decisions.md#wo-143-d005--board-up-ver-001-f2-the-delayed-claimant-fixture-does-not-detect-removal-of-the-claim-time-fence).
- **Observed:** `worker-store.ts:205` rechecks the canonical link after a
  successor claim. D001, product 03 and the README all name this check as what
  stops a delayed claimant from touching shared state. Mutant M3 deletes only
  that line, and all eight WO-143 tests still pass. The fixture asserts four
  things: refusal, one claim, an intact guard link and the successor's
  acquisition. `release()` re-checks the link at `:217` before unlinking, so
  the guard stays intact either way.
- **Reproduction:** `delayed.mjs` replays the fixture's steps and records
  `host.lock`. On this tree the delayed claimant refuses, and `host.lock` keeps
  the dead original's pid. Under M3 the refused delayed claimant publishes its
  own pid in `host.lock` while the successor holds the guard. By code reading
  (not exercised: the probe SIGKILLs it), the mutant also leaves the claimant
  with `#locked = true`, so a later `release()` would unlink the successor's
  lock.
- **Severity and route:** minor. The shipped code is correct. What is missing is
  one assertion, for example that `host.lock` content and inode are unchanged by
  the refused claimant. Final review owns routing (D005).

## Observations

- **O1 — pre-existing contention race, boarded up in
  [D004](../../evidence/WO-143/decisions.md#wo-143-d004--board-up-a-pre-existing-contention-race-met-during-verification).**
  - **The race:** `acquire` reads `present(lock)`, then `regularFile(lock)`
    and `readFileSync(lock)` (`worker-store.ts:274-278`). A live holder's
    `release()` needs no guard. With the contender paused after `present`, the
    holder's release makes the contender throw a raw `ENOENT`.
    `ResidentStore.transaction` retries only
    `/already has a live host|recovery is busy/` (`resident-store.ts:127`). A
    presence command or a resident transaction therefore fails instead of
    waiting.
  - **Released behavior:** reproduced identically on released v0.32.0; this
    order moved the check but did not create it.
  - **Consequences:** no event written or lost; the store reopens.
  - **Unreproduced inference, carried in D004's follow-up:** `rmSync` of a
    retired target can throw `ENOTEMPTY` if a delayed claimant links into it
    mid-removal. That would make `acquire` throw after publishing `host.lock`.
    It is based on Node's documented `maxRetries` default of 0 and on the
    release order. I could not step inside the native `rmSync`.
- **O2 — refusal latency roughly doubled.** A permanently refusing guard (legacy,
  live or malformed) now takes 8.1 to 8.3 s at the CLI, against 4.5 s for
  released behavior on this host. The retry budget is the same (200 attempts).
  Inference: each attempt now creates, fsyncs and removes a prepared owner
  directory. No criterion bounds this. It lengthens the wait before the
  inspection message, and it makes transient contention more tolerant.
- **O3 — residue is real and bounded per kill.** After 40 in-flight kills, 4
  unreferenced `.host-lock-*` directories remained (3 holding `owner.json`, 1
  holding `owner.json` and `host.lock`). By code reading, not classified in
  the run, this includes a killed claimant's own prepared directory: the next
  reclaim removes the old target and its own directory, not the claimant's.
  D001 and the README disclose residue. Nothing reads it, and the normal path
  leaves none (the compatibility test asserts `["events.jsonl"]`).
- **O4 — the per-call coverage is at the Node `fs` call level.** The executor
  states this, and it matches the trace. Partial effects inside one native call
  (`rmSync`, `writeFileSync`) are not stepped. All of them fall on unpublished
  or already-retired private paths.
