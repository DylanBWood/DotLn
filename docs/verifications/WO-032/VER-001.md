## Draft assumptions the sources do not support

Criterion 2 asks for facts that are not in the evidence it names. I verified this
myself against the original files rather than accepting the executor's account.

- **"different loadout hashes."** `docs/evidence/WO-011/selfhost-audit.jsonl`
  records only `policyHash` (`fnv1a64:d0000feb2622b0d4`, the `feedback-v1` policy
  axis) and `selfhost-verification.jsonl` records only `inputHash`
  (`fnv1a64:eb312ec46e198b93`, the `verification-v1` capsule axis). I walked every
  key containing "hash" in both logs; **no `LoadoutGraph` semantic hash exists in
  either.** The board shows the two real hashes with an explicit `hashKind` and
  leaves `loadoutHash` `unknown` with the reason. Renaming a policy hash into a
  loadout hash to satisfy the sentence would have been a fabricated provenance,
  which the same work order's "evidence-backed only" rule forbids.
- **"activation, review, and release-close events."**
  `docs/control/orders/WO-031.jsonl` holds exactly six events:
  `WorkOrderActivated`, `ImplementationReady`, `VerificationRequested`,
  `VerificationCompleted`, `FinalReviewRequested`, `FinalReviewCompleted`. There
  is **no release-close event**, and the three operator dispatches carry **no
  actor attestation** — the `actor` field appears only on the three model
  completions. A person's identity is therefore unavailable, and the board says
  so instead of inventing one or asking the operator to attest retroactively.
- **`renderTooltip`.** Not an exported compiler API. The implementation uses the
  actual tooltip-bearing `renderCompiledDiff` and proves hash equality against its
  receipt text. A naming error in a draft is not an interface contract.
- **"blockers" from `status --json`.** Status has no blocker-reason field. The
  board renders `blockers` as the recorded failure source when a verdict is
  `fail`, states in the cell explanation that absence is not proof of being
  unblocked, and keeps the generated index's conservative dependency evidence in a
  separate `dependencyCheck` cell rather than merging two different claims.

I judge these **work-order draft defects, not implementation defects.** The
implementation satisfied the binding constraint, made every gap visible in the
product itself, and recorded the reconciliation in both the work order and the
receipt where the final reviewer will hit it. Criterion 2's only stated failure
condition concerns the human row, which is present. Nothing here changes behavior,
contracts, acceptance or authority, so no repair episode is warranted.

## Observations for the final reviewer (non-blocking)

1. **`exportedLoadouts` invokes exports by name suffix.** Any export matching
   `/Loadout$/u` is called with the fixed expiry `86400000`. Today the three
   matching exports are all factories and no non-factory export shares the suffix
   (`compileLoadoutProgram` and `compilePlanRefuter` do not), so behavior is
   correct. But a future `*Loadout`-suffixed non-factory export would throw inside
   `collectSources`'s single try/catch around the whole module loop and silently
   degrade the **entire** Builds panel — and possibly `feedbackUnits` — to
   `unavailable`. Per-export isolation would confine that blast radius. The README
   documents the heuristic; the risk is forward-looking only.
2. **`ProjectionContext.section` catches every exception**, including a genuine
   projector bug, and reports it as `Unsupported or invalid <title> source` —
   blaming the source for what may be the projector's fault. The state is honest
   and visible rather than an empty success, which is what criterion 1 asks for,
   and a live-collection test asserts all eleven named sections are `available`
   against current repository sources. Worth knowing when a panel goes
   `unavailable` in the field.
3. **`builds.ts` `maturityReason`** is declared `let` and never reassigned. Style
   only.
4. The board's `refutation-verdicts` section shows only the lexicographically
   latest receipt by dated filename, which is the documented rule and matches the
   convention today. It is not a staleness or gate-legality judgment, and the cell
   explanation says so.
