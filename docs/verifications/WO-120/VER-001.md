## Observations (none routed to repair)

- **O1 — the registered-repository branch has no committed fixture.** Severity:
  low. It is correct as verified above, but the suite would not catch a future
  change to the `**Repository:**` line's format. Not routed to repair: the
  order's criteria do not require it, the behavior is verified here, and
  fabricating a fixture repository belongs to whichever order next touches that
  renderer. Reproduction of the check is recorded above.
- **O2 — allocation serialization is launchpad-local.** Severity: low,
  disclosed. `materializeOrder` shares one `WorkerStore` lock at
  `<control>/local/derived-orders`; two disconnected checkouts of the same
  repository can allocate the same identity. This is stated in D001's reopening
  condition and in both product write-backs, so it is a declared boundary, not
  an undisclosed gap.
- **O3 — an out-of-shape human edit fails the whole index, not one row.**
  Severity: low. `readIndex` runs `checkGeneratedSections` on any authority
  whose header declares provenance, so adding a section to a filed draft makes
  `work-orders index` refuse until it is edited back. The refusal names the
  path and is recoverable, and the documented edits (objective, criteria,
  surfaces, dependencies, release classification) all keep the shape. Recorded
  as a limit of the contract, not a defect.
- **O4 — the `dotln intent` bridge resolves scripts from the installed kit.**
  Severity: low. `packages/skeleton/src/dotln.ts` reaches
  `../../../../scripts/lib/derived-orders.mjs` relative to its own build
  output, so the command works from the kit and not from a skeleton package
  published without `scripts/`. The packages are private and
  `prepublishOnly` refuses publication, so nothing is broken today; a future
  publication decision inherits this coupling.
