## Findings

**F1 — close output escapes the retained report (criterion 3).** Low severity; it breaks the criterion's text on a reachable publish path.
- Observed: `release.mjs:2128` calls `refreshHarnessRuntime` on the no-release, non-dry-run path. That function writes `Refreshing pinned runtime (<cause>); npm run build.` straight to `process.stdout` (`scripts/lib/harness-runtime.mjs:199`), not through `writeOutput`.
- Expected: the full report holds what standard output holds today, and stdout carries the summary.
- Reproduction: a session-scratch copy of `scripts/test-release.sh`, pointed at this worktree's scripts, with one added case:
  - it pins an old materialized runtime, re-pins to unmaterialized bytes, commits WO-099 at `v0.0.2` below `v0.2.0` and runs `release close WO-099 --publish`;
  - result: outcome `no-release`; stdout's first line is `Refreshing pinned runtime (pins-differ); npm run build.`; the named full report does not contain it.
- Reach: a no-release close whose runtime is stale. A Claude close that went through this order's recovery has a current runtime; a Codex close need not.
- Rule a repair must hold: every line `release close` writes during a close reaches the retained report, and stdout carries only the summary. A no-release, stale-runtime fixture asserts both.
- Alternative: the operator waives criterion 3 with `npm run resume -- waive 3`, naming their words.

**R1 — a leftover with restricted beacons never clears (criterion 4's surface).** Medium. It contradicts no criterion clause.
- Path:
  - `packages/beacons/src/control-beacon-fs.mjs:149` creates `.control-beacons/restricted/<hash>` at `0o111`;
  - `finish` opens these to `0o700` (`prepareBeaconDisposal`) before the snapshot and `git worktree remove`;
  - on a failed removal, the callers' `restoreBeaconPermissions()` puts back `0o111` on what survives;
  - `verifyWorktreeRemoval` then walks the leftover with `readdirSync`.
- Reproduction (session scratch, real `scripts/lib/worktree-removal.mjs`):
  - the same matching receipt verifies at `0o700`;
  - at `0o111`, `verifyWorktreeRemoval` and `removeUnregisteredWorktree` throw `EACCES … scandir` and the subject stays;
  - after a manual `chmod 0o700`, the same receipt removes it.
- Consequence: every same-run attempt and every re-run records a `leftover` blocker that names the path. The branch and the writer are retained. Nothing unsafe is deleted. The session can finish only with a hand chmod, the kind of rescue the order exists to remove.
- Rule a repair must hold: leftover verification and removal open anchored restricted beacon directories the way `finish` does and restore their mode on failure. A fixture leaves a `0o111` restricted beacon directory behind a partial removal and shows a valid receipt removes it on retry.

**R2 — retry bookkeeping (criterion 4's surface).** Low. From source reading, checked against the diff.
- In `finishPublishedWorktree`, removing any one leftover resolves every blocker with the matching action, `finish` or `settle`. A different row's settle failure then loses its reason and retry line in `row.blockers` and the summary. Cleanup stays `blocked` while that row is retained.
- Retained paths are gathered from every `previousAttempts` row whatever its outcome. A path an earlier attempt removed, if later reoccupied (for example by another branch's registered worktree), becomes a `retained` row with no reason.
- Rule a repair must hold: a leftover removal resolves only blockers that name its path; earlier paths are re-checked only when an earlier attempt left them retained; a retained row always carries a reason and a retry command.

**R3 — an unrecorded leftover (criterion 4's surface, at the edge of the Design).** Low. From source reading.
- Trigger: no retained record names the subject. Either the record is unreadable, or the earlier partial removal came from `worktree.mjs finish` run directly.
- Result: `subjectPath` is undefined, the branch is deleted and cleanup reads `clean` while the unregistered directory remains. Its removal receipt in `docs/control/local/retained/WO-NNN/` names the path, but nothing reads that lane.
- Why no criterion breaks: the order requires recovery only for a path a retained record names. Branch deletion in this state predates the order. The role sentence's completion check ("its directory is gone") would still catch it in a session.
- Rule: settle through Adjacent Repair or record a reasoned deferral. If repaired, a retained removal receipt for the order that names a directory still on disk keeps the branch and a blocker naming the path.

- If a child's `Material recovery:` or `Worktree removal proof:` line fails `JSON.parse`, that child's stdout is skipped from the transcript.
- If `finish` removes the subject but its own branch deletion fails, the run records `deleted` after its retry and still reports `blocked` until the next run.
- The removal snapshot refuses sockets and FIFOs and hashes every file in the subject, so a worktree holding an unreadable file now blocks removal where `git worktree remove` alone would not. I found no socket or FIFO in this worktree and no DotLn source that creates one there.
