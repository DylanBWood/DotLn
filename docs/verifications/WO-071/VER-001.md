## Observations and limits

Recorded, not routed to repair. None contradicts an acceptance criterion.

- **O1 — the registered-profile compile has no production caller.** `compileRegisteredRepositoryLoadout` and `applyRegisteredRepositoryProfile` are reached only from `scripts/test-authority-grants.mjs`. This repeats the boundary WO-042's final review recorded for `compileRegisteredLoadout`, is fail-closed, and matches WO-072 owning the first consumer. The order's deliverable is the compile, and criterion 2 judges the compiled WorkOrder, so the adapter plus its proof discharges it; wiring is not this order's scope.
- **O2 — a profile's `allowedEffects` does not narrow the base; only `deniedEffects` does.** This is the decided semantics (D003's rejected alternative, and criterion 2's own clauses), and it is correct under WO-042's monotone floor. But the product 07 write-back does not say it, and WO-033 §Phase 2 describes a profile's allow list as if it bounded authority ("never merge, deploy, or write to another repository"). Under the implementation that bound requires explicit `deniedEffects` entries. WO-072 and WO-073 should not assume otherwise.
- **O3 — exactly one active mechanic is required.** `registeredProfileGrant` throws `INVALID GRAPH` for any other count. Today's `seiri` and `contributor` loadouts each declare one, so the restriction is currently unreachable; a multi-active loadout would meet it as an error rather than a diagnostic.
- **O4 — malformed-profile refusal presents as an uncaught module-load throw.** It names the configuration path and the exact field, so criterion 3 is met, but it is a stack trace rather than the clean `error:` line that the unknown-id and missing-base refusals print. I reproduced the identical presentation for a pre-WO-071 malformed key (`unknown configuration key "unknownSection"`): the cause is `loadConfig` running during `scripts/resume.mjs` module initialization, inherited from WO-069, and unchanged by this order.
- **O5 — the schema refuses the bare `*` effect pattern.** `validateEffectPatterns` rejects `"*"` in both `allowedEffects` and `deniedEffects`, so a registration cannot express a total deny-all even though product 02 defines effect patterns as "exact strings or prefix globs ending in `*`". The direction is fail-closed and no criterion requires it, but the registration schema is narrower than the envelope contract it claims to instantiate.
- **O6 — criterion-2 evidence uses a synthetic graph.** Both the executor's case and my probes compile the compiler's `authorityFixture`, not a real skeleton loadout. The semantics are established; behavior against a shipped loadout's real envelope is untested.

Two things I checked and found sound rather than defective, recorded so a later reader need not re-open them. The everyday-AI-user edition gained a registered-target claim although it links neither product 07 nor 12; its `06-roadmap.md#roadmap--application-release-ladder` link is the document's H1 anchor, whose locked section runs to end of file and therefore covers the new WO-071 release-boundary paragraph, so product 08's claim-traceability rule holds and the lock refresh is attributable.
