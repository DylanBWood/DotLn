refusal. A loud refusal on an unusual source shape is explicitly acceptable; a
partial list published into a tag is the defect. I ran the shipped extraction

Twelve of fourteen refuse loudly or extract correctly. The two exceptions are the

`.prettierrc.json` sets `endOfLine: lf` and leaves `useTabs` and `tabWidth` at
their defaults (`false`, `2`), so the assumption matches the formatter actually in
force, and — per the table — a change to either produces a loud refusal rather
than a wrong manifest.

### A correction to my own analysis

My first end-to-end reproduction of the `default:`-relocated variant ran inside a
release fixture and reported that `release close --publish` **succeeded** and
published a manifest declaring five implemented cadences deferred. That result was
misleading and the adversarial refuters caught it. The fixture installs a stub
`npm` on `PATH` (`scripts/test-release.sh:90`, `printf "fixture npm test passed"`),
so the fixture's own evidence gate is simulated, not executed.

In the real pipeline `close()` calls `runEvidence(root)` at
`scripts/release.mjs:858`, **before** `baseManifest` at `:861` and `publishTag` at
`:870`, and `evidenceCommands` includes `npm test`, which runs the real
`scripts/test-release.sh`. Because this diff makes that suite copy the live kernel
source and assert the exact six and eight arrays, a relocated `default:` arm makes
`npm test` fail, `runEvidence` throws, and the close refuses before any tag is
constructed. That variant is therefore a loud refusal end-to-end, and the
executor's design is sounder than my first reading of it. I re-ran the check
correctly and record the corrected result in the table above.

The remaining variant is not covered by that argument, and is recorded as
Observation 1.

## Observations — recorded, not scored

### 1. A `case` clause placed after the trailing `default:` arm is silently ignored

This is the one variant that survives the whole gate. Appending
`case "Burst": …` **after** the `default:` arm in `evaluateCadence` leaves
`evaluable` and `deferred` byte-identical to the canonical arrays, so the suite's
`deepStrictEqual` assertions still pass, `npm test` is green, and a published
manifest would declare `Burst` deferred while it is implemented. I confirmed this
end-to-end against the real, unmodified `scripts/test-release.sh`:

```text
Burst case inserted AFTER the default arm
RESULT: SUITE PASSED -> the evidence gate is SILENT about the mis-derivation
cadence manifest evaluable: ["Once","After","Every","Gate","Until","Backoff"]
cadence manifest deferred:  ["Burst","Calendar","Window","While","Sequence","Merge","Race","Repeat"]
```

`tsc --strict` accepts the shape, Prettier preserves it, and the repository has no
ESLint config, so nothing in the toolchain forbids it. This is **not scored
against WO-015**: the order named this exact boundary ("bound the evaluator case
capture at the switch's `default:` arm"), its fail-closed clause enumerates
*missing* structures rather than reordered ones, all nine acceptance criteria hold
against canonical source, and reaching the state requires editing
`packages/kernel/`, which this order forbids and which is byte-identical here.

It is a real latent gap for whichever future order implements a currently deferred
cadence — **WO-102 (cadence boundary sweep) is the obvious one**. A bounded remedy
exists inside the same function and the same declared scope: capture the switch
body through its own closing brace and count case labels across the whole body,
not only the slice before the arm.

```js
/^([ \t]*)switch \(cadence\.kind\) \{([\s\S]+?)^\1  default:([\s\S]*?)^\1\}/m
// caseCount = countCases(group2) + countCases(group3)
```

I validated it: canonical source yields the identical six and eight arrays, while
both `default:`-ordering variants refuse loudly. Recommended as a one-line
hardening for a follow-on order, not as a WO-015 repair.

### 3. The fixture is now coupled to live kernel source

representative, and the work order asks for exactly that. The consequence is that

doing its job and the failure is loud; noted so a future implementer is not
surprised, and so the pin is updated rather than deleted.

  future hardening.
