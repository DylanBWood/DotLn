## Observations

**O1 — an unjudged *earlier-dated* enforced pass still diverges from the gate.**
`checkPlanGate` demands a receipt for every enforced pass, while
`latestPlanningPass` considers only passes on the latest enforced date. If a
pass is filed on day 1 and a second on day 2 before either is judged, the gate
stops on day 1's missing receipt and the selector aims at day 2. This is not a
regression — the previous implementation also selected by maximum date — and the
order's design explicitly keeps latest-date selection; D001 already names it as
a reopening condition ("latest-date selection disagrees with the gate outside
the reported same-day case"). Recorded for the planner, not against this order.

**O2 — two *unjudged* same-day passes now fail loudly instead of silently.**
`latestPlanningPass` throws `ambiguous planning passes on <date>` rather than
inventing chronology from file position, so the gate is unsatisfiable through
the supported commands in that state. The previous behavior was not better: it
re-selected the same position-first pass on every dispatch and stopped at "one
judgment per pass", which is the stuck state the order was filed to remove. The
fixture pins both the selector and both transports on this path. Recorded so the
reviewer does not read the new error as a capability loss.

**O3 — the direct-request filename change is contained.** Requests are now
`direct-<64 hex>-<pass id>-<scope>.json`, and `fileDirectRefutation` accepts both
the new and the legacy shapes through one regex, which the fixture exercises by
filing a legacy-named pending request. The evidence-pass id (`evidence-<slug>`)
can never reach that filename: `refute --direct` rejects every option except
`--scope`, so the direct path always holds a `planning-` pass. The added
`pending.pass` comparison is redundant with the filename for new requests and
load-bearing for legacy ones.
