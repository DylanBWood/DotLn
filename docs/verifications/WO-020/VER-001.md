## Acceptance criteria

**1. Exhaustive round trip, malformed lattice, future codebook — met.**
My independent decoder assigned 104 v1 codewords with no collision, largest
`51064`, and round-tripped every one. Sweeping every integer from `0` through
`102128` (twice the largest) gave `known=104`, `malformed=101292`,
`future-frames=733`, totalling `102129`, with no integer decoding to a guessed
state. The shipped test reaches the same three numbers through its own inline
framing oracle. Framed versions `2` and `3` return only `unknown-codebook` and
the version; version `0` is reserved and malformed; `code >= 672` and the
eight unassigned outcome slots per refusal/provenance pair (64 codes) are
malformed. `decodeBeaconSize` also refuses `-1`, `0.5`, `NaN`, `Infinity`,
`Number.MAX_SAFE_INTEGER + 1`, and `-1n`, and labels a `10^30`-scale framed
future size `unknown-codebook` without interpreting its higher digits.

**2. Live and replay byte-identical; audit inputs unchanged — met.**
`beacon-fs.test.ts` writes the live and replayed projections into separate
directories, compares them with both `readFileSync` equality and the external
`cmp(1)`, and asserts `st_size` and `mtimeNs` equality: size `49764`,
`mtimeNs 1200007000000`. `beacon.test.ts` separately serializes the events and
the full audit projection before deriving beacons and re-compares after,
proving non-mutation, and asserts the nested receipt is the last entry of
`projectL0Receipt`, with `action` `schedule.cancel` and `time` equal to the
last event's `occurredAt`. I confirmed the same file independently: the host
beacon's 467 JSON bytes decode to a `beacon-projection` whose `receipt` is the
L0 entry `audit:evt_21:external-effect` at `time: 1200007`. I also ran the CLI
twice into separate directories; both files were byte-identical with identical
`mtime_ns`. `packages/skeleton/src/audit.ts` and `reactor.ts` are byte-identical
to the base, so the audit projections used as inputs cannot have moved. The
executor's self-reported claim is tested separately, as the criterion requires.

**3. Sweep decodes unreadable and garbled content — met.**

## Observations (non-blocking)

**O1 — `sweepBeacons` throws `ENOENT` on a directory that was never created.**
`createBeaconWriter` deliberately does not create the directory, and `emit`
creates it lazily, so a writer that produces no records leaves nothing to
enumerate and `readdirSync` throws. This is unreachable from the shipped CLI,
because the committed fixture always yields at least one host projection before
`renderConstellation(sweepBeacons(...))` runs, and I confirmed the current
behavior directly. WO-021's cross-worktree sweeps will call this on directories
it does not own, so returning `[]` for an absent directory is worth deciding
there.

**O2 — staging is a sibling of the beacon directory, and for the documented
in-repo invocation that sibling is the repository root.**
`mkdtempSync(join(dirname(directory), ".dotln-beacon-stage-"))` is the right
call for the stated goal — keeping partial names outside the observed directory
— and `rmSync` in a `finally` cleans up on both success and exception, which I
confirmed leaves `git status` untouched. But `.dotln-beacon-stage-*` is not in
`.gitignore`, so a hard kill between `mkdtemp` and the `finally` would leave an
untracked, non-ignored directory in the repository root. One `.gitignore` line
would close it. The README's "staging is removed on normal completion/failure"
is accurate for exceptions and does not claim crash safety.

**O3 — the staging-plus-rename design assumes one filesystem (inferred, not
tested).** `renameSync` across a mount boundary returns `EXDEV`. If a beacon
directory were itself a mount point, its parent would be a different filesystem
and emission would fail rather than fall back. Nothing claims otherwise, and
the probe explicitly limits itself to per-file atomicity on the checkout's
volume, so this is recorded as a boundary to name in WO-021 rather than a
defect.

**O4 — `scripts/probe-beacon.py` hard-requires `codex --version`.**
The version block calls `check_output` for `node`, `npm`, and `codex` outside
the `attempt` wrapper, so the probe cannot run on a host without the Codex CLI
even though nothing it measures depends on it. It reproduced cleanly here only
because this harness happens to have `codex-cli 0.153.2` installed. Its
temporary directory is also created in the repository root; it is self-cleaning
and I saw no residue.

**O5 — the generated index links this report before it exists.** After the
`verify` dispatch, `docs/work-orders/README.md` links
`docs/verifications/WO-020/VER-001.md`, which the allocator had named but no
one had written. This is correct behavior for a projection of control state,
and the link resolves as of this file.
