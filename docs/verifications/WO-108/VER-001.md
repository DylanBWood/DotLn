## Instrument disclosure

The deliverable is the instrument. `corpus/mutation/mutate.mjs` both produced
the evidence and ships a `--check` mode that certifies it, and `resume verify`
allocated this report through `scripts/resume.mjs`, itself a prior deliverable.
The execution guide's self-referential-instrument rule applies, and abstention
is not the right response: the failure mode here is loud, not silent — the
matrix is append-only JSONL, the manifests are regenerable from committed source
alone, and every claim is arithmetic over data I can read myself. Compensating
controls used throughout:

1. **`--check` was never its own oracle.** I re-derived the census and the
   selection in a separate Node process by importing `loadSnapshot`,
   `enumerate` and `selectCampaign` directly and byte-comparing the result to
   the committed manifests, and I recomputed every published statistic from the
   raw `kill-matrix-*.jsonl` with my own code. `--check` passing is reported
   below as a fact, not as the reason the numbers are trusted.
2. **Sites were checked against Git, not against the runner.** For all 32 sites
   I fetched the base blob with `git show <base>:<file>` — bypassing the
   runner's snapshot code entirely — and confirmed the recorded byte range,
   source hash, and line number.
3. **The measurement was re-executed.** I ran the full gate and an independent
   `--reproduce-survivors` batch in this session on this host.

## What was verified

### 1. Determinism of census and selection (contract 1, 2)

Importing `loadSnapshot`/`enumerate`/`selectCampaign` in a fresh process at the
pinned base regenerated `candidates-<base>.jsonl` (1,292,014 bytes) and
`sites-<base>.jsonl` (15,517 bytes) **byte-identically**, and a second in-process
run was stable. `--enumerate` separately passed the runner's `stableFile`
comparison without rewriting any pinned artifact — after a measured run it can
only compare, never overwrite. Census 2,901; selection 32.

The census enumerates twelve operator classes covering every shape contract 1
names: comparison swap (1,231), condition neuter (620), condition invert (617),
numeric off-by-one (180), arithmetic swap (102), statement delete (83), ordered-
array deduplicate (48), trace-string perturb (10), early-return delete (7), plus
three single-site historical shapes. The enumerator's opacity limits are real
code, not prose: comments, regexes and whole templates including interpolations
are marked opaque, and unterminated constructs throw rather than being guessed.

**Selection is verdict-independent structurally, not just by assertion.**
`selectCampaign(candidates)` receives only the candidate array — it has no
parameter, import, or filesystem read that could reach the matrix, the
transcript, or any verdict. The rule is: the eight seeds located by unique
exact-text search with an explicit ambiguity guard, then per declared
file/operator the median of the preferred group. It cannot discard a compile
kill, a timeout, or an inconvenient survivor because it runs before any of them
exist and is reproducible from committed source alone.

### 4. The runner refuses rather than guesses (contract 3, 4)

Read directly in `evaluate()`: a compile failure with no `error TS` diagnostic
refuses with "no verdict"; an empty package suite after fresh compilation
refuses; a missing or empty TAP report refuses; a nonzero test exit with no
named failing test refuses. Only `exit 0 && failed === 0 && cancelled === 0 &&
passed > 0` yields `survived`. `requireGreenBaseline` refuses any non-green
baseline before a single row can be appended. `runMatrix` additionally upgrades
a `survived` verdict to `killed-by-test` with a named runner assertion whenever
the mutant's total test count differs from the baseline's — a mutant cannot
survive by deleting tests. Each row is validated before append, and an observed
matrix-size change refuses instead of rewriting.

Both campaign baselines in the transcript are green at 281/281, and the run
completed in ~27 minutes against the declared 45-minute budget.

## Disclosures

**D1 — Self-referential instrument.** Recorded above under Instrument
disclosure. The runner certifies its own evidence via `--check`; that result is
reported but is not the basis of this verdict.

**D2 — A sample, not coverage.** 32 of 2,901 candidates were measured — about
1.1%. The 62.1% detection figure describes those 32 sites and nothing else. The
work order, corpus README, findings header, policy `selection` field, ledger and
planning map all say so; no surface I checked claims whole-codebase coverage.

**D3 — Operator skew inside the selection.** `condition-neuter` supplies 21 of
the 32 selected sites, so the aggregate rate is largely a statement about
guard-neutering detection. In the census the largest class is `comparison-swap`
at 1,231 sites, of which 2 were selected. The composition is fully visible in
the per-operator table, but the headline percentage should not be read as
representative of the census mix.

**D4 — Three single-candidate operators.** `condition-force-true`,
`array-content-delete` and `numeric-force-zero` have exactly one census
candidate each. They are seed-specific shapes for historical probes 1, 3 and 8
rather than general enumeration classes. Their sites verify against the base
source, but their per-operator rows are single-site observations.

**D5 — The work order was rewritten in place.** The 2026-09-06 amendment
replaced most of the original document rather than appending to it; the original
survives only in Git history at `HEAD:docs/work-orders/WO-108-mutation-probe.md`.
I cannot verify an operator instruction given in a chat. What I did verify: the
change is dated, names the five things it supersedes, states that the objective
and the survivor/non-fix boundary remain, and is independently recorded in
`docs/planning/work-order-map.md`. It did not weaken evidence in the executor's
favour — the delivered artifacts satisfy the original acceptance criteria 1
through 4 as written, and the only criterion the amendment widened is 5's path
list, whose new entries are all present, disclosed and justified. The one
substantive narrowing is the exhaustive-run expectation, which D2 covers.

**D6 — M00030's verdict is unknown, not survived.** Neutering the sparse-storage
premise guard in `writeV3BeaconFile` removes a `throw`, letting v3 Beacon writes
proceed on an incompatible profile; the suite then reached 120,003 ms with no
TAP report. The runner recorded `timeout` / phase `test` / `compiled:true` and
excluded it from the conclusive denominator rather than relabeling it a kill or
a survivor. That is exactly the contract's required handling. The mutant's true
verdict remains undetermined at this bound; a longer-timeout re-measurement is a
candidate for a future order, not a defect here.

**D7 — Kill rows may report fewer than 281 tests.** The executor's audit records
M00010 at 275 tests with 44 failures, because a failing test can abort nested
test registration. No statistic depends on that field: strength uses verdict
counts only, and survivor rows are separately required to show 281/281.

## Observations (non-blocking, no repair required)

**O1 — `parseTap` takes the last summary block.** With `node --test` this is the
top-level total, and both baselines plus all eleven survivors show a coherent
281/281, so the parse is correct here. It would be fragile if a future runner
emitted trailing per-file summaries after the aggregate.

**O2 — `--reproduce-survivors` has no closing baseline.** `--run-all` brackets a
session with `baseline` and `baseline-after`; the reproduction batch checks a
green baseline only before the loop. Each mutant still gets a fresh scratch
build, and a changed verdict refuses, so no recorded evidence can drift silently
— but a post-batch baseline would close the same environment-drift gap that
`--run-all` already closes.

**O3 — Reproduction is slower on this host than on the executor's run.** My
independent baseline took 62.8 s against the executor's 44.1 s for the same 281
tests. The 120 s per-mutant timeout still cleared, but the margin on this host
is narrower than the campaign's was, which is worth knowing before anyone reads
a future timeout as a code change rather than a load difference.

**O4 — `--check` is not in `npm test`.** The amendment scopes the root wiring to
"run the runner's self-tests in `npm test`", and that is what was done, so this
is compliance rather than a gap. But the consequence is that the standard gate
would not notice a stale `findings-WO-108.md`, an edited matrix row, or a
transcript that stopped corroborating its totals — only a deliberate `--check`
does. It is a read-only re-derivation that runs in seconds against a base commit
that is now main's head, so a future order could wire it cheaply.

**O5 — The runner is a single-writer command by convention.** It detects an
observed matrix-size change before appending, which is a real guard, but the
README correctly declines to call it a concurrent-writer lock. Nothing in this
work order needs more; a future order that parallelizes campaigns would.
