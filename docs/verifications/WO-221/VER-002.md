## Nonblocking follow-ups

### VER-002 F1 — A literal-fallback order leaves main unclean for the next start

**Class:** defect in a declared surface; follow-up. It breaks no criterion and no behavior `main` had, because it needs the new `hostRules: "literal"` opt-in.

Under the opt-in, `worktree start` writes `.codex/rules/dotln-WO-NNN.rules` into the main checkout, and neither core's `.gitignore` nor `scripts/kit/gitignore.template` ignores that path. `literal-dirty-main` shows main reporting `?? .codex/rules/dotln-WO-999.rules`; the next `worktree start` then exits 1 with `working tree is not clean` naming that file. Without the opt-in (`control-dirty-main`) the second start succeeds. With the file ignored (`literal-ignored-rules-main`) the rules remain and the second start also succeeds. So an instance that turns the fallback on can start no other order while a literal-fallback order is in flight. `release close` tolerates untracked files, so the order's own close is unaffected.

**Repair rule:** a DotLn-owned per-order rules file must not make main unclean for `worktree start`, and an instance's seeded `.gitignore` must not need a hand edit. Add a fixture that starts a second order while a literal-fallback order is in flight. Boarded in [D035](../../evidence/WO-221/decisions.md#wo-221-d035--ver-002-follow-up-a-literal-fallback-order-leaves-main-unclean-for-the-next-start).
