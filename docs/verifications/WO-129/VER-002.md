## Findings

### F1 — a full gate can pass while persisting none of its successes, and nothing says so (non-blocking, high)

- **Criterion:** not an unmet acceptance criterion; it bears on the objective's premise that a gate's successes are reusable, on the Cost line, and on operator-review assumption 1.
- **Observed:** the repair's final evidence gate (`npm run test:full` under `npm run harness -- evidence`, tree `054427e5`, recorded 2026-09-13T03:20:31.668Z, `executionMode: "fresh"`, 78 executed and passed, 717.6 s, exit 0) left no record in the shared cache. Every one of the 69 suite directories has its newest record at 02:59:46.486Z, from the previous gate; the 03:20:31Z gate's source digest differed from every stored record, so a record from it would have been a new file. It is not a missing precondition: 27 of that gate's 37 suite rows carry an `inputHash`, none is marked reused, all exit 0, and the recorded `freshReasons` carry no `unreusable snapshot` or `undeclared suite` policy — so `before.reusable` was true and identity was computable. Nor did it throw: the runner's top-level `catch` sets exit 1, `runHarnessEvidenceChecks` would then have recorded a failing row, and instead it recorded the runner's green row and a clean `git diff --check`. The gate rows from that same process did persist — they are written to `docs/control/local/harness/checks.json` inside the worktree, while the cache is now outside it.
- **Expected:** a passing gate's executed successes are retained, or the gate says they were not.
- **Reach:** 717 s of executed evidence is unavailable to compose from, and any later gate at those inputs re-executes. Reuse is unaffected wherever the cache is writable, which is why AC7's rows, the fixtures and my own runs are unaffected. The order's own `saveSuiteSuccess` returns a boolean that `runGateChecks` discards (`test-runner.mjs:888–905`), so this condition is indistinguishable from a normal fresh run.
- **Why I did not make this blocking:** the identity and cache logic are correct and repeatedly demonstrated, including seven gates in this same series that did persist, one of them mine minutes ago on the same cache. The distinguishing factor is the writing process's environment — the cache now lives in the sibling checkout, outside the worktree a sandboxed executor is scoped to — and I cannot reproduce the Codex host's write context from this session, so I will not assert its cause. WO-129's criteria do not require this, and operator-review assumption 1 already accepts a disposable cache rebuilt by execution.
- **Repair shape, if taken:** have the runner count persisted successes and report the count beside `freshSuites`/`reusedSuites`, failing or warning when an executed, hashed, passing task is not retained. That makes the condition visible wherever it occurs and costs one counter. Diagnosis of the 03:20:31Z invocation should come first; a follow-up row is the right home.
- **Reproduction:** read the retained gate rows and the cache; see items 6, 7 and 8 below.
