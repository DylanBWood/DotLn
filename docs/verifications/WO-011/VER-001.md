## Criterion 5 — fail-conservative correction on semantic events only

**Met.** There is no surface-language path to inspect, which is the strongest
form this criterion can take: neither `applyFeedbackCorrection` nor the
reactor's correction branch reads message text at all. The trigger is the
conjunction of `actorId === "operator"` and one of the four typed
`SEMANTIC_CORRECTIONS`.

The transition is a monotone meet. `allowedEffects` can only shrink — wildcards
and every declared destructive effect are filtered out; `scopeExpansionAllowed`
is forced false; `preserveEvidence` and `diagnosisRequired` are forced true;
the correction id is appended, which also makes the transition idempotent. No
branch restores an effect, re-enables scope expansion, clears
`diagnosisRequired`, or discards evidence, so a mistakenly classified event can
only tighten. Downstream, `diagnosisRequired` blocks both
`FeedbackAuditRequested` and `FeedbackAuditExecutionRequested`, so the
tightening actually binds rather than being recorded and ignored.

The negative paths are covered and I confirmed the shapes in source: a
worker-authored `OperatorCorrectionReceived` leaves policy unchanged and takes
the `feedback-untrusted-event` branch; an operator-authored ordinary message —
the test uses `"profanity alone"` explicitly — leaves policy unchanged; a
genuine correction narrows `allowedEffects` to `["feedback.audit"]`, emits a
`FeedbackDiagnosisRequested` continuation, and makes the next execution request
refuse. Live and replayed state and decisions are compared for equality, so the
correction survives replay rather than living only in the live host.

Named evidence: `WO-011 correction is pure, typed, idempotent, and
monotonically tightens every semantic correction kind` in the compiler tests;
`WO-011 regression fail-conservative-correction` and `WO-011 shared reactor
dispatches a pinned audit, refuses expiry, and makes semantic correction a
durable diagnosis request` in the skeleton tests.

## Non-blocking observations

None of these blocks the verdict; none requires a change to code, contract,
acceptance, schema, compatibility, authority or prior evidence. They are
recorded for the final reviewer and for whoever extends this rung.

1. **The attribution predicate does not match a session-URL trailer.**
   `hasAiAttribution` catches the `Co-authored-by: <AI>` and
   `Generated/Written/Co-authored with|by <AI>` families — I confirmed it also
   catches an emoji-prefixed variant and a bare `Generated by ChatGPT`, and
   correctly passes a human co-author, a `Claude` mention in a subject line, and
   prose about generated-with-AI docs. It does not match a
   `Claude-Session: <url>` trailer or an `Assisted-by: Claude` trailer. For
   equipped worker invocations the generation-side rung covers the first case
   (`attribution.sessionUrl: false`), so the defence-in-depth pair holds where
   both rungs apply; the byte-side predicate alone does not. This matters
   concretely at final review: some Claude Code sessions are instructed by their
   harness to append exactly such a trailer, and the operator's standing rule
   forbids AI attribution on commits and PRs. The repository's history is clean
   (zero matching trailers across all commits), and the hook is installed only
   in the fixture, so nothing is currently wrong — but a reviewer relying on the
   hook to catch it would not be protected. Extending the predicate is a
   candidate, not a WO-011 obligation.
2. **The pinned verifier subject excludes two of the order's own artifacts.**
   `FEEDBACK_SOURCE_PATHS` pins seventeen files, which does not include
   `scripts/feedback-evidence.mjs` or the two new test files other than the
   fixtures module. The blinded verifier therefore could not inspect the
   generator that validates the retained streams. That is a defensible boundary
   — the generator is not what the two acceptance criteria are about — and the
   repository verifier reads it instead, as I did. Worth stating so a later
   reader does not over-read the capsule's coverage.
3. **`operatorPreference` is carried but deliberately unconsulted.** The
   `evidence-judgment` request records the operator's preferred answer and
   `reason()` never reads it; the verdict depends only on consistent
   independent witnesses. That is the correct and strictly stronger reading of
   correctness-over-sycophancy, and the field usefully records what was
   available and ignored. A reader expecting the field to be used may
   momentarily read it as dead code; it is not.
4. **One workstream branch per store.** The reactor now tests the feedback
   branch before the verification branch, so a store carrying both would route
   everything into feedback and leave a verification workstream unadvanced
   (foreign-workstream events land on `feedback-outside-workstream`). This is
   the same shape WO-010 already established for `state.verification`, and the
   self-hosted path uses separate `audit/` and `verifier/` stores, so nothing is
   broken. It is a standing structural constraint worth naming before a third
   branch is added.
5. **Advisory enforcement disables the correction reactor entirely.**
   `applyFeedbackCorrection` requires the `semantic-correction` mechanism to be
   equipped *and* `hard`; an advisory profile would neither tighten nor record.
   The shipped personal profile is hard, and product 02 already requires another
   profile to declare its own correction policy, so this is consistent — but the
   all-or-nothing behaviour at the advisory rung is worth a sentence if a
   non-hard profile is ever authored.
6. **`npm ci --ignore-scripts --offline --no-audit --no-fund` is
   executor-reported.** I did not re-run it: it removes `node_modules` and a
   cache miss would leave the worktree unbuildable mid-verification, which is
   not a risk worth taking for a claim of this weight. I checked the reachable
   part instead — the lockfile records TypeScript without `dev: true` and with
   `@dotln/skeleton@0.12.0` depending on it, and `npm ls typescript --omit=dev`
   resolves the runtime tree correctly. The clean-install claim stands as the
