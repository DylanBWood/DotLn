1. **The roadmap does not record WO-026's application of the release-assignment
   default.** `06-roadmap.md` §Release boundary ends with "WO-028 applies the
   default as `v0.5.1` above published `v0.5.0`" and gained no matching
   sentence for `v0.5.2`. The base and classification *are* recorded, in the
   work-order header, the README release block, and the planning map, and the
   execution guide's wording ("Complete a missing activation target under
   `06-roadmap.md` §Release boundary and record the base/classification") is
   ambiguous about location. I did not edit the roadmap, because doing so would
   stale the publication locks mid-verification and mix verifier prose into the
   subject. Final review may want a one-line continuation of the WO-028
   precedent.
2. **`release list`'s fallback attribution widened.** `listPublishedReleases`
   now falls back to `manifestWorkOrders(manifest)`, which can yield several
   ids from `changedFiles`, where `68b1ab2` used only `manifest.workOrder.id`.
   The change makes `release list` agree with the index's attribution rule, the
   release fixtures pass, and I verified the rendered output is byte-identical
   on the current tag set, so today the difference is latent. It is a small
   behavior widening in a sibling helper rather than a pure extraction, and it
   is worth a reviewer's eye.
3. **`WO-011` renders `malformed` in the Version column.** Its H1 contains the
   product-generation token "Feedback compiler v1", which is version-shaped but
   is not a strict application version, so the conservative rule reports
   `malformed` where the pilot map said "version unassigned". This is
   documented behavior ("never guessed", attributed by the Path column) and is
   arguably the right call, but it is the one real-repository cell whose label
   could be misread as a broken header, and the activation comparison — which
   compares phase, release, and dependency tokens — does not call it out.
