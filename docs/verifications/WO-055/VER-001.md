### Criterion 1 — derivation containment

**Source read.** `packages/skeleton/src/repair.ts`:

- Evidence ids resolve only to witnesses with the finding's criterion and the
  subject revision.
- An adverse host witness must match `observed` and `expected`.
- Surfaces are the finding's likely surfaces plus the witnesses'
  `codeSurfaces`. Each must pass `repositoryPath` and be contained in the
  original surfaces (exact or `surface/` prefix).
- Each command must match the exact-command pattern and equal a named test.
- An expansion needs a requested grant that:
  - equals a host registry entry in full;
  - names the order's repo;
  - uses no wildcard;
  - uses only effects already in the original `allowedEffects` and
    operations already in its `allowedOperations`;
  - carries `repo.write` for a path or `shell.run` for a command;
  - is consumed only for its exact extra scope.

The derived order spreads the original WorkOrder, clears `knownFacts` and
`decisions`, and keeps the envelope object unchanged.

packages/skeleton/dist/test/repair.test.js` gave 6 of 6 passing in 145 s. That
covers the pure AC1 test and the host-level refusal test for both path and
command.

## Observations (non-blocking)

- **O1 — repair surfaces include the criterion's cited test files.**
  - Derived surfaces are `contract-test.mjs`, `fixture-test.mjs` and
    `fixture.txt`, because witnesses contribute the criterion's
    `codeSurfaces`.
  - This matches the order ("the files the finding names plus the tests it
    cites") and AC1's "referenced files". Product 02 documents it.
  - The consequence is that a repair writer may edit a named test that
    re-verification then runs. The contract text and command names are
    unchanged, but test bytes are subject content, as in WO-054's snapshot
    model.
  - Planning candidate for WO-056/WO-066: protect cited test files from a
    repair unless the finding names them.
- **O2 — a malformed path names `finding`.** For a traversal, absolute or
  `.git` path, the pure derivation returns `NeedsHuman` with offending
  `finding` ("malformed finding"), not the path.
  - Through the host this is unreachable: `parseEvidenceResult`
    (`verification-protocol.ts:290`) applies the same `copyFinding` check
    before the repair slice sees a finding.
  - AC1's outside-path case, a well-formed path outside the surfaces, names
    the path.
- **O3 — `roundLimit` placement.** `roundLimit` is a per-order field of
  `RepairOriginal`, beside the WorkOrder. It is not a field of the compiler
  `WorkOrder` type, although the order's Design line says "a WorkOrder field".
  - Per-order behavior and the default of two are demonstrated (criterion 3
    table), and the compiler contract stays `0.14.0`.
  - Product 02 and the README describe the actual placement.
  - The reviewer may judge whether the Design wording needs a correction note.
- **O4 — pre-existing stale README heading.** The skeleton README heading
  reads `@dotln/skeleton` 0.24.0. It was already stale on `main` at 0.26.0
  and remains so at 0.27.0. It is outside this order; nominate it as bounded
  cleanup.
- **O5 — the `Await` timeout is declarative.** The round program's
  `Await(SourceChangeObserved, After 180000 ms)` timeout is not evaluated by
  kernel `stepProgram`, which only waits. A stalled child therefore relies on
  the WO-052 and WO-054 host deadlines, leases and locks. The order requires
  no timeout branch; this is a limit for WO-056's live loop.
