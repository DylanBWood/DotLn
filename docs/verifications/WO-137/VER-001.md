## Observations (not findings)

- **O1 — the live smoke rows came from an earlier client revision.**
  - **Evidence.** The live `timeout` row has `abortAtMs` equal to `latencyMs`
    to every recorded digit: 102.00995800000237. The current `request()`
    stamps `abortAtMs` inside the timer callback, before the request settles,
    so it cannot produce that equality. The later load row (4,677.84 vs
    4,678.64) and the live cancellation row (903.72 vs 904.77) both show the
    expected gap.
  - **Inference.** The 22:33Z smoke ran before the audit corrections that D003
    describes. No checkpoint lies between activation (22:24Z) and
    `ImplementationReady` (23:25Z), and the packet records no client code
    identity, so the exact client bytes that produced the rows are not
    retained. D003 discloses that no second smoke was run.
  - **Mitigation.** The request shapes are identical and the recomputed
    assessment matches.
  - **Wording.** The markdown's "observed abort at about 102 ms" is really the
    settle time. The abort itself happened at or before 102.01 ms.
  - **For review.** The profiling contract asks for results linked to exact
    commits. This order's provenance list does not name client identity. The
    reviewer may want the next live row to record the probe's content hash.
- **O2 — the live smoke client can record a deadline as a cancellation.**
  - **Cause.** D003 says the audit corrected "timeout overwritten by
    cancellation" and added the regression "deadline during cancellation
    observer retains timeout as the first cause". That regression uses an
    asynchronous observer. The live `main()` in `local-runner-smoke.mjs` uses
    `execFileSync` inside `observeState`, which blocks the event loop, so the
    deadline timer cannot fire during the observation.
  - **Reproduction.** On a loopback double with a 40 ms deadline and a 100 ms
    observer: a blocking observer produced `status: "cancelled"`, with
    `abortAtMs` 119. An asynchronous observer produced `status: "timeout"`,
    with `abortAtMs` 41.
  - **Impact.** No recorded row is affected. With the live 30,000 ms deadline
    and an observer capped at 2,000 ms, this needs the first delta to arrive
    within about 2 s of the deadline. The live first delta came at 730.75 ms.
    The load client already moved to asynchronous readers.
  - **Disposition.** D003's correction claim is only partly supported: it holds
    for asynchronous observers but not on the smoke client's own live path.
    Product 07 §Research rule 4 routes any promotion of this client through a
    separate implementation order, which should use an asynchronous observer.
- **O3 — some packet strings lost spaces.** Several `steps[].observation`
  strings and one `ruledOut` string are missing spaces between words and
  numbers: "port1234", "Model loaded9.90s", "llama.cpp2.38.0", "at22:33:22UTC",
  "over5seconds". The values are still unambiguous. This is legibility only.
- **O4 — there is no npm `probe:` entry point.** Product 07 §Research rule 5
  says live evaluations run under explicit `probe:` or `evidence:` commands.
  The live entry points are `node scripts/probes/local-runner-*.mjs --live …`:
  an explicit, required `--live` flag, never reachable from `npm test`. The
  order's deliverables name only the script paths. The property the rule
  protects holds; the naming convention does not.
- **O5 — operator time was not measured.** `budget.operatorTimeCounter` is
  `null`. The canonical implementation phase lasted 3,662,309 ms (61.0 min),
  under the 90-minute budget. It is inference that this phase bounds the
  operator's in-dispatch participation. The operator-reported Terminal history
  came before activation and is not counted.
