## Findings

### F1 — major — a SIGKILL inside the append-lock recovery window leaves a store that refuses until a human removes a directory

- **Criterion:** 2 (met as specified; this bounds how far the guarantee reaches).
- **Observed:** `ResidentStore.transaction` (`resident-store.ts:101-132`) runs a
  full `WorkerStore.acquire()`/`release()` cycle on the `.resident-append` store
  for **every** transaction — several times per tick, and again on each 20 ms
  poll that sees a change while an episode is in flight.
  `WorkerStore.acquire` removes its `host-lock-recovery` guard directory only in
  a `finally` (`worker-store.ts:269`). A SIGKILL landing inside that window
  leaves the guard behind, and every later `dotln resident` and `dotln presence`
  against that store refuses permanently.
- **Expected:** the order's Design section states "the log is the state, so a
  killed resident costs nothing," and criterion 2 promises that a restart
  "resumes from the log."
- **Reproduction:** I created `.resident-append/host-lock-recovery` and ran a
  fresh `--once`: refused after 2,210 ms with `host lock recovery is busy or
  interrupted; inspect before recovery`. I measured the window directly —
  `appendStore.acquire()` takes 4.0–17.3 ms (median 8.8 ms, two fsyncs) per
  transaction. A delegated reproduction agent independently measured 7 of 30
  randomized `kill -9` trials leaving the guard behind at `--tick 10` (~35 %
  duty cycle), and ~0.53 % at the README's documented `--tick 1000`.
- **Why this is not a criterion failure:** the behavior is disclosed in the
  runbook ("Torn logs or interrupted lock-recovery guards refuse for inspection
  without truncation", `packages/skeleton/README.md:220-221`) and it implements
  WO-048's inspect-before-reclaim contract, which the order cites as a
  dependency and instructs the executor to follow. No events are lost or
  truncated; recovery is a documented manual step. The executor also recorded
  that the crash fixture kills "while no append transaction is active", so the
  fixture avoids this window by construction rather than hiding it.
- **Limits and suggested direction (not a repair instruction):** unlike
  `host.lock`, the guard carries no owner pid, so it cannot be liveness-checked
  and reclaimed the way a dead owner's lock is. Either stamping the guard with
  an owner pid or taking it off the per-transaction hot path would close this
  without weakening WO-048's contract. I did not attempt either.

### F2 — major — a `scope.budget` ceiling is silently discarded when its key collides with `scope.changeSize`

- **Criterion:** none. This is in resource-checking code the executor added
  beyond what the order requires; criterion 3's effect check is separate and
  correct.
- **Observed:** `resident-state.ts:135-138` builds
  `{ ...phase.scope.budget, ...phase.scope.changeSize }`. Spread is last-wins,
  so a `budget` entry named `files` or `lines` is overwritten by the looser
  `changeSize` value instead of the two being combined by minimum.
  `packages/compiler/src/types.ts:370-375` makes this reachable: `changeSize` has
  fixed `files`/`lines` keys while `budget` is an open
  `Readonly<Record<string, number>>`, and `presence-schema.ts` does not restrict
  budget keys.
- **Expected:** both authored ceilings bind; the tighter one governs.
- **Reproduction:** with `scope.budget.files = 0` and `scope.changeSize.files = 1`,
  `residentRefusal` returned `null` (allowed) for a spec reserving `files: 1`.
  The baseline case behaves the same, confirming the budget value is simply not
  consulted.
- **Limits:** the authority envelope's `resourceLimits` still binds
  independently, so the reservation cannot exceed the compiled authority — the
  exposure is the scope budget only, and only for the two colliding key names.
  The kernel's own "resource limit exceeded" rule never fires here because
  `residentRefusal` passes no `intent.resource` (`kernel/src/core.ts:449-453`),
  so this hand-rolled check is the sole scope gate. No fixture covers a
  colliding key.

### F3 — minor — the NoOp dedupe never resets on a fresh absence edge

- **Criterion:** 3 and 4 (both met; the required event is recorded on first
  occurrence and no fallback dispatch ever happens).
- **Observed:** `resident-host.ts:98-105` suppresses a `ScriptEpisodeRefused` or
  `ActorUnavailable` when `state.lastNoOp === reason`, and `lastNoOp` is cleared
  only on `ScriptEpisodeDispatched` (`resident-state.ts:258`). The dedupe key is
  the reason string alone; `phaseId` is in the payload but not in the key.
- **Expected:** a later absence arm that refuses again for the same reason
  leaves a record of that arm.
- **Reproduction:** with an unavailable `local-model` actor — tick 1 recorded
  one `ActorUnavailable`; a second tick in the same phase correctly deduped; and
  `back` → fresh `away` → tick recorded **nothing**, leaving the count at 1.
  `launches` stayed 0 throughout.
- **Limits:** the dedupe itself is necessary — without it a refusing phase would
  append one event per tick (3,600/hour at `--tick 1000`). This is a
  log-completeness gap, not a behavioral one: the refusal is still evaluated
  every tick and no fallback dispatch occurs. Severity minor for that reason;
  one delegated verifier argued major, the other refuted it entirely, and I am
  recording my own reading between them.

### Refuted — the extracted interpreter does **not** diverge on the idle deadline

A delegated reviewer claimed that `PresenceMachine.outcome()`
(`presence-machine.ts:157-160`) adds `this.lastActivity = at`, which the
pre-extraction WO-067 interpreter lacked, silently extending `After(idleMs)`.
I probed it. Every outcome transition in the emitted table carries `arm-phase`
(`probe|widen|peak --verified-success/--failure`), and `arm-phase` already sets
`lastActivity = now`, so old and new expire at exactly the same time (150 in my
trace, both ways). My first emulation appeared to show a divergence only
because it clobbered `arm-phase`'s own assignment. The line matters solely when
the guard blocks the transition, and from the emitted table that shape is
unreachable while absent: the two generation-bumping transitions available to a
phase with `current` set are themselves gated on a *matching* generation, and
`idle-expired` requires `!current`. Both delegated verifiers independently
refuted the claim, one noting the added line moves the interpreter **toward**
WO-067 conformance. No finding.
