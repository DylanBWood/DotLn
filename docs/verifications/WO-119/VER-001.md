### Criterion 2 — resident script episode, fake clock, no operator await: met

`discovery.test.ts:258-366` is a real dispatch, not a simulation: a real

I traced the hazard that would matter most here: whether a contract actor can

truncation path is therefore not reachable, and `resident-store.ts:67` validates
the complete fold before making any event durable, so even a hypothetical
mismatch would abort the append rather than poison the log.

## Findings

**F1 — release staging is half-landed (minor, not a criterion failure).**
`packages/skeleton/package.json` declares `0.22.0`, but
`packages/skeleton/src/version.ts:2` still reads
`HARNESS_HOST_VERSION = "0.21.0"`, and every emitted pin derived from it —
`.claude/harness-manifest.json:139`, `:695` and all nine
`.claude/hooks/*.mjs` — still says `skeletonVersion: "0.21.0"`. At `HEAD`
(`37d0388`) the two were in lockstep at `0.21.0`, and the history shows them
bumped together in release-preparation commits (`53f9c7b`, `a0dc383`,
`37d0388`). `scripts/release.mjs` contains no reference to `version.ts` or
`HARNESS_HOST_VERSION`, so nothing rewrites it automatically. This contradicts
D002's recorded decision to "stage application v0.26.0 / skeleton 0.22.0",
`implementation.md:26`, and `RELEASE-NOTES.md:21`. Nothing breaks functionally —
`harness-host.ts:2449` compares the emitted pins against `HARNESS_HOST_VERSION`
and both are `0.21.0`, so they agree with each other. Repair is a one-line bump
plus a harness re-emit. Because final review "integrates main and retimes under
the existing classification", the reviewer may be the right place to settle the
final numbers; the internal inconsistency between the package and the constant
is not a retiming question and should be fixed either way.

**F2 — a repair repeated more than 128 times aborts the whole report (minor).**
`discovery.ts:440` passes `eventIds: group.ids` as an evidence fact, and
`work-candidate.ts` `strings()` rejects any list longer than 128. The repair
history limit is 256 lines (`discovery.ts:406`), so 129–256 occurrences of one
group is an admissible target that the producer refuses entirely. Reproduced:
128 occurrences yields one `repeated-repair` candidate with 128 `eventIds`; 129
throws `invalid discovery string list`, and no other candidate survives either.

**F3 — an over-long repair key aborts the whole report (minor).**
`discovery.ts:427` builds `repairKey` as `repairId` plus the JSON of the sorted
path list and stores it as an evidence fact, but `work-candidate.ts` `text()`
caps a fact string at 1024 characters. Reproduced with 40 paths of 62 characters
— each well inside `discoveryPath`'s 240-character limit and the 128-entry list
limit — giving a 2683-character key and `invalid discovery evidence`. As with
F2, one legal-but-large fact suppresses every observation for that target.

For F2 and F3 the failure is conservative: the producer emits nothing rather
than emitting something false. Neither is reachable from the fixture, the
defaults path, or any repository this project currently observes, which is why
they are findings for repair rather than blockers.

## Observations

- **O1 — D002's probe is true and was unrecorded.** No artifact in the
  repository recorded the "bounded profile-comparison probe" that D002 cites. I
  reproduced it: `sandbox-exec` with the full `discoverySandbox` profile starts
  Node (exit 0); the same profile with only `(literal "/")` removed kills it with
  `SIGABRT` before any user code runs. The claim is sound; the evidence gap is
  closed by this report.
- **O2 — `outputContract` is accepted on any absolute command.**
  `actor-contract.ts:116` allows `outputContract: "work-candidates-v1"` on any
  script spec and, when set, drops the `expectedStdoutSha256` pin entirely. Only
  the *sandbox selection* in `script-episode.ts:53-60` is pinned to the discovery
  CLI invocation. AC2 does not require command pinning and D002 claims only the
  sandbox selection is pinned, so this is accurate — but the digest-pin
  relaxation is wider than the pinned producer the order describes.
- **O3 — the stale-generated corpus exclusion is mode-asymmetric.** The
  reference corpus excludes `profilePath` (`discovery.ts:372`), but
  `profilePath` is only ever set on the profile branch (`:237`). With conventions
  passed directly, a declaration file that names the generated path suppresses a
  true candidate. `discovery.test.ts:216-221` pins exactly this behaviour, so it
  is known; the effect is a missing candidate, never a false one.
- **O4 — the executable-kind assertion is a type tautology.** Only the
  `notEqual(p.kind, "Await")` carries content, and `walk()` has no case for
  `Emit.next` or `Await.next`. Sufficient today; a latent gap if the program
  gains either node.
- **O5 — checks run with `HOME` and `TMPDIR` set to the target root**
  (`discovery.ts:316-318`), so state a check writes lands in the observed tree
  and re-enters the second inventory at `:342`. Deliberate and bounded, but it
  means the "observation-only" producer can add files to the target. Neither the
  order, `RELEASE-NOTES.md` nor the skeleton runbook says so.
- **O6 — `discovery-cli.ts` is registered in one inventory of three.** It is
  pinned as a harness runtime file in `scripts/lib/harness.mjs` but appears in
  neither `scripts/lib/evidence-sources.mjs` nor
  `packages/skeleton/src/feedback-audit.ts`, while `decisions.md:104` states
  "New transitive runtime/evidence inputs are named in the existing inventories."
  The other four new modules are in all the lists they belong to.
- **O7 — `ImplementationReady` was recorded with 25 outputs unread at current
  bytes** (`docs/control/orders/WO-119.jsonl:2`). Explicitly advisory under the
  executor skill and the CLAUDE.md harness block, not a violation. Recorded
  because this verifier is the first party to have read those bytes.
- **O8 — the suite cannot run inside Claude Code's own sandbox.** Running the
  discovery tests under the session's macOS Seatbelt fails 8 of 10 with
  `discovery: check sandbox or launch refused`, because macOS will not install a
  nested sandbox — the same condition D002 records for Codex. My passing run used
  an authorized outside-sandbox host. Any future verifier needs that host.
