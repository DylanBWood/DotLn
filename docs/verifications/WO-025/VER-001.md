## Observations for the final reviewer

None of these blocks the pass. They are judgment calls, disclosed limits, or
seams a reviewer should accept consciously rather than inherit silently.

1. **The activation-preflight gap repeated (governance).** For the second
   consecutive order, activation left a planner placeholder in the H1 and the
   executor forward-corrected its own scope authority. WO-024's VER-001 already
   named the underlying process gap as the activation preflight. Here the draft
   itself instructed the rewrite, so the executor's action is narrower than
   WO-024's, but the pattern is now a trend rather than an incident, and the
   operator may want to fix activation rather than keep ratifying corrections.

2. **`worktree publish` no longer emits "has not passed final review".** The
   closed-phase gate moved from a `resume status` string match into
   `checkSurfaces`, which is strictly better — it reads the committed log rather
   than a generated projection, which is what defeats the hidden-projection
   attack in probe C. The observable consequence is a changed refusal message
   (`committed surface check requires closed WO-NNN control state; observed …
   in phase …`). Nothing in the repository still promises the old wording, but
   it is a user-visible change the deliverable list did not name.

3. **The README still links only the `v0.2.0` release artifacts.** Line 101–103
   points at the release index plus the `v0.2.0` notes and manifest. Those
   labels name their own version, so they assert nothing about currency and AC1
   is satisfied. Still, the front page's only concrete release links are to the
   oldest release, which is the same class of drift the order exists to prevent
   — just not the class the block rule checks. A pointer to
   `npm run release -- list` or the Releases page would age better.

4. **`packages/skeleton/README.md`'s H1 is a second version-bearing surface that
   nothing checks.** It now reads `# @dotln/skeleton 0.3.0` and agrees with
   `package.json`, and the sentence beneath is properly dated. But
   `check-surfaces` only compares `package.json` with the previous tag manifest,
   so a future bump that forgets this heading reintroduces exactly the defect
   this order was cut against, one level down. Extending the component rule to
   the component README H1 would be a small follow-on.

5. **One disclosed profile blind spot, characterized precisely.** A list-item
   continuation paragraph that begins *after a blank line* and is indented four
   or more spaces is exempted as an indented code block, so a soft wrap inside
   it is accepted. The adjacent shapes are all caught: the same continuation
   indented two spaces is refused, and an immediate continuation with no blank
   line is refused at any indent. This is the indented-code/list-continuation
   ambiguity a dependency-free profile cannot resolve without real list-context
   parsing, and the order's receipt names it in advance ("deliberately covers the
   supported final-review Markdown subset rather than claiming to be a complete
   Markdown parser"). It fails *open* in that one shape — it accepts a wrap
   rather than blocking legitimate prose — which is the safer direction. A
   related, more obscure case: a line beginning with a multi-digit ordinal such
   as `2024.` is treated as a new list item, though GitHub would render it as a
   lazy continuation.

6. **`manifest-from-tag v0.2.0` fails, and always has.** WO-024's VER-001 states
   that all six then-published tags parse "each reporting `schemaVersion: 1`".
   That is inaccurate for `v0.2.0`: I read the raw tag object and its annotation
   is a single subject line with no `DOTLN-MANIFEST` block, which matches
   06-roadmap.md's statement that the hand-closed `v0.2.0` manifest lives under
   `docs/releases/` instead. Nothing in WO-025 changed this, and `release notes
   v0.2.0` correctly falls back to the historical file. I record it so a later
   reader does not treat the earlier sentence as a baseline. The one place it
   touches WO-025 is the component rule's `manifestError` branch, which is
   unreachable in practice because `latest` only ever moves forward.

7. **The `github-body-profile` rule label also carries release-notes structural
   failures.** `githubBodyRule` runs `parseReleaseNotes` inside the same
   try/catch as the profile, so a malformed notes file at close reports
   `FAIL github-body-profile: observed …: missing required heading "## Release
   overview"; expected one physical line per prose paragraph or list-item
   paragraph`. The observed half names the real defect exactly; only the rule
   label and the "expected" half are mismatched. It is a diagnostic wart, not a
   correctness problem, and it does add a useful second structural check at
   close that `worktree publish` previously performed alone. A related seam
   worth conscious acceptance: when the latest tag is not present locally,
   `worktree publish` fails closed with `expected a previous component version
   from vX.Y.Z (local annotated tag vX.Y.Z is unavailable)` rather than fetching
   it, while `release close` fetches first. The message says what to do, and
   fail-closed is right, but the two gates differ.
