### F1 — criterion 2, earlier installed snapshots stop close

Expected: a target's installed kit snapshots are recognized as owned
residue and removed on its first close, while foreign files remain refused.
Observed: a complete current snapshot closes successfully; when a complete
earlier snapshot remains beside it after a runtime update, close exits 1,
retains both snapshots and records `undeclared-ignored-material` at
`worktree-removal`. The blocker names the earlier snapshot.

The reproduction uses `harnessInstallation` and `preserveHarnessRuntime`
for both trees. It changes only the package version in the fixture's copied
runtime, installs the earlier tree, restores the runtime's current bytes,
then installs the current tree and closes. This is a supported installer
output across a runtime update, not an invented snapshot-shaped directory.
The current-tree control inventories 542 regular files and deletes 548
entries including package links, with a null blocker.

`verifiedSnapshots` in `scripts/lib/target-worktree-close.mjs` derives only
the current inventories of the serving runtime and main. It cannot establish
the earlier installation's ownership. D005 explicitly left this state
untested and named its refusal as a reopening condition; that decision does
not narrow criterion 2's installed-snapshot requirement.

Repair rule: preserve or recover verifiable ownership of previously installed
snapshots across runtime updates. Delete legitimate earlier snapshots while
retaining the existing refusals for foreign notes, edited package files and
tracked content. Directory names alone are insufficient proof. See
[D016](../../evidence/WO-252/decisions.md#wo-252-d016).

Reproduce from the worktree root:

```sh

```

and in the new `scripts/test-harness.mjs` test, which skips the router and
