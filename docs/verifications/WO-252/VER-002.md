snapshot and retains both.

packages supply its payload. This is production installer output with its

`verifiedSnapshots` supplies the current serving runtimes' lists. D019's
compatibility limitation is therefore exercised. It does not amend the
original installed-snapshot requirement or settle VER-001 F1.

Repair rule: preserve or recover verifiable ownership for earlier
record-less snapshots when the historical pinned list differs. Keep the
foreign-file, edited-content, tracked-file and interrupted-deletion
protections. A snapshot name alone is insufficient proof. This is a
blocking closeout failure; see

### F2 — stopped removal loses the independent prune route

Expected baseline behavior: a valid expired root with a dead owner remains
eligible for ordinary prune after close stops and its owner checkout stays.
Observed: with the fixture target locked using Git's supported worktree
lock, the baseline close helper from
`b9e843b6978e057d6794b9d0a76af557e9547ba0` refuses close, retains the ledger
and preserves prune eligibility. Restoring the repaired helper in the same
fixture deletes the ledger before Git refuses removal. The target remains
and the close record carries the root in `ownedTemporaryRoots`, but
`judgeTemporaryRoot` refuses it because the surviving owner's ledger no
longer registers its token at that path.

The two arms use the same valid root, target lock and surrounding release
harness; only the close helper changes. The fixture finally unlocks the
target and retries successfully. Data is retained and that recovery works;
the regression is the loss of ordinary prune while the target remains,
not permanent data loss. It reproduces D022's explicit reopening condition
and the repair review's unresolved criteria F1.

Repair rule: preserve or restore the ownership binding if removal stops,
without weakening the existing-owner ledger check or making successful
closes wait for retained scratch to expire. The blocking basis is the
executed baseline regression, not the Cost paragraph's disputed ledger
lifetime. See [D025](../../evidence/WO-252/decisions.md#wo-252-d025).
