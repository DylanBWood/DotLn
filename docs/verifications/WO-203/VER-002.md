## Findings

**F1 — A revision preview refuses when the instance removed a kit file (follow-up).**

- Class: report-only refusal on a kit input (operator flow). It sits in the declared `planUpdate` and `previewFromRevision` surfaces.
- Observed: the fork commits `git rm .claude/skills/probe/e.md`, and the incoming revision leaves `e.md` unchanged. `preview --from origin/main` exits 1 with `error: cannot read regular file: <fork>/.claude/skills/probe/e.md` and prints nothing else. A real merge keeps the removal without a conflict on it.
- Cause: `planUpdate` throws on an absent path that the prior and incoming manifests carry (`scripts/launchpad.mjs:1401-1402`). This is the update's input-failure rule, which the preview shares by design. The differential probe shows VER-001's subject had the same behavior.
- Why not blocking: criterion 3's named cases all print. The README's update paragraph documents the refusal by path. `main` had no preview.
- Repair rule (D015, FUP-9c558fa0f869290e):
  - in the revision preview only, such a path becomes its own local-removal row, marked unchanged upstream when its hashes match;
  - every other row and action still prints;
  - the from-core preview and the update keep refusing before any write;
  - add a fixture case and a README line.

**F2 — The from-core preview lists byte-identical paths as `replace` (follow-up).**

- Class: undifferentiated core preview rows (operator flow). It sits in the declared shared renderer.
- Observed: on the real corpus, a core commit that edits `scripts/kit/README.client.md` and `scripts/kit/KIT-ACTIONS.json` and adds `scripts/probe-added.mjs` previews as `865 replaced; 1 added; 0 removed; 1 refused`. In the starter's history, the update that follows changes only those two files and `UPSTREAM.md`, adds the new file and rewrites `KIT-MANIFEST.json`, so 862 `replace` rows rewrite identical bytes.
- Cause: `planUpdate` already computes `unchanged` for every row (`scripts/launchpad.mjs:1429-1433`). `renderUpdatePlan` uses it only for revisions (`:1952-1955`), as D002 and D012 chose.
- Why not blocking: the rows are accurate, and criterion 1 asks only for each path's kind. The README discloses the behavior.
- Repair rule (D016, FUP-bf112b957627334d, which reopens D012):
  - the shared renderer labels and counts byte-identical `replace` rows as unchanged in both the from-core preview and the update summary, so criterion 2's equality holds;
  - mutation kinds, writes, the receipt and the WO-078 cases stay unchanged;
  - extend the core preview fixture and align the README.

Other review observations, not findings:
- Report-only action planning restores the draft, the rename count and the write map after a failed action, and validates configuration after each action only in report-only mode. The actual apply path differs from VER-001's only by `structuredClone` on an incoming default, which serializes to the same JSON.
- The `planKitUpdate` comment still tells callers to apply its plan immediately, because `applyKitUpdate` does not re-check the destination. WO-207 should keep that in mind.
