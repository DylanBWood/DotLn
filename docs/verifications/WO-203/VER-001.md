## Findings

**F1 — The revision preview cannot show which kit files the merge will change (blocking).**

- Class: misreported revision plan (correctness and tests). It sits in the declared `scripts/launchpad.mjs` planner and renderer and the fetched-starter fixture.
- Observed: revision B changes `a.md`, the harness snapshot and `KIT-ACTIONS.json`, drops `c.md`, adds `d.md`, and leaves `e.md` and `f.md` unchanged. The fork's preview prints `kit files: 5 replaced; 0 added; 1 removed; 2 refused.` The `replace:` rows for `a.md`, `e.md` and `f.md` look the same. `preview --from HEAD` names a revision whose manifest equals the instance's, a merge that changes nothing, and prints 6 `replace:` rows.
- Cause: `planUpdate` (`scripts/launchpad.mjs:1404-1428`) keeps a path when its current bytes match the incoming, prior or pending hash. It then records `replace` whenever the incoming manifest carries the path. The renderer prints `<kind>: <path>` (`:1949`). The fixture asserts only that `replace: <changed>` appears (`scripts/test-launchpad.mjs:2403`). The README discloses the behavior at lines 336 and 387. D002 rejected an unchanged classification for parity, which the repair can keep.
- Expected: the in-instance preview prints "the kit files the merge will change" (criterion 3; objective: "the kit files the merge will change"), for an operator who wants "an idea of what will come in before we hit a point of no return".
- Severity: blocking, because criterion 3 is unmet.
- Repair rule (D011):
  - Identify the kit files whose incoming manifest hash differs from the instance's current bytes, separately from kit files the merge leaves unchanged.
  - A revision whose manifest equals the instance's reports no changed kit file.
  - Keep one planner and one renderer, so criterion 2's row equality holds.
  - Leave the update's writes, receipt and the WO-078 update cases unchanged.
  - Assert in the fetched-starter fixture that an unchanged kit path is not presented as changed, and bring the README rows in line.

**F2 — A report-only preview refuses on an action it only describes (blocking).**

- Class: report-only refusal (operator flow). It sits in the declared `planInstanceActions` report-only mode and `previewFromRevision`.
- Observed: the starter adds `{"kind": "change-phrase", "from": "Old phrase", ...}`. The fork's `CLAUDE.md` is instance-owned and customized, and does not contain the phrase. `preview --from origin/main` exits 1 with `cannot apply probe-phrase: expected one phrase in .../CLAUDE.md`, and stdout is empty.
- Cause: `previewFromRevision` calls `planInstanceActions(..., { reportOnly: true })` (`scripts/launchpad.mjs:1891`), but report-only mode still throws (`:1640-1643`). The README calls these actions "manual work after the merge" and their `apply` rows "hypothetical", and the merge itself is not blocked by them.
- Expected: criterion 3's preview prints the actions declared at the revision, alongside its plan rows.
- Severity: blocking. For a realistic instance input, the preview prints none of what criterion 3 requires.
- Repair rule (D011):
  - In report-only mode, an incoming action that cannot apply becomes its own action-plan row naming the reason.
  - The kit plan rows and every declared action still print, and the preview is not refused for that action.
  - The core `--apply` preview and the update keep refusing before any write.
  - Add a fixture case with such an action.

**F3 — A locally modified file that the revision does not change reads as a conflict (follow-up).**

- Class: correctness, in the same declared rows.
- Observed: `b.md` is edited in the fork and unchanged upstream, and is printed as `refused: ... (locally modified; prior hash retained: ...)`. The design reads a `refuse: locally modified` row as "a file the merge will conflict on". A real `git merge origin/main` in a throwaway copy conflicts only on `d.md` (add/add) and leaves `b.md` unconflicted.
- It breaks no criterion: criterion 3 names "a locally modified kit file as refuse", and the README calls these judgments conservative. `main` had no preview, so no behavior regresses.
- Boarded in D011: once rows distinguish changed paths, label such a refusal as unchanged upstream.
