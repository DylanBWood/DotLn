## Findings

### F10 — Criterion 11: one failed use is answered and counted once per concurrent observer

**Class/severity:** duplicate delivery and count under concurrency; medium.

Criterion 11 promises that the observer answers a diagnostic and appends one row
for it, and VER-003's F8 repair rule requires one count and one answer for a
failed use. The failed-result route answers a failed command at the next observed
call. When two calls finish together, both observers see the same unanswered use,
and each answers and appends.

Reproduced live in this session's real host, at `2026-09-29T20:57:19Z`. One
command that zsh refused (`ls *.dotln-race-probe-1`, exit 1) was followed by two
harmless Bash calls in one message. Both calls returned the same guidance
context, and the shared lane gained two rows for the same failed use one
millisecond apart (`20:57:19.952Z` and `20:57:19.953Z`, one `use` hash). The shell
agent's isolated fixture reproduces it: with one failed result and N concurrent
observers, N=2 gave two rows and two answers in four of five trials, N=3 and N=4
in every trial, and N=8 gave eight rows and eight answers. I re-ran its N=8
script and read eight rows.

The cause is in `packages/skeleton/src/harness-host.ts`, where the answered
identities are read from the lane and the row is appended afterwards with no
exclusive claim between the read and the append. Parallel tool calls are ordinary,
so the plan-failures label "a lower bound" does not hold once a count can be
inflated this way, and the guidance repeats.

**Repair rule:** claim each failed use atomically before answering, for example an
exclusive-create marker named by the use's hash beside the lane, following the
existing `.advisory` marker precedent, and answer and append only when the claim
succeeds. Keep privacy, nonblocking behavior and the declared limits. Test with
concurrent processes, and confirm live that two calls after one failed command
give one context and one row.
