## Findings

### F1 — the live-gate guard admits `>&`-redirected writes to gate inputs under `packages/*/dist` and `./node_modules` (blocking, criterion 9)

Criterion 9 keeps exactly two refusals. The second is "a write to gate inputs or the success record during the reviewer's live `npm test`". Its fixture requires that "a live-gate write [is] still refused".

Mechanism, at the current source:

1. The tokenizer keeps a descriptor-duplication operator and its operand as one word (`packages/skeleton/src/harness-command.ts:201–211`), so `>&packages/skeleton/dist/x.js` is a single token.
2. `shellWritePaths` matches it with `/^(?:\d*>>?|&>>?)(.*)$/` (`harness-command.ts:320`) and records the destination **with** the leading `&`: `&packages/skeleton/dist/x.js`. The correct `&>` form is split cleanly and records `packages/skeleton/dist/x.js`.
3. `gateInputPath` (`packages/skeleton/src/gate-evidence.mjs:102–182`) resolves that spelling literally. The `&packages` first segment escapes the `packages/*/dist` rule (:142) and the installed-root prefix rule (:143–151). `git check-ignore` still matches the unanchored `dist/` component (`.gitignore:9`), so :175–180 classifies the path as ignored scratch.
4. The guard's `paths.every(!gateInputPath)` branch (`packages/skeleton/src/harness-host.ts:2289–2300`) returns no refusal. bash and zsh then write the real file: `>&file` and `1>&file` truncate it in both shells, and zsh's `>>&file` appends.

Reach, established by two independent runs and mine:

- **Admitted:** relative and absolute destinations under `packages/*/dist`; `./node_modules/…`.
- **Denied**, because the corrupted spelling happens to be non-ignored:
  - tracked sources;
  - the success record and check history (anchored `/docs/control/local/`);
  - bare `node_modules/…`, whose first segment becomes `&node_modules`;
  - the spaced `>& file` form, recorded as the path `&`.
- The same misparse makes `ls 2>&-` a false refusal (O1).

`packages/*/dist` is what the gate builds first and every later suite executes. A write there during the gate changes the code the recorded row claims to have tested, while the row stays keyed by source identity.

Provenance: the tokenizer, the redirect regex, the guard shape and the `echo`/`printf`/`cat`/`pwd`/`true`/`false` admission are identical on `main` (`git show main:packages/skeleton/src/harness-command.ts`, lines 201 and 336), introduced by `c8983cc`. The `cat`/`echo` form of this bypass therefore predates WO-132. A refuter transpiled `main`'s adapter and confirmed it returns the same `&`-prefixed path for `cat`. The repair's only functional change to the adapter added `ls`, `head` and `grep` to that list (`git diff refs/dotln/checkpoint/WO-132/4 refs/dotln/checkpoint/WO-132/7 -- packages/skeleton/src/harness-command.ts`). That moved those programs from refused to admitted through the defective parse. Two repair records conflict with this result:

- WO-132-D005 names its own reopening condition as "a redirected or chained gate-input write is admitted", and that is now observed.
- [The repair record](../../evidence/WO-132/repair-validation.md) says all three hooks "retain protected-file and success-record write denials, including redirection". That holds for `>`, `>>`, `&>` and `tee`, and not for `>&`.

Severity, and the disagreement I preserve. The independent refuter reproduced every subject row and graded F1 **non-blocking**. Their reasons: the spelling is unusual, it cannot reach tracked source or the success record, the mechanism predates the order, and criterion 9's named fixture passes. The original finder and I grade it **blocking**, for four reasons:

1. It defeats one of only two refusals this order deliberately keeps, and the order's own decision record names this exact observation as its reopening trigger.
2. WO-132 makes that invariant load-bearing in a way it was not before. The reviewer's single `npm test` row is now the release evidence, and criterion 10's close runs no suite to catch a tampered run.
3. The repair widened the defect's reach, so this is a regression in this order's own change, not inherited behavior it merely failed to improve.
4. The fix is small and needs no new mechanism.

This is not a constructed hypothetical in criterion 11's sense. The defect is executed hook behavior at the current subject, reproduced three times.

Repair, bounded so it cannot re-open VER-001's over-refusal:

- In `shellWritePaths`, treat `N>&word`, `>&word` and `>>&word` whose operand is not a descriptor number as a redirect to `word`, stripping the `&` exactly as the `&>` branch already does. Treat the operand `-` as a descriptor close with no destination.
- Returning null (opaque) for any non-numeric operand is an acceptable fail-closed alternative, at the cost of refusing `>&scratch`.
- Either way, ordinary `ls`, `head` and `grep` reads stay admitted.
