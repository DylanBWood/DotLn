Expected: a dispatch under a synthetic `CODEX_THREAD_ID` with no record creates

Criterion, observed and expected are in Criterion 3 above. Reproduction:

### Finding 2 — this order turns its own final-review gate red. Severity: major.

Expected: the order's evidence gate passes at final review.

Observed: it will fail, and this order's change is the sole trigger.

`configuration-root` is a machinery suite, so the no-flag `npm test` excludes it,
which is why the 23/23 run above is green. The final-review gate is
`npm test -- --review`, which adds `changedMachinery(...)`: machinery suites with
a source changed against the merge base. Reproduction:

    $ npm test -- --review --list | grep -c " — protects:"
    32
    $ npm test -- --review --list | grep configuration-root
    configuration-root — protects: an absent dotln.config.json reproduces today's
    layout, a declared launchpad moves every document root and root derivation,
    and a malformed configuration refuses by path

That suite fails:

    $ npm test -- --only configuration-root
    not ok 6 - no control-plane script keeps a literal document root or a second
    root derivation
      + 'scripts/probes/local-model-role-qualification.mjs:
         fileURLToPath(import.meta.url)),"../.."'
    suite:configuration-root: 1 passed; 1 failed; 3.16 s

Attribution. `machinerySources["configuration-root"]` lists eight sources:
`scripts/lib/config.mjs`, `scripts/test-configuration-root.mjs`,
`scripts/resume.mjs`, `scripts/work-orders.mjs`, `scripts/worktree.mjs`,
`scripts/lib/control.mjs`, `scripts/lib/control-store.mjs`,
`scripts/lib/paths.mjs`. Exactly one is changed by this order:
`scripts/resume.mjs`. So the *failure* is pre-existing in
`scripts/probes/local-model-role-qualification.mjs`, which this order leaves
byte-identical — but the *selection* is new, and it is caused by this order.
Without this order's `scripts/resume.mjs` edit, `--review` would not select the
suite.

D003 disposed the repair of that probe as out of scope, and its reasoning is
sound: the concrete `TOOL_ROOT` fix invalidated 38 committed episode hashes, and
rewriting them without rerunning the episodes would fabricate evidence. I agree
with that judgment and am not asking for it to be reversed. The gap is that
neither D003 nor the implementation record reconciles the disposition with
criterion 5, nor notes that the deferred `--review` run will now select the
failing suite. The order is staged to arrive at final review with a red gate and
no recorded expectation that it will be red.

Repair options, for the executor and operator to choose between: reconcile the
episode subject under a reviewed versioned boundary (D003's own second branch);
or obtain an explicit operator scope expansion amending criterion 5 and record
the authorization in the order's structured decisions per
`npm run plan -- amend-order`; or otherwise make the `--review` selection green.
Boarding it up in a report sentence alone is not sufficient, since the gate is
executable and will run.

### Finding 4 — the begin is silently skipped on an unbuilt tree. Severity: minor to moderate.

The dispatch guard is:

    process.env.CODEX_THREAD_ID && codexDispatchRole && existsSync(harnessHostPath)

where `harnessHostPath` is `packages/skeleton/dist/src/harness-host.js`
(`scripts/resume.mjs:1156-1173`). `dist/` is gitignored
(`.gitignore:10`), and neither `scripts/resume.mjs` nor `scripts/worktree.mjs`
builds it — `grep -n "npm run build\|build.mjs\|npm ci\|npm install"` returns
nothing in either. So in a fresh clone or worktree that has not yet been built,
a Codex lifecycle dispatch writes no session record, emits no advisory, and the
receipt falls back to `unknown; cause no-session` — reproducing exactly the
condition this order exists to remove, in the one state where the operator has
least reason to suspect it.

The guard itself is correct: without it the dynamic import would throw and take
down the dispatch. The gap is that the degraded path is silent. The surrounding
code establishes the convention — `measureHarnessSessionUsage` writes "DotLn
advisory: process-cost counters unavailable; recorded unknown." and
`measureHarnessUsage` writes "DotLn advisory: process-cost dispatch unavailable;
reported unknown." on their degraded paths. This one writes nothing. The fixture
cannot catch it because `repo(t, { runtime: true })` always supplies the built
runtime.

Not covered by any acceptance criterion, so it does not by itself change the
verdict; recorded because it is a live hole in the order's objective sentence
and is cheap to close with one advisory.
