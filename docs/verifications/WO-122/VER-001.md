## Operating conditions

This dispatch could not start when first issued. The `verify` phrase was
refused by `concurrent-work-requires-worktrees`: the worktree was still reserved
by the prior executor's Codex session (`actor c3f36b5c93ce`, owner pid 78699,
`source: "parent"`, `liveness: "unavailable"`, `alive: "unknown"`). No dispatch
was recorded and no lifecycle change occurred. The operator released the
reservation from their own terminal, after which the phrase was re-issued and
the harness recorded the dispatch and allocated this report's path.

The operator asked why the Codex session did not release its own lock. Two
causes, both evidenced, neither a WO-122 defect:

1. **Nothing in Codex enforces the release.** `.claude/harness-manifest.json`
   records, for `concurrent-work-requires-worktrees`, that no project hook fired
   in the bounded Codex probe and "the role skill carries the remaining duty".
   In Claude Code the invariant is hook-enforced; in Codex it is role text a
   model must remember to execute, so a session that ends, is killed or exhausts
   its context leaves the reservation behind. *Labelled inference:* the manifest
   probe is recorded for profile `codex-cli-0.153.4`, while the session that
   held this lock was 0.154.0 (`docs/control/orders/WO-122.jsonl:2`). That
   0.154.0 also fires no hook follows from the unchanged residue but was not
   itself probed; it is unknown by observation.
2. **The harness then refused to reclaim it, by design.** Codex does not set
   `CLAUDE_PID`, so ownership fell to the last-resort branch at
   `harness-host.ts:847`, yielding a raw parent pid with no `startedAt` — while
   this session's own reservation resolved through `CLAUDE_PID` with
   `alive: true`. Without `startedAt`, `harnessProcessAlive` (`:850-863`) cannot
   defend against pid reuse, and `writer-teardown.mjs:89-92` is explicit:
   "Cleanup needs proof of no holder, not a guess about process liveness.
   Malformed, live, stale and unknown holders all preserve the worktree until
   released by the existing writer protocol." Operator release was the intended
   remedy, not a workaround.

The reservation was not stale on arrival: it was taken at 12:44:47.862Z and the
same session recorded `ImplementationReady` at 13:30:36.972Z, 46 minutes later.
The exposure worth naming for planning — and it belongs to the harness, not to
this order — is that a Codex executor can strand every subsequent session in a
worktree with no automatic recovery, and only a human can clear it.
