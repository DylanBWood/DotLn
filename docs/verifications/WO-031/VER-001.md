**3 — Label validation. Met, and exceeded.** I exercised
`validateAccountLabel` directly with 19 invalid forms and 6 valid ones. All
five cases the criterion names refuse — `Test`, `a b`, `x@y`, a 17-character
label, and both U+2028 and U+2029 — as do embedded and trailing LF, CR, tab,
NUL, empty, leading digit, leading hyphen, underscore, surrounding whitespace,
non-ASCII, and every non-string type. `a1` and `claude-2` are accepted, as are
`a`, a 16-character label, `a-1-2`, and `z9`; `undefined` is legal.

The trailing-newline case deserves a note because it is the classic escape from
an anchored regex. `scripts/lib/control-actor.mjs` does not rely on `$`
positioning: it compares `label.match(...)?.[0] !== label`, so a match that
covers only a prefix refuses regardless of anchor semantics.

Refusal is before append. Invalid values throw inside `parseActor`
(`scripts/resume.mjs:498`), which runs before any write; the fixture asserts a
byte snapshot of the segment and `current.md` is unchanged after each of the 11
refused forms, the missing-value and duplicate-flag forms, and an invalid
environment default. Environment default and flag override are checked through
all four completion commands. Precedence is correct in code —
`values.has("--account-label")` is consulted before `process.env`, so an
explicit flag wins even when the ambient default is invalid, exactly as
07 §Model-specific notes claims.

`parseActor` previously enforced arity with `args.length !== allowedFlags.size * 2`,
which the optional sixth flag makes unusable. I checked that removing it opens
no gap: unknown flags, non-string or empty values, values beginning `--`, and
repeat flags are each rejected inside the parse loop
(`scripts/resume.mjs:439`), and the five required flags are still checked for
presence. A trailing odd argument fails as an unknown flag; a flag with no
value fails the `typeof value !== "string"` test.

## Shared pairing refactor

`controlTimeProjection` was rewritten on top of the new
`completedPhaseAttempts` generator, so the existing status timing is at risk
even though no criterion mentions it. I checked equivalence rather than
assuming it. The old form reset on each `WorkOrderActivated` and skipped
foreign orders, which makes only events after the final activation observable;
the new form takes `findLastIndex` of the activation, slices there, and filters
to that order — the same set. Every caller passes `eventsForOrder(control, id)`
(`scripts/resume.mjs:630`, `:664`, `:674`), so no caller relies on cross-order
behavior. The suite's pre-existing timing regressions — latest completed
attempts, in-flight retries, activation reset, legacy absence, and backward
clocks — all still pass, and the fixture adds direct assertions that a
reactivation does not borrow a stale start and that interleaved orders keep
separate start maps.

   `scripts/lib/control-actor.mjs` now compute the same `unknown (raw: …)`

   line from the attestation line in the same projection.

6. **`docs/control/local/` does not exist yet.** The convention is documented

## Disclosures

1. **The activation snapshot's byte-for-byte claim is not re-runnable.** The
   evidence README states that regenerating `usage` before the completion
   transition reproduced the first raw report byte for byte. The log has since
   advanced by two events, so I could not repeat that comparison. I substituted
   a check I consider stronger for the property that matters: the recorded
   totals plus exactly the one new completion attempt reproduce the live totals
   to the millisecond, and four of five recorded segment digests still match.
2. **I regenerated `docs/work-orders/README.md` after dispatch.**
   `resume verify` moved the phase to `verifying`, which made the index stale
   at line 3 and would have failed `npm test`. Per 07's rule that verification
   actors refresh the index after dispatch, I ran `npm run work-orders -- index`
   before the gate. That regeneration is mine, not the executor's, and it is
   one of the 28 modified tracked files in the subject count above.
3. **I did not evaluate the label mechanism under real concurrent accounts.**
   No operator has yet set `DOTLN_ACCOUNT_LABEL` in anger; every check of the
   two-terminal workflow is a fixture that sets and clears the variable in
   process. The mechanism is correct as specified, but its ergonomics are
   unexercised.
4. **Wall-clock semantics are documented, not validated.** Every span in the
   report includes waiting, interruption, and any overlap between concurrent
   orders, and attribution is to the completion actor's own attested claim.
   The command, `03-architecture.md`, `06-roadmap.md`, the playbook, and the
   evidence README each say so. I verified the disclaimers are present and
   consistent; I did not attempt to establish that any recorded span
   corresponds to model work.
