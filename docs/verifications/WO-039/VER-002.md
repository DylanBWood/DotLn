## Finding F1 — concurrent dead-owner recovery admits two writers (high, blocking)

**Requirement.** WO-039 Design Phase 1 requires the generated writer-isolation hook to establish exclusive worktree ownership before writable dispatch. The equipped unit's desired behavior is exactly one registered writer for that worktree. This is part of the order's objective to govern actual sessions. Criterion 3's same-facts boundary parity passes, but parity cannot correct stale host facts.

**Observed versus expected.** In `packages/skeleton/src/harness-host.ts:402`, each contender reads a reservation into a local variable. After deciding its owner is dead, line 412 unlinks the pathname without checking that it still represents that reservation. Exclusive creation at line 434 protects creation only; another contender can delete the new file after creation. Line 454's reread also cannot protect a caller once its hook has returned permission.

The independently executed schedule was:

1. Seed a synthetic reservation whose owner process has exited.
2. Start B's generated writer hook; pause immediately before its stale-lock unlink, after it has read and classified the old holder.
3. Start A's generated writer hook and pause at the same point.
4. Release A. It removes the old reservation, creates its own, and returns an allowed verdict. Confirm that the reservation belongs to A and that A's recorded harness owner is still alive.
5. Keep A's authorized work outstanding and release B. B deletes A's reservation using its earlier dead-owner decision, creates B's reservation, and also returns an allowed verdict.

The observed result, with the disposable checkout path reduced to a shape, was:

```json
{
  "sessionAAllowed": true,
  "sessionBAllowed": true,
  "sessionAOwnerStillAlive": true,
  "finalReservation": "B",
  "writerEvents": ["reclaimed", "reclaimed"],
  "fixtureRoot": "<scratch>"
}
```

**Expected:** at most one contender receives write permission while that session's reservation and authorized work remain active; the second contender must preserve the replacement and refuse or retry safely. Both observed reclaim events name the original dead holder, so the journal also omits that B displaced a live reservation.

**Reproduction and limits.** The runnable fixture below uses the emitted hook and unchanged, pinned built runtime. A preload delays only the real filesystem unlink to impose a possible scheduling interleaving; it does not replace the liveness result, file contents, writer facts, compiled predicate or hook verdict. Both owners remain the live fixture coordinator for the duration of the test. This is a deterministic subprocess counterexample, not a claim that two live model sessions collided during this verification or an estimate of collision frequency. No user reservation, source file or real session was disturbed.

**Why existing evidence misses it.** The new WO-039 fixture and two live scenarios test one reclaimer or one live foreign holder at a time. They pass and remain useful. The final paragraph of the second repair receipt acknowledges last-writer-wins recovery but concludes that the loser is refused at its next dispatch and therefore at most one writer proceeds. The schedule above falsifies that conclusion: the first effect has already been authorized before the replacement is deleted. Refusing a later dispatch does not retract that authorization.

**Repair obligation.** Serialize the complete observation/reclaim/acquire operation so a contender cannot unlink another contender's replacement, and add a generated-hook concurrency regression that keeps the first owner's work outstanding. Preserve dead-owner recovery, live/unknown-holder refusal, diagnostics and recovery records. Recheck release and owner-refresh mutations against the same ownership protocol. The existing `WorkerStore.acquire` uses an exclusive recovery guard around its observation and replacement; its four-contender test passed in this very full gate. That is relevant prior implementation to inspect, not a direction to copy a new abandoned-lock failure into this host. Update the repair receipt's concurrency claim to match the repaired evidence. No implementation repair was made here.
