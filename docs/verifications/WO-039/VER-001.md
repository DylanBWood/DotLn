# VER-001 — WO-039 Harness lowering: compile a saved build into enforceable harness configuration, and run this repository on its own compiled build (v0.14.0)

**Verdict: WO-039 fails.** Six of the eight acceptance criteria are met and were
reproduced independently here, including the two that carry most of the order's
risk: the emitted bundle is byte-identical to what is installed (criterion 5),
and the startup-context reduction is real and mechanically derived rather than
asserted (criterion 6). The full gate is green in this verifier's hands.

Four findings block the pass. One is a literal miss against criterion 3: the
generated `finish.mjs` Stop hook has neither the required `feedbackBoundary`
parity proof nor the required removal-allows proof, and the shared `parity()`
helper cannot express it. One is a methodological weakness in criterion 4: the
live read comparison runs inside a closed read scope that *refuses* out-of-set
reads, so the reported "no read outside the directed set" is a product of
enforcement rather than of the skill, and two of the four role runs contain
refused out-of-set `Read` attempts that the executor's summary does not mention.
The third is a substantive defect in delivered enforcement that only appears
when the build actually governs this repository — the order's own Objective:
the installed rung-6 `read-your-own-output` gate obligates whole-file read
receipts for all **127** files changed since the session-entry revision, ten of
which exceed the Read tool's hard 25,000-token cap and therefore can never mint
a receipt at all, while its refusal names no file. No session can cleanly
complete in this repository while that hook is installed as generated. This
verifier ended on that refusal. The
fourth is small but consequential for the next reader: the executor's receipt
claims drift-fixture coverage for four behaviors when only two are asserted.

None of the four falsifies a shipped mechanism. All four are bounded repairs.

## Findings for repair

### Finding 1 — `finish.mjs` has no boundary-parity or removal proof (criterion 3, moderate)

- **Observed.** `scripts/test-harness.mjs` applies the `parity()` helper at
  `:231`, `:240`, `:250`, `:263`, `:280`, `:763` and `:773`, covering six
  distinct unit hooks — `no-attribution`,
  `concurrent-work-requires-worktrees`, `no-lint-type-disables-as-fixes`,
  `verify-app-before-done`, `no-partial-completion` and
  `read-your-own-output` — and the commit-message adapter has its own
  equivalent fixture at `:681`. `finish.mjs` is exercised only as
  `assert.equal(allowed(invoke(root, "finish", input(root, "Stop"))), false)`
  at `:307`, as `true` inside the loop at `:342`, and as a bare `invoke` at
  `:589`. Neither its equality with `feedbackBoundary` on the same host facts
  nor "removing the unit makes the hook allow" is asserted.
- **Expected.** Criterion 3 says "For each generated hook". `finish.mjs` is a
  generated hook that carries the compiled feedback policy (rung 6, origin ids
  spanning all five roles and all ten units), so both halves are required.
- **Why the helper does not cover it.** `parity()` calls
  `harnessFeedbackFacts(config.policy, …)` once, and that function dispatches on
  `policy.units[0].trigger` — a single-unit policy. `finish` instead loops
  `for (const unit of config.policy.units) { const policy =
  compileFeedbackUnits([unit]); … }` (`packages/skeleton/src/harness-host.ts:797`).
  A parity fixture for `finish` must loop the same way; the existing helper
  would silently test only the first unit.
- **Reproduction.** `grep -n 'invoke(root, "finish"' scripts/test-harness.mjs`
  returns invocations only, and no `parity(` call site names `finish`.
- **Severity: moderate — literal criterion miss, low behavioral risk.**
  `finish`'s implementation calls `boundary(policy, fact, …)` directly, so there
  is provably no second predicate, and its three constituent Stop units each
  carry full parity and removal coverage. The gap is the undischarged proof, not
  a suspected divergence.
- **Repair.** Add a `finish`-shaped parity assertion that iterates units exactly
  as the host does, plus the removal-allows leg.

### Finding 2 — criterion 4's read comparison is made under an enforcing scope, and the refusals are not surfaced (criterion 4, moderate)

- **Observed.** The smoke installs a closed read scope into the scratch
  checkout (`scripts/harness-live-smoke.mjs:190`), and `readScopeRefusal`
  (`packages/skeleton/src/harness-host.ts:550`) *refuses* any `Read` outside the
  mechanically directed set, any `Skill` other than the selected one, and any
  `Bash` outside an allow-list. `outsideDirectedSet: []` is therefore produced by
  refusal, not by restraint. Two of the four current records contain refused
  out-of-set `Read` attempts:

  | Record              | `Read` refused as outside the directed set | Bash route refusals | `actualReads` |
  | ------------------- | -----------------------------------------: | ------------------: | ------------: |
  | `executor-007`      |                                          1 |                   1 |             8 |
  | `verifier-004`      |                                          0 |                   1 |             8 |
  | `reviewer-003`      |                                          2 |                   1 |             8 |
  | `release-close-003` |                                          0 |                   2 |             7 |

- **Expected.** Criterion 4 states its own discriminating purpose: "so a skill
  that merely suggests the guide while the session reads it anyway cannot pass."
  Under a scope that forbids the out-of-set read, the comparison can no longer
  discriminate — a skill that leaves the session reaching for the guide produces
  the same clean `outsideDirectedSet: []` as one that does not.
- **What the record cannot answer.** The refusal observation retains only the
  reason string; the attempted path is not recorded
  (`record(root, input, { allowed: false, readScopeRefusal: scopeReason })`).
  So it is not possible to tell from the committed evidence whether the three
  refused reads were reaching for the execution guide — the exact question the
  criterion exists to settle.
- **Framing.** The closed scope itself *is* disclosed, in
  `docs/evidence/WO-039/README.md` ("it denies alternative shell or model read
  routes") and in 02. What is not disclosed is that the model-route denial
  actually fired: the same README says "All four report effective `xhigh`, no
  read outside the directed set, and a finished observer", which reads as an
  unconstrained observation.
- **Reproduction.** Count `observations[].readScopeRefusal` per record in
  `docs/evidence/WO-039/harness-live/`.
- **Severity: moderate.** No shipped mechanism is falsified and no claim is
  false; the criterion's evidentiary value is what is reduced.
- **Repair.** Either record the refused path (relative to the directed set, so
  no new privacy surface is created) so the criterion can discriminate, or run
  one role with the scope in observe-only mode; and state the refusal counts in
  the receipt alongside the "no read outside the directed set" line.

### Finding 3 — the installed rung-6 output-review gate obligates 127 whole-file read receipts and names no file when it refuses (delivered enforcement, high)

- **Observed, live in this session.** The Stop hooks refused this verifier's
  first completion with
  `DOTLN_HARNESS_REFUSED: read-your-own-output: output not read at its current
  bytes`. The obligation is
  `harnessOutputs(root, session.startingRevision)`
  (`packages/skeleton/src/harness-host.ts:481`), where `startingRevision` is
  `git rev-parse HEAD` captured at role resolution (`:743`). This project forbids
  branch commits before final review, so `HEAD` is always `main` and the
  obligation is the **entire accumulated work-order diff**: on this tree
  **127 files** (32 tracked A/M + 95 untracked) as measured before this report
  existed, 128 with it, of which 125 were written by the executor rather than by
  this session.
- **What is intended and what is not.** The cost itself is intended: the
  generated verifier skill says "Read every changed output at its current
  bytes", and 02 explains the session-entry baseline as preventing a final-review
  commit from hiding files. Two things are not intended, and are the defect: the
  refusal is undiagnosable, and five of the required outputs silently cannot
  produce a receipt at all. Whether the obligation should scale with the branch
  diff or with what the session actually wrote is an open design question for
  the operator, not a claim of this report.
- **The obligation is unsatisfiable by construction, not merely expensive.**
  `observeRead` mints a receipt only when
  `file.content.replace(/\n$/, "") === contents.replace(/\n$/, "")` — the read
  must deliver the whole file. A ranged read mints nothing. I tested this
  directly: a full-file `Read` of `docs/evidence/WO-039/checks-002.txt` is
  **refused** by the tool — "File content (44634 tokens) exceeds maximum allowed
  tokens (25000). Use offset and limit parameters" — and offset/limit is exactly
  the ranged form that mints no receipt. **Ten of the 128 required outputs are
  over that cap and can therefore never produce a receipt by any means:**

  |   Bytes | Path                                                        |
  | ------: | ----------------------------------------------------------- |
  | 853,972 | `docs/evidence/WO-039/feedback-initial/selfhost-verification.jsonl` |
  | 730,258 | `docs/evidence/WO-039/feedback/selfhost-verification.jsonl` |
  | 557,323 | `docs/lineage/idea-ledger.md`                               |
  | 133,700 | `docs/evidence/WO-039/checks-001.txt`                       |
  | 108,992 | `docs/evidence/WO-039/checks.txt`                           |
  | 108,105 | `docs/product/02-domain-model.md`                           |
  | 107,707 | `docs/product/03-architecture.md`                           |
  | 106,019 | `docs/evidence/WO-039/checks-002.txt`                       |
  |  90,995 | `docs/product/06-roadmap.md`                                |
  |  82,019 | `docs/planning/work-order-map.md`                           |

  The cap is on tokens, not lines, so which files fail is not predictable from
  the line count the host uses. Several are files this very order wrote or
  changed — its own `npm test` transcripts, its own feedback streams, and the
  02/03/06 write-backs criterion 7 requires. **The consequence is that no
  session can cleanly complete in this repository while this hook is installed
  as generated**, including the executor's, this verifier's, and the final
  reviewer's.

- **It is isolated, which sharpens the diagnosis.** The first completion attempt
  was refused by three Stop units. After this verification filed VER-001, ran
  `npm run harness -- evidence` (both required checks executed, exit 0) and
  recorded `VerificationCompleted`, `no-partial-completion` and
  `verify-app-before-done` both pass — they were satisfiable through ordinary
  lifecycle work, exactly as designed. `read-your-own-output` alone still
  refuses, with the whole verification complete and recorded. The gate that
  cannot be discharged by doing the job correctly is this one.
- **The refusal is not actionable.** The message is the bare predicate reason
  from `packages/compiler/src/feedback.ts:424`; it names none of the 127 paths
  and does not say how many lack receipts. The per-session journal that would
  answer it lives under `docs/control/local/harness/`, which the generated
  `permissions.mjs` hook refuses to let the session read — I was refused
  (`DOTLN_HARNESS_REFUSED: compiled authority does not permit this effect`) when
  I tried.
- **Why no fixture caught it.** `scripts/test-harness.mjs:322` loops
  `harnessOutputs(root)` over a scratch tree the fixture itself created — roughly
  seven small files, all authored by the fixture session, none near the line cap.
  The four live smokes run against the same synthetic WO-999 tree (7–8
  `actualReads`). Nothing exercises the gate at the scale of a real work-order
  branch, which is precisely the scale criterion 5 puts it into production at.
- **Reproduction.**
  `{ git diff HEAD --name-only --diff-filter=AM; git ls-files --others --exclude-standard; } | sort -u | wc -l`
  → 127; then attempt to end a session.
- **Severity: high, and blocking.** This is delivered enforcement in the
  repository's own committed configuration, installed by criterion 5, and it is
  the order's stated Objective ("Make a saved build govern the sessions that
  actually run") meeting its first real tree. No acceptance criterion names it,
  which is exactly why it has to be said here rather than left for the next
  session to rediscover. I am ending this session with the gate still refusing;
  that refusal is this finding, not an incomplete verification.
- **Repair.** The whole-file receipt rule is the defect, so start there: accept
  a set of ranged receipts that together cover the file, or verify the delivered
  bytes against the on-disk hash without requiring one delivery. Then make the
  refusal name the missing paths and a count — with 128 outputs and a silent
  cap, the current message cannot be acted on. Separately, the operator should
  settle whether the obligation is meant to scale with the branch diff or with
  what the session actually wrote: the unit is named `read-your-own-output` and
  02 describes "output obligations", but what is enforced is the former.
  Until one of these lands, expect every session in a work-order worktree to end
  on a refusal it cannot clear.

### Finding 4 — the receipt claims drift-fixture coverage that does not exist (evidence accuracy, low)

- **Observed.** `docs/evidence/WO-039/README.md` states: "Fixtures reject
  one-byte drift, stale owned files, unowned collisions and symlink escapes
  before writing." Only two of those four are asserted anywhere. The single
  drift assertion is `assert.throws(() => checkHarness(root), /harness drift/)`
  at `scripts/test-harness.mjs:380`, reached by appending one byte to a generated
  skill, plus the symlink refusal immediately after.
- **Uncovered.** `scripts/lib/harness.mjs` raises four other refusals that no
  fixture reaches: `harness drift: missing` (`:214`),
  `harness drift: unexpected` (`:225`), `harness drift: manifest` (`:232`), and
  `unowned harness output refuses replacement` (`:188`) — the last being exactly
  the "stale owned files / unowned collisions" behavior the receipt claims is
  fixture-backed.
- **Reproduction.** `grep -rn "harness drift" scripts/` returns one assertion and
  four raise sites; `grep -n "unowned\|obsolete\|walkOwned" scripts/test-harness.mjs`
  returns nothing.
- **Severity: low.** Criterion 5 requires only the one-byte drift fixture, which
  exists and passes, so this does not change that criterion's verdict. It matters
  because the final reviewer will read the receipt rather than the fixtures, and
  the sentence would carry them past four untested refusal paths in the code that
  owns this repository's committed configuration.
- **Repair.** Either add the three `checkHarness` branch assertions and the
  unowned-replacement assertion, or narrow the sentence to the two behaviors the
  fixtures actually prove.
