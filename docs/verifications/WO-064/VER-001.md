## Goal-aligned judgment

The critical-path benefit is an operator-granted source-change branch becoming a target pull request that a later order can observe. The granted fixture and operator smoke support that benefit. The matrix defect works against it: a PR can appear to carry independent acceptance evidence for the published WorkOrder when the row belongs to another verification contract. Rule beating and seeking the wrong goal are the material traps here. Policy resistance is bounded by the existing compiler, guard and lint; the repair should preserve that single authority path. Commons cost is one new suite in a 279.30-second gate and no dependency or subagent. The implementation does not normalize a weaker test baseline (drift), add an autonomous retry/process loop (escalation), prefer an incumbent publish body without evidence (success to the successful), or require the operator to handwrite the body (shifting the burden). Naive Interventionism argues for a criterion binding check at the existing generator/host seam, not a new verification subsystem. NoOp would leave the source-to-deliverable loop incomplete; accepting this verdict and repairing the matrix binding is the bounded route to that outcome.

## Finding F1 — an unrelated matrix can claim acceptance verification

**Criterion:** 1, generated pull-request body from the WorkOrder contract, diff and acceptance matrix; consequential to criterion 2's outward content claim.

**Expected:** when a matrix is supplied, each status in the PR's acceptance table describes the corresponding criterion of the compiled WorkOrder for the observed head. A matrix with unrelated criteria must refuse before a remote call or leave the current WorkOrder criteria explicitly unverified.

**Observed:** `acceptanceMatrix()` in `scripts/lib/target-publish.mjs` selects a replayed matrix solely by `subjectRevision === commit` and forwards `row.criterion.description` plus status. `generateTargetPullRequest()` in `scripts/github-body.mjs` then replaces the WorkOrder's acceptance rows with those matrix rows. The projection in `packages/skeleton/src/verification.ts` carries `workstreamId`, revision and rows, but no WorkOrder identity; a Git revision alone does not bind the verifier's chosen criteria to the published contract.

**Reproduction:** I called the exported generator with a WorkOrder whose only criterion was `Input is rejected safely`, base `a` repeated 40 times, head `b` repeated 40 times, and a matrix for that same head whose only row was `Unrelated behavior works` with status `verified`. It returned a PR body containing `| Unrelated behavior works | verified |` and `Independent verification: acceptance matrix for bbbb…: 1 verified, 0 failed, 0 stale, 0 incomplete.` No error occurred. The direct test uses the same public function that publication calls after the store projection. The existing target fixture covers a matrix for a *different revision*; it does not cover same revision with different criteria. The static host path forwards those rows unchanged, so the same mismatch reaches `gh pr create` if such a store is supplied.

**Severity:** major. The optional matrix is presented as independent acceptance evidence in an outward artifact. Its criterion can be unrelated to the WorkOrder even while every reported row says verified. This is a substantive implementation finding, not a failure of the test gate. [D008](../../evidence/WO-064/decisions.md#wo-064-d008--verification-finding-bind-the-acceptance-matrix-to-the-published-workorder) names the follow-up: bind the replayed rows to the compiled WorkOrder's criteria and exercise a same-head mismatch through the host path. I did not edit implementation to change this verdict.
