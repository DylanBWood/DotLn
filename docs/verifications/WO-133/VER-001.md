## Findings

### F1 — every non-runtime advisory shares one per-session marker, so the first `classification` advisory silences all later distinct ones (non-blocking; as-designed, nominated to planning)

The marker key is `JSON.stringify([sessionId, cause])`
(`packages/compiler/src/harness.ts`, `showHarnessAdvisory`), and `cause` is the
reason class only when it is one of the three runtime classes; everything else
collapses to the single literal `classification`
(`packages/skeleton/src/harness-host.ts:2980–2990`). `reasonClass` defaults to
`config.kind` for every advisory that is not an error path, so the Stop hook's
support advisory (`finish`), the permission hook's authority advisory
(`authority`), the command classifier's advisory and `HarnessStateUnreadable`
all claim and consume the same marker.

Reproduced against the built runtime:

```
$ node --input-type=module -e '
import {showHarnessAdvisory} from "./packages/compiler/dist/src/harness.js";
const claimed=new Set(); const claim=k=>claimed.has(k)?false:(claimed.add(k),true);
…'
SHOWN      PreToolUse command classification
SUPPRESSED Stop pending verify-app-before-done
SUPPRESSED PreToolUse attribution pre-check
SHOWN      PreToolUse pins-differ
marker keys claimed: ['["live-session","classification"]','["live-session","pins-differ"]']
```

Observed end to end in this verification session, whose runtime is healthy and
which therefore exercises only the non-runtime path. At 05:11:44Z the journal
held 1,119 rows, 12 of them advisory rows carrying five distinct messages, and
exactly one advisory marker file existed — claimed by the first message at
04:58:37.735Z, on my first compound Bash command of the session:

```
04:58:37.735Z PreToolUse  feedback     command classification: Shell control syntax …   ← shown
04:58:37.860Z PreToolUse  permission   command classification: Shell control syntax …   ← suppressed
05:05:30.517Z PreToolUse  permission   compiled authority does not permit settings.user ← suppressed
05:05:30.784Z PostToolUse observe      runtime-unavailable: Path outside the worktree   ← silent by design (criterion 1)
05:06:29.190Z Stop        finish       pending no-partial-completion, verify-app-…      ← suppressed
05:11:44.440Z PreToolUse  feedback     command classification: Dynamic shell substitut… ← suppressed
```

The order's own fixture amendment is the second independent witness. At `HEAD`,
`scripts/test-harness.mjs` asserted that both Stop attempts after a source
change return the visible advisory:

```
    for (const response of [first, second]) {
      assert.equal(allowed(response), true);
      assert.match(response.systemMessage,
        /^DotLn advisory: pending .*verify-app-before-done/);
```

In the subject that assertion now reads `assert.equal(response.systemMessage,
undefined)` for both, and the advisory text is recovered from the journal
instead. Both are suppressed, not merely the second, because an unrelated
advisory earlier in that fixture session had already claimed the marker.

Why this is recorded and not routed to repair: the order's Design section says
the marker is "keyed by session id and cause class (`pins-differ`,
`snapshot-missing`, `runtime-unavailable`, `classification`)" and that
"`protocolAdvisory`" consults it. The executor implemented the order as written,
disclosed the four classes in the product 07 write-back, and no acceptance
criterion requires repeat non-runtime advisories to survive. Judging the design
itself is planning's call, not this verifier's.

Why it still matters: the order's Objective and Cost line are about the runtime
flood — "the advisory that today repeats on every hook event", 344 rows in one
session. What shipped also silences WO-132's support signals. The
`pending no-partial-completion, verify-app-before-done` line exists to make an
unverified completion visible at the moment it is claimed; in any session that
has run one compound shell command it is now invisible for the rest of the
session. The release-facing text in `README.md` describes the change as
"Runtime advisories appear once per session and cause", which reads narrower
than what the code does.

Reopening observation and repair shape, if planning wants it: key the marker on
the advisory's own identity — the support ids or a digest of the message —
instead of one `classification` bucket, or exclude non-runtime causes from
suppression entirely; the flood the order measured is carried wholly by the
three runtime causes. A one-session regression that emits two distinct
non-runtime advisories and expects two visible messages would pin it.

## Observations

**O1 — `unreadable-state` also lands in the `classification` bucket.** A
`HarnessStateUnreadable` advisory sets `reasonClass = "unreadable-state"`, which
is not one of the three runtime classes, so it shares the same marker as the
command classifier. Unreadable control state is exactly the condition an
operator needs to see; it is silent after any earlier advisory. Same mechanism
as F1, same nomination.

**O2 — the source-only pin reader hard-codes a narrow path shape.**
`scripts/lib/harness-runtime.mjs` accepts a pinned runtime file only if it
matches `^packages/(?:compiler|skeleton)/dist/src/[a-z-]+\.(?:js|mjs)$`, and
returns `runtime-unavailable` otherwise. All 14 pins in both installed profiles
match today, which I checked directly. A future runtime file whose basename
contains a digit, an underscore or a capital would be read as
`runtime-unavailable`; `refreshHarnessRuntime` would then build once and throw
`Built runtime still runtime-unavailable; checkout preserved`, failing every
release close and worktree finish until the regex is widened. Reopening
observation: the first pinned runtime file outside `[a-z-]`.

**O3 — `version.ts` is outside every machinery declaration by construction.**
That is what criterion 5 asks for, and it is what makes the file a place where
behaviour could be added without selecting any machinery suite. The file is two
lines and its comment says release metadata only; the risk is latent, not
present. Reopening observation: any executable statement added to `version.ts`.
The now-dead projections for `HARNESS_HOST_VERSION` and `skeletonVersion` in
`packages/skeleton/src/evidence-editions.mjs` are harmless residue.

**O4 — the adjacent fixture repair (D004) narrows two frozen comparisons and
preserves the one that matters.** `reactor-slices.test.ts` now recompiles the
stored WO-050 correction program with the current compiler and generates the
scenario log live through `runScenario` instead of reading
`wo050/scenario.jsonl`; both tests assert slice ownership and predicate
behaviour rather than byte identity, so the substitution is defensible. The
19-case byte oracle in `wo050-identity.json` is preserved and still compares
recorded bytes, under a test-only loader that substitutes a single constant in a
single module and asserts it is invoked only from
`reactor-identity.mjs --check-historical`. I ran it: 19 fixtures verified under
recorded compiler identity 0.11.1, without state normalization. Production
artifact validation is unchanged, and D004 plus the fixture README disclose the
narrowing. Reopening observation: a compiler change beyond its release identity.

**O5 — read-only Bash was refused throughout my own gate; pre-existing, not this
order.** While `npm test` was live, this session's `wc -c <path>`,
`sed -n '1,80p' <path>` and `node -e` calls were all refused with
`DOTLN_HARNESS_REFUSED: write may change gate inputs during active gate`. This
is the conservative shape of the kept refusal and the same class WO-132 VER-001
reported as F2; WO-133 changes no classifier and its non-goals exclude it. I
used the host's file reader for those reads and lost no coverage. Recorded so
the reviewer does not read it as a regression of this order.

**O6 — the evidence editions moved to WO-133 for all four kinds.**
`docs/evidence/current.json` now selects WO-133 for `authority` (revision 001),
`artifact-identity`, `verification` and `feedback`, and the corresponding
directories exist under `docs/evidence/WO-133/`. D004's prose says those checks
"still pass without replacement", which reads as though the editions were
unchanged; they were re-issued. The four evidence suites pass in my gate run, so
this is wording, not behaviour, and the untracked evidence directory is normal
before final review.
