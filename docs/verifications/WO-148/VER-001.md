## Goal-aligned outcome

The intended capability is worthwhile: one explicit bind removes the recurring
hand-written store while retaining explicit surfaces and immutable stores. NoOp
would leave WO-099's mechanism impractical for daily work. The observed result
does not yet safely deliver that benefit. F1 is rule beating—a successful
freshness check does not prove the subject that will be judged. F2 shifts the
burden back to the operator by printing unusable commands after accepting the
store. F3 defeats the privacy and recoverability reason for the local lane on a
configuration the control plane supports. Repairing these narrow boundaries is
smaller and more reversible than weakening the documented guarantees or
expanding into automatic rebinding, surface derivation, pruning or a
resident-host change.

The other system-trap lenses do not change the decision: no authority or
budget is widened, no new recurring process is proposed, the successful core
fixture remains reusable, and the findings are not reasons to replace the
existing resident mechanism. They are reasons to make its advertised boundary
true before handoff.

## F1 — high — `--check` accepts a store retargeted through unchecked mission-source fields

**Criterion and promise.** The objective requires the binding to record the
decisions file, surfaces, vision path and thesis headings used by the mission
check. Criterion 2 requires stale bindings to refuse their launch line.
Criterion 5's product write-back says `--check` compares “the store's own
declared source” with the binding. D005 records the same decision.

**Observed.** `bindingMismatches` compares only `root`, `contractPath`,
`baseCommit` and a comma-joined `declaredSurfaces` string. It never compares
`decisionsPath`, `decisionLimit`, `visionPath` or `thesisHeadings`. It also reads
plain JSON rather than decoding the resident configuration during check.

The probe kept every canonical observation and every compared field identical,
then changed all four omitted fields in the stored actor. The returned mismatch
array was empty. A real `--check` therefore proceeds to the success heading and
launch lines.

**Expected.** Every stored declaration that changes the dispatch-time mission
subject must match its binding record, and the configuration must remain a
valid resident configuration, before any launch line is printed. Array fields
must be compared structurally; joining paths with punctuation is not an exact
array comparison.

**Why consequential.** `startCliEpisode` passes the stored `missionSource` to
`observeMissionSubject` on every pulse. The omitted fields select the decisions
and vision context the model actually judges. This is not stale display
metadata: the successful check can authorize a resident aimed at a different
mission context than its binding says.

**Severity:** high. The command's conservative-staleness guarantee can be
green while the consequential subject differs. Repair is bounded to the check
comparison and its regressions; no resident-host or schema change is needed.

**Ownership:** boarded in
[WO-148-D012](../../evidence/WO-148/decisions.md#wo-148-d012), which names the
repair and one-field-at-a-time negative fixtures.

## F2 — moderate — a successful check of a relocated retained store prints unusable paths

**Criterion and promise.** Criterion 1 requires printed operational lines to
name the store. The runbook tells the operator to use `--check <store>` before
the next launch. The implementation's own moved-store fixture deliberately
accepts a relocated retained store as fresh.

**Observed.** `readBinding` resolves and returns the directory passed to
`--check`. `checkBinding` discards it, and the success path calls
`launchLines(binding.store)`. After moving a newly bound store, checking its new
directory exited 0, but every actionable line still named the missing original
directory and none named the checked directory.

**Expected.** Because relocation is admitted, successful output must use the
directory that was checked for launch, presence, status, export and the next
check. The original binding path can remain provenance. Alternatively,
relocation would have to refuse explicitly, but that would reverse the current
fixture's product choice.

**Reproduction.** A disposable real-Git launchpad ran the actual bind, renamed
the store, and ran the actual `--check` against the new location. Result:
`checkExit: 0`, checked-path launch absent, original-path launch present.

**Severity:** moderate. The subject being judged is unchanged, but the command
returns success with instructions that cannot open the store it just checked.

**Ownership:** boarded in
[WO-148-D013](../../evidence/WO-148/decisions.md#wo-148-d013), including the
missing assertion in the existing moved-store fixture.

## F3 — high — a configured control root can put physical paths on a Git-visible surface

**Criterion and promise.** Criterion 3 is explicit: the binding and store live
in the ignored lane, and no physical path enters a committed surface. The
objective depends on WO-069's configured control lane. Product 03 and the
runbook both call the resolved destination ignored.

**Observed.** `docPath(launchpad, "control", "local/resident")` correctly
follows a configured control root, but bind never asks Git whether that resolved
lane is ignored. The repository's shipped ignore rule names only the default
`/docs/control/local/` path; the configuration schema validates containment and
does not create or require a corresponding rule.

In a real-Git launchpad with the supported control root `records/state` and no
matching ignore rule, the actual command exited 0 and wrote both files under
`records/state/local/resident/WO-999-1/`. `git status
--porcelain --untracked-files=all` exposed both files. The binding record held
absolute worktree and store paths, so an ordinary broad add could place those
physical paths on a committed surface.

**Expected.** Before creating a path-bearing store, bind must prove that the
resolved local lane is ignored or refuse by name. A configured-root positive
fixture must add the correct ignore rule and finish with a clean Git status.

**Severity:** high. This directly fails criterion 3 on a configuration the
order claims to support, at the privacy boundary the ignored lane exists to
protect.

**Ownership:** boarded in
[WO-148-D014](../../evidence/WO-148/decisions.md#wo-148-d014), with refusal and
positive configured-root fixtures named.
