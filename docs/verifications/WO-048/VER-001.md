## Non-blocking observations

- **O1 — the inventory tripwire misses a module-local rebinding (minor; the only literal gap against criterion 1's wording).** The AST walk resolves `fs` import aliases and namespace/property forms, but derives the API name from the call expression's own text. A read added as `const bytes = readFileSync; … bytes("planted.json", "utf8")` yields the name `bytes`, matches no read-API pattern, and the suite passes with that unguarded read present. Reproduction: mirror `packages/skeleton/{src,fixtures}` and `dist/test/worker-read-inventory.test.js` into a temp tree with `{"type":"module"}`, insert the two lines above into the `worker-host.ts` copy, and run `node --test` on the mirrored test — P0/P1/P2/P4 behave as expected (pass, fail, fail, fail) and P3 passes. Impact is bounded: this is a tripwire against accidental additions, it catches every form present in the codebase plus three of four planted evasions, and the manifest deep-equal independently proves the current complete read set. `read-paths.md` is accurately scoped ("rejects added ordinary, aliased and namespace reads") and does not overclaim. Closing it would mean tracking module-local bindings of the imported symbols; the reviewer decides whether that is worth a follow-up.
- **O2 — refusals raised inside the acquisition preflight are prefixed with the wrong path (cosmetic).** `acquire` wraps the caller's preflight in `atPath(this.logPath, "recovery state", preflight)`, so a malformed *receipt* discovered during contextual loading reports `…/events.jsonl: invalid recovery state: …/cmd_….result.json: invalid saved result receipt: …`. Both the path and the shape are named, so criterion 2 holds and the corpus assertions are satisfied, but an operator reading the leading path is pointed at the log rather than the offending file. Observed in my oversized-summary, control-character and foreign-candidate probes. Refusals raised by `acquire`'s own receipt scan (foreign receipt, `__proto__` key, receipt-as-directory) correctly lead with the receipt path.
- **O3 — `saveResult`'s staging guard is unreachable (dead code, harmless).** `saveResult` calls `this.loadResult(request)` before its own `if (present(staging))` check, and `loadResult` now refuses on a present `.pending` first. The later branch can never be taken. It is defensive depth, not a defect.
- **O4 — a leftover `.pending` no longer self-heals (intended, but an operational change worth the reviewer's attention).** Before this order, `saveResult` unlinked a stale staging file and proceeded; it now refuses permanently until an operator inspects it. A crash between `durableWrite(staging)` and `linkSync` therefore wedges the store rather than recovering on the next run. This is the order's own recorded declined alternative ("silently deleting malformed files — inspection is the operator's") and is documented in the skeleton README, so it is authorized, not a regression to repair.
- **O5 — `preflightVerificationRecovery` is stricter than `acquire` about capsules (untested by me).** It calls `assertVerificationTask` on every `CommandPersisted` unconditionally, whereas `acquire` decodes a capsule only when the effect is `verification.evaluate`/`repair.propose` or the payload has a `capsule` key, and `verification-demo.ts:458` defensively tolerates a capsule-less persisted command. With the shipped authorization path every verification command carries a capsule, so I judge this unreachable, but I did not construct a store that proves it.
- **O6 — pre-existing harness advisory.** `harness-evidence.mjs` prints `process budget exceeded: coldStartBytes.release-close=8865 > 8192`. Neither `.claude/skills` nor `CLAUDE.md` is modified in this subject (`git diff --stat main` over both is empty), so I read this as pre-existing and unrelated to WO-048. I did not re-run the script at `main` to confirm.
- **O7 — log payloads outside the decoded set keep their recorded shape (scope note, not probed).** `acquire` positively decodes `CommandPersisted` commands/capsules and the three lease payloads; other payloads pass only `decodeLog`'s envelope validation. `worker-demo.ts:191-215` and `verification-demo.ts:417-447` reuse `CommandResult` payload envelopes from disk when completing a crashed history. That sits outside criterion 1's three-host scope and outside the order's enumerated read set, and `read-paths.md` does not claim otherwise; I did not probe it. It is a candidate for the follow-up that WO-045 VER-001 O1 already nominated for this area (validating the assigned envelope before writing).

The promised benefit is observed. Every malformed shape I tried — 33 shipped plus 12 of my own — refuses before any lock reclaim, event append, transport dispatch or result acceptance, and leaves the store byte-identical for inspection. NoOp would have left those casts in place on the path the runtime depends on most.

- **Rule beating** was checked directly rather than from the executor's aggregate green: I re-ran the full gate, ran the focused suites, planted four reads against the inventory tripwire, and probed twelve store shapes the corpus does not contain. One tripwire bypass surfaced (O1); the substantive refusal guarantee held everywhere.
- **Drift to low performance / fixes that fail:** the stricter `.pending` refusal (O4) trades automatic self-healing for preserved evidence. That is the order's recorded choice and is documented for operators, but it is the change most likely to surprise someone running a live store, so I have surfaced it rather than let it pass silently.
- **Shifting the burden:** O2 and O7 are recorded, not repaired here; neither changes a verdict.
- **Commons, escalation, success to the successful, policy resistance, seeking the wrong goal:** immaterial. No dependency, no schema, no contract, no new process, and the gate time is unchanged.
- **Naive Interventionism** argues against reopening anything. The decoders are correct, the existing WO-009/WO-010 fixtures are literally unchanged and green, and the smallest useful probe — malformed recovery beside unchanged history — is exactly what the corpus does. O1 is a follow-up at most.
