## Finding for repair

**F1 — the missing-browser failure names an install command that does not fix it (class: correctness, wrong remediation instruction; severity: major; criterion 6).**

- **Observed.**
  - `packages/browser-evidence/test/scenario.test.mjs:24` sets `process.env.PLAYWRIGHT_BROWSERS_PATH ??= join(root, ".runtime/playwright")`, so the suite launches from the ignored per-worktree directory `.runtime/playwright`.
  - When the pinned browser is absent, the suite fails with `Pinned Chromium launch unavailable; run npx playwright install chromium --only-shell` (the reason from `src/index.ts:323`).
  - Run from the repository root without that variable, `npx --no-install playwright install --dry-run chromium --only-shell` reports `Install location: ~/Library/Caches/ms-playwright/chromium_headless_shell-1243` (the home directory abbreviated). With the README's `PLAYWRIGHT_BROWSERS_PATH="$PWD/.runtime/playwright"` prefix, it reports `<repo>/.runtime/playwright/chromium_headless_shell-1243`.
  - Probe `install-probe.zsh` built a scratch repository copy with no `.runtime/playwright`. It linked the pinned `chromium_headless_shell-1243` and `ffmpeg-1011` into a fake `HOME`'s `Library/Caches/ms-playwright`, which is the named command's destination. Results:
    - (a) The package driver, run as a default-environment `runScenario` caller, returns `available` (exit 0).
    - (b) The package suite's `installed pinned browser` case still fails (exit 1, pass 0, fail 1) with the same instruction: `AssertionError [ERR_ASSERTION]: Pinned Chromium launch unavailable; run npx playwright install chromium --only-shell`.
    - (c) The same suite passes when `PLAYWRIGHT_BROWSERS_PATH` names that cache (exit 0).
  - The executor's `missing-browser` fixture passes `PLAYWRIGHT_BROWSERS_PATH` explicitly, so the default is never exercised. It checks that the command is named, not that it works.
- **Expected.** Criterion 6 requires that "the package's suite fails naming the install command". The Design gives the reason: "so a session installs it before the gate", and operator-review assumption 2 relies on the same thing. The named command must install the pinned browser where the suite launches it. `.runtime/` is per-worktree and ignored, so every new worktree's `npm test` reaches this failure. Following the instruction there repeats the failure.
- **Rule a repair must hold.**
  - The absent-browser failure of the package suite, and of the product gate row that runs it, names a command that, run as printed from the repository root, installs the pinned headless shell into the directory the suite launches from.
  - A fixture establishes this against the suite's actual default, not an explicitly supplied path. For example, the named command's `--dry-run` install location equals the suite's browsers path, or the suite's browser case passes once that destination holds the pinned revision.
  - The adapter's own `unavailable` reason stays accurate for a default-environment `runScenario` caller, as probe (a) shows it is now.
  - The README and the failure message name the same command.
  - Either direction satisfies this: name the `.runtime/playwright` form, or have the suite use Playwright's resolved default. Criteria 5–6 and the existing refusals must still hold.
  - A repair that changes `package-lock.json` or a judged source re-runs criterion 8's live episode, as the order states.
- **Limits.** The probe simulated the install with symlinks to the pinned revisions already in this worktree. It did not download a browser. The dry-run locations are Playwright 1.63.0's own reports on this macOS host.
