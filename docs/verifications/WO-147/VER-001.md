## Goal-aligned judgment

The order removes the one recorded ownerless way a live-contended store ends a
presence command or a resident transaction, directly ahead of WO-111's first
unattended hour. NoOp leaves an intermittent, operator-visible exit in the
always-on resident — the reason WO-143 D004 boarded it rather than accepting it.
Naive Interventionism is avoided: the intervention is one guarded re-inspection
inside the path that already holds exclusion, with no new error class, no widened
transaction retry, no new mechanism and no new dependency, gate or schedule.

Rule beating is the live trap here, and the order anticipated it: a fixture that
merely passes would prove nothing, so criterion 1 demands a discriminating
assertion. I checked that directly rather than trusting the passing run — see
criterion 1. Drift to low performance is checked by re-measuring the lock cycle
rather than assuming it. Seeking the wrong goal is checked by asserting prior
event bytes across the contended acquisition instead of treating a successful
retry as the outcome. Shifting the burden and policy resistance are bounded by
the unchanged refusal surface: malformed, missing and live state still refuse,
and the retry is keyed to a filesystem code rather than to diagnostic wording.
Escalation and tragedy of the commons are bounded by zero subagents and no new
recurring command (D002). Success to the successful is addressed by D001's
recorded comparison against a transaction-level retry and a new lifetime mutex.

## Criterion 1 — a lock released between observation and read

**Expected:** two real processes; the contender pauses after observing
`host.lock` and before reading it, the holder releases, the contender acquires
with no `ENOENT`; prior event bytes identical; `ResidentStore.transaction`
completes on the contended path; a mutant with the re-inspection removed fails.

**Observed:** `WO-147 a lock released between observation and read is
re-inspected under the guard` passes in **498.10 ms**, covering both arms. The
contender pauses at `lstatSync` on `host.lock` — which is `present(lock)`, the
first inspection call — the holder's `release()` unlinks the lock, and the
contender's subsequent `regularFile(lock)` raises `ENOENT`, which the new
`try`/`catch` converts into one re-inspection under the guard it already holds.
For the transaction arm the holder owns `.resident-append/host.lock`, which is
exactly the lock `ResidentStore.transaction` takes first, so the contended path
is the real one.

**Reproduction of the discriminating claim:** I replaced the compiled
`try { abandonedLock = inspectLock(); } catch … { abandonedLock = inspectLock(); }`
with a single `let abandonedLock = inspectLock();` in
`packages/skeleton/dist/src/worker-store.js` and re-ran the fixture. It failed in
**139.24 ms** with
`AssertionError … Error: ENOENT: no such file or directory, lstat '…/acquire/host.lock'`,
`actual false, expected true`. Rebuilding from unchanged sources restored the
pass. The fixture discriminates the change, as WO-143 F2 required of this class
of evidence.

**Limit:** the byte-identity assertion is substantive only on the transaction
arm, whose log carries `seedFlight` content. On the direct-acquire arm the log is
the empty file `acquire()` creates, so that arm's comparison is trivially true.
This weakens one assertion; it does not weaken the `ENOENT` claim, which is what
the criterion is about.

**Judgment:** pass. Severity: none.

## Criterion 2 — the retirement inference

**Expected:** a delayed claimant links into the retired target while retirement's
`rmSync` is paused; either `ENOTEMPTY` reproduces and the repaired retirement
completes, or the decisions file records the probe's pause points, attempts and
outcome and that the inference did not reproduce.

**Observed:** `WO-147 retirement probe tolerates a delayed claim present when
recursive cleanup begins` passes in **3.95 s**. In each of 20 attempts the
retiring peer pauses before `rmSync`; the test first asserts that `host.lock`
already holds the original's pid, so the pause is genuinely after publication;
the delayed peer then hard-links a valid `next-<token>.json` successor claim
into the retired target and the test asserts that entry exists. Retirement then
completes, the original acquires, and the delayed claimant refuses. `reproduced`
is 0 over 20 attempts. `acquireGuard` is unchanged. WO-147-D003 records the
disposition, and the decisions index carries it.

**Limit, checked rather than accepted:** the probe pauses at `rmSync`'s entry,
not inside the recursive traversal that WO-143 D004's inference names. I tested
whether the stronger pause is reachable at all: patching `fs.unlinkSync`,
`fs.lstatSync`, `fs.readdirSync` and `fs.rmdirSync` and then calling
`fs.rmSync(dir, { recursive: true, force: true })` on a non-empty directory
observed **no JS-level `fs` call** (`[]`). Node's recursive removal traverses
natively, so this fixture's interception technique cannot pause inside it. The
executor's pause point is the only reachable boundary, the claim is stated
accurately rather than overclaimed, and D003's reopen condition names precisely
this gap ("a probe that links during native recursive traversal rather than at
its paused entry"). The criterion's negative branch is satisfied.

**Judgment:** pass. Severity: none.

## Criterion 4 — unchanged refusals, compatibility and cost

**Expected:** live, unreadable and legacy guards refuse unchanged; a store
written by v0.32.1 opens unchanged; the lock cycle D006 measured at about 19 ms
is re-measured and reported.

**Observed:** the four WO-143 guard fixtures pass —
`live, unreadable and legacy guards refuse unchanged; released locks remain
compatible` (308.57 ms, which also carries the released-event compatibility
case), `malformed resident state preserves dead append guard and lock before
reclaim` (193.06 ms), `concurrent dead-guard starts publish exactly one reclaim
claim` (116.63 ms) and `a delayed claimant cannot unlink a successor through a
retired target` (217.33 ms).

I read the refusal surface rather than inferring it from the passes. The retry
is keyed to the filesystem code, not to a message: `atPath` now copies the
underlying Node `code` onto `StorePathError`, and the catch rethrows anything
whose code is not `ENOENT`. A malformed lock, a non-regular lock, an `EACCES`
read and the `already has a live host` refusal all carry no `ENOENT` code and
still propagate. The `process.kill` inner catch still rethrows everything that
is not `ESRCH`. The only reader of `host.lock` in the packages is `acquire`, so
the objective's surface is fully covered by this one path.

**Cost, re-measured independently:** 400 timed `acquire()`/`release()` cycles
after 20 warm-ups on a fresh system-temp store, run twice: medians **18.071 ms**
and **18.039 ms**, p90 22.044 and 21.975 ms, p99 24.023 and 23.228 ms. This
agrees with the executor's 17.942 and 17.296 ms medians and shows no regression
against WO-143 D006's recorded ~19 ms median on this host. The change adds no
filesystem call on the uncontended path, which the measurement is consistent
with.

**Judgment:** pass. Severity: none.

## Limits and disposition

The proof is bounded to conforming local writers. A same-user process that
creates or removes `host.lock` behind the acquisition guard is outside this
order, and the single re-inspection is not a fixed point against such a writer;
D004 records that and its reopening condition. `ESRCH` remains the only
establishment of death, and ambiguous liveness still refuses. The retirement
inference is closed as unobserved at the only pause point Node's native
recursive removal leaves reachable, not disproved. Criterion 3's stability
evidence addresses the pid-reuse hypothesis WO-069 D015 raised; it does not
claim the first unattended hour, which WO-111 owns and which remains this work's
reopening observation.

Two disclosures about instruments rather than about the subject:
`docs/discovery/environment.json` records `claude-code` observed versions only up
to `2.1.263` while this session's installed CLI is `2.1.278` (the `2.1` version
line is recorded as observed, so the attestation resolves against it); and the
executor's session counters were unavailable, so its receipt carries no token
totals to compare against this one.

No defect was encountered and deferred, so no follow-up decision or repair route
is due from this dispatch. Next legal workflow on this pass is
