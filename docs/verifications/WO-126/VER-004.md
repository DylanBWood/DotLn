### F21 — group, redirected, unlisted-shell and unlisted-interpreter routes admit a denied invocation the `v0.16.0` envelope refused (criterion 8, major; continues F1, F10 and F17)

**Expected.** The non-goals exclude "removing the writer guard, the
attribution guard or the permissions envelope"; the `v0.16.0` regex
`/\bgit\s+push\b/` is the floor (VER-001 F1, VER-003 F17). D015 retains
pipeline inputs and screens interpreter programs so that "an opaque interpreter
route containing a literal denied invocation requires an explicit adapter", and
its reopening condition is "a supported route hides a denied effect".

**Observed.** Direct `invocationEffects` calls on the built module and the
pinned snapshot (identical), and the installed `permissions.mjs` on a synthetic
session where marked. Every row is one command line whose literal text the
`v0.16.0` regex denied and which executes the push on this host; nothing was

`/bin/csh`, `/bin/tcsh`, `/usr/bin/tclsh` and `/usr/bin/swift` exist on this
host; `python3 -Ic 'print(…)'`, `ruby -ne 'BEGIN{…}'`, `csh -c` and `tcsh -c`
each ran a harmless program here, so the combined flags and the shells are
live routes. The adjacent shapes the repair covers show how close each miss
is: `echo … | { sh; }` refuses while `{ echo …; } | sh` does not; `sh -c`
denies while `csh -c` does not; `python3 -c` refuses while `python3 -Ic` does
not; `find -exec git push` refuses as an unknown wrapper while
`find -exec sh -c 'git push …'` does not.

**Cause.** (1) `finish` (`harness-command.ts:105-107`) returns before
recording the pipeline when `current` is empty, which is the state after `)`
or `}` closes a group, so a group is never a pipeline producer. (2) The `&` in
`2>&1` is read as a list separator, so the stage before the pipe is `1`.
(3) `shellPrograms` (`:50`) names `bash`, `sh`, `zsh`, `dash` and `ksh` only.
(4) `inlineInterpreter` (`:554`) matches `-c` for Python only at the start of
the token, `-e` for Ruby only at the start, `-r` for PHP only lower-case, and
`interpreterPrograms` (`:552`) omits `tclsh`, `swift` and every interpreter
not on its list. (5) A program outside `shellPrograms`,
`interpreterPrograms` and `dataPrograms` is classified by its own name only;
the "Unknown wrapper around a denied invocation" rule (`:636`) fires when the
denied invocation appears as separate tokens, not inside one quoted token.

**Consequence.** As F17: `remote.unapproved` is the effect the
no-commits-before-final-review rule depends on, and the Codex profile has no
other layer. Each repair has covered the shapes the previous report named and
left the next shape one token away, because the mechanism enumerates routes
rather than stating the rule the floor already states.

**Repair direction.** State the floor as a rule and prove it with a corpus,
instead of extending the lists: for any invocation whose program is neither a
data program (`echo`, `printf`, `grep`, `rg`, `cat`, `sed`, `sort`, `wc`,
`jq`, …) nor a known effect program classified by its operand (`git`, `gh`,
the package managers, `ssh`), a literal denied sequence (`git push` or
`send-pack`, a `gh` write verb, `<pm> publish`, `ssh|scp|sftp`) in any
argument token, heredoc body or pipeline-stage token refuses with the
classification reason. Under that rule the shell list, the interpreter list
and the flag regexes are needed only for the `-c` recursion that yields the
exact effect. Track groups as pipeline producers (promote the last finished
invocation when `|` follows `)` or `}`), and parse `>&`, `<&` and `&>` as
redirection operators before `&` is a separator. Add `csh` and `tcsh` to the
shell set for `-c` recursion. Fixture: for every command in a corpus that the
`v0.16.0` regexes deny, assert the classifier refuses or denies it unless its
program is a data program, and assert every data-program control above stays
admitted; add each row of this table.

### F22 — a `gh api` request with a body classifies as a read (criterion 8, moderate; continues F18)

**Expected.** D015: "mutating GitHub API methods, field-implied POST requests
… carry `remote.unapproved`"; D015's reopening condition names a supported
route that hides a denied effect.

**Observed.** `gh api --input body.json repos/o/r/pulls`,
`printf '{"title":"x"}' | gh api --input - repos/o/r/pulls` and
`gh api graphql --input q.json` classify as `shell.run` from both modules, and
the installed hook allows the first. GitHub's CLI on this host documents
(`gh api --help`, read with a temporary `GH_CONFIG_DIR` because the sandbox
refuses its configuration file) that "the default HTTP request method is
`GET` normally and `POST` if any parameters were added", that `--input`
supplies "the file to use as body for the HTTP request", and its own example
creates a ruleset with `--input file.json` and no `--method`; a request with a
body is sent as `POST`. The classifier (`harness-command.ts:531-548`) implies
`POST` for `-f`, `-F`, `--field` and `--raw-field` only.

**Consequence.** Not a regression against `v0.16.0`, which never matched
`gh api`; but the repair's own decision claims mutating requests, and a body
is the general form of one. `gh api --input - …` is the route a session
would take to open a pull request without `gh pr create`.

**Repair direction.** Treat `--input` and `--input=` as a body, implying
`POST` unless an explicit `GET`, `HEAD` or `OPTIONS` is given; treat
`gh api graphql` as `POST` always (the CLI sends it so). Add the three rows to
the fixture. While there, record in the effect table the answer for the other
remote writes that still classify as `shell.run` (`gh release upload`,
`gh workflow run`, `gh secret set`, `gh variable set`, `gh gist create`,
`gh repo fork|sync`, `gh label create`, `gh run cancel|rerun`, `gh pr ready`),
either way.
