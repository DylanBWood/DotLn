## Findings

### F17 — a shell reading a piped program, and interpreter one-liners, admit a denied invocation the `v0.16.0` envelope refused (criterion 8, major; continues F1 and F10)

**Expected.** The non-goals exclude "removing the writer guard, the
attribution guard or the permissions envelope". Criterion 8 asks the classifier
to classify the command's own invocation so that a heredoc or search pattern is
not refused as an effect; the `v0.16.0` regex `/\bgit\s+push\b/` is the floor.

**Observed.** `executableInvocations` re-tokenizes `eval` and `bash|sh|zsh -c`
and follows a quoted heredoc body into a shell, but a shell with no `-c` and
no heredoc is an ordinary program, and an interpreter's inline program is one
quoted token that `deniedInvocation` never opens. `awk` is listed in
`dataPrograms`, so its arguments are not scanned at all. Direct
`invocationEffects` calls on the built module and the pinned snapshot (identical
results), against the `v0.16.0` regex:

| Command | Now | `v0.16.0` |
| --- | --- | --- |
| `echo 'git push origin wo-126' \| sh` | `shell.run,shell.run` | `remote.unapproved` |
| `printf 'git push origin wo-126' \| bash` | `shell.run,shell.run` | `remote.unapproved` |
| `node -e "require('child_process').execSync('git push origin wo-126')"` | `shell.run` | `remote.unapproved` |
| `perl -e 'system("git push origin wo-126")'` | `shell.run` | `remote.unapproved` |
| `python3 -c 'import os; os.system("git push origin wo-126")'` | `shell.run` | `remote.unapproved` |
| `ruby -e 'system("git push origin wo-126")'` | `shell.run` | `remote.unapproved` |
| `awk 'BEGIN{system("git push origin wo-126")}'` | `shell.run` | `remote.unapproved` |
| `bash <<'EOF'` … `git push origin wo-126` … `EOF` | `shell.run,remote.unapproved` | `remote.unapproved` |
| `sh -c 'git push origin wo-126'` | `remote.unapproved` | `remote.unapproved` |
| `sh <<< 'git push origin wo-126'` | refused ("Unclosed shell heredoc") | `remote.unapproved` |

The heredoc row is the subject's own rule: a program delivered to `bash` on
stdin is classified. The pipe rows deliver the same program to the same shell
and are not. `sh deploy.sh` and a bare `sh` were `shell.run` under `v0.16.0`
too and are not regressions; they are the same unreadable route.

**Consequence.** `remote.unapproved` is the effect the no-commits-before-final-review
rule depends on, and the Codex profile has no other layer. VER-002's repair
direction said "a quoted argument is one token and cannot match a two-token
sequence, so `grep -rn 'git push'` stays a read", and the repair follows that
direction faithfully; the direction did not distinguish a data program from an
interpreter, so the envelope is still below `v0.16.0` for every interpreter a
session can reach.

**Repair direction.** Treat interpreters as execution routes, not data: a shell
(`sh`, `bash`, `zsh`, `dash`) invoked without `-c` or a heredoc, and an inline
program for `node`, `deno`, `bun`, `perl`, `ruby`, `php`, `python*`, `awk`,
`osascript` and `expect`. For those, refuse with a classification reason when
any literal token of the invocation, or of an earlier stage of the same
pipeline, contains a denied sequence (`git` then `push`, `gh` `pr|release|repo`
`create|merge|edit|delete`, a package manager then `publish`, `ssh|scp|sftp`);
move `awk` out of `dataPrograms`. `echo`, `printf`, `grep`, `rg`, `cat` and
`sed` stay data, so search patterns and heredocs are unaffected. Add each row
above to the fixture.

### F18 — configuration-defined subcommands and push plumbing bypass the effect table (criterion 8, moderate)

**Observed.** `gitOperandIndex` reads a `-c` option, skips its value and
classifies the next operand, and `invocationProgram` strips leading
assignments, so an alias supplied through either route defines the subcommand
the classifier then reads as harmless:

| Command | Now | `v0.16.0` |
| --- | --- | --- |
| `git -c alias.p=push p origin wo-126` | `shell.run` | `shell.run` |
| `GIT_CONFIG_PARAMETERS="'alias.p=push'" git p origin wo-126` | `shell.run` | `shell.run` |
| `git send-pack origin refs/heads/wo-126` | `shell.run` | `shell.run` |
| `gh api -X POST repos/o/r/pulls -f title=x` | `shell.run` | `shell.run` |
| `gh pr comment 1 --body hi` / `gh pr review 1 --approve` / `gh issue create --title x` | `shell.run` | `shell.run` |

None is a regression: the `v0.16.0` regexes matched `git push` and four `gh`
verbs only. But the classifier's stated rule is that an invocation it cannot
read is refused, and here it reads the alias definition and discards it, which
is the F12 shape with the variable spelled as configuration. `send-pack` is the
plumbing behind `push`; the `gh` rows write to the remote through a route the
table does not name.

**Repair direction.** Refuse, with a classification reason, a `-c` or
`--config-env` value or a `GIT_CONFIG_*` assignment whose key starts with
`alias.`; classify `send-pack` with `push`; decide whether `gh api` with a
mutating method, `gh pr comment|review` and `gh issue create` are
`remote.unapproved`, and record the answer in the effect table either way.

### F19 — concurrent hooks on one session refuse spuriously as "host facts or pinned runtime unavailable" (criteria 4 and 8, moderate)

**Expected.** A refusal names its reason (VER-001 F3, VER-002 F11); a hook that
prevents irreversible damage stays hard at PreToolUse, which means its false
positives deny real tool calls.

**Observed live.** At 14:44:02.014Z, during a batch of parallel Read calls, one
PostToolUse `no-lint-type-disables-as-fixes` invocation journaled its
`hookTiming` row and no evaluation row, and Claude reported a PostToolUse hook
blocking error, `DOTLN_HARNESS_REFUSED: host facts or pinned runtime
unavailable`. Every other hook run in that window evaluated normally.

**Reproduced** with synthetic sessions and the installed hooks:

| Sample | Invocations | Refused |
| --- | --- | --- |
| feedback hook and `read-observer`, 3 concurrent pairs × 40 rounds | 240 | 0 |
| feedback hook and `read-observer`, 4 concurrent pairs × 200 rounds | 1,600 | 7 (4 feedback, 3 observer; 332–339 ms each) |
| feedback hook alone, 6 concurrent × 200 rounds | 1,200 | 0 |
| bare `readFileSync(0)` of a 4 KB payload, 8 concurrent × 200 | 1,600 | 0 |
| in-process `evaluateHarnessHook` in a tight loop beside 360 `read-observer` writers | 3,396 | 3 × `SyntaxError: Unexpected end of JSON input` |

**Cause.** `writeJson` is `writeFileSync`, truncate then write
(`harness-host.ts:228-233`), and `readJson` is `JSON.parse(readFileSync(...))`
(`:222-227`). Every hook reads the session state at the start of
`evaluateHarnessHook` (`:1799`); `read-observer` writes it after every observed
tool (`:1971`) and `write-observer` before every `Edit`, `Write`, `Bash` and
`NotebookEdit` (`:1946`). Claude runs the four PreToolUse hooks concurrently and
the two PostToolUse hooks concurrently for each tool call, and parallel tool
calls multiply the pairs. The state is 38,671 bytes for this session (34,934
for the synthetic one) because `beforeOutputs` carries a hash for each of the
297 changed paths, so the truncated window scales with the order's diff. The
throw lands in `runHarnessHook`'s catch-all, so the session sees the runtime
message.

**Consequence.** A PreToolUse race denies a real tool call; a PostToolUse race
blocks one; both with the message VER-001 F3 showed a session cannot tell from
a destroyed runtime. The rate here was one in about 340 live hook runs and 0.44
% under four-way concurrency. WO-126 added the PreToolUse writer and the
`beforeOutputs` growth, which is why this is judged here rather than
time-indexed to WO-039.

**Repair direction.** Write the state through a temporary file and `rename`,
as `saveSuiteSuccess` already does; re-read once on an empty or unparsable
read; and have the wrapper name the failing step ("session state unreadable")
instead of the catch-all. Fixture: N concurrent observer and feedback
invocations on one session must never refuse.

**Repair direction.** Accept a bare `\d+\.\d+\.\d+` command on the verified
