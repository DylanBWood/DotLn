## Findings

### F31 — supported message and search spellings outside the enumerated forms are refused (criterion 8, minor; D027's reopening condition)

**Expected.** Criterion 8: a heredoc or search pattern containing `push`,
`publish` or `.env` is not refused as that effect. D027 reopens when "a
supported message/search control is refused". `commitMessageInputs` in the
same module accepts `-[aqsv]*m` with a separate value, so `git commit -am
'…'` is a supported message form.

**Observed.** On both modules and the installed hook (the first two rows were
hook-probed), each of these classifies as a denied invocation although the
denied text is a message or a pattern: `git commit -am 'Refuse git push
inside hooks'` (also `-qm`, `-sm`; the attached form `-am'…'` and `-a -m '…'`
are admitted), `git tag -am 'git push' v1`, `git commit -F - <<'EOF'` with the
text in the heredoc, `git log --author='git push'`, `git log --format='%s git
push' -1`, `git grep -C2 'git push'` and `git grep --color 'git push'` (the
bare, `-n -F`, `-e … --` and `--` forms are admitted).

**Cause.** `floorOperands` recognizes `-m`, `-F`, `--message`, `--file` with a
separate value and `-[aqsv]*(m|F)<text>` inline, but not `-[aqsv]*m` followed
by a separate value; heredoc input to `git commit -F -` enters the floor as
program input; `--author=` and `--format=` are not listed as data; and grep's
implicit pattern inference stops at any option outside its flag list.

**Consequence.** A session gets a classification refusal on an ordinary
commit or search whose text names a denied effect, retries with another
spelling, and the meter counts a guard refusal. No denied route opens.

**Repair direction.** Share the message parser with `commitMessageInputs`;
treat stdin to `git commit|tag|notes … -F -` as message data; add `--author`
and `--committer` to log's data values; in grep, stop inference only on
options that take a value (`-C`, `-A`, `-B`, `--context`, `-O`,
`--open-files-in-pager`, `-f`, `-e`); add the spellings above as controls.

### F32 — two data programs execute a command-valued operand on other hosts (criterion 8, minor)

**Expected.** The `v0.16.0` regexes refused `sed '1e git push origin wo-126'
README.md` and `less '+!git push origin wo-126' README.md`; the floor should
not fall below them.

**Observed.** Both classify `shell.run` on both modules and the installed hook
allows both, because `sed` and `less` are `dataPrograms` and the floor is
skipped for them. On this host neither executes: `/usr/bin/sed` is BSD sed
and answers `invalid command code e`, no `gsed` is installed, and `less` with
its output on a pipe copies the file and ignores `+!`; the sandbox refused a
pseudo-terminal (`script: openpty: Operation not permitted`), so the
interactive `less` route could not be tried. GNU sed's `e` command and
`s///e` flag run their text through the shell on any Linux host.

**Repair direction.** Screen sed's script operands (the first non-option
argument and `-e`/`-f` values) and less's `+` operands with the literal floor
while keeping pattern-only forms admitted, or answer both in the effect table;
`sort --compress-program` needs nothing, since it executes a program name
without a shell.

**Expected.** Criterion 18: `npm run test:full` green. Criterion 6: suites run
concurrently under a CPU-derived bound with serialization groups. D012 moved
