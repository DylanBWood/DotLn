## Finding F1 — the remote T2 comparator arm was rejected by the probe's own schema, and the cause was discarded

**Criterion.** Acceptance criterion 2 (per task and model measurements), and the
order's Objective, which asks for the local result "compared with one remote
transport under the same order, build and prompt". The T2 floor
"within 10 points of the remote comparator's agreement under the same
conditions" depends on it.

**Expected.** Six remote T2 cells (five baseline repeats and the
`t2-triage-rubric` factor cell) return either a model envelope or a typed
failure attributable from the retained record.

**Observed.** All six are `{"code":"transport-failed","detail":""}` with
`usage: null`, `tokensPerSecond: null` and a median latency of 1,910 ms against
11,137 ms and 13,665 ms for the remote T1 and T3 arms. `results.json` reports
(T2, remote) as `schemaValid 0/5`, `oracleAgreement [0,0,0,0,0]`,
`typedFailures 5`, and consequently T2 `localMinusRemote: 0.828571` and
`withinTenPointsOfRemote: true`.

**Reproduction.** Calling the subject's own exported
`runCodexEpisode({model:"gpt-5.6-sol", prompt:<trivial>, schema: taskSchema("T2", inputs)})`
throws `{code:"transport-failed", message:"remote transport exit-1", detail:"", latencyMs:2905}`
— the same empty-detail record. Re-running the identical argv while retaining
stdout returns exit 1 in 2,059 ms with empty stderr and this on stdout:

```
{"type":"error","message":"{ \"type\": \"error\", \"error\": { \"type\": \"invalid_request_error\",
  \"code\": \"invalid_json_schema\", \"message\": \"Invalid schema for response_format
  'codex_output_schema': In context=('properties', 'result', 'properties', 'ranking'),
  'uniqueItems' is not permitted.\", \"param\": \"text.format.schema\" }, \"status\": 400 }"}
```

**Evidence.** `taskSchema("T2", inputs)` is the only one of the three schemas
that emits `uniqueItems: true` (on `result.ranking`), and T2 is the only remote
arm that failed — T1 and T3 both returned 5/5 valid envelopes at agreement 1.0
under the same CLI flags, model and build. Two defects compound:

1. `scripts/probes/local-model-role-qualification.mjs:1159` and the schema
   builder emit `uniqueItems`, which the remote structured-output endpoint
   refuses with HTTP 400 before any inference. The keyword is redundant:
   `validateAnswer` already rejects duplicates
   (`new Set(value.result.ranking).size !== value.result.ranking.length`), so
   removing it from the emitted schema loses no host guarantee.
2. On a non-zero exit the failure detail is `sanitizeDetail(run.stderr)` and the
   record then uses `error.detail ?? error.message`. `??` does not fall back on
   an empty string, so both the exit status carried by the message and the
   whole `--json` stdout stream — where this transport reports its errors — are
   discarded. That is why the cause was unrecoverable from the retained bytes.
   This is the same class of loss the executor already corrected for local
   invalid output in WO-138-D002.

**Severity.** Substantive; routes to repair. It is decision-consequential rather
than cosmetic: T2 is the only task this order qualifies, `qualifies: true`
requires all five floors, and one of those five was never exercised. The remote
model scored 1.0 on both other tasks, so a working T2 comparator could plausibly
land above `0.928571` and fail the ten-point floor, which would remove T2 from
the qualifying set and change the packet's outcome and the
`03-architecture.md` catalog role. The order's own D001 names this reopening
condition: "A recorded cell differs in prompt, schema, task input or build
between transports."

**Limits of this finding.** I did not run replacement T2 comparator episodes, so
the remote model's actual T2 agreement is unknown; I claim only that it was
never measured. The 400 response is observed, not inferred. Whether repair
requires recollecting the whole 38-cell matrix under one new build hash — the
constraint D003 and D005 imposed on themselves — is the executor's scoping call,
not a determination of this report. Nothing in this finding disturbs the local
T1, T2 and T3 measurements or the remote T1 and T3 measurements, which reproduce
exactly.

## Advisory observations

**A1 — the emitted T1 schema does not carry the 40-character bound the host
enforces.** `validateAnswer` requires each T1 field except `summary` to be a
string of at most 40 characters, but `taskSchema("T1", …)` declares only
`type: "string"` with `maxLength` on `summary` alone. The local model's five
rejections are recorded as `invalid T1 criteriaMet` for values such as
`"All six acceptance criteria of \`docs/work-orders/WO-052-source-change-host.md\` are met by the current subject."`.
This does not change the T1 verdict — the returned values are JSON-encoded
arrays and prose rather than the oracle's `"6"`, `"5"`, `"0"`, `"515.40"`, so
agreement would remain 0 at any length bound — but a subject can currently
satisfy the published contract and still be refused by the host, which makes
the schema-validity rate harder to interpret. Adding `maxLength: 40` to those
properties would make the contract self-describing.

**A2 — `results.json` records T2's comparator floor as met without a flag.** A
reader of the machine-readable result alone sees
`"withinTenPointsOfRemote": true` for T2 with no indication that the comparator
produced zero valid episodes. The prose in `decision-packet.md` does disclose
this ("The remote comparator is evidence, not a gold standard: all five T2
episodes were typed transport failures") and correctly rests T2 on its absolute
floor, and `03-architecture.md` claims no parity. The gap is between the two
surfaces, not inside the packet.

**A3 — the injected T1 cell adds little information.** `failure-local-T1-unexpected-input`
fails with `invalid T1 criteriaMet`, the identical failure mode as all five T1
baselines, so it does not distinguish blocking behavior from the baseline
defect. The packet's description ("a retained typed validation failure") is
accurate and claims no more than that.

**A4 — retained attempts are consistent with their stated exclusions.** The five
`attempts/` sets and the `postformat-stale-006` set carry no canonical status;
the canonical directory holds exactly the 38 registered episode ids, and
`evaluateRecords` refuses any other count. I confirmed `run-local.json` and
`run-codex.json` list `retainedEpisodes: []` and completed exactly their planned
cells.
