## Blocking finding (route to repair)

### F1 — Row B2 ★: a later statusless observation demotes a terminal task and restarts its elapsed time

- **Criterion:** row B2(b)'s required result, "corrected with a regression",
  for "a task whose completion notice arrived keeps state `dispatched` with
  growing elapsed". Also criterion 1, and D016's reopening conditions ("a
  native task form remains unobserved"; "retrospective journal ingestion
  changes a newer terminal fact").
- **Observed (source):**
  - `observeBackgroundTool` records `unknown` for a `TaskOutput` or `TaskStop`
    whose result has no status or is an error
    (`packages/skeleton/src/observed-facts.ts:133-146`).
  - Claude transcript reconstruction reads the `tool_result` text, not the
    structured result. So a `TaskOutput` text result, or a `TaskStop` error,
    parses to no status (`:535-563`).
  - `observedFacts` folds by `observedAt` alone, so the newer `unknown` row
    replaces the earlier terminal state (`:163-181`). `unknown` is not
    terminal, so elapsed is recomputed "since dispatch" against `now`
    (`:200-205`).
- **Reproduction, live (Claude Code 2.1.278):**
  - Task 2 was a 20 s timer that completed through its native notice at
    15:51:00.783Z.
  - At 16:04:55Z I called `TaskStop` on it, which returned "No task found with
    ID".
  - The next prompt's delivered facts, at 16:06:10.179Z, read: "task 2 …
    last observed state unknown; elapsed since dispatch 925318 ms".
  - A replay of the same journal and flushed transcript through the current
    build showed the same demotion at 16:04:55.411Z.
- **Reproduction, real transcripts:**
  - I replayed 213 local transcripts that contain native notices through
    `observationBoundary`. 38 terminal tasks end in a state other than their
    notice's:
    - 32 `completed` → `unknown` and 3 `failed` → `unknown`. Each has a later
      reconstructed `unknown` row.
    - 3 `killed` → `stopped`, from a later successful `TaskStop`. Both states
      are terminal, but the terminal time moves.
  - The later calls on those tasks were `TaskOutput` with a text result, 35
    times on CLIs 2.1.251–2.1.274, and `TaskStop` with a JSON result, 3 times
    on 2.1.274 and 2.1.277.
- **Expected:**
  - Once a task has a terminal observation, a later non-terminal, statusless or
    error observation does not replace its state or restart its elapsed time.
  - The first terminal time stands.
  - Regressions cover the three real shapes: a notice followed by a
    `TaskOutput` text result, a notice followed by a failed `TaskStop`, and
    `killed` followed by a successful `TaskStop`.
- **Severity:** blocking. The starred row's named symptom still occurs on the
  current CLI through a real native sequence, and on 35 real tasks under replay.
- **Limits:** `TaskOutput` is not offered by Claude Code 2.1.278, so the
  2.1.274 path was reproduced by replay only. On that CLI a live `PostToolUse`
  row may also carry a structured status, so the live outcome depends on which
  row is newer. That timing is unobserved.
- **Repair direction** (not prescribed): make a terminal state sticky in the
  fold. Keep the first terminal time. Replay the local transcript corpus as the
  class check, as the guard's parity corpus did for B3.
