## Instrument disclosure

The compiler and the skeleton reactor are simultaneously the deliverable and the
only in-repo instruments that can compute what they claim. Trusting
`compileLoadout` to certify its own `artifactIdentity`, or the executor's
`scripts/artifact-identity-evidence.mjs` to certify its own generated files,
would be circular. Compensating controls were used:

1. **A second oracle for every hash.** Every `definitionHash` and both
   `semanticHash` values were recomputed with `referenceStableHash` from
   `corpus/harness/id-corpus-lib.mjs` — WO-101's independent 32-bit-pair FNV-1a-64
   implementation that shares no code with the compiler's BigInt recurrence.
2. **A second canonicalizer.** I wrote my own canonical-JSON serializer in the
   probe rather than calling the compiler's `canonicalStringify`, so the
   preimage was reconstructed independently of the code that mints it.
3. **A real pre-change build.** Rather than reading
   `docs/evidence/WO-029/baseline.json`, I extracted commit `961601a` with
   `git archive`, built its compiler and skeleton with `tsc -b` in a scratch
   tree, and computed the pre-WO-029 hashes from that build.
4. **Probes, not the executor's helpers.** The reactor, audit and factory
   behavior was exercised by scripts I wrote against the built `dist/`, not by
   re-running `packages/skeleton/test/artifact-identity.test.ts`. The
   executor's suite was also run, but only as a second signal.

## Acceptance criteria

### 1 — Exact identities and manifest membership · met

Two compiles of each fixture, one of them from a deep clone of the source graph
and a fresh environment object, produced byte-equal `ArtifactIdentityV1` values
for both Seiri and Entropy Reducer. The identity's component keys equal the
compiled manifest's participating `(componentKind, componentId, version)` tuples
exactly — same members and same order — at 6 entries for Seiri and 9 for
Entropy Reducer. Reversing `supportFacets`, `activeMechanics` and `links` in the
source, and separately reversing the property-key order inside every support
facet, each left the entire identity byte-equal. A body edit that appended a
value to one facet's first emission, under an unchanged component id and
version, moved exactly one definition hash — that facet's own — and also moved
the whole-program hash, since that edit changes compiled semantics. The
derivation reads its definitions from `normalizeLoadoutGraph`, and
`compileLoadout` passes the already-normalized graph
(`packages/compiler/src/compile.ts:1024`), so the documented "normalized source,
not a source view" requirement holds at the only call site.

### 2 — Pinned domain, preimage, scheme, and an unchanged semantic hash · met

`COMPONENT_DEFINITION_DOMAIN` is `dotln:component-definition:v1` and
`COMPONENT_DEFINITION_HASH_SCHEME` is
`dotln-component-definition-fnv1a64-v1`; both are asserted in
`packages/compiler/test/artifact-identity.test.ts` and stated in
`docs/product/04-interfaces.md`. The pinned public vector was reproduced
end-to-end: feeding the exact 214-byte preimage string documented in 04 and in
the test — the `Quiet 雪` ambient definition — to WO-101's independent oracle
yields `3a5e415be9582bed`, matching the doc and the test. All 15 fixture
definition hashes and both fixture semantic hashes were likewise reproduced
through that oracle over my own canonical serialization. The compiler's own
`fnv1a64` also still matches the published RFC 9923 §8.3 anchors for `""`, `"a"`
and `"foobar"`.

The unchanged-preimage requirement was checked against the real base, not the
executor's baseline file. Building commit `961601a` produced
`fnv1a64:9ca8d0229c6bd8db` for Seiri and `fnv1a64:c5ddbca75f1c4cee` for Entropy
Reducer at `/fixture/repository`, base `fixture-base`, `episodeEndsAt` 11000 —
byte-identical to the values the changed compiler produces now. That base build
also confirms the shape change is purely additive: its `CompileResult` keys were
`diagnostics, ok, program, semanticHash` with no `artifactIdentity`, and it
exported no `deriveArtifactIdentity`. The receipt retains the reproduction
inputs (`compilationEnvironment` with `environmentId`, `version`,
`capabilities`, `repo`, `baseCommit`, plus `authorityExpiresAt`). Relocating
Seiri to `/relocated/repository` changed only the whole-program key
(`fnv1a64:9ca8d0229c6bd8db` → `fnv1a64:a20fffda0d4e31e6`) and left every
definition hash identical, and the `relocation` negative transcript records the
required explicit re-equip.

### 3 — v2 equip, atomic pin, no pre-equip authority · met

`initialState()` now returns `authority: null` with no pin and no equip
reference; the previous unconditional default-loadout authority is gone. A
program-consuming event before any equip emits `ArtifactIdentityUnavailable`
with no intents, no schedules and null authority. `createLoadoutEquippedPayload`
mints exactly `{payloadVersion, graph, artifactIdentity}` at version 2 and has no
branch that can produce a legacy shape. A valid v2 equip recompiles first, then
stores the pin, the equip event id and the compiled authority together. Payload
discrimination is exactly as documented: absence of `payloadVersion` is the only
legacy discriminator, while `1`, `3`, `"2"`, `null` and an extra unknown key each
produce `ArtifactIdentityInvalid` with null authority. A graph paired with a
stale pin — one facet's version bumped, pin retained — produced a canonical
`ArtifactIdentityDrift` with no intent, no schedule and no authority. The host
driver additionally throws on a caller-supplied legacy `LoadoutEquipped` draft
and on a caller-supplied enforcement boundary.

## Non-blocking observations

1. **The adjacency association branch is retained but no longer exercised by any
   fixture or test.** WO-029 correctly adds a stronger `explicit-event-link`
   association that prefers `CommandRefused.causationId`, and retargets the one
   test that previously asserted `derived-same-episode-time-adjacency`. Both the
   canonical scenario and the preserved legacy fixture now take the explicit-link
   path, and the new host append loop interleaves a `DecisionRecorded` between the
   attempt and the refusal, so `events[index - 1]` is no longer the attempt in any
   log this repository produces. I confirmed the branch still works when its
   precondition genuinely holds — a synthetic historical shape with the attempt
   immediately preceding an unlinked refusal still yields
   `derived-same-episode-time-adjacency` — and that stripping the link from a
   current-shape log falls through to `refusal-event-only`, which is correct. So
   the fallback is functional but uncovered. `refusal-event-only` and
   `explicit-event-link` both retain coverage. No acceptance criterion covers this
   label and 03 and 09 describe the new precedence honestly; the risk is only that
   a future refactor could break the historical path silently.
2. **`duplicate-boundary` is named in the evidence gate's transcript list but is
   not a row in `negative-transcripts.json`.** The property itself is proven by an
   executable test that asserts state equality after a replayed duplicate boundary
   and exactly one boundary event in the log, and I reproduced idempotence
   independently. This is evidence packaging, not a functional gap.
3. **The `compilation-environment` drift axis cannot fire at the equip boundary.**
   `equipDecision` compiles with the pin's own declared `compilationEnvironment`,
   so that field necessarily agrees at equip; the axis is reachable only for a
   stored pin that has been mutated after equip. This is consistent with the
   order's explicit "changing graph and pin together is outside the assurance
   claim" limit and with the docs, which say a writer who can replace graph and
   pin together passes this check. Noted so that no reader mistakes the axis for
   an equip-time environment guarantee.

## What this verification does not establish

It does not establish cryptographic integrity, collision resistance or
authenticity for any value in the receipt; FNV-1a-64 equality is a deterministic
content-equality key and the code, docs and audit projection all say so. It does
not establish protection against a writer who can replace both the graph and its
pin, nor the absence of hidden adapter effects, nor detection of a queued pulse
whose schedule id is reused from an earlier equip — all three are declared
non-goals and are recorded as standing limitations. It does not verify behavior
against a real out-of-process worker, which does not exist yet, and it does not
authorize WO-009 to start. It says nothing about merge, tag or release
publication, which remain separate operator-dispatched acts.
