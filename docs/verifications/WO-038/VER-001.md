## Observations (non-blocking, no repair required)

1. **The executable refusal is the lifecycle guard, not `private: true`.**
   `npm publish --dry-run --ignore-scripts` against a copy of the real kernel
   manifest returns exit 0 and prints `+ @dotln/kernel@0.2.1`; the guard is
   suppressed and nothing else refuses. `docs/LEGAL.md` states that
   "`private: true` remains npm's ordinary publication barrier, including when
   lifecycle scripts are explicitly suppressed." I could not execute that
   claim. An unauthenticated real `npm publish --ignore-scripts` against an
   unresolvable registry with empty configuration exits at `ENEEDAUTH` before
   any private check runs, so npm 10.8.0's ordering of its auth and private
   checks is untested here, and testing it further would require real
   credentials, which is out of bounds. This is not a defect against AC1, which
   scopes the requirement to `npm publish --dry-run`, and the sentence is
   defensible as documented npm behavior. A reviewer should simply read it as
   documentation rather than as evidence this order produced. The defense that
   *is* evidenced is: private metadata, an absent `publishConfig`, an exact
   lifecycle refusal, and a preflight that observes all three.

2. **The exemption is pinned to one of the operator's two public author
   identities.** `operatorAuthor` pins the identity on the license-decision
   commit. This repository's own `main` also carries commits authored by the
   operator's GitHub web-merge identity — a different name and email pair,
   visible on merge commits `ed2070a` and `01c2e32`. My fixture confirms a
   commit under that second identity is reported as
   `outside author without matching sign-off`. The practical consequence: a
   work-order branch that picks up a GitHub-created merge commit, for example
   through the "Update branch" button on an open PR, would be refused at
   `worktree publish` until that commit carried a matching trailer. The
   behavior fails closed, is disclosed in CONTRIBUTING.md ("a different author
   identity requires its own matching sign-off"), and cannot admit an unsigned
   outside commit. But the work order's operator-review assumption 1 — "the
   operator's own commits carry no sign-off requirement" — reads broader than
   what is implemented, and the operator should know which of their identities
   the exemption covers before they first meet the refusal.

3. **Sign-off matching is case-sensitive on the email.**
   `Signed-off-by: Out B <B@Example.Invalid>` against author
   `<b@example.invalid>` is refused. `git commit -s` always emits the exact
   author identity, so this only reaches a hand-typed trailer. It combines
   awkwardly with the deliberate omission of identities from the failure line
   (a privacy choice the code comments explain): a contributor who hits it sees
   `outside author without matching sign-off` with no hint that the mismatch is
   only letter case. A diagnosability nit, not a correctness defect, and the
   privacy trade-off behind it is a reasonable one.

4. **The feedback-audit recovery wrapper is an untested executable helper.**
   `docs/evidence/WO-038/feedback-audit-recovery.mjs` sits between a live model
   and evidence that `npm test` enforces. I read it and confirm its scope claim
   holds: it appends a formatting sentence to `outputInstructions`, and in
   `--summary-pointer` mode replaces exactly
   `schema.properties.envelope.properties.summary` with a single-value enum. It
   refuses any role other than `verifier`, never edits returned result bytes,
   and prints only booleans and a character count. Nothing else in the schema,
   the capsule, the process profile, or the host's admission checks is touched.
   It has no automated test, and the receipt's "offline launch comparison" is a
   manual check whose transcript is not in the evidence directory. The
   execution guide's rule that an ad hoc executable helper carries tests
   proportionate to its risks, and that "small script" is not an evidence
   exemption, applies to it. Related, and the reason reading the source
   mattered: the host's recorded `inputHash` is identical
   (`fnv1a64:eb312ec46e198b93`) across all four attempts, so the audit's own
   tamper-evidence does not cover the wrapper's prompt and schema adjustment.
   The committed wrapper source is the only attestation of what changed. The
   receipt says exactly this; I confirm the statement is accurate rather than
   merely disclosed. The right home for a test is the nominated helper the
   planning map already carries, not a repair inside this order.

5. **A real latent defect in shipped code was found and correctly deferred.**
   `packages/skeleton/src/verification-protocol.ts` requires `envelope.summary`
   to be a single line of at most 320 characters, but `evidenceResultSchema`
   requests `summary: { type: "string" }` with no bound, and the verifier's
   instructions omit the constraint that the executor inspection prompt in
   `worker-protocol.ts` states. A fully compliant model can therefore return a
   result the host rejects — which is what happened three times. I confirmed
   the mismatch by reading both files. It is outside WO-038's scope and was
   correctly not fixed here. Both required write-backs exist: a `candidate`
   entry in `docs/lineage/idea-ledger.md` and an unallocated candidate in
   `docs/planning/work-order-map.md`, each carrying the instruction to include
   the host's full return-format contract and bounded rejection diagnostics.

6. **Cosmetic, below the repair bar.** In `docs/README.md`'s map block, the new
   `CONTRIBUTING.md` line starts its description at column 19 while its
   neighbours use column 20. I did not correct it: `docs/README.md` feeds the
   publication source locks, so a one-character edit would restale
   `check-publication.mjs` and require regenerating both TOC locks for an
   invisible gain. Fold it into the next documentation pass.
