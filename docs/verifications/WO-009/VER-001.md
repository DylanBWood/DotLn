## Instrument disclosure

The worker host, its adapters and the shared reactor are simultaneously the
deliverable and the only in-repo instruments that can exercise them. Accepting
`packages/skeleton/test/worker.test.ts` as proof of `packages/skeleton/src/worker-*.ts`
would be circular, and the two most load-bearing claims — that the canonical
launch shapes are *real* host controls, and that an authenticated model actually
completed an episode — cannot be settled from inside the repository at all.
Compensating controls were used:

1. **A second vendor peer.** I wrote my own synthetic CLI, distinct from
   `packages/skeleton/fixtures/worker-cli.mjs`, that records the exact argv and
   the exact prompt bytes it receives, embeds its own private canary, and can
   emit five adversarial result shapes the executor's fixture does not produce.
2. **My own drivers.** Rows 2, 4 and 6, the worktree lifecycle, the status
   projection and the fail-closed model paths were driven by scripts I wrote
   against the built `dist/`, asserting on the argv and prompt actually delivered
   to a spawned child rather than on `canonicalWorkerArgs` in isolation.
3. **Out-of-band host probes.** Every flag, config key and feature name in both
   canonical launch shapes was checked against the installed `claude 2.1.261`
   and `codex-cli 0.153.4` directly, including negative controls that prove the
   hosts would have rejected an invented name.
4. **Internal-consistency cross-checks on the live receipt.** The one limb I
   cannot re-execute was cross-checked against values this build computes.

## Acceptance criteria

### 1 — One real episode replaces the fake executor; compact envelope · met

Driving `runWorkerDemo` with my own vendor peer through
`ClaudeCliPrintWorkOrderTransport` and `CodexCliExecWorkOrderTransport`, both
transports completed the demo with a real spawned child process. The returned
envelope's key set is exactly
`episodeId, requiresHuman, resultId, status, summary, workOrderId` — six fields,
nothing more — and `packages/skeleton/src/dotln.ts` writes only
`JSON.stringify(result.envelope)` to stdout, with every error path reduced to a

my peer emitted a `VERIFIER_SECRET_LEAK_CANARY` field alongside its structured
output on every successful run and in its stderr on every failing run, and the
canary appears nowhere in the canonical JSONL store in any of the fourteen

The stronger form of "replaces *only* the executor" was checked by comparing
projections rather than by reading the test's assertions. I ran the deterministic
fake `runScenario(fixture)` and the real-worker demo over the same fixture and
compared their `projectScenario` output field by field. `verified`, `candidates`
(identical path, classification and all three evidence strings), every
`workOrder` field, and the full projection key set are identical; the only
differences are `workOrder.repo` and `workOrder.baseCommit`, which are
necessarily environment-dependent because the real run uses a real detached Git

(`adapterEffects`, `adapterDispatches`, `recoveredCommands`). The canonical event

lifecycle events and their paired `DecisionRecorded` audit records interleaved.
Structural deletion refusal, the fake verifier and operator-return cancellation

The fake verifier is genuinely checking the worker, not rubber-stamping it. My

### 3 — Deterministic worktree lifecycle · met

Driving `WorkerWorktrees` myself against a real Git fixture repository: `create`
produces a detached worktree whose `rev-parse --show-toplevel` is its own path;
a second `create` with the same command id and base is idempotent and returns a
deep-equal record; a different base commit for an existing path is refused; a
`../escape` command id is refused; `verify` refuses a mismatched base. Cleanup is
the part worth adversarial attention, and it holds: I added a file matched by
`.gitignore` — not merely an untracked file — and `cleanup` refused with
"dirty worker worktree retained for inspection" and left the file in place. The
production path never passes `--force` and re-verifies before removing. After
removing my scratch file, `cleanup` removed the worktree and `existsSync`
confirmed it. Every successful demo run I performed left `worktrees/` empty and
recorded exactly one `WorkerWorktreeRemoved`.

### 4 — `dotln status` renders the live in-flight projection · met

During each of my real episodes I spawned `dotln status --store <dir> --json` as
a *separate OS process* from the `onRunning` callback. It reported exactly one
running episode and one pending command, with the launched model visible on the
episode record, and the store bytes were byte-identical immediately before and
after the observation. Directly against the built CLI: status on a non-existent
store prints an empty projection, exits 0 and creates no file or directory;
unknown and duplicate options are refused; `--beacons` is rejected for `status`;
and the `demo` subcommand refuses without `DOTLN_LIVE_WORKERS=1`. The projection
function takes only an event array — no clock, no filesystem, no transport — so
it cannot synthesize expiry, and `WorkerLeaseExpired` is appended only by the
host.

### 5 — No silent model substitution in either direction · met

Four cases (two transports × two model labels) each fail closed with
`model-unavailable`, exactly one launch, `--model` set to the exact requested
value, no `--fallback-model` anywhere in the argv actually delivered to the
child, one pending command retained, no `CommandResult`, and no vendor
diagnostic bytes in the store. I confirmed out of band that `--fallback-model`
is a *real* flag in `claude --help` at `2.1.261`, so its absence is a deliberate
omission rather than an unavailable capability. The second direction of
substitution — a store silently changing selection between runs — is enforced
separately by `runWorkerDemo`, which compares the persisted
`WorkerHostConfigured` payload against the requested selection and refuses with
"persisted worker selection differs; no silent model substitution"; I hit that
path when re-querying a Codex store with a Claude transport.

The honest limit, already stated in the executor's evidence, is that this proves
adapter behavior and not provider-side model identity. I confirmed the limit is
stated rather than glossed: `effectiveModel` and `effectiveEffort` are recorded
as `unknown` on every `WorkerAttemptStarted`, with `selectionSource:
"host-launch"`.

## Observations (non-blocking)

1. **The worker prompt discloses the absolute worktree path.** `workerPrompt`
   serializes the whole compiled `WorkOrder`, whose `repo` field is the absolute
   path of the mounted inventory — e.g.
   `…/<store>/worktrees/cmd_5ee0c6d8e207bd25/inventory.json`. With the runbook's
   documented `--store .runtime/claude`, that resolves under the operator's home
   directory, so the vendor model receives that path. It is not a secret, the
   work order's constraint is about secrets, and the CLI is already launched with
   that directory as its cwd — but no document says the prompt carries it, and
   09 §Privacy and minimization's collection-minimization posture would prefer it
   named. Recording it so a later reader does not discover it by surprise.
2. **A `--store` path that traverses a symlink is refused.** `WorkerStore` uses
   `resolve()` while `WorkerWorktrees` requires `realpathSync(dir) === resolve(dir)`.
   On macOS a store under `$TMPDIR` (a symlink into `/private/var/folders`)
   therefore refuses with the generic sanitized host message. This is fail-closed
   and the documented `.runtime/` path is unaffected; my own first probe run hit
   it, which is how I noticed. A more specific refusal string would save an
   operator a debugging round.
3. **The Claude launch writes a schema file it never references.** `dispatch`
   always writes `result.json` into a private temp directory, but the Claude
   argv passes the schema inline via `--json-schema`; only Codex uses
   `--output-schema <path>`. The file is 0600 and removed in a `finally`, so this
   is a harmless redundant write, not a leak.
4. **AC5's "either direction" is carried by the launch assertions, not by the
   model names.** The test loops over `required-higher-model` and
   `required-lower-model`, but the synthetic peer ignores the name; the actual
   proof is one launch with the exact `--model` and no fallback flag. The
   executor's evidence already states this limit plainly, so this is a note on
   how to read the test, not a gap.
5. **Both version pins are exact equality.** A routine `claude` or `codex`
   upgrade will make the corresponding real transport refuse with
   `profile-refused` until the profile is re-probed. This is deliberate, tested,
   and documented in the runbook and discovery addendum; it is recorded here only
   because it is the most likely source of a future "it stopped working" report.

## What this verification does not establish

It does not establish that any effective model or effort was used — every such
field is recorded as `unknown` by design, and accepted launch flags are launch
claims, not readback. It does not establish provider-side model identity, so
"no silent substitution" is proven of the adapters and the store, not of the
vendor. It does not establish that the CLI broker process is confined; the
profile constrains model perception and tools, and the child still inherits the
parent environment so the CLI can resolve its own authentication — a hostile
same-user broker is explicitly outside this boundary and the docs say so. It is
not an exactly-once protocol for arbitrary external writes; it is an idempotent
read-only inspection protocol, and the crash window may safely repeat inspection.
It says nothing about general mounts or Senses (WO-022), real verifier episodes
(WO-010), a durable background scheduler, or performance — efficiency and
operator usefulness remain unknown, and process counts and envelope sizes are not
a comparative baseline. It does not authorize merge, tag or release publication,
which remain separate operator-dispatched acts.
