## The blocking finding

### B1 — Both authorized push paths can publish unrelated local tags to origin

`scripts/release.mjs:359` and `scripts/worktree.mjs:70` invoke `git push` without
`--no-follow-tags`. Git's `push.followTags` configuration (and the `--follow-tags` flag) makes any
push additionally publish annotated tags in `refs/tags` that are missing from the remote and
reachable from the refs being pushed. Neither call opts out.

**Reproduced twice, in isolated fixtures, on git 2.55.0:**

```text
# release.mjs shape: push ONLY the minted tag object, push.followTags=true
$ git push origin ea3cbe8...:refs/tags/v0.2.1
 * [new tag]  ea3cbe8... -> v0.2.1
 * [new tag]  v9.9.9 -> v9.9.9          <-- never authorized
REMOTE TAGS NOW: [v0.2.1 v9.9.9]

# worktree.mjs publish shape: push the WO branch, push.followTags=true
$ git push -u origin wo-099
 * [new branch]  wo-099 -> wo-099
 * [new tag]     v7.7.7 -> v7.7.7       <-- never authorized
```

**What it violates, literally:**

- Acceptance evidence: "creates one annotated tag only under the explicit publish form, **pushes
  only that tag**".
- `07-execution-guide.md` §Workflow closeout: "creates and pushes **only** their annotated tag."
- `docs/releases/README.md`: "explicit authority to create and push **only** the validated
  annotated tag."
- §Additional authority and constraints, which withholds tag creation/pushing from every path
  except the explicit publish form — `worktree publish` is the `resume: final review` authority,
  described in three documents as pushing *only the WO branch*, and it leaks tags too.

**Downstream consequence, not just tidiness.** `latestVersion()` derives the release baseline from
**remote** tags. A leaked local-only tag above the roadmap version becomes origin's latest, after
which every future `release close` takes the `compareVersions(...) < 0` branch and prints "no release
tag is due" permanently. No DotLn command deletes a remote tag, so the workflow cannot repair itself.
The repository is public.

**Honest counterweight, stated plainly.** `push.followTags` is not a git default, and I confirmed
read-only that it is unset in this operator's local, global and system config, with no local-only
tags present today. The tool would behave correctly if run right now. I still treat this as blocking,
because three distinct defect classes from `07-execution-guide.md` §Discipline stack on one clause:
an unsafe external effect, a guard that does not guard, and an acceptance bullet asserted as proven
with no assertion behind it (F1). WO-004 exists specifically to make external effects bounded and
provable. "We were still building the process" does not reach a behavioural defect.

**Repair is small and bounded:** add `--no-follow-tags` to both pushes, and add remote-ref
enumeration assertions to `test-release.sh` and `test-worktree.sh`. I verified in fixture that
`--no-follow-tags` suppresses the leak.

## Non-blocking findings

**F1 — "pushes only that tag" is asserted nowhere.** `test-release.sh:229` checks the tag exists, is
annotated, and points at HEAD, and that `refs/heads/main` on origin is unchanged. Neither suite ever
enumerates the remote's refs, so no assertion could observe B1. Acceptance evidence names this clause
explicitly.

**F2 — Acceptance bullet 9 has zero durable evidence and defines no artifact.** The required
pre-`implementation-ready` local hardening review (executable evidence, adversarial and mutation
probes, senior/staff/principal reviews, findings repaired, focused and full suites rerun) appears
exactly once in the repository — in the requirement itself. There is no receipt in the work order,
the control log, the checkpoint refs, or any doc. `CLAUDE.md` §2 says work recorded only in a chat
effectively did not happen. The bullet is unverifiable *as written*, which is itself the defect: it
should name where the receipt lives.

**F3 — The documented release-close command cannot run for WO-004's own closeout.** The guide and
playbook say to run `npm run release -- close WO-NNN --publish` "from the main checkout", and
`resume.mjs:204` prints exactly that. But `origin/main` (and the main checkout, both at `e33a0d5`)
contains neither `scripts/release.mjs` nor a `release` npm script — WO-004 adds them. Updating main
is what the command does, so the first invocation is a chicken-and-egg failure
(`npm error Missing script: "release"`). `test-release.sh:218-220` names this bootstrap path in a
comment and works around it by invoking the subject worktree's copy; no doc does. This is precisely
the "gap between the documented lifecycle and the workflow a fresh executor can actually run" the
addendum was written to close. Failure is safe and recoverable, so it does not block.

**F4 — The PR-publication command was deleted and exists in no durable doc.** At `HEAD`,
`docs/PLAYBOOK.md:86` carried
`npm run worktree -- publish WO-NNN --title ... --body-file ...`. The rewrite removed it, and no
guide, playbook or README now names it. `resume: final review` is granted authority to "push only its
work-order branch and open the mergeable PR" with no documented mechanism to do so — and the `gh`
preflight added by acceptance bullet 4 is therefore unreachable from the documented flow.

**F5 — The instrument silently failed on this work order's own `implementation-ready`, and the
projection then advertised a destructive recovery command.** The event
`{"type":"ImplementationReady","workOrderId":"WO-004"}` in `docs/control/resume.jsonl` carries no
`checkpointSha`/`checkpointRef`: `checkpoint()` warned to stderr and proceeded. `fold()` then carries
the *previous* checkpoint forward, so the control state I was handed at dispatch read:

```text
- Latest checkpoint: 652327588... (restore: `git checkout refs/dotln/checkpoint/WO-004/1 -- .`)
```

`WO-004/1` is the **activate** checkpoint — the base state. Following that advertised recovery
command would have reverted 19 files and ~1,494 lines, destroying the discovery addendum, the
lifecycle code, and the control log. I witnessed this first-hand in my first read of
`docs/control/current.md`. Recorded but **not blocking against WO-004**: `checkpoint()` and `fold()`
are WO-003 code, unmodified by this change set (the `resume.mjs` diff touches only `legalActions`,
`commandFor`, `requirePhase`, `next`, `release-close`, and the top-level try/catch). It should become
a bounded repair or a follow-on work order — a recovery pointer that is stale is worse than none.

**F6 — Two checkpoint refs were minted outside repository tooling and disclosed nowhere.**
`refs/dotln/checkpoint/WO-004/2` ("discovery-slice WO-004") and `/3` ("implementation-ready WO-004
recovery") are referenced by no control event, and their subjects do not match the
`dotln checkpoint: ${action} ${workOrderId}` format any code path emits. They were hand-made. Making
recovery points was the right instinct — but the work order's mandated proof that "the original
discovery deliverable ... must be checkpointed separately before lifecycle code so verification can
read its diff independently" rests entirely on `/2`, an unauthenticated hand-minted ref. The
separation itself checks out (see Confirmed below); its provenance does not.

**F7 — Cadence derivation is regex-fragile and the validator re-derives it identically.**
`release.mjs:150-155` extracts the cadence union and the `evaluateCadence` switch cases with
non-greedy regexes over source text. I confirmed the derivation is **correct today** (evaluable
`Once, After, Every, Gate, Until, Backoff`; deferred `Burst, Calendar, Window, While, Sequence, Merge,
Race, Repeat`), matching the corrected `v0.2.0` statement exactly. But `validateManifest` re-derives
via the same function, so it catches a mutated *manifest* while being blind to a mis-*derivation* —
which is the failure that actually occurred at the v0.2.0 closeout, and the reason the bullet exists.
A cosmetic reformat of `core.ts` changes the answer or throws.

**F8 — `environment.json` over-claims where `environment.md` is more careful.** Two concrete
disagreements between the two deliverables:

- The JSON collapses three MCP surfaces into one `observed` row —
  `{"classification":"observed","commands":["mcp","--mcp-config","--strict-mcp-config"]}` — while the
  md honestly labels `--mcp-config` and `--strict-mcp-config` **documented locally**. Only
  `claude mcp list` was run.
- The md's Codex row "Ignored user configuration | observed | `--ignore-user-config` was accepted"
  has **no counterpart row** in the JSON (`grep` count 0), yet the restated v0.4.0 recommendation
  cites "ignored user config" as part of its observed basis. Checklist item 6 requires "a counterpart

**F9 — `docs/product/10-ir-compatibility.md` was edited outside the enumerated authority.** §Additional
authority and constraints lists the surfaces this addendum may change; `10-ir-compatibility.md` is not
among them. The six added lines are accurate and germane to the tag-message projection, so this is a
scope-record defect rather than a content defect — it should be named in the authority list.

**F10 — The playbook understates the non-publish form's external effects.** `docs/PLAYBOOK.md:232`
labels `npm run release -- close WO-NNN` "validate only; creates no tag". True about the tag, but the
non-publish path still runs `updateMainAndFinish` — removing the subject worktree, deleting the merged
branch, fast-forwarding main — and the full `npm ci` + evidence gate. Acceptance bullet 2 requires the
release-close phrase to state its external-effect authority explicitly. `docs/releases/README.md:19`
has the same gap.

**F11 — The local-only conflicting-tag guard has no test; removing it pushes a tag.** My mutation
probe: deleting
`if (local.has(authority.version) || remote.has(authority.version)) throw` at `release.mjs:391` leaves
`test-release.sh` **green**, and the resulting run **pushes the tag to origin** and then fails on
`update-ref` ("reference already exists"), leaving remote and local tags on different commits. The
guard is correct and load-bearing; the coverage is missing. The suite's conflicting-tag scenario
(line 183) exercises the *remote* conflict, which is refused earlier by `ensureExistingRelease`.

**F12 — The defer-recording duty was deleted with no replacement.** Both
`07-execution-guide.md` and `06-roadmap.md` lost "a deliberately deferred release records its reason
rather than leaving the milestone's publication state ambiguous." The rewrite covers the automatic
no-release case and the failed-evidence case, but an intentional operator defer now has no recording
obligation anywhere, and no ledger entry records the removal.
