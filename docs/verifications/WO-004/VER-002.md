## Closure of the VER-001 blocking finding

**B1 — both authorized pushes could publish unrelated local tags — is closed.** Verified four ways,
each first-hand:

1. **The leak still reproduces without the flag.** In fresh fixtures on git 2.55.0 with
   `push.followTags=true` and a reachable unrelated annotated tag, the pre-repair shapes publish it:
   `git push -u origin main` → `* [new tag] v9.9.9 -> v9.9.9`.
2. **The repaired shapes suppress it.** `git push --no-follow-tags -u origin main` and
   `git push --no-follow-tags origin <mktag-object>:refs/tags/v0.2.1` leave the remote holding
   exactly the authorized ref.
3. **Mutation-proof that the new assertions are load-bearing.** Removing only `--no-follow-tags`
   from a *copy* of each script and running the corresponding copied suite:
   `m_release_tags/test-release.sh` **exit 1**, `m_worktree_tags/test-worktree.sh` **exit 1**.
   Both suites now set `push.followTags=true` and mint a reachable unrelated annotated tag
   (`v9.9.9` / `v7.7.7`) *before* the authorized push, so their green result is a suppression proof
   rather than an absence of stimulus.
4. **Attack matrix.** The explicit refspec plus the command-line flag beats configuration:
   `remote.origin.push=refs/tags/*:refs/tags/*`, `push.default=matching`, and
   `push.followTags=true` at repo, global and `GIT_CONFIG_*`-injection scope all leave the remote
   with exactly the one authorized ref. `remote.origin.mirror=true` refuses
   (`--mirror can't be combined with refspecs`) rather than leaking.

Exactly two remote-writing git commands exist in the whole repository — `worktree.mjs:72` and
`release.mjs:359` — and both carry `--no-follow-tags` and a single explicit refspec. There is no
`--force`, no `--tags`, no `npm publish`, no `.github/` workflow.

## Non-blocking findings

**G1 — the `release-close` resume projection still prints the command VER-001 proved cannot run.**

**G2 — the printed publish handoff is not shell-safe for a real title.** `resume.mjs:197` prints

`test-resume.sh:75` pins the unquoted string, so the shape is test-locked. Outward-facing (a wrong PR

placeholder in the printed message and in the assertion.

## Observations (no action required to pass)

- **O-a — VER-001 F5's root cause is still live, and it fired again during this work order.**
  `docs/control/resume.jsonl:15` (`RepairRequested`, the `fix` transition) carries no
  `checkpointSha`/`checkpointRef`, and no `fix` checkpoint ref exists. The contract clause is
  satisfied — the projection now says "unavailable for the latest transition; do not use an older
  checkpoint" instead of advertising a stale destructive restore — but the underlying failure was
  not addressed. The mechanism is now identified: this is a **linked worktree**, so its object store
  is `/Users/dylanwood/Projects/DotLn/.git/objects`, *outside* the worktree directory. An executor
  sandboxed to the worktree cannot write there, and `checkpoint()`'s `git add -A` fails. Reproduced
  in a fixture by making a main repo's object database read-only and running `resume` from its linked
  worktree: `error: insufficient permission for adding an object to repository database … fatal:
  adding files failed; proceeding without one`, followed by exactly the projection the repair added.
  This matches which WO-004 transitions lack checkpoints — `implementation-ready` and `fix`, the two
  run by the in-worktree executor — while `activate` (run from main by `worktree start`), `verify`,
  `verification-result` and `repair-complete` all carry refs. Ruled out by fixture: action-specific
  failure (all six transitions mint refs in a clean fixture), identical-tree `commit-tree`, unborn
  HEAD, ref-number collision, and linked-worktree-ness by itself. Residual: a failed checkpoint still
  exits 0 with only a stderr warning, so the two most repair-critical transitions may still get no
  recovery point. The work order explicitly defers "checkpoint retention/recovery" as a follow-on
  candidate, so this is recorded, not charged.
- **O-b — `fold` never reads the field the repair persists.** `checkpoint()` now returns
  `{checkpointUnavailable: true}` on failure and the marker lands in the event (asserted at
  `test-checkpoint.sh:89`), but `fold` re-infers unavailability from *absence* of both checkpoint

## Method

Twelve independent examiners across two fan-outs — push authority, checkpoint fold and root cause,
release/publish lifecycle, evidence integrity, version retiming, README claims, doc↔code parity, and
the checklist/acceptance ledger — each required to work from executable fixtures under a scratchpad
directory and forbidden to write to the repository. Every finding they returned was then re-verified
first-hand by me before being written down: I independently reproduced the B1 leak and its
suppression, ran five mutation probes against copied suites, re-derived the control projection with
my own fold, executed the untested ordinary handoff arm, reproduced the `G2` title truncation through
a logging `gh` shim, reproduced the `G4` refusal-path tag fetch, and enumerated the `G6` encoding
split key by key. Candidate findings I could not reproduce, or that turned out to be unreachable
defence (`O-c`) or adequate representation in another shape (the settings-source rows, whose content
is fully present in `environment.json` as `present`/`notFound`/`debugReferences` membership), were
discarded or downgraded rather than reported. HARDENING-001 was read to know what was claimed; no
claim in it was accepted as evidence.
