## Findings

**F1 — follow-up; test-coverage; the export case's carried-schema assertion cannot fail.** In the WO-225 case of `scripts/test-launchpad-export.mjs`, the carried `dist/test` cases run as a nested `node --test` child. The fixture's `env` (`scripts/lib/launchpad-fixture.mjs`) copies `process.env` and keeps `NODE_TEST_CONTEXT`, and the launchpad suite runs this file under `node --test`. The nested runner therefore prints `run() is being called recursively within a test file. skipping running files.` and exits 0. My probe reproduced this through the fixture's own `run` and `env`: exit 0 with both schemas present, and exit 0 with either schema moved aside. With the variable removed, the same carried run passes 2 of 2 and exits 1 when either schema is moved aside. The criterion's behaviour holds; the gate's evidence for it was vacuous. Repair rule: the nested child runs without `NODE_TEST_CONTEXT`, asserts that the named carried cases ran and passed, and is paired with a schema-removal control that fails. Recorded in [D021](../../evidence/WO-225/decisions.md#wo-225-d021), `FUP-268c774fd159addb`.

**F2 — follow-up; correctness (diagnostic label); a killed child is reported as `invalid format`.** `readFailureReason` (`packages/console/src/values.ts`) checks `status` before its code lists, so a child with `status` null and a signal falls through to the default `invalid format`. Through the compiled function, exceeding `maxBuffer` gave `ENOBUFS` with signal `SIGTERM`, and a self-sent `SIGKILL` gave status null; both returned `invalid format`. Exit 3 gave `command failed (exit 3)`, and a timeout gave `timed out`. The reason stays coded and path-free, so criterion 1 holds; the label misdirects an operator. Repair rule: a signal or output-limit end receives a command-failure code, every reason stays path-free, and the README's code list and the coded-reason test include the new code. Recorded in [D022](../../evidence/WO-225/decisions.md#wo-225-d022), `FUP-ce1f662a6b966a2a`.
