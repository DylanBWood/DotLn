## Findings

### F1 — the adapter forwards effort values the row never observed (blocking, medium)

- **Criterion:** the order's design sentence "The adapter forwards the flag only for levels the row observed accepted". Also its objective ("accepts `--effort` values from the declared set, forwards the override exactly as observed"), the refusal clause of criterion 2 and WO-125-D001.
- **Observed:** `packages/skeleton/src/worker-transport.ts:223` refuses only when `request.effort !== "unknown" && harnessVersion !== "0.154.0"`. Lines 261–263 then interpolate any other string into `-c model_reasoning_effort="<effort>"`. No runtime check restricts `effort`: `validateTransportRequest` delegates to `validateRequest` or `validatePlanRequest`. Both restrict the model to the characters `[a-zA-Z0-9._:-]` within 100 characters and check profile fields, but neither checks the effort. `WorkerEffort` is a compile-time union only.
- **Reproduction:** each value was dispatched through `new CodexCliExecWorkOrderTransport(runner, "0.154.0")`, with a runner that captures the launch and stops. The values `minimal`, `none`, `MAX` and `max"` + newline + `sandbox_mode="danger-full-access` all reached the runner as `model_reasoning_effort="<value>"`. HEAD's adapter refused all four with `profile-refused`.
- **Expected:** refusal before launch for any effort outside the levels the row observed accepted on `0.154.0` (`low`, `medium`, `high`, `xhigh`, `max`), with the record named, as HEAD refused every non-`unknown` value.
- **Impact and limits:** the shipped entries check membership first (`scripts/refute-plan.mjs:262`, `packages/skeleton/src/dotln.ts:71` and `:139`), so none of them reaches this path today. The exported transport and builder are also consumed by untyped `.mjs` scripts, where the union offers no protection. A forwarded value would additionally be recorded as a `host-launch` effort claim. I did not test whether Codex `0.154.0` applies a second key embedded in one override, because there was no live run. This finding rests on the order's design constraint and on the regression from HEAD's fail-closed boundary, not on a demonstrated exploit.
- **Bounded repair:** in the Codex branch, refuse a non-`unknown` effort unless it is one of the five levels observed on the admitted version, and name the record. Add a negative test showing that an out-of-set value on `0.154.0` refuses before any process launch. Surfaces: `packages/skeleton/src/worker-transport.ts`, `packages/skeleton/test/worker.test.ts`.

### F2 — an omitted version admits explicit effort (non-blocking, low)

`canonicalWorkerArgs(name, request, schemaPath, harnessVersion = "0.154.0")` assumes the observed version when a caller omits it. Reproduced: an omitted version with `max` returns `model_reasoning_effort="max"`. `CliWorkOrderTransport.dispatch` always passes its parsed version. The only direct Codex caller that omits it, `scripts/probe-codex-effort.mjs:87`, requests `unknown`. I recommend making the parameter required, or defaulting it to a non-admitting value, in the same repair. A pass does not require it.

### F3 — I changed gate inputs while the full gate was running (blocking, operator-directed)

- **What happened:** I started `npm run harness -- evidence` in the background, then wrote this report and edited it while the gate's suites were running. Nothing in the verification required writing before the gate finished. After 651.64 s, the runner compared each suite's inputs with its starting snapshot. It marked every row whose inputs had changed as failed, with the output "Suite inputs changed during the gate" (`scripts/test-runner.mjs:603–608`), and reported `14 passed; 23 failed; … tree changed`. `runHarnessEvidence` then stopped with "Source changed during required checks" before recording the gate and diff-check results (`packages/skeleton/src/harness-host.ts:1401–1403`). Apart from `console` (O6), every suite had passed while running. The run's time was wasted and its aggregate result is unusable.
- **Gap:** nothing stopped the write. The role's write hook admitted a worktree write while a gate run was active, and the runner detects the change only after every suite has finished.

## Goal alignment

WO-125 removes a transport prerequisite for a Codex refuter or worker at `max` in the independent-verification loop on the critical path. Its premise, stated in the order's design and in Principle 15, is that selection follows observation. The verdict protects that premise at the boundary later callers will reuse, such as the writing-worker harness and a third transport.

- **NoOp (pass as filed):** no shipped command reaches F1 today. The fail-open boundary would ship in `v0.17.2`, and D001's "only the observed version/level pairs" would describe behavior the code does not have. This would reopen if the operator decides that membership checks at the command layer are the intended sole guard.
- **Naive Interventionism:** the F1 repair is one guard and its tests, in files the order already names. Valid inputs are unaffected, and the change is locally reversible. The smallest useful probe is the negative test. F3's guard touches the shared gate and hooks, so it needs its own fixture showing that a marker from a dead run cannot block writes.
- **System traps:**
  - Rule beating applies to F1. The current tests pass without the "only observed levels" behavior; F1 closes that gap.
  - Drift to low performance applies to F1. HEAD's adapter was fail-closed, and accepting a type-only guard would normalize a weaker baseline.
  - Shifting the burden applies to both. Without F1's guard, every future caller must validate for itself; without F3's, the operator has to catch mid-run writes.
  - Tragedy of the commons applies to F3: my mid-run write wasted a full gate run of shared compute and operator attention.
  - Escalation is bounded: one repair cycle covers F1 and F3, with no new review step.
  - Policy resistance is immaterial, because the command-layer and adapter checks agree.
  - Success to the successful and seeking the wrong goal are immaterial. The findings target the stated behavior, not a proxy.
