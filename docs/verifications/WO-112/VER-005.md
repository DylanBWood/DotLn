### F1 — Medium, blocking: model intake treats host-side failures as transient, so the resident never holds the draft

**Class and scope:** an operator-flow and cost defect in the run-time intake
episode that D012 added. It is in `scripts/lib/vertical-runtime.mjs`, a declared
surface. It is the defect class VER-004 F1 routed for triage, left on intake.

**Observed:** `modelIntake` wraps every `recordedJudgment` error as
`IntentPreparationRefusal(…, judgmentRetryable(error))`. `judgmentRetryable` is
true for everything except `invalid-result` and `profile-refused`, so host-side
failures become named transient refusals. `vertical-resident.ts` defers a named
transient refusal with no attempt cap.

**Reproduction (I1, I2):** 40 resident ticks, one second apart, with the default
backoff (1 s base, 300 s cap, three unnamed attempts):

| Mode | Preparations | Intake episodes | `IntentHeld` |
| --- | --- | --- | --- |
| Live-worker opt-in missing | 6 | 0 | 0 |
| Record directory unwritable | 6 | 6 | 0 |
| Unnamed host error (contrast) | 3 | 0 | 1 (NeedsHuman) |

In the first two modes the first refusal is named and transient. Separately
(I2), an intake record rewritten to `schemaVersion: 2` is refused at the next
preparation as a named transient refusal.

**Expected and repair rule:** only an intake episode's launch and return may
make a model-intake preparation transient, as D041 now requires for triage. A
missing live-worker opt-in, an unreadable or unbinding record and a record that
cannot be written end as a held decision with their reason, or as a bounded
unnamed attempt. None is an unbounded named transient refusal. A record that
cannot be written never launches a further episode. Keep I1 and I2, with the
unnamed contrast, as regressions.

**Severity and limits:** Medium. In the resident, a configuration or disk fault
stalls the draft silently and indefinitely. When the record cannot be written,
the resident spends a model episode on every retry, up to one per 300 s.

The one-shot command reports the reason on each invocation, so that path is not
routed. The historical live runs hit neither path, so their scores stand.

### F2 — Medium-Low, blocking: a deferred continuation leaves the resident re-preparing drafts it cannot admit

**Class and scope:** a commons-cost defect introduced by D041's deferral, in
`vertical-resident.ts`, the repair's own surface.

**Observed:** a deferred continuation keeps the intent slot (`intentStep`
stays set). With the slot set, the tick skips `machine.due` and reaches the
draft loop. There it calls `ports.prepare` for any filed draft, and the
admission transaction then refuses because the slot is busy.

**Reproduction (D1):** from the first interrupted triage on, the resident also
lists a second draft. Across the 1, 2 and 4 s deferrals, at one tick per second,
the second draft was prepared on all 4 non-retry ticks and never admitted or
held. The first run still resolved.

**Expected and repair rule:** while a deferred continuation holds the intent
slot, a tick prepares no draft it cannot admit. Keep D1 as a regression that
counts preparations during deferral.

**Severity and limits:** Medium-Low. At the default 1 s tick, a long model
outage with a second filed draft causes about one forge-backed preparation per
second for the whole outage. That rate is an inference from D1 and the default
cadence; the real forge was not exercised.

Before this repair the resident exited instead. From source, I found no other
state that leaves the slot held without a runnable continuation; that reading
is an inference, not a probe.

### F3 — Low, blocking: checkout recovery prunes every stale registration in the operator's target

**Class and scope:** an authority defect in `withDetachedCheckout`, in
`scripts/lib/vertical-primitives.mjs`, a declared surface. The comment says
"Prune only when this checkout's own registration outlived its directory". The
code then runs `git worktree prune`, which acts on every stale registration.

**Reproduction (P1):**

1. A target repository has an unrelated worktree on branch `side`, with staged
   work.
2. That worktree's directory is moved without `git worktree move`.
3. The run's own `input-tree` registration outlived its directory.
4. Recovery then removes both registrations.

Afterwards, `git status` in the moved worktree fails and its staged state is
gone. Its files remain.

**Expected and repair rule:** recovery removes only this checkout's own
registration. An unrelated registration, stale or valid, is untouched. Keep P1
as a regression.

**Severity and limits:** Low. It needs a crash-left own registration and an
unrelated stale worktree. The effect deletes operator Git metadata outside the
run's own state. The executor's regression keeps the unrelated directory
present, so it does not cover this case.
