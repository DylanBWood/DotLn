### F1 — Medium, blocking: a retryable triage failure ends the resident's run loop

**Class and scope:** a liveness and operator-flow regression introduced by the
D036 repair. It is in this order's declared surfaces:

- `vertical-host.ts` now rethrows `RetryableTriageError` from the resolution
  step;
- `review-comment-loop.mjs` raises it.

**Observed:** `VerticalHost` keeps the resolution command pending and rethrows.
Its resident caller, `vertical-resident.ts`, swallows only a live-host
collision and rethrows everything else. `ResidentHost.run` awaits `tick()`
with no catch. So `dotln resident` exits.

Intake's identical failure takes a different path. It is wrapped as a transient
`IntentPreparationRefusal`, which the resident defers with its capped backoff
of 1 s to 300 s.

**Reproduction:** probe R1 drives `ResidentHost.run({cycles: 60})` with a
declared judgment double that is interrupted once. The loop throws
`RetryableTriageError` on tick 19. The run is non-terminal with `resolution`
pending, and the double was called once. Probe R2 applies the same interrupted
failure to model intake: the resident keeps running for all 60 cycles.

The executor's regression "resident resolution preserves retryable triage
scheduling through restart" shows the same thing: it catches the error from
`tick()` and builds a new host to continue.

**Second part, inferred from source:** in `vertical-primitives.mjs`, `triage`
runs `resolutionInput` inside the classified `try`. That function calls
`withDetachedCheckout`, which can raise the "checkout directory identity
drift" safety refusal, and runs the detached `worktree add`.
`judgmentRetryable` treats every error except `invalid-result` and
`profile-refused` as retryable. So a deterministic host-side refusal stays
pending and repeats on every restart, where it used to be a typed stop.

The classification of an untyped error is executed here: B1's cap error
surfaced as `RetryableTriageError`. The executor's untyped-triage tests show
it too. Reaching the identity-drift path itself was not executed.

**Expected and repair rule:** the responsible host retries a retryable triage
failure without operator rescue. In the resident, the continuation is deferred
with the backoff intake already uses, and `ResidentHost.run` never ends because
of it. Only the triage episode's own launch and return are classed by
`judgmentRetryable`. Host-side preparation before the episode keeps a typed
stop. Keep R1 as a regression in which the loop survives and later resolves
without a restart.

**Severity and limits:** Medium. With the always-on runtime, a brief model
outage or an interrupted episode stops the resident until someone restarts it.
That is the operator tending that VER-003 F3's repair was meant to remove.

That gap was partly mine. VER-003's rule said "leaves the item or body undecided
for a fresh episode" without naming the host that schedules the episode, and
the repair met that literal text.

The one-shot vertical command already ends its invocation on such a failure
and resumes on the next one; that path is not routed. The historical live runs
hit neither path, so their scores stand.

### F2 — Low, blocking: one invocation launches unbounded review-body episodes

**Class and scope:** a termination and cost defect introduced by D036's
re-observation in `review-comment-loop.mjs`.

**Observed:** after each `ReviewBodyJudged`, the loop now calls `observe()` and
continues. A body whose text differs on the next observation has a new subject

**Reproduction:** probe B1 uses an automated summary whose status line changes

**Expected and repair rule:** one invocation launches a bounded number of
review-body episodes. A body still changing past the bound ends the invocation
with a typed outcome that names the item, and nothing is sealed against a
subject it did not judge. Keep B1 as a regression.

**Severity and limits:** Low. It needs a reviewer that edits its body
continuously. Each extra episode is a real model launch in production. The
executor's test covers a single change only.
