### Criterion 2 — why the enumeration test is real

The left side of every assertion is the `sliceEventTypes` declaration; the right
side is extracted from the reactor's own fold bodies by scanning for `case "X":`
and `event.type === "X"` (`reactor-slices.test.ts:141-190`). A `case` added
without a declaration fails at `:143-146`; a declaration with no fold branch
fails the `deepEqual`s at `:156`, `:171`, `:175`, `:182`. I re-derived the
walking bijection by hand: 18 `case` labels in `foldWalkingEvent` + 3 surviving
literal branches in `walkingDecision` + 5 `ARTIFACT_REFUSAL_TYPES`, deduplicated
to the 25 declared names.

"Folded by two slices" is enforced **within an active mode**, which is the
correct reading: ownership is `(active mode, event type)`, stated in source at
`reactor.ts:245-246`. Names deliberately repeat across modes — `CommandPersisted`
and `CommandResult` appear in walking, verification and feedback — and mode
precedence is pinned executably at `:88-89` and `:105-115`. Within walking mode,
the one pair that genuinely shares a mode, exclusivity is asserted at `:75-80`.

The extraction is source-text scraping bounded by `indexOf` markers. If a marker
were renamed, the window would collapse and the `deepEqual` would fail loudly —
fail-safe, not silently vacuous. Noted as brittleness, not a defect.

### Disclosed environment finding 1 — the writer reservation leaks on the Codex path

The `resume: verify` dispatch was refused before any lifecycle change because
the worktree writer reservation from the executor's Codex session was still
held. Observed via `node scripts/harness.mjs writer --show`:

```
{"contract":"harness-writer-v1","reserved":true,
 "actorId":"32347bccefb884d48ddde604109f4d19e7767992d0d6207b6fa8e570d5075c28",
 "owner":{"pid":20286,"source":"parent"},
 "reservedAt":"2026-09-16T00:19:04.543Z",
 "liveness":"unavailable","alive":"unknown"}
```

Reserved `00:19:04.543Z`, about four minutes after `WorkOrderActivated`; the
executor reached `ImplementationReady` at `00:46:24.316Z` and the reservation
survived it. `owner.source: "parent"` — the Codex host process itself holds it.
Because `liveness` is `unavailable`, the harness fails conservative and refuses
indefinitely; recovery required an operator `writer --release`.

Root cause is already recorded in this repository's own capability residue:
`codex-cli-0.153.4: concurrent-work-requires-worktrees: No project hook fired in
the bounded Codex probe; the role skill carries the remaining duty.` Under
Claude Code, hooks enforce *and* tear down the reservation; under Codex no
project hook fires, so `packages/skeleton/dist/src/writer-teardown.mjs` has
nothing guaranteeing it runs at session end.

Secondary effect worth a planner's attention: the hook classifies `Bash` as
`shell` (`.claude/hooks/concurrent-work-requires-worktrees.mjs:167`), so a held
reservation refuses *every* shell command including read-only `cat`, `grep` and
`pwd`. A stale reservation therefore disables all shell-based diagnosis of
itself, including `harness.mjs writer --show`.

**Planner nomination:** guarantee writer teardown on the Codex path (or expire a
reservation whose owner cannot be probed), and consider admitting read-only
shell while a reservation is held so the leak remains self-diagnosable.

  (`0.154.0`, `gpt-6-astra`, `max`, `operator-attested`).
- The first degraded one is WO-067 at **`2026-09-15T18:22:25.138Z`**
  (`0.154.0`, `unknown`, `unknown`, `unknown`).

It is **not** a `codex-cli` version regression: `0.154.0` recorded
`gpt-6-astra`/`max` correctly for five days before the boundary. The regression
window is roughly `2026-09-15T16:37Z`–`18:22Z`.

`operator-attested` → `unknown` → `session-tools-no-effective-readback`

attestation path being switched from operator attestation to session readback,

**Planner nomination:** restore an operator-attested fallback when effective
