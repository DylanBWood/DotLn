**F1, medium severity, elected workflow only.** After approval and
application, the executor integrates `main` before its complete run (the
integrate-first duty in the executor root). In the ordinary case that is a
fast-forward. HEAD moves, and `planFirstView` then reports `changed: ["base
commit"]`, so the approval reads `null`. From there the hook refuses
implementation writes again, `implementation-ready` prints
`DOTLN_PLAN_FIRST_REFUSED … changed since proposal: base commit`, and the
drive stops at `awaiting-plan-approval`. The refusal says to revise the
proposal, but `draft WO-NNN --new` clones the new committed HEAD without the
applied working-tree change. The renewed candidate's diff is 0 bytes, so it
cannot show the operator the change they already approved. The operator must
approve again with no change in content, and the executor must rebuild the
change in the new candidate by hand. Reproduction:
[probes.mjs](../../evidence/WO-242/ver-001/probes.mjs) test `F1` fails at
`changed` = `["base commit"]`.

It does not block. Criterion 2 requires that a moved base clear the approval,
and the implementation does exactly that. Main had no plan-first workflow to
regress. Planning receipt 064 lists this as criterion 2's known issue. Its
reopen condition, a fixture showing an approval cleared by an integration
after the approval, has now occurred. The 2026-10-30 pass had recorded the
reading that a clean integration keeps the approval, but the order's text
never took that reading in.

Repair rule: a clean integration after application keeps the approval. That
means an integration that leaves the approved diff applied and touches none
of its paths, with the approval bound to the applied diff rather than the raw
HEAD. A conflicting or path-touching integration still needs a new proposal,
and its candidate must carry the applied change.
