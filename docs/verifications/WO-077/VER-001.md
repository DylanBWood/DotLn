## Findings

**F1 — a kit-declared root move can land inside a kit tree (follow-up).**
- **Observed.** In S3 I declared `rename-root` for `evidence`, from `docs/evidence` to `scripts/evidence`, then ran an opted-in update with `--apply`. It exited 0, moved the root into `scripts/` and recorded `roots.evidence: "scripts/evidence"`.
- **Cause.** `instancePath` (`scripts/launchpad.mjs:1344-1358`) compares the destination only with the listed kit files, through `overlaps` (`:1080`). But `kitPath` (`:1092`) treats every path under the kit trees (`:146`, `scripts` and `packages/beacons`) as kit-owned.
- **Documentation.** D003 says kit paths refuse; the client README says overlaps with kit files refuse.
- **Consequence (inferred from `planUpdate`).** A later kit file under `scripts/evidence/` would be refused as an instance-owned collision.
- **Rule for a repair:** a root move refuses any `from` or `to` that is, or lies under, a path the manifest's ownership predicate treats as kit-owned.
- **Reachability:** only a kit author can declare such an action.

**F2 — a converged kit file is refused for good (follow-up).**
- **Observed.** `probe2.mjs` R1 writes source B's bytes into the export's `scripts/ver-changed.txt`, as a fork that took core's change by hand would. The update lists the file as refused (`locally modified; prior hash retained`), the manifest keeps A's hash, and the next update refuses it again.
- **Cause.** `planUpdate` compares the current bytes only with the prior hash (`:1225`).
- **Relation to the known issue.** This is a narrower case of the planning receipt's criterion:1 issue. Here no merge is needed, because the file's bytes already are upstream's.
- **Rule for a repair:** current bytes equal to the incoming candidate's count as converged. The manifest records the incoming hash and the file is not refused.

**F3 — an update that fails after its kit writes cannot be retried (follow-up).**
- **Observed.** In `probe2.mjs` R2, an opted-in instance has a read-only `records/` directory and a declared move of `docs/evidence` to `records/evidence`.
  - Preflight passes.
  - The kit writes and the removal of the dropped file happen (`:1510-1516`).
  - Then `renameSync` fails with `EACCES` (`:1518-1521`).
  - The manifest stays at A while the replaced files already hold B.
  - After the permission is restored, the retry exits 1 with `cannot read regular file …/scripts/ver-dropped.txt`, because the update requires every prior kit file to be readable (`:1468`).
- **Without the dropped file.** F2's classification would instead refuse every file the first run had replaced.
- **Relation to D002.** D002 records that the update promises no crash-atomic transaction. This probe adds two facts: an unwritable instance directory reaches this state, not only a disk failure, and retrying does not recover it.
- **Rule for a repair:** a retry after such a failure completes. One way is for a dropped prior path that is already absent to count as removed, with F2's rule covering the replaced files. Another is to perform the instance moves before any kit write, or to check that their parents are writable during preflight.
