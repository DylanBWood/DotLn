## Acceptance criteria

**1. SUPPORT INACTIVE on an incompatible link — met.** The string is produced by
the compiler, not by the test: `packages/compiler/src/compile.ts:183` for a
capability mismatch and `:196` for a tag mismatch. The capability diagnosis
names the exact capability id, the active, the support, and the link group, and
carries corrections built from graph and environment data
(`compile.ts:91-105`), not fixed prose. The corrections are executable —
feeding an emitted `provide-capability` back into the environment flips
`ok: false` to `ok: true` with the support present in the manifest. The compile
boundary is hard: `compile.ts:1004` returns `{ ok: false, diagnostics }` before
`emitProgram`, the failing result carries no `program` and no `semanticHash`
key, and both consumers (`cli.ts:48-51`, `reactor.ts:106-109`) throw rather than
degrade. Diagnostics are not truncated; a graph with four bad supports returned
all five. Degrading the message, emptying the corrections, forcing the
capability check to pass, and making the diagnosis non-fatal were each killed by
the AC1 test.

The criterion's own wording is about the missing **capability**, and that half
is fully evidenced. The **tag** half of the same compile step is not — see
finding F3.

**2. View equivalence, round-trip, and a live equip effect — met.** The three
editable views are genuinely distinct encodings, and all three compile to
`fnv1a64:9ca8d0229c6bd8db`, which I reproduced verbatim. The hash is a real
function of the program: perturbing an objective string, an authority effect, a
cadence interval, a support's `resourceMultiplier`, a cost number, or an
evidence requirement each changes it, while reordering set-like collections and
reformatting whitespace do not. `decode(encode(x)) = normalize(x)` holds for
each view. Equipping and unequipping changes the running program, not merely a
preview: `WO-008 AC2 an unequipped support changes the live reactor program`
runs the scenario twice and gets different decisions and different WorkOrder
constraints, and severing the compiled cadence identifiers in the reactor kills
`WO-008 AC2 the running reactor consumes compiled cadence identifiers`.

Two caveats are recorded as findings F5 and F6: the pipeline-multiplicity
guarantee has no test, and the round-trip law as specified cannot detect content
loss because both sides route through the same `normalize`.

**3. Nine-level precedence, conflicts, commutativity — met.** The nine layers in
`packages/compiler/src/types.ts:19-29` match
`docs/product/03-architecture.md` step 3 name-for-name and in order, and the
test pins them against its own hardcoded literal
(`packages/compiler/test/compiler.test.ts:17-27`), not against the
implementation's constant — so a reordering is caught, and inverting the
comparator kills 12 tests. The nine-way conflict test exposes the winner **and**
every overridden claim with its layer; the adjacent-pair test covers all eight
pairs. Conflicting hard supports reject with an explanation. A non-commuting
pair without a pipeline is rejected, an explicit pipeline governs the transform
order, and permuting ordinary links leaves the hash unchanged — Principle 13
holds. A winning `authority.<effect>` claim rewrites both the emitted
`AuthorityEnvelope` and the WorkOrder operation lists, so the trace and the
kernel's runtime authorization agree; wildcard patterns reject as a diagnostic
rather than being silently dropped.

The degenerate case — two claims at the same layer with the same hardness and
different values — is outside the criterion's wording, and the compiler's answer
there (reject) is correct but untested. That is finding F4.

## Findings

No finding defeats an acceptance criterion. Three were raised to me as blocking
by the delegated review; I reproduced all three and downgraded each for the
reason stated, and I record that reasoning so the final reviewer can disagree
on a documented basis.

**F1 — the receipt misdescribes what one named AC6 test proves, and that test's
lead assertion cannot fail.** _Non-blocking; correction required._
`docs/work-orders/WO-008-composition-compiler.md:118` states that
`WO-008 AC6 the running scenario consumes the compiled Seiri loadout` "proves
the integration boundary". That test (`packages/skeleton/test/scenario.test.ts:210`)
never calls `runScenario`, and its first assertion compares
`compileWorkOrder(loadout)` with `compiled.workOrder` where
`compileWorkOrder` is defined at `packages/skeleton/src/reactor.ts:113-118` as
`compileLoadoutProgram(equipped, baseCommit).workOrder` — both sides are the
same call, so the assertion holds for any WorkOrder content whatsoever.
Downgraded from blocking because the integration boundary **is** proved by other
named tests that I confirmed are load-bearing (the AC6 frozen-trace test, and
the two AC2 tests that die when the compiled cadence identifiers or the
equipped support set are severed), and because AC6's own substance is met and I
reproduced it independently. The defect is a false sentence in committed
documentation plus a dead assertion — both correctable without touching
behavior, contracts, schema, or authority.

**F2 — a graph can grant itself deletion authority, and the tooltip does not
notice.** _Recorded observation; not a WO-008 criterion._ A single linked
support declaring `{target: "authority.repo.delete", value: "allow", layer:
"safety-invariants", hard: false}` compiles with `ok: true` and no diagnostic,
and `repo.delete` moves into the emitted `AuthorityEnvelope.allowedEffects`
while the rendered tooltip still prints `Deletion remains operator-owned` under
RESTRICTIONS. I reproduced both halves directly. This is not a defect against
WO-008: the compiler is a pure function over an author-supplied graph, no
criterion asks for a claim-layer authorization floor, and the write-back in
`02-domain-model.md` describes the mechanism honestly without claiming one.
But it means the top precedence layer is a label any support may self-assign, so
"safety invariants" currently confers ordering, not safety; and the tooltip's
RESTRICTIONS are hand-authored `inspection` strings rather than a projection of
the compiled envelope, so the visible payoff can contradict the program it
previews. For the delivered Seiri loadout both are accurate. The final reviewer
should decide whether this becomes a bounded follow-on before saved builds or
community builds — the rungs at which a graph stops being author-trusted — and
`04-interfaces.md`'s "Honest status effects only" inspector doctrine is the
relevant standard.

**F3 — the tag half of the cited link type-check has no test.** _Non-blocking;
test required._ `docs/product/03-architecture.md` step 2, which AC1 cites,
defines the check as "tags vs supportedTags, capability requirements".
Replacing `compile.ts:174` with an always-true expression builds clean and
leaves the suite at 73/73 — I ran this mutation myself. No test in the
repository references `supportedTags` or the `link-compatible-active`
correction. The branch is behaviorally correct (an incompatible support yields
`SUPPORT INACTIVE: support "…" supports tags […], but active "…" exposes […]`
with a correction), so nothing is broken; it is simply undefended. Downgraded
from blocking because AC1's own wording is about the missing capability, and
that half is fully evidenced and mutation-resistant.

**F4 — the equal-precedence rejection has no test.** _Non-blocking; test
required._ The `AMBIGUOUS SUPPORT CONFLICT` guard at `compile.ts:407` is the
only thing preventing two same-layer, same-hardness, different-valued claims
from being settled by the sort order. I confirmed it fires correctly, and I
confirmed that neutering its condition builds clean and leaves the suite at
73/73. No test references `AMBIGUOUS`. Downgraded from blocking because AC3's
three clauses are each tested and the tie case is outside its wording — but this
is precisely where the nine levels give no answer, so it deserves a test.

**F5 — pipeline multiplicity is documented as load-bearing and untested.**
_Non-blocking._ `docs/product/04-interfaces.md` says "Most importantly,
`ExplicitPipelineV1.orderedSupportFacetIds` retains both order and
multiplicity". Order is defended — sorting that array kills the explicit-pipeline
test — but deduplicating it (`normalize.ts:313`) leaves the suite green. No test

**F6 — the round-trip law cannot detect content loss.** _Non-blocking._ `encode`

it is derived, so this is a weak specification honestly implemented rather than
a false claim; a test comparing the decoded graph against the **authored**
source would give it teeth.

**F7 — three further shipped rejections and one cost field are undefended.**

### Control-plane limitation this exposes

harness, and `effortHarnessEvidence` matches it exactly. Recording `2.1.260`
therefore retires the `2.1.259` datum rather than adding to it, and every future
Claude Code upgrade silently invalidates all effort attestation until someone
re-runs discovery — the failure surfaces only at the next
`verification-result` or `final-review-result`, i.e. at the worst moment. A
versions array, or a range, would remove a recurring stall. This belongs to the
WO-019 lineage rather than to WO-008 — the `effortReadbackProbe` block carries
`"workOrder": "WO-019"` even though the enclosing file is a WO-004 artifact — and
I record it here because this episode is where it bit, not to expand scope. The
staleness is not theoretical or slow: that probe's own `observedAt` is

already one patch version behind the running harness by the time the gate was
