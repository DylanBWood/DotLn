`Skill(name)` and `Skill(name *)`. The host documents aliases, display names and
a Claude Desktop plugin form as names of the same skill.

- **Observed.** Under an off election, the hook admitted `Skill` with

- **Host behaviour, per its documentation.** The skills page says
  `Skill(anthropic-skills:<name>)` also blocks the plugin delivery. It says
  only `Skill(skill:<name>)` blocks a skill under all of its names. Inferred
  from that documentation and the emitted rules, not observed:
  - for an alias, neither layer refuses;
  - for the plugin form, the host refuses but without DotLn's reason.
- **Unknown.** I did not observe whether the host resolves these spellings to
  the listed skills.
- **Impact.** The desktop and operator-browser tools themselves stay refused
  under every probed name, so loading a skill's text reaches no desktop.
- **Repair rule.** Both layers deny the same set of names for each listed skill:
  - emit `Skill(skill:<name>)` beside the current forms;
  - classify the documented equivalent names in `isDesktopControlTool`;
  - keep unrelated skills unclassified;
  - add a fixture for each form.
- **Record.**

  `FUP-4763c82de6324631`.

## Observations, not boarded

- **Kit prediction.** `expectedHarnessBundle` in `scripts/launchpad.mjs`
  predicts the harness bundle without the target's election, as it already does
  for `build.overlay`. Two consequences:
  - When an elected instance is updated, the update reports its re-emitted
    `.claude/settings.json` as refused (locally modified, prior hash retained)
    and ends with the existing `re-emit` instruction.
  - A starter refresh of a starter that itself elects the feature would fail
    its byte comparison, as an overlay starter would today.

  Instance-configured emission already has this limitation and the failure is
  conservative, so it is not boarded here.
- **Worker definitions.** `.claude/agents/dotln-worker.md` and
  `dotln-worker-fable.md` do not carry the sentence. Workers read only their
  assigned inputs. Under Claude their tool calls pass through the same hook and
  host rules (the probe refused a subagent call). Codex workers keep the worker
  transport's disabled features.
- **Diagnostic wording.** An election that is neither a boolean nor an object
  reports `features.desktop-control must be an object`. That is accurate but
  does not mention the boolean form, and the executor's test pins this message.
- **Target workers.** `lowerTargetWorker` emits no desktop deny rules. Its hook
  refuses `desktop.control` through compiled authority and fails closed (D012).
- **Case variants.** A name such as `mcp__Computer-Use__screenshot` gets the
  classification advisory. Host tool names are case-sensitive, so this is
  outside the vocabulary.
