## Instrument disclosure

The deliverable is a verification mechanism, so this report is a human verifier
judging a machine verifier. Two consequences were controlled for rather than
assumed away.

1. **The subject cannot be its own oracle.** The fixture "verifier"
   (`fixtureVerificationResult`) derives its verdicts from the same host
   witnesses the matrix consumes, so a green loop proves the host/kernel
   machinery, not model judgement. I therefore did not accept the loop's own
   completion as evidence for AC2/AC3. Instead I constructed adversarial
   results myself — implementer-actor events, forged all-pass evaluations,
   a pass asserted over a genuinely failing witness, a synthetic
   `CriterionVerified` event type, repairs outside the focused surface, repairs
   adding files, empty and no-op repairs — and confirmed each fails closed
   against the shipped `verificationReactor` and `parseEvidenceResult`. Results
   are in the criteria sections below.
2. **The blinding claim needed my own sentinel.** The executor's test plants
   `IMPLEMENTER_NARRATIVE_NOT_ADMITTED`. I planted a different string,
   `VERIFIER_BLINDING_PROBE_SENTINEL_9X7`, through
   `runVerificationDemo({implementerNarrative})`, captured every
   `CommandPersisted` payload, and confirmed the marker appears in the host log
   exactly once — on `ImplementationReported` by actor `implementer` — and in
   none of the three compiled capsules. The assertion is not vacuous: the
   marker demonstrably reaches the log.

## Acceptance criteria

**1 — Planted defect caught, repaired in a fresh episode, re-verified green,
end to end through the kernel's event loop. Met.** From a clean store I ran the
shipped CLI (`dotln verify-demo`) and then folded its log myself. The recorded
sequence is 31 events: `VerificationOpened` → dispatch → `CommandPersisted` →
`WorkerAttemptStarted` → `CommandResult` (fail) → repair dispatch →
`CommandResult` (proposal) → `VerificationSubjectSubmitted` → third dispatch →
`CommandResult` (pass), with `WorkerWorktreeRemoved` after each attempt. Row
status advances `incomplete/incomplete/incomplete` → `verified/failed/verified`
→ `stale/stale/verified` → `verified/verified/verified`, and `next` advances
`verify` → `repair` → `verify` → `complete`. The three episodes are physically
distinct (`ep_verifier_1_attempt_1`, `ep_repairer_2_attempt_1`,
`ep_verifier_3_attempt_1`) in three distinct worktrees; the executor's suite
additionally asserts three distinct `cwd` values across the CLI launches. The
loop is genuinely the kernel's: `decideProgram` emits exactly three intents
(`verification.evaluate`, `repair.propose`, `verification.evaluate`) carried
through `Program.Invoke`, the durable `CommandPersisted` outbox and
`VerificationContinuation`; `pendingCommands(replayOutbox(log))` is `0` at the
end; and replaying the log through `seiriReactor` reproduces all 31 live
Decisions byte-identically (`JSON.stringify` equality, trace
`reactorId: independent-verification`). The defect is real rather than
narrated: the fixture's behavior witness runs an actual Node subprocess over
`select.mjs` and observes `["unused.tmp","used.tmp"]` against the expected
`["unused.tmp"]`. Determinism is strong — my independent run reproduced the
executor's recorded `commandId` `cmd_a55351b8ec012a11` and `resultId`
`result_cmd_a55351b8ec012a11` exactly.

**2 — The implementer episode never certifies itself, structurally. Met.**
Blinding is positive construction, and I checked it by enumeration rather than
by reading the claim: a live capsule's key sets are exactly
`contractVersion, compilerPackageVersion, role, workOrder, criteria, subject,
finding, inputHash`; subject `repo, baseCommit, revision, diff, files,
evidence`; files `path, contents`; criteria and evidence exactly the domain
model's pinned field lists. `prohibitedOperations` includes `transcript.read`
and `self.certify`. My sentinel probe (Instrument disclosure 2) confirms no
implementer prose reaches any capsule. Certification is equally closed. Against
the state immediately before the first accepted result, all of the following
left `rows` unchanged and `lastResultEventId` null: the identical accepted
payload re-emitted with `actorId: "implementer"` (ignored — every non-host
actor is dropped before any acceptance branch); a host-actor result with every
verdict forged to `pass` and `evidenceRefs` emptied (refused, recorded in
`refusedResults`); a host-actor result asserting `pass` on `AC-selection` while
citing the real failing witness (refused); and the same payload retyped as
`CriterionVerified` (no acceptance path exists for that type). `mutations` in
the executor's suite cover thirteen further shapes and I reproduced the class
independently. The repairer cannot certify either: its result schema has no
`evaluations` field, a repair result retyped as `kind: "verification"` is
refused, and on application the repairer's episode id is appended to
`implementerEpisodes`, so a later result claiming it is refused by the same
producing-episode gate that rejects `ep_implementer_1`.

**3 — Full VerificationFinding shape; each blocking finding compiles a focused
repair WorkOrder. Met.** The recorded finding carries every field the domain
model pins: `findingId`, `criterionId`, `severity: "blocking"`, `observed`
(`["unused.tmp","used.tmp"]`), `expected` (`["unused.tmp"]`), one non-empty
`reproductionSteps` entry, `evidenceRefs` resolving to the adverse witness
`19e16d73…:exclude-referenced`, and `likelySurface: ["policy.json"]`. The
compiler refuses an incomplete or non-blocking finding (severity `minor`, empty
`observed`, empty reproduction steps, empty evidence refs, a `../outside` path,
and a surface outside the criterion's declared dependencies all throw), and the
protocol additionally requires the finding's observed/expected pair to match an
actual failing witness — a fabricated `observed` is refused. Each blocking
finding gets its own compiled plan: replaying the accepted result yields
`repairPlans` containing `repair_1_finding_verification_1_AC-selection` with
`role: "repairer"` and `allowedOperations: ["repair.propose"]`, and the

focused: proposals touching `README.txt`, adding `select.mjs`, proposing no

      which has no aliasing problem. macOS is the only platform in this
      repository's recorded evidence, so the release's headline runbook does
      not work as written for its own operator. Suggested fix: use a
      repo-relative store (`.runtime/verification`) as the existing runbook

      realpath requirement.
- [ ] **`docs/evidence/WO-010/cli-smoke.txt` presents a reduced projection as
