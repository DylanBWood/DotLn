## F2 — Status poll outlives `close()` after a watcher error

**Severity:** low (P3). **Criterion:** none; a regression in the exported
`watchRuntimeStatus` library API.

**Expected:** after a consumer calls `watcher.close()`, no further `changed`
or `unavailable` callback arrives. This held before the repair, which had no
poll.

**Observed:** `packages/console/src/runtime-status.ts:111-113` starts an
unref'd 250 ms `setInterval(refresh)` and clears it only on the watcher's
`close` event. Node v26.9.0's `FSWatcher` error path (status below 0) closes
its handle "to avoid firing the close event". Its `close()` then returns early
because the handle is null, so the interval is never cleared.

**Reproduction:** a scratch probe imported the built
`packages/console/dist/src/runtime-status.js` and drove the real
`FSWatcher` error path with `_handle.onchange(-5, …)`. It then called
`close()` and atomically replaced the status file. It printed `close events 0`
and `changed callbacks after close() 1`. The refuter independently saw 3
callbacks after `close()` with the repair and 0 on the pre-repair source.

**Limits:** `statusCli --watch` never calls `close()` and exits after a watcher
error in both versions. No in-repo consumer calls `close()` after an error; the
exposure is the public export at `packages/console/src/index.ts:6`. Deleting
the watched directory on this macOS host produced `change` events, not an
error, so the trigger is uncommon here.

**Repair target:** stop the poll on the watcher's error as well as on close,
or make `close()` always clear it. Add a regression on the error path.
