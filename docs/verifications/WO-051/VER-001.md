## Findings

### F1 — the Claude writer launch drops `--settings '{"autoMemoryEnabled":false}'` that the inspection launch sets (non-blocking; no criterion affected)

**Observed vs expected.** `wo051-inspection-baseline.json` pins the inspection
Claude array with `--settings {"autoMemoryEnabled":false}` and
`--disable-slash-commands`; `wo051-writer-args.json` pins the writer array
without either. The writer profile is the strictly more capable of the two — it
is the only one with `Edit`, `Write` and a live `Bash` — so the harness's
automatic memory is left at its default for the launch that can change source,
and suppressed for the launch that cannot.

**Reproduction.** Compare lines 234–238 of `wo051-inspection-baseline.json` with
lines 11–35 of `wo051-writer-args.json`; the writer array goes from
`project,local` straight to `--strict-mcp-config`.

**Why it is not routed to repair.** It fails no criterion. The order's Objective
enumerates the Claude writer flags exactly and `--settings` is not among them,
and C-W2's recorded shape does not carry it either. The asymmetry is with the
Codex side, where the order says "and the existing hardening flags" and the
implementation duly retains every inspection `-c` override. Nothing in the record
forbids carrying `--settings` across the same way; it was simply not asked for.

**Severity: low, with a privacy edge.** The order cites 09 §Privacy and
minimization, whose "explicit treatment of derived data … model inputs/outputs …
transcripts" bears on this. `--no-session-persistence` is present and C-W9
observed no session file, but automatic memory is a separate store that C-W9 did
not measure. Recorded so the reviewer's choice to carry it or not is deliberate.

### F2 — the writer profile re-enables the shell while retaining `shell_environment_policy.inherit="none"`, and 03 §Ports calls that "non-shell hardening" (non-blocking; no criterion affected)

**Observed vs expected.** `sourceChangeArgs` filters `shell_tool` and
`unified_exec` out of the `--disable` list because the writer needs the shell,
but keeps `-c shell_environment_policy.inherit="none"` from the inspection
profile, where the shell was disabled and the setting could not matter. The
pinned array confirms it at line 77. 03 §Ports describes the retained set as
"the existing non-shell hardening", which does not describe that entry.

**Reproduction.** `wo051-writer-args.json` line 77 against the `codexDisabled`
filter in `worker-transport.ts`; the same `-c` appears in the inspection array.

**Why it is not routed to repair.** The order's Objective directs exactly this —
X-W1/X-W2's shape "and the existing hardening flags" — and the live smoke is
WO-053's non-goal for this order, so no criterion here can settle it.

**Severity: low as filed, unknown as deployed, and that is the point.** The
three commands the profile authorizes (`node fixture-test.mjs`, `git add -A`,
`git commit -F <path>`) all need binary resolution, and a commit additionally
needs identity. Whether an empty inherited environment breaks them depends on
whether the harness's command shell restores a default `PATH`, which neither
X-W1 nor X-W2 exercised — both ran without this override. **This is untested in
both directions; I am not claiming it fails.** What I am recording is that
neither the order's limits nor `validation.md` names the interaction, while
`validation.md` does name the adjacent question ("whether the live worker can
satisfy all prompt instructions under that shape"). WO-053's live smoke should
run the pinned array unmodified so this resolves as an observation rather than a
surprise, and 03 §Ports should either drop "non-shell" or name the exception.

## Observations

**O1 — the transport accepts a commit-message path that the worker's own `git add -A` will commit.** The order's Design places the message "inside the worktree
… WO-049's exclude hides `/.dotln/`", and the fixture uses `.dotln/message.txt`
with that exclude configured. `validateSourceChangeEnvironment` enforces only
that the path is canonical, inside the mount and a regular file — not that it is
ignored. I built a scratch worktree with the message at
`<worktree>/commit-message.txt`, and `sourceChangeProfile` accepted it; `git add
-A` then staged `commit-message.txt` alongside `fixture.txt`, so the host's
commit message would land in the commit it describes. This fails no criterion —
criterion 2 asks only for refusal of a path *outside the mount* — and the host
that chooses the path is WO-052's. Recorded against that order, not this one:
either the environment check should require the path to be ignored, or WO-052
should own the `.dotln/` placement as a contract rather than a convention.

**O2 — the authority envelope's expiry sits inside the durable retry key.** `workerRequestKey` strips only `episodeId`, so my probe confirms `ep_1` and
`retry` share a key while `expiresAt: 1000` and `expiresAt: 2000` do not. That is
correct and harmless for an inspection worker, where a missed cache hit costs one
read-only relaunch. For a writer it means a retry under a re-issued authority —
the ordinary outcome of a long or interrupted episode — misses the stored result
and relaunches an episode that may already have committed. The added
`observedCommit` is exactly the signal a host needs to detect that, which is why
this is a handoff note rather than a defect: WO-052 owns episode orchestration
and the order's non-goals fence the repair loop. The comment on
`workerRequestKey` claims the key holds "kind, mount authority, command and host
message path"; it holds rather more than that.

**O3 — the writer result's strictness is carried by the parser, not by a schema flag.** The inspection Claude launch passes `--json-schema` and reads
`structured_output`; the writer launch passes neither and parses
`terminal.result` as text, because C-W2's recorded shape is `stream-json`. The
schema still reaches the model, inside `writerPrompt`'s `outputSchema`. This is
not a gap — `parseWriterResult` enforces the exact six-key set, the pinned
`workOrderId`/`episodeId`/`resultId`, the status enum and a real string status —
and the `spoof`, `wrong-id`, `failed-wire`, `nonzero` and `missing-denials`
doubles all reject. Recorded so the reviewer does not read the missing
`--json-schema` as an oversight; it is the record's shape plus a strict parser.
