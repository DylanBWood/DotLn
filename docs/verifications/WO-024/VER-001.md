## Observations for the final reviewer

None of these blocks the pass. They are judgment calls or seams a reviewer
should accept consciously rather than inherit silently.

1. **The edition is heading-major, and the order's prose describes a
   concatenation.** The design paragraph says the edition is "the concatenation,
   in first-parent commit order, of every `RELEASE-NOTES.md` … one subsection
   per work order, followed by a machine-derived 'Evidence and compatibility'
   block," and AC2 repeats "one subsection per work order." The implementation
   instead emits five top-level sections, each containing one subsection per
   work order. I judge this to satisfy AC2 and to be the better reading, because
   the order's own constraints are otherwise unsatisfiable: a literal
   concatenation of five-section files yields N repeated `## Release overview`
   headings, which is not the five-section edition 08-publication-compiler.md
   specifies, and there would be no single "Read before upgrading" for the
   design's own clause "appended to 'Read before upgrading' … after the
   reviewer's items" to attach to. The executor documented the resulting shape
   in `docs/releases/README.md` and 06-roadmap.md but did not flag it as a
   departure from the order's wording. Worth an explicit ratification.

2. **Reviewer-authored `###` headings become siblings of machine-generated
   ones.** The validator refuses `##` outside the five required headings but
   permits `###`. In the edition, a reviewer's own level-3 heading sits at the
   same level as the generated `### WO-NNN — title`, `### Derived from the
   diff`, and `### Machine-derived release evidence` headings — so a reviewer
   could author a subsection indistinguishable from a machine-derived one. No
   content is lost or misattributed and release membership is unaffected (the
   executor's fixture tests exactly that with a `### WO-999 …` heading), but the
   ambiguity is real. Probe D confirms `### Machine-derived release evidence`
   inside reviewer prose validates and publishes.

3. **`## Release overview` containing only `None.` is accepted.** The design
   says "The overview and read-before-upgrading sections must be non-empty,"
   which reads as "may not be `None.`" given that every other section is already
   required to be non-empty. The implementation enforces literal non-emptiness
   only. AC1 says "empty," so the criterion is met as written; whether a `None.`
   overview should be refused is a reviewer call.

4. **The executor amended the work-order authority (governance).** Activation on
   2026-09-02 retained the planner's placeholder H1 ("version assigned at
   activation"). The executor rewrote the H1 and the Release classification
   paragraph to `v0.3.2`, rewrote the closeout's backfill sentence, and updated
   the WO-024 row in `docs/planning/work-order-map.md`. `docs/verifications/README.md`
   says new authority comes only from the operator or an amended work order. I
   verified the substance is correct — `v0.3.1` is the latest published tag
   locally and on origin, `v0.3.2` is the map's stated second consecutive patch
   target, the append-only activation event was not replayed or edited, and the
   correction is disclosed in the work order, the ledger, and the map. The
   forward-correction was also necessary: `release close` derives the version
   from the H1 and would have refused the placeholder. Still, an executor
   editing its own scope authority is a seam the operator should ratify rather
   than absorb. The underlying process gap is the activation preflight, not this
   executor.

5. **`worktree publish` gained more than Deliverable 2 named.** Deliverable 2
   asked only for the `RELEASE-NOTES.md` refusal. `publish` additionally gained
   a `gh auth status` preflight, `--repo <host/owner/repo>` pinning with
   fetch/push agreement checking, `GH_REPO`/`GH_HOST` scrubbing, and reading the
   PR body from `HEAD` rather than the working tree. The design's phrase
   "mirroring `worktree publish`" presumed an auth preflight that did not exist,
   so adding it makes the sentence true, and the `--repo`/env-scrub changes
   close a real path by which an ambient environment variable could redirect a
   PR or Release to another repository. Reading the body from `HEAD` matches the
   guide's existing "committed, contained PR body file" contract, and
   `ensureClean` already runs first so the two sources cannot diverge. All are
   fixture-covered. I record them as scope beyond the literal deliverable, not
   as defects.
