## Acceptance criteria

### 1 — Deterministic committed-only subject: **met**

Reproduced in a throwaway repository built from this worktree's content
(`git init`, single base commit), driving `buildPlanSubject` directly.

- The hash is deterministic across repeated builds of the same revision.
- A one-byte change moves the hash for each of the five named families: the
  map's sequence block (label text), a listed order file, a vision thesis
  section, the judged roles table, and a capability row. Each was tested in
  isolation and reverted before the next.
- Committed-only holds: in every case the workspace edit left the committed

  `work-order-map.md` outside the sequence block, and appending to

### 3 — Closed result and receipt-writer screen: **met for the schema, failed for the screen**

The validator was exercised against twenty hand-built results over the real

**The local-terms screen is where this criterion fails.** Driving
`checkLocalTerms` directly against a synthetic list:

| List entry | Surface | Outcome |
| --- | --- | --- |
| `Wibblesprocket` | `Wibblesprocket`, `WIBBLE-sprocket` | refused |
| `Wibble Sprocket` | `Wibble Sprocket` | refused |
| `Wibble Sprocket` | `WibbleSprocket` | refused |
| `Wibble Sprocket Cloud` | `Wibble Sprocket Cloud` | **passed through** |
| `Wibble Sprocket Cloud` | `WibbleSprocketCloud` | refused |
| `Big Wibble Sprocket Cloud` | `Big Wibble Sprocket Cloud` | **passed through** |
| `Wibble Sprocket` | term split across a line break | **passed through** |

`checkLocalTerms` builds candidates from unigrams and adjacent bigrams only,
so a list entry of three or more tokens can only ever match if the surface
happens to write it with no separators at all. The list is accepted without
complaint — the only list-shape check is that no entry normalizes to empty —
and the screen still reports `present`, which reads as an assurance that it
is enforcing. The order's fixture uses the single-token `SyntheticForbidden`
and matches it as a bigram in `Synthetic Forbidden`, so it proves the one- and
two-token paths and never exercises a three-token list entry.

This matters because this screen is the executable part of the repository's
locked Clean Room floor, and multi-word product names are the ordinary case
for the terms it exists to catch. Reporting presence honestly while silently
under-matching is a false assurance about that floor, not an absent
convention.

### 5 — Evidence-gate check: **met in every listed behavior, but the deferral escape hatch is a hole**

The listed behaviors all hold. Where the executor's fixtures cover a
behavior, I checked the fixture actually asserts it rather than counting the
`PASS` line, and reproduced the highest-value ones on real repository content
in a history-preserving clone with the WO-041 change committed as its
introduction commit:

- **Forward-only enforcement.** With the introduction commit present, the gate
  reports `enforcement: "2026-09-07"` with `passes: 0`: the pre-existing
  2026-09-06 planning pass is correctly exempt. Adding a synthetic
  2026-09-07 planning-pass heading makes the gate refuse with
  `planning pass planning-… needs a receipt`, and the committed evidence-only
  live receipt does not satisfy it.
- **An actual transport is required.** Writing a `planning`-kind receipt
  through the fixture transport and re-running the gate refuses with
  `planning gate requires an actual transport`, before the hold check.
- **Receipt text can never grant an override.** Committed receipts are
  immutable in the strong sense: appending override prose to the `.md`,
  changing one character of it, flipping the verdict in the `.json`, or
  deleting either file are all refused
  (`immutable Markdown differs from its receipt`, `receipt digest mismatch`,
  `expected contained regular evidence`). Overrides are read only from
  `docs/control/plan-refutations.jsonl`.
- The disposition chain, the whitespace and changed-elsewhere refusals, the
  three-consecutive-hold stop, the captured attributed override, and the
  stale-standard refusal are asserted by the order's fixtures, which pass; the
  stale-standard clause is further supported by my criterion-1 hash-sensitivity
  results, since staleness is exactly a hash difference.

**The hole.** A non-goal may carry
`<!-- dotln-plan-defer: <thesis> -> WO-NNN -->`, which suppresses the
"uncovered thesis" hold. `buildPlanSubject` validates that the thesis is
known, that the named order is not the order itself, that it does not occur
*earlier in the current sequence*, and that some committed
`docs/work-orders/WO-NNN-*.md` exists. It never requires the named order to be
a future order at all. In this repository there are 38 committed order files
outside the marked sequence. I added a marker on the last sequence order
pointing at **WO-001** — merged long ago and not in the sequence — and the
structural hold vanished: with the marker, a `largestGap` naming a thesis that
no order touches returned `pass` with zero holds; without it, the identical
result returned `hold`. The order's fixture only defers to `WO-902`, which is
in the sequence and later, so the happy path is the only path tested.

The work order conditions this exception on deferral "to a named later
order", and a deferral to a completed order is incoherent on its face — if
WO-001 had shipped that thesis it would be covered, not deferred. The README
faithfully documents the weaker implemented rule ("cannot occur earlier in the
sequence"), so code and docs agree with each other and both diverge from the
scope authority. Since the planner writes the non-goals and this marker is
one of only three structural holds, this is a mechanical bypass available to
exactly the party the mechanism exists to constrain.

## Required repairs

Both are narrow. Neither needs a design change, and neither should reopen
anything else in this order.

1. **`scripts/lib/terms.mjs`** — make the screen's matching depth honest.
   Either build candidates for the full token length of the longest list
   entry, or refuse a list entry whose token count exceeds what the matcher
   supports, so that a three-word term is never silently inert. Add a fixture
   with a three-token synthetic entry in spaced form. Consider the
   cross-line case as well: matching is per line today, so a term split by a
   newline is also missed.
2. **`scripts/lib/plan-subject.mjs` deferral validation** — require the named
   later order to be a genuine later order: in the marked sequence and after
   the deferring order, or otherwise demonstrably not-yet-done. Add a fixture
   for a marker naming an out-of-sequence order and one naming a closed order,
   both refusing. Update `docs/planning/refutations/README.md`, whose current
   sentence describes the weaker rule.

Re-verification should re-run criteria 3 and 5 and leave 1, 2, 4, 6, and 7 as
verified here.

## Non-blocking observations

1. **The gate's staleness rule will bite ordinary execution work.** Once a
   planning pass dated after the introduction commit exists,
   `checkPassReceipt` requires the latest planning receipt's subject hash to
   equal the current one. Any later work order that edits the capability
   table, a sequence order file, a vision thesis section, or the judged roles
   table will therefore turn `npm test` red until a fresh refutation runs.
   This is exactly what criterion 5's last clause asks for and the receipt
   "goes stale when the standard moves" by design, so it is not a defect —
   but it is a real operating cost that lands on the *next* order, not this
   one, and the operator should meet it deliberately. WO-041 itself adds a
   capability row, so the pattern is not hypothetical.
2. `admitReceipt` requires, for every prior held planning receipt across all
   passes, that at least one of its held criteria differ in the current
   subject. That set only grows. It is currently harmless and probably right,
   but it is an accumulating constraint worth watching.
3. A receipt's `semanticHash` depends on the dispatch timestamp, so it is only
   reproducible with the recorded time from the receipt itself. Fine as
   provenance; worth knowing before anyone treats it as a build identity.
4. The `.md` of the first manual redirect receipt is still formatter-owned
   (only `*-NNN.md` and `*.json` are ignored). Harmless, since `readReceipts`
   skips all six manual receipts, but the asymmetry will look accidental to a
   later reader.
5. Clean-room screen: I read every new and changed surface for employer-derived
   material and found none — no commercial tracker or ALM product name, no
   predecessor-system name, no managed-host, gateway, or employer-policy
   description, and no credential or secret shape. The receipt's committed
   free text is model output and was read directly for the same reason.
