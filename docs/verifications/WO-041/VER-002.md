## Criterion 3 — local-terms screen: **now met**

VER-001's finding was that `checkLocalTerms` built candidates from unigrams and
adjacent bigrams only, so a list entry of three or more tokens was silently
inert in its ordinary spaced form while the screen still reported `present`.

The repair replaces the candidate construction with contiguous token spans
bounded by the longest normalized term's character length, over a token stream
flattened across the whole surface. I drove `checkLocalTerms` directly against
synthetic lists in a scratch root — no receipt writer, no fixtures — with the
list `[Zorbulator, Wibble Sprocket, Wibble Sprocket Cloud, Big Wibble Sprocket
Cloud Nine]`:

| Surface | Outcome |
| --- | --- |
| `Zorbulator`, `Zorb-ulator`, `Zorb\nulator` | refused |
| `the Wibble Sprocket runs`, `WibbleSprocket`, `Wibble\nSprocket` | refused |
| `the Wibble Sprocket Cloud offering` (VER-001's silent miss) | refused |
| `Wibble-Sprocket_Cloud`, `Wibble\r\nSprocket Cloud` | refused |
| `our Big Wibble Sprocket Cloud Nine thing` (five tokens) | refused |
| `Big Wibble,\nSprocket (Cloud) Nine` | refused |
| `ＷＩＢＢＬＥ　ＳＰＲＯＣＫＥＴ` (fullwidth, NFKC + case) | refused |
| a six-token entry, longest in its list | refused |
| a short entry in the same list as a six-token entry | refused |
| ordinary prose with none of the terms | passed through, `present` |
| `Wibble` in one surface, `Sprocket Cloud` in another | passed through — surfaces stay separate |

Diagnostics stay private: every refusal message is exactly
`local-terms list present; refused [{"file":…,"line":…,"count":…}]`, carrying
the surface name, the span's starting line and a count, and never the term.
Multi-line surfaces report each starting line separately
(`[{"line":1,…},{"line":3,…}]`). List hygiene still fails loudly: a
whitespace-only or comment-only list refuses as `present but empty or
malformed`, and an absent list returns `unavailable` rather than a silent pass.

## Non-blocking observations

1. **The screen matches whole token spans, so a listed term embedded inside a
   longer token is still missed** — `PreZorbulatorSuffix` passes a list
   containing `Zorbulator`, while `WibbleSprocketCloud` as a whole token is
   caught. This is a deliberate boundary, not VER-001's defect: the README now
   says the screen "keeps token boundaries", and substring matching would
   refuse receipts over ordinary words. It is worth knowing that a term
   appearing only as part of a compound identifier is outside what this
   backstop catches; the human clean-room screen remains the primary control.
2. **Spanning is separator-blind, so it can over-match across sentence
   boundaries** (a two-word term matches text where the words end and begin
   adjacent sentences). Over-refusal is the safe direction for this screen and
   the list is operator-controlled; noted so a future false refusal is not read
   as a bug.
3. **Counts are matching spans, not distinct occurrences.** A surface
   containing `Wibble Sprocket Cloud` reports `count: 2` when both
   `Wibble Sprocket` and `Wibble Sprocket Cloud` are listed. The count is a
   diagnostic, not an assertion about how many terms appear.
4. VER-001's four standing observations still apply unchanged — most usefully
   the first: once a planning pass dated after the introduction commit exists,
   any later order that edits the capability table, a sequence order file, a
   vision thesis section or the judged roles table turns `npm test` red until a
   fresh refutation runs. That is the designed staleness rule, and it lands on
   the next order rather than this one.
