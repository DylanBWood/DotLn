## Findings

**F2 — a damaged gate-history archive stops a failed gate from recording (blocking: breaks behavior `main` had).** Low severity: the CLI entry catches the throw and exits 1, so no false pass is possible.
- **Observed.** The failure block selects the previous row with `readGateChecks(repo)` (`scripts/test-runner.mjs:2525`), which this order added.
  - That function reads the hot index and every archive in `docs/control/local/harness/check-history`.
  - It throws on non-JSON or non-array bytes (`packages/skeleton/src/gate-evidence.mjs:876-877`) or a `null` row (its sort at `:899`).
  - The throw escapes before `recordGateChecks` (`scripts/test-runner.mjs:2544`).
  - Main's runner never calls `readGateChecks`. Its one history read in a gate is the composition lookup, which catches the error, prints `passing-row lookup unavailable` and runs the selection (`:2077-2086`, unchanged from main).
- **Reproduction** (`archive.mjs`, host scratchpad, under `harness bounded`):
  - The fixture is a one-commit repository with a `build` task and a failing `beta` task, and one earlier failed `npm test` row in its hot index.
  - I wrote one damaged archive: `{}`, `not json`, `[null]`, or truncated JSON under a 40-hex archive name.
  - Each was run once with `--serial --again` and once with plain `--serial`.
  - Subject: all eight runs reject (`Malformed host gate evidence`, a JSON `SyntaxError`, or `Cannot read properties of null (reading 'recordedAt')`). The hot index, read directly, keeps 1 `npm test` row, and no `npm test: N passed` summary prints.
  - `HEAD` `b06c6081`: exit 1, 2 rows and one summary in all eight runs.
- **Controls, not counted.**
  - A hot index of `[null]` throws in both, because main's `recordGateChecks` also reads the hot file.
  - A lone hot row with a numeric `recordedAt` did not reproduce in either.
- **Why it matters.**
  - Product 07 tells the verifier to vary forged and stale records, and VER-001 routed F1, the same class, as blocking.
  - The main checkout holds 1670 archives. A full read of its 10760 rows took 439 ms with no error, so no live damage exists now.
  - Archives are written through a temporary file and a rename, so damage needs a hand edit, disk damage or a future format change.
- **VER-001 escape.** The read and its position are unchanged since VER-001's subject, so F2 is not a defect of the repair. VER-001 varied a row's snapshot fields but not the files the new read consumes, so its repair rule covered F1's shape only.
- **Rule a repair must hold.**
  - No failure while reading or selecting the previous row of the same check may escape the failure block. That covers reading the hot index or an archive, parsing, sorting and filtering rows.
  - Such a failure supplies no since-previous baseline, the same as a legacy row. The during-run interval is still compared.
  - The failed row is still recorded with exit 1 and its summary.
  - A runner fixture writes one damaged archive, for example non-JSON bytes. It runs a failing `--again` gate and asserts exit 1, the failed row in the hot index with its own four-field snapshot, one summary line and no throw.
  - A damaged hot index stays out of scope: main throws on it too.
