## Findings

### F1 — automatic prompt dispatch bypasses writer ownership and active-gate protection (blocking, high)

**Requirement.** The locked floor requires one writable coding agent per worktree. The cited execution guide's gate-input-protection contract prevents agent writes to the candidate tree while evidence runs. [D011](../../evidence/WO-130/decisions.md#wo-130-d011) adds automatic dispatch while promising to preserve the existing lifecycle and guards. This finding concerns that authorized expansion and its affected consumers; it does not reopen the accepted absolute-path residual of replica execution.

**Observed.** At `packages/skeleton/src/harness-host.ts:340`, `recordDispatch` spawns `scripts/resume.mjs` as soon as canonical status permits the action. Its caller at line 2189 handles `UserPromptSubmit`. Writer reservation is collected by the separate `writer-isolation` feedback boundary; this path does not call it. `activeGateWriteRefusal`, called near the top of `evaluateHarnessHook`, returns immediately unless the event is `PreToolUse` (line 2018). The directly spawned lifecycle child does not generate an agent tool event.

I reproduced both consequences using actual generated hooks and the current, unmodified `scripts/resume.mjs` and supporting modules in two synthetic repositories. Their control histories contain `WorkOrderActivated` and `ImplementationReady`, so `verify` is legally available. The first has a foreign writer reservation whose owner is the live probe process; the second has a live `beginGateRun` marker. Before each prompt, the corresponding generated pre-tool hook rejects `npm run resume -- verify` and leaves the history unchanged. Sending `resume: verify` through the generated session hook then succeeds:

| Existing condition | Ordinary command | Prompt blocked | Events before → after | Resulting phase |
| --- | --- | --- | --- | --- |
| Another live session owns the writer | denied | false | 2 → 3 | verifying |
| An evidence gate is active | denied | false | 2 → 3 | verifying |

In the first case the foreign reservation still belongs to the original owner after the append. In the second the gate marker remains active. The real command appends `VerificationRequested`, allocates a report and refreshes the control projection; these are candidate-tree mutations, not merely a misleading briefing. The probe asserts each result and exits 0 only when the defect is reproduced. The executable reproduction is retained below.

**Expected.** A prompt-triggered mutation must meet the same existing effect preconditions as the command it replaces. A live foreign writer or active gate must prevent the dispatch before any checkpoint, lifecycle event or candidate projection changes. An uncontended legal prompt should continue to record once and deliver its briefing; repeated or illegal prompts should preserve D011's documented behavior.

**Reach and severity.** A second session can change lifecycle state and checkpoint another session's work before its first tool call is refused. A prompt can also invalidate an in-flight evidence subject, recreating the repeated-gate cost this work is intended to remove. No user-data loss or false passing application aggregate was demonstrated, and none is claimed. The bypass itself is reproducible with the public host APIs and ordinary supported prompt. It violates an existing execution invariant and is blocking even though the current positive dispatch fixture passes.

**Repair direction.** Apply the existing writer and active-gate admission to the effectful prompt-dispatch path before invoking the lifecycle. Preserve the same-session, already-recorded and read-only paths. Extend the dispatch fixture with a live foreign reservation and a live gate, asserting refusal and byte-identical control/checkpoint state. Do not solve this by weakening the ordinary guards or discarding D011's automatic-dispatch behavior. The executor owns the repair and its exact design.

**Reopening condition.** Close F1 when both guarded cases refuse without mutations, the uncontended dispatch still records exactly once, and the relevant generated-hook tests pass at the repaired source. This report does not require a new approval mechanism or a new control layer.
