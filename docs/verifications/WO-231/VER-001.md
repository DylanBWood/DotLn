## Findings

- **F1 — follow-up (diagnostics; operator flow).** When `refs/remotes/origin/<baseBranch>` is present, the refusal never names it, its commit or the remedy. A stale ref (probe A) or unrelated history (probe D) yields a refusal that looks exactly like a run without the change. A ref that resolves to a tree is reported as "absent" (probe C). The order's Known issues expect the remedy (fetch, then retry) to be visible. Repair rule: when the ref is present, the refusal names it and its commit. When the ref is present but unusable, the refusal says why instead of "absent". When the described base is the activation base while the ref is present, the refusal names the remedy: fetch the base branch in the target clone and retry. Each gets a case. Boarded as [WO-231-D006](../../evidence/WO-231/decisions.md#wo-231-d006--ver-001-boards-the-unnamed-tracking-ref-and-corrects-the-no-fetch-rationale) (`FUP-e4fa2bbf7c3968ec`), which also records the rationale correction receipt 055 assigned to this order's decisions. It is not blocking because criterion 3 is met as written and the stale-ref fallback is conservative.
- **F2 — follow-up (correctness at the review gate; receipt 055 criterion 4).** A tracking ref moved onto the subject empties the described range. `final-review-result pass` then records `FinalReviewCompleted` and closes the order over an order commit it never linted (probe B). The untouched-ref control refuses that commit. The publish backstop holds: its lane-fetched lint refuses the commit and opens no pull request. But the closed order's reviewed commit cannot be published without a new commit. Repair rule: a range the clone's ref empties must not pass silently. When the subject is reachable from the ref, lint from the activation base, and print the linted-range sentence on a pass as well as on a refusal, with the moved-ref case and its control. Boarded as [WO-231-D005](../../evidence/WO-231/decisions.md#wo-231-d005--ver-001-boards-a-review-range-a-moved-tracking-ref-can-empty) (`FUP-378c5638bf515e52`). It is not blocking for two reasons. The order's own rule makes the clone's ref the selector, and its non-goals exclude a fetch at review, so the change from `main`'s always-activation range is the specified behaviour and not an unordered regression. The precondition is also a locally moved ref, which receipt 055's reopening condition names. WO-226-D021 is the precedent for routing a design-replaced behaviour this way. A reviewer who reads the moved-ref pass as a regression of `main` should weigh probe B against that reasoning.
