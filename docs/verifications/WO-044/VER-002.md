## Findings

### F1 — Medium: the skeleton declares a compiler version the workspace no longer contains

`packages/skeleton/package.json:17` still pins `"@dotln/compiler": "0.9.2"`
while `packages/compiler/package.json` is now `0.9.3` (D010). The declaration is
false: skeleton 0.15.12 is built and tested against compiler 0.9.3. `npm ls` in
this worktree exits `ELSPROBLEMS` and reports
`@dotln/compiler@0.9.3 deduped invalid: "0.9.2" from packages/skeleton`; at
`HEAD` the same pair is coherent (compiler 0.9.2, pin 0.9.2) and the immediately
preceding release bump, `71beba3`, moved the pin and the component version in
the same change. `package-lock.json:100` mirrors the stale pin, so the lockfile
is self-consistent and hides the drift; `scripts/release.mjs` checks only that a
component whose `src` changed carries a new version, so no preflight sees it,
and the full gate passes over it. The false declaration would be carried into
the v0.17.7 release manifest, which records component versions from these
manifests.

Expected: the cross-package pin follows the component bump D010 already claims
for "package manifests, lockfile entries and the pinned version literals" —
`packages/skeleton/package.json:17` and `package-lock.json:100` at `0.9.3` — or
a recorded decision states why skeleton declares an older compiler than the one
it is built against. No other cross-package pin is affected: `@dotln/kernel`
stays at `0.2.1`, which matches the unchanged kernel manifest. Reproduction was
`npm ls` plus manifest and history reads; nothing was installed or modified.

### F2 — Medium: the process-debt suite's green is nondeterministic, decided by git's detached auto-gc

Two checks recorded by this verification disagree at bytes that differ only in
`docs/`:

| Recorded | Tree | `suite:process-debt` |
| --- | --- | --- |
| 2026-09-14T23:03:17Z, `node scripts/test-runner.mjs --only process-debt` | `157f9cc5` | exit 1 |
| 2026-09-14T23:16:45Z, the full gate | `f3925b2b` | exit 0 |

The failing row is `session outputs include only two observed edits; generated
and oversized files owe checks`. Its body passes; the failure is
`failureType: hookFailed` in the shared fixture teardown at
`scripts/test-process-debt.mjs:162`, where `rmSync(root, {recursive, force})`
throws `ENOTEMPTY` on the fixture's `.git`. The residue left behind is exactly
`.git/info/refs` and `.git/objects/info/packs`: a detached `git gc` recreates
them after rimraf has already walked those directories. Node's `rmSync` does no
retry unless `maxRetries` is set, so the collection's timing decides the
result.

Observed four times without any override before the gate run — twice with
`node --test scripts/test-process-debt.mjs`, once with `--test-name-pattern`
isolating the single test, and once through the canonical gate path inside its
own replica and temporary directory. The mechanism is established by two
controls: the same isolated test passes with `gc.auto=0` and passes again with
`gc.autoDetach=false`, which makes the same collection run synchronously. It is
not a generic property of this host: a probe that creates a fixture repository,
writes 1, 10, 40 and 120 files, commits and immediately removes it saw 0 of 20
cleanups fail.

The failing test and the `repo()` teardown are not changed by this order, so
this is pre-existing code, not a regression introduced here. It is filed as a
finding rather than a queue item because this order's amendments are the gate's
own reliability contract — D011's self-stop, F3's cancellation, criterion 9's
reuse — and a suite that records exit 0 or exit 1 from the same bytes
depending on background collection timing defeats all three: a reused success
can be a coin flip that landed heads. Expected: the fixture teardown completes
regardless of git's default background maintenance — a bounded `maxRetries` and
`retryDelay` on the owned fixture removal, or `gc.auto=0` in the fixture's own
repository config — so the suite's result is decided by its assertions. No
process outside the fixtures was signalled and no suite was edited.

## Judgment and limits

The intended contribution is empirical harness truth for WO-049, WO-051 and
WO-068 plus dependable release-close teardown, and the eight VER-001 findings
are genuinely repaired — every counterexample I could reproduce is rejected at
these bytes. Fail-and-repair still beats pass because F1 is a false component
declaration that the gate structurally cannot see and that a tag would make
permanent, and its repair is two lines. Naive Interventionism argues against
editing either file myself; a verifier that repairs its own subject cannot
verify it. Policy resistance and shifting the burden would both show up as
letting a recorded green stand over a reproduction, or as charging my own
sandbox's temp-file failure to the executor; correctness over sycophancy
requires naming which is which, so the sandbox failure is disclosed and not
counted, criterion 8 is recorded green on its own terms, and the verdict rests
on F1 — the one defect no gate reads. Commons cost is the reason F2 is filed
with its mechanism and its two controls rather than with another sweep of the
suite.

Two observations for the next planning pass, neither charged to this order.

First, process cost on the fail path. The reuse repair does work: the three
gates here ran 82 fresh / 0 reused, 18 fresh / 64 reused and 17 fresh / 65
reused, at 595 s, 77 s and 67 s. The cold run followed a rebuild of the
installed roots; once only this report changed, reuse held. So the executor's
recorded cost finding is narrower than stated — the cost concentrates in runs
that touch `scripts/` or rebuild, not in every gate. What is not narrow is the
fail path: `scripts/lib/lifecycle-evidence.mjs:38` requires only
`git diff --check` for a failing verdict, but `runHarnessEvidenceChecks` runs
`npm run test:full` first, unconditionally, and `harness evidence accepts no
overrides` — so a failing verification runs the whole suite set to reach a
126 ms check that is the only one its own contract asks for, and runs it again
for every correction to the report. The two modules agree on what a failure
needs and are not connected.

Second, the operator recovery control does not reach this gate. `CLAUDE.md` and
product 07 state that `operator override:` suspends DotLn gates for authorized
recovery "despite repo/harness failures", and the prompt hook confirms hook
enforcement is suspended, but `requireLifecycleEvidence` reads no operator
control and refused `verification-result` while an override was open. An
operator who opens the documented recovery control to file a blocked verdict
still cannot file it. Observed directly in this verification, at
`scripts/lib/lifecycle-evidence.mjs:23-45`.

Recorded live while filing this report, as further evidence for D011: an
in-flight gate was ended from this session with
`node scripts/harness.mjs evidence --stop`, which stopped all four gate
processes and recorded no check, and the guard refused the same command when it
was joined to a `cd` prefix.
