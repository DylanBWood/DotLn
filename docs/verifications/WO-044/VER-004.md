## Blocking finding

### F1 — Medium: the prepared release block declares components this release does not ship

`README.md:87`, inside `<!-- DOTLN-RELEASE-BEGIN -->` … `<!-- DOTLN-RELEASE-END -->`,
states "This source prepares DotLn `v0.17.7`. … Compiler `0.9.2` and skeleton
`0.15.11` lower the [Contributor build] into project permissions, hooks and role
skills." This tree ships compiler **0.9.3** (`packages/compiler/package.json:3`,
`COMPILER_PACKAGE_VERSION` at `packages/compiler/src/artifact-identity.ts:15`)
and skeleton **0.15.12** (`packages/skeleton/package.json`), and its own
generated `.claude/harness-manifest.json` records `compilerPackageVersion`
`0.9.3` and `skeletonVersion` `0.15.12` for both installed profiles. The block
therefore contradicts the tree it describes, and it is the surface a v0.17.7 tag
makes permanent.

That line is this order's own edit: `git diff main -- README.md` is exactly one
changed line, moving the prepared target from `v0.17.6` to `v0.17.7` while
leaving the component pair untouched. Product 07 (`docs/product/07-execution-guide.md:959-964`)
states that updating the root README release block to the target "is an executor
deliverable, not a post-tag repair" and that "the README block must match release
truth". The three preceding preparations kept that pair equal to the shipped
components — v0.17.3 `0.9.1`/`0.15.3`, v0.17.4 `0.9.1`/`0.15.4`, v0.17.5
`0.9.1`/`0.15.8`, and `main`/v0.17.6 `0.9.2`/`0.15.11`, the last confirmed by
WO-131's FINAL-001 ("the application target remains v0.17.6, with compiler 0.9.2
and skeleton 0.15.11").

No check reads it. `releaseBlockRule` (`scripts/release.mjs:395-448`) validates
only that the block carries exactly one strict version equal to the target, and
`strictVersionsIn` (`scripts/lib/release-records.mjs:11-16`) matches only
`v`-prefixed forms, so the bare `0.9.2` and `0.15.11` are invisible to it;
`componentVersionRules` (`scripts/release.mjs:450-525`) reads package manifests
and the previous tag's manifest, never README prose. `npm run release -- prepare
--local`, `check-surfaces` and the full gate all pass over the false pair. This
is the same class as VER-002 F1 — a component declaration that is wrong in a way
no gate can see — at a different surface, and the same class the operator chose
to repair there (D013).

Expected: the release block names compiler `0.9.3` and skeleton `0.15.12`, or a
recorded decision states why the prepared release describes older components.
Reproduction was manifest and manifest-pin reads, `git diff main -- README.md`,
and `git show <prior release commit>:README.md` for the convention; nothing was
installed or modified. A repository-wide scan found no other live surface
carrying the stale pair — the remaining `0.15.11`/`0.9.2` occurrences are
WO-131's immutable evidence, verifications, final review and decision rows, which
are correctly frozen. Reopen F1 when the block names the shipped components or a
decision records the divergence.

## Judgment and limits

The order's contribution is empirical harness truth for WO-049, WO-051 and
WO-068 plus a dependable release-close and gate path, and that work stands: the
33-row record is reproducibly derived from its runs and honestly labelled, every
VER-001, VER-002 and VER-003 finding is repaired at these bytes, and the newest
repair is the smallest one that could fix its defect. F1 is not a request for
more support and does not reopen any closed question; it is one false sentence
on the release surface, created by this order's own edit to that line, that
`npm run release -- prepare --local` and the full gate structurally cannot see.
Passing it would certify a v0.17.7 tag whose public description names the
components of v0.17.6 — the same trade the operator already declined at VER-002
F1, so consistency, not novelty, decides it. Naive Interventionism argues
against editing the line myself: a verifier that repairs its own subject cannot
verify it, and the fix is two tokens for the executor. Shifting the burden would
be passing it for the reviewer to notice, in a role whose gates do not read that
prose either. Commons cost favours one bounded finding and the cheap fail
receipt this order itself shipped over another sweep of already-verified ground.

Carried forward, not re-litigated: VER-003's two disclosed nonblocking limits —
distinct nested repositories retained at the same path merge as directories, and
the concurrency row's phrasing under a synthetic launch error. Both remain
disclosed in VER-003; in the filed record all three concurrent launches
succeeded, so that row's text is supported by its own data. C-U4's blocker text
is terse but consistent with the evidence README's fuller reason.

Bounds on this verdict: no live provider launch, authentication-lifetime,
scheduler or effective-effort observation was rerun — the retained field shapes
and their stated labels bound that part. Criteria 9–12 rest on the source I read
plus the fixtures I executed, not on a second full-gate sweep. The full suite set
was not re-executed here: a failing verification owes only `git diff --check`
under `lifecycleRequiredChecks`, the contract this order shipped, and the
executor's own green `npm run test:full` at tree `7294aea5` (648.4 s) remains the
recorded application evidence for the code, which differs from this tree only by
this dispatch's control event, the refreshed work-order index and this report.
