## Findings

### F1 — background shell tasks are never journaled at dispatch, so the block reports their dispatch time and elapsed as unknown (non-blocking; recorded for planning, not routed to repair)

The objective's clause (a) asks for "the dispatch time and elapsed time of every
background task the session started". `observeBackgroundTool`
(`packages/skeleton/src/observed-facts.ts:100`) treats a call as a dispatch only
when the tool is `Agent`, `Task` or `spawn_agent`; any other tool is kept only
when it is `TaskOutput`, `TaskStop`, `wait_agent` or `close_agent`, and
everything else returns `null`. A `Bash` call with `run_in_background: true`
matches neither branch, so its `PostToolUse` — which fires at dispatch, while
the task id and the clock are both in hand — journals nothing.

Reproduced against the built runtime:

```
F2 background Bash dispatch NOT observed   observeBackgroundTool("Bash",
  {run_in_background: true, command: "npm test"}, {task_id: "bw1", status: "running"}) → null
F3 TaskOutput yields a task row with no dispatch time → ["completed", null]
F1 agent dispatch observed → dispatchedAt 2026-09-17T14:06:00.000Z
```

Observed end to end in this session, which started three background tasks — two
background shell gates and one agent. This session's journal holds exactly
this:

```
21:15:43.993Z tool=TaskOutput {"state":"completed","observedAt":"21:15:43.993Z"}
21:16:24.989Z tool=Agent      {"state":"dispatched","dispatchedAt":"21:16:24.989Z", …}
21:21:47.292Z tool=TaskOutput {"state":"completed","observedAt":"21:21:47.292Z"}
```

and the block that reached me at the next boundary therefore read:

```
task 1: dispatched unknown (dispatch-unavailable); … elapsed since dispatch unknown (dispatch-unavailable) ms
task 2: dispatched 2026-09-17T21:16:24.989Z; … elapsed since dispatch 322443 ms
task 3: dispatched unknown (dispatch-unavailable); … elapsed since dispatch unknown (dispatch-unavailable) ms
```

The two shell gates appear at all only because I happened to call `TaskOutput`
on them. Had I waited for their completion notifications instead, the session
would have started three background tasks and the block would have named one.

Why this is recorded and not routed to repair: no numbered criterion is
breached. Criterion 1 requires the block to print from a fixture journal and to
print `unknown` with a cause code where a value is missing, and it does both,
here included — the mechanism reports what it did not observe and invents
nothing, which is the rule the order exists to enforce. The executor also
disclosed the boundary in the implementation evidence ("Unsupported or absent
task metadata is unknown"), and the order's motivating incident was an agent
dispatch, which is covered.

Why it still matters: the order's purpose is that "the agent has the value and
nothing to estimate". For the background task this harness produces most often,
the agent has nothing, and an agent that wants to state how long its own gate
has been running is back where the order started — with the honest option of
saying `unknown`, but without the measurement. Two of this session's three
background tasks were in that position.

Repair shape, if planning wants it: admit `Bash` into the dispatch branch when
`input.run_in_background === true`, keyed on the task id the tool response
already returns; the identifier is hashed on the way in, so nothing new is
retained. A regression that dispatches a background shell task and expects a
`dispatchedAt` would pin it.

## Observations

**O1 — the Stop surface did not fire once on its own in this session, so the
usage half of the block was unknown at every boundary.** Across every journal in
this worktree there was no `finished` row until I wrote one by invoking the hook
directly; my writer reservation also sat unchanged from session start at
`21:09:25.305Z` until that invocation moved it, and the Stop path releases and
re-acquires the reservation on every pass. The consequence is specific: usage
counters are recorded by `measureHarnessSessionUsage` in the Stop path, so the
observed-facts block reached me with `inputTokens unknown
(counter-unavailable) … source unavailable` at every boundary of this session.
Invoking the generated hook by hand produced them immediately — `inputTokens
158; cachedInputTokens 4962777; cacheWriteInputTokens 205212; outputTokens
40416; totalTokens 5208563; source claude-transcript-message-usage; scope
dispatch; cutoff 2026-09-17T21:24:36.354Z`. This is host behaviour and not a
WO-141 defect: the hook is correctly wired in `.claude/settings.json`, the
generated file carries `const event = "Stop"`, and when it runs it does exactly
what the order specifies. It is recorded because it decides how much of this
order actually reaches an agent in this host today: the facts block does, via
the prompt-submit surface; the hedge advisory, which is journaled only at Stop,
does not.

**O2 — in Claude the briefing prints a second, contradictory facts line.**
`observedFactsReport` (`scripts/lib/harness-runtime.mjs:93`) returns
`Observed facts at <now>: unknown (session-identity-unavailable).` whenever
`CODEX_THREAD_ID` is absent, and `scripts/resume.mjs` appends that line to every
action outside `status`, `times` and `usage`. In Claude the session hook then
prepends the real block, so the agent's first prompt of a dispatch reads:

```
Observed facts at 2026-09-17T21:09:26.346Z: unknown (session-identity-unavailable).
Observed facts at 2026-09-17T21:09:26.745Z (session journal and gate rows):
task 1: …
```

Both lines are true of their own source and nothing is invented, so no criterion
is breached. But an order whose objective is that the agent "has the value and
nothing to estimate" opens its briefing by declaring the value unknown, 399 ms
before supplying it. Naming the harness in the cause, or skipping the line when
a hook will supply the block, would remove the contradiction.

**O3 — a task that completes by notification keeps a growing elapsed counter
against a stale state.** State is only ever updated by a later `TaskOutput` or
`TaskStop` call, so this session's agent task still read `last observed state
dispatched; elapsed since dispatch 495521 ms` when the agent had finished
minutes earlier. The label is literally correct and the executor disclosed it
("Task state is the last recorded observation, not a liveness probe"), but
`dispatched` plus a large elapsed value reads as a task still running.

**O4 — a hedge marker set off by commas escapes the scan.** `scanHedges` splits
clauses on `,(?!\d)`, so "It was dispatched, probably, 10 minutes ago" puts the
marker in a clause of its own with no quantity and journals nothing, while "It
was dispatched probably 10 minutes ago" is caught. This is inside the order as
written — the design scopes the rule to "a marker within one clause of a
number" — and the executor's special case for a trailing ", probably" shows the
boundary was considered. It under-counts rather than misattributing, which is
the safe direction. Recorded because the counter is a measurement instrument and
its floor should be known.

**O5 — background-task rows are not self-describing.** The `PostToolUse` path
merges the observation into `record()` rather than `appendObservation`, so those
rows carry no `workOrder` and no `phase`; all three in this session read
`undefined` for both. The meter's filter falls back to the session state for
rows without the key, so the count is unaffected, and correction and hedge rows
— the only rows the counter reads — do carry both fields. The rows are simply
less useful on their own than the ones written through the journal helper.
