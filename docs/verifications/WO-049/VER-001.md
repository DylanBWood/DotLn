## Findings

### F1 — `remove --target` destroys pre-existing content in the target's `info/exclude` (blocking; criterion 3)

When the target's `info/exclude` is non-empty and lacks a final newline at first
emit, `emit` correctly adds a separator newline — but it places that newline
**inside** the managed block, and `remove` then deletes the block by naive
substring replacement, taking the separator with it regardless of what now
follows.

`scripts/lib/harness.mjs:549` captures `needsNewline` once, at registry
creation. `:569-571` builds the block as
`` `${registry.needsNewline ? "\n" : ""}${marker} begin\n…${marker} end\n` ``.
`:572-574` rewrites with `contents.replace(registry.block, nextBlock)`, where
`nextBlock` is `""` on removal. `:553-554`'s drift guard is only
`contents.includes(registry.block)`, which an append after the block does not
break, so nothing refuses first.

Reproduced end to end:

```
$ printf '# my own rule, no trailing newline' > <target>/.git/info/exclude
$ node scripts/harness.mjs emit --target <target> --runtime-root .
$ printf '/my-build-output/\n' >> <target>/.git/info/exclude
$ node scripts/harness.mjs remove --target <target> --runtime-root .
harness remove: 6 target surfaces
$ cat <target>/.git/info/exclude
# my own rule, no trailing newline/my-build-output/
```

The two lines are joined. The consequence is the one the order exists to
prevent, inflicted on the user's own content rather than the bundle's:

```
$ mkdir my-build-output && echo artifact > my-build-output/bundle.js
$ git status --porcelain
?? my-build-output/
```

The user's ignore rule is gone, so a `git add -A` in the target now stages
output it previously ignored. Removal reports success throughout.

**Second manifestation, same root cause.** Because the block is located by
substring rather than by its markers, a duplicated exclude file is not drift and
`String.prototype.replace` with a string pattern rewrites only the first match:

```
$ cat exclude exclude > exclude       # two identical managed blocks
$ node scripts/harness.mjs check --target …   → harness check: 6 target surfaces
$ node scripts/harness.mjs remove --target …  → harness remove: 6 target surfaces
$ grep -c 'target-worker .* begin' exclude → 1
```

`remove` reports success and leaves a complete managed block — every bundle
exclude line still present — which is the opposite failure of the first case and
equally a breach of "deletes exactly the manifest-listed … exclude lines".

Why it routes to repair: it fails a numbered criterion, it is reachable through
the documented CLI with no unusual flags, it destroys content in a repository
the order promises to leave untouched apart from the bundle, and it is silent.
The executor's own fixture seeds precisely the no-final-newline case at
`scripts/test-target-harness.mjs:134` and asserts byte-exact restoration at
`:187`, so the gap is not the scenario but the absence of any append after the
block. Nothing in D001–D006 or `implementation.md` records this as accepted; on
the contrary `implementation.md` claims "Original unrelated exclude content is
preserved in place", which these two runs falsify.

A repair should locate the block by its `begin`/`end` markers rather than by
substring identity, and should restore the original trailing-newline state only
when the block is still at end of file. Both manifestations then fall to one
change. Regression coverage should append a line after the block before
removing, and should duplicate the exclude file.

### F2 — the target profile's attribution pre-check can never decide a commit (no criterion; recorded, not routed)

The Design bullet commits the profile to "the attribution pre-check on commit
commands", and the Non-goals exclude "a `.git/hooks` commit-message install in
the target" on the stated ground that "attribution is the `PreToolUse`
commit-command check". Both hooks are registered under the same `.*` matcher, so
Claude Code denies if either denies — and the permission guard denies every
`git` invocation before attribution is reached:

```
permissions.mjs   ← git commit -m 'A plain message'
  deny: target shell destinations unavailable; host must run opaque commands
no-attribution.mjs ← same command
  {}
permissions.mjs   ← git status
  deny: target shell destinations unavailable; host must run opaque commands
```

`shellWritePaths` returns `null` for any program outside its read-only
allowlist, and `packages/skeleton/src/harness-host.ts:3235-3238` turns that into
a refusal. So no commit can reach the attribution check through the guarded
shell tool, and the Non-goals' rationale for omitting a commit-message hook does
not hold as stated.

Not routed to repair: no acceptance criterion tests attribution, the delivered
behaviour is disclosed accurately in `packages/skeleton/README.md` ("Opaque
shell commands, including test scripts and Git commits, need a host route; this
profile does not claim universal shell containment"), and the alternatives —
widening the shell classifier or dropping the guard — are design changes beyond
this order. Recorded so the reviewer and the planner can decide deliberately,
and so WO-051's host route is specified knowing attribution currently rides on
it.

### F4 — a backslash in the import root passes validation and produces an unloadable URL (minor)

`packages/compiler/src/harness.ts:251-259` accepts any absolute path without
`.`/`..` segments or control characters. `importURL` at `:889` encodes each
segment with `encodeURIComponent`, turning a literal backslash — legal in a
POSIX path — into `%5C`, which Node's ESM resolver rejects:

```
importRoot: "/tmp/back\\slash"
accepted by assertHarnessProfile validation: true
generated import URL: file:///tmp/back%5Cslash/snap/mod.js
import FAILED: ERR_INVALID_MODULE_SPECIFIER
```

Every hook invocation would then fall into the prelude's catch and deny with
"pinned launchpad runtime unavailable", which is fail-closed and therefore not a
containment hole, but is a misdiagnosis: the runtime is present. The compiler
fixture covers a space, `#` and non-ASCII in the import root but not a
backslash. Minor because it needs a launchpad path containing a backslash.

## Observations

**O1 — a pre-existing user exclude line makes the bundle's invisibility depend
on a line the tool does not own, and that is handled correctly.** If the user
already excludes `/CLAUDE.local.md` before the first emit,
`scripts/lib/harness.mjs:542-548` records it as an original line and
`:564-567` keeps it out of the managed block forever. If the user later deletes
their own line, the installed bundle becomes Git-visible. This is detected and
fails closed: `check --target` refuses with `target exclude missing:
CLAUDE.local.md` — the dedicated refusal at `:693-694` — and a fresh `emit
--target` refuses the same way rather than reporting success. I raise it as an
observation because the trigger is the user deleting their own line and the tool
never lies about the result.

**O2 — a bundle-shaped line the user adds after a remove/re-emit cycle is
duplicated.** `originalLines` is computed only when the registry file does not
yet exist (`:539-552`), and `writeTargetExclude` recreates the registry on every
mutation including removal, so the baseline never refreshes. After
emit → remove → user adds `/CLAUDE.local.md` → emit, the file carries two
identical anchored lines. Harmless: duplicate Git ignore rules are legal,
`check` passes, and `remove` restores the user's line correctly. It is not a
criterion-1 breach, because criterion 1 describes a fresh scratch repository.

**O3 — removal leaves empty directories.** `removeTargetUnlocked` unlinks files
only (`:725`), so `.claude/hooks/` survives a removal that created it. Git does
not track empty directories, `git status` stays clean, and
`packages/skeleton/README.md` discloses "Empty target directories may remain".

**O4 — criterion 1's missing-exclude-line fixture is caught by the coarse
guard.** `scripts/test-target-harness.mjs:182` deletes a line from inside the
managed block, so `excludeRegistry`'s block-drift throw fires before the
per-file check; the assertion's `/exclude/` regex cannot distinguish them. The
behaviour the criterion asks for — a refusal — is correct either way, and the
per-file branch is reachable (I reached it in O1), but no fixture covers it.

**O5 — criterion 2's `feedbackBoundary` comparison is direct only for the
feedback units.** The fixture compares the hook's decisions against the
criterion's enumerated expectations and separately exercises `feedbackBoundary`
on writer-isolation facts at `:245-269`. The permission guard's decisions do not
route through `feedbackBoundary` at all — they go through `harnessAuthorization`
and `protect()` — so for two of the three enumerated cases the literal phrasing
has no corresponding call. I verified the enumerated decisions themselves
directly, which is what the criterion is for.

**O6 — the Codex smoke's `hookEvents: 0` cannot fail.** `hooks` counts rows in
the launchpad journal (`scripts/target-worker-smoke.mjs:148-156, 176`), and only
a generated hook file writes those rows; the Codex profile emits none. The
measurement is structurally incapable of a non-zero result, so it confirms
rather than tests. The "no Codex hook event" claim properly rests on discovery
rows X-W3, X-W4 and X-W10, which do exist and do say that.

**O7 — a non-canonical path denies, fail-closed.** On macOS a payload whose

`settings.user` and denies, because `permissionEffect` compares against

the Contributor bundle, and not a WO-049 regression — recorded because it will

changed: compiler `0.11.2`→`0.12.0`, skeleton `0.19.0`→`0.20.0`, snapshot
