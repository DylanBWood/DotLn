# WO-135

Twice in two days a work order that added a capability row could not merge cleanly: the planning gate refused the new id as a planning claim, each final review found the document gate red, and each was cleared by a purpose-built planning pass and a refutation dispatch after the review had already passed. This work order removes that class of rescue and closes two neighbouring gaps the same passes exposed. An appended `## WO-NNN dated addition` or `dated reassessment` section is now an execution update whenever the order is in the judged sequence, whether or not its capability ids are already known; a new id is reported as `dated-capability-addition`, and its level claim is judged by the order's verification, its final review and the next planning receipt, never by a planning dispatch after a final review. Both public gates, `plan check` and `work-orders index --check`, now read the typed dependency blocks against the committed sequence and refuse an order that precedes an order it depends on through an unmet blocking edge, or a two-entry lane pair that contains one, naming the orders and the edge; the 2026-09-16 sequence carried two such reversals that a receipt had judged aligned. And on a `planning/` branch the generated Claude hooks refuse a classified tool write to a repository path outside `docs/` and root Markdown, naming the path and the `operator override:` route, so a document-only dispatch can no longer carry source onto `main` and void a reviewed gate.

What it changes for a reader: a capability write-back is no longer a merge prerequisite that waits on a planning chore; the sequence is checked against every typed hard edge instead of a hand-run script; and DotLn has three hook refusals rather than two, with the compiled instruction, every role skill, product 07 and the security runbook saying so. The refusal classifies known tool destinations only, so an opaque shell program stays host-delegated; this is a classified-effect boundary, not an operating-system sandbox, and the runbook says which is which.

**What the fixtures pin.** The real WO-068 `runtime.resident` and WO-052 `worker.source-change` sections are replayed against the receipts that preceded their purpose-built passes, receipts 014 and 015, and are admitted as additions with the judged subjects byte-identical before and after; an unknown order, an invalid date, a stray heading and an empty observation cell still refuse with the unchanged messages. The 2026-09-16 sequence is frozen with its control sources so a future close cannot erase the two named reversals, and both gates refuse it; the corrected 2026-09-17 sequence is pinned as fourteen pairs and one serial run, sensitive to a lost or added blank separator, and the current fifteen-pair sequence passes. The harness fixture drives three generated hooks on a `planning/` branch over nine denied and thirteen admitted requests, including physical aliases through `docs/` symlinks, `rm` and `touch -h` no-follow semantics, an out-of-repository scratch path and the override on and off.

**What the diff contains.** One widened form in `reassessments` and a forty-line `checkSequenceTopology` shared by both gates; `planningWriteRefusal` in the harness host with `shellWriteTargets` carrying per-path follow semantics; five planning fixtures, one harness fixture and four compiler assertions; the three-refusal instruction sentence compiled into `CLAUDE.md`, `AGENTS.md` and all twelve role skills; the write-backs to product 07, the security runbook, the planning map and the decisions record; compiler `0.13.1` and skeleton `0.25.3` with the regenerated bundle pins, console fixtures and fresh WO-135 evidence editions; and, under the operator's expanded scope, a rewrite of `docs/AI-HARNESS-SECURITY.md` recording both harnesses' current modes and settings locations, with the personal SSH/SCP/SFTP rules it describes installed outside the repository. No dependency changes; `package-lock.json` moves only the three workspace version strings.

**Validation.** `npm test -- --review` passed 29 suites with 0 failures in 1063.57 s, exit 0, 73 fresh tasks, for tree `e1df1a9a` at code identity `34cc85aa`, recorded `2026-09-18T01:31:45.851Z`; the review selection included the `harness-fixtures`, `plan-refutation`, `work-orders-fixtures`, `process-debt`, `compiler` and `skeleton` suites this diff's sources select. `npm run test:docs` on the integrated tree passes 15 of 17 limbs; the two red limbs, `plan` and `plan-refutation-current`, carry the sibling's condition described under Integration, and VER-001's 17 of 17 on the pre-merge tree covers every document this order changes. `harness check` reports 28 generated surfaces, the console fixtures match, all four selected evidence editions verify, `npm run publication:check` reports both editions current, `npm run format:check` passes, and `git diff --check` and `git diff --cached --check` are clean. VER-001 passed all six criteria independently with its own `npm test` and `npm run test:docs` on the pre-merge tree; the [final review](FINAL-001.md) re-derived the topology, receipt-integrity, lockfile, hook-diff, suppression and clean-room claims on the integrated tree and judged the integration.

The branch was merged onto `f7ec9f3` with twenty-four conflicts, none in a source file; `npm run release -- prepare` against origin's tags retimed the target to `v0.29.4` under the existing patch classification, skeleton moved to `0.25.3`, and the two evidence editions the merge invalidated were re-recorded: authority `003` with a transcript byte-identical to `002`, and feedback `003` from a fresh live audit whose report differs from `002` in its source subject alone. One condition is documented, not raised: the document gate's `plan` limb is red on clean `main` because the merged sibling's order file changed a criterion no planning receipt judged; it is isolated in the final review with the enforcing line, blocks neither this PR nor its close, and needs a planning decision the operator owns.
