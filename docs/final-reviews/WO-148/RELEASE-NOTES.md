## Release overview

DotLn's resident can now be aimed at the order you are actually working with one command instead of a hand-written store. `node scripts/resident-bind.mjs WO-NNN`, given the declared surfaces, the transport, the model and the effort as flags, reads the canonical control state for the order, finds its worktree, pins the merge base and the contract, and writes a store whose `mission-check` actor watches that worktree; `--check` over a store refuses a launch line for any binding canonical state no longer matches, naming each mismatch. This release is for the operator who runs a resident beside daily work and for whoever plans the orders that extend absence work: it turns the mission check WO-099 delivered from a mechanism that needed a purpose-built store into one this repository runs on its own in-flight orders, and it did so on this order itself.

## Read before upgrading

No authority, gate, hook, schema, event or runtime changes, and no dependency is added. Three things need attention before the first bind. The store and its binding record carry physical worktree and store paths, so they may only be written where Git cannot see them: bind asks `git check-ignore` about both files before creating anything and refuses by name when either would be visible, which means a launchpad that has moved its control root under `dotln.config.json` must ignore its control root's `local/` lane itself before binding. The stale-binding refusal lives only in the command: a resident already running, a shell that still exports `DOTLN_RESIDENT_STORE` for an old store, or an outside scheduler keeps judging the subject it was declared with, so run `--check` before each launch and rebind after a phase, base or worktree change. No `claude-cli-print` mission check can run in this release, because the shared mission-check result schema emits duplicate `contract-clause` enum items and the Claude CLI refuses the schema before any model call; the defect is reproduced, boarded with a public follow-up for its own order, and the delivered live row used the `codex-cli-exec` transport, which is unaffected. Each bind also costs about 291 KB of ignored store, and retained stores are not pruned.

## Substantive changes

**Binding a resident to the active order.** The command reads canonical state in the order's own worktree (where an in-flight order's activation and transitions live before merge), locates the worktree by the branch the order names, takes the base commit as the merge base with `origin/main` or `main` (or the commit supplied with `--base` for an integrated sibling), and writes the control lane's `local/resident/WO-NNN-n/` directory holding `resident.json` and `binding.json` at mode 0600. The store's `MissionSource` names the worktree, the authority file, the decisions file when present, the base, exactly the declared surfaces, the vision document and its thesis headings; nothing is derived, and a bind with no surface refuses because the out-of-surface rule is only as good as the declaration. A rebind writes the next index and never edits an existing store, keeping configuration immutable within a store. Unknown, closed or worktree-less orders, unknown transports and non-repository-relative surfaces refuse by name.

**Checking a binding before a launch.** `--check` over a store decodes the store with the runtime's own decoder, compares the binding record's phase, worktree, base and contract bytes with canonical state, and compares every field of the store's declared source with the record (arrays element by element, an undeclared field named too). Every mismatch is printed, the exit code is non-zero and no launch or export line appears. A retained store that has been moved is accepted, and every printed command names the directory that was checked, with the bound path shown once as provenance. A merge base moved by integrating `main` is a named mismatch, and the next bind records the new base.

**Operator-presence policy and runbook.** Product 03 §Operator-presence policy states how a store is bound, what stays declared, what `--check` compares, the relocated-store behaviour and the Git question asked before writing; the skeleton README's resident runbook names the command as the ordinary path and keeps the hand-written store shape as the reference for every other policy.

**The live row.** `scripts/evidence-resident-binding.mjs` binds one real in-flight order, runs the shipped `dotln presence away` and `dotln resident --once` against the store from a detached child on the real clock (waiting out the 900 s Contributor cadence), and files a counts-only row: launch origin, transport, capsule path counts against the declared surfaces, base equality, verdict, hold and explicit limits, with no physical path or capsule text. The filed row for WO-148 records an actor-origin Codex CLI launch, 20 of 20 changed paths inside 15 declared surfaces, and a `drift` verdict whose two findings are explained in the implementation record.

Known limitations, each on the record. The stale-binding refusal is one-sided: only a launch line requested through the command is refused, and a resident already running keeps judging its declared subject until WO-111's evidence or the prune follow-up decides otherwise. Surfaces are typed by hand until WO-124 derives them. Only the Contributor build can be bound; any other loadout uses the hand-written shape. The `claude-cli-print` transport cannot run a mission check until the duplicate-enum follow-up lands. `git check-ignore` is the only authority bind trusts for the lane. The live row proves aim, not the work, and was not rerun after the repair, which changed no bind-time output except the pre-write refusal. A store bound from inside its worktree is preserved into `main`'s ignored lane by `worktree finish`; four such stores exist for this order.
