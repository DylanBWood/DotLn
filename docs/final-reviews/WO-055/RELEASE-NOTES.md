## Release overview

A failed verification can now produce its own next attempt. The skeleton gains a pure derivation, `deriveRepairOrder`, that turns a blocking finding into a bounded repair WorkOrder, and a `RepairHost` that dispatches it to a fresh source-change worker at the failed commit and re-verifies the result from the complete original contract. The loop stops at a declared round limit, two by default, with a terminal `RepairExhausted` event naming the last finding, and it survives a killed host without dispatching a second repair. In the recorded proof a planted defect is repaired in one round touching one file and re-verified green, and a worker that repairs wrongly twice is stopped before a third dispatch.

The audience is anyone running DotLn's source-change and verification hosts who has been carrying findings between them by hand. This is the fixture-level proof with synthetic repair and verifier workers over real scratch repositories on macOS; the live loop is WO-056.

## Read before upgrading

Application minor `v0.31.0` stages skeleton `0.27.0`. Compiler `0.14.0`, kernel `0.5.0` and console are unchanged, no dependency was added, and `package-lock.json` moves only the skeleton version string. Event schema 1 is unchanged; the repair event types are additive. No migration is required.

Authority: a repair never widens the original order. The derived order keeps the original effective envelope, operation lists, contract and base. A finding that names a path outside the original declared surfaces, or a reproduction that is not one of the original named test commands, yields `NeedsHuman` naming it, derives no order and dispatches nothing. The only expansion route is an exact scope grant with WO-042 provenance that matches a host registry record in full, names the repository, uses no wildcard and covers exactly the extra path or command; its id is recorded on the derived order and it cannot add an effect or operation. The registry is trusted host input and is not cryptographically authenticated, and the requested grants and the registry arrive in the same host options; the separation is from verifier output, which can never supply or select a grant.

One change reaches existing source-change writers: the writer prompt now lists the declared surfaces and instructs the worker to edit only those, where it previously said to edit only within the worktree mount. The host already refused a commit outside the declared surfaces, so admitted results do not change, but a live WO-052 or WO-053 worker now reads different instructions.

Repair surfaces include the failed criterion's cited test files, as the order specifies. A repair worker may therefore edit a named test that re-verification then runs. The contract and command names cannot change and the verifier sees test bytes in its diff, but treat a repair that touches its own tests with the same care as any other change to an oracle.

The round program's `Await` declares a 180-second timeout that the kernel does not evaluate; a stalled child is bounded by the existing source-change and verification host deadlines, leases and locks. Child stores, repair worktrees and verification copies are retained for inspection with no automatic cleanup.

## Substantive changes

- Repair derivation: `deriveRepairOrder(finding, original, grants)` is pure. Evidence ids resolve only against the failed subject's pinned witnesses with the same criterion and revision, and a failing host witness must match the finding's observed and expected text. Surfaces are the finding's likely surfaces plus those witnesses' code surfaces; tests are exact named commands resolved from the reproduction steps, with no prose-to-shell interpretation. The derived order carries the original contract and its equality hash, the finding, `round + 1`, the recorded grant ids and `executionBaseCommit`, and drops earlier worker facts and decisions.
- Refusals: no evidence references, an unknown or foreign reference, a non-blocking finding, an invalid or outside path, a command that is not an exact named test, an unadmitted, duplicate, broader or mismatched grant, and a reached or invalid round limit each return `NeedsHuman` with the offending input and a reason.
- Repair host: `RepairHost` runs a persisted executable program in the shared reactor, a `Sequence` of the repair `Invoke`, `Await(SourceChangeObserved)` and the verification `Invoke`, followed by `Guard` branches for success and the round limit. Opening and per-round programs are persisted and validated on replay; parent `RepairCommandPersisted` and `RepairCommandResult` events record orchestration ownership while child stores keep the worker outbox and immutable commit receipt.
- Execution baseline: the source-change host accepts an optional `executionBaseCommit`. A repair branches from the failed revision and its diff is measured from there, the original base must be an ancestor, and the WorkOrder's contract base is unchanged. The existing surface check applies to that repair diff.
- Re-verification: after the repair commit the host runs every derived reproduction command, refuses any that changes committed source, prepares a fresh WO-054 snapshot with the original contract, criteria and named tests, and gives each round a distinct verifier episode namespace. The reactor refuses a verification result whose capsule contract, criteria, tests, base or revision differ from the original's and the observed commit. Unverified evidence or an attention request yields `NeedsHuman`, never success.
- Recovery and termination: a committed child or a prepared snapshot is reused after host death; an interrupted, unpublished snapshot directory is preserved and a new attempt uses a fresh one. `repairNextAction` returns `human` for exhausted and needs-human states, `none` for completion and `run` while the program is active.
