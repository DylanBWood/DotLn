# WO-156

Every planning pass and every final review runs `npm run test:docs`, and its two plan tasks each cost about 25 s because `node scripts/refute-plan.mjs check` took 16 to 20 s: the subject builder rebuilt the work-order path pattern for every committed path of every sequenced order, and each rebuild re-read the launchpad configuration with a `statSync`, 3.9 million times per check. This pull request lands WO-156. The check now finishes in about 1.6 s on the operator's host ([VER-003](docs/verifications/WO-156/VER-003.md): 1.61 s against 18.04 s for the original modules on the same tree; this review: 1.54 to 1.60 s), `plan subject` in 0.10 s, and the two `test:docs` tasks in 1.90 s and 1.81 s. `plan subject` and `plan check` output is byte-identical to the original modules on the same tree, compared as buffers in every measured pair.

**What changed.** The subject builder resolves the configured work-order root once per call and compiles one expression per sequence id outside the committed-path filter; `loadConfig` and its per-call stat are untouched. The receipt reader reads every committed receipt's bytes in one `git cat-file --batch` per 32 objects instead of one launch per file, prefetches each receipt's subject sources into the existing bounded tree and blob caches, and reuses a tree only for a full id already resolved as a commit in the same root, so `HEAD`, branches, moved tags and annotated tags still resolve afresh and an edited committed receipt is still refused. A failed multi-object read splits until singletons, which still propagate. The pure NFKC/whitespace normalization used in receipt comparisons is memoized by exact input inside 512 entries and 1 MiB of string storage, with oversized inputs bypassed. Git launches per check fell from 242 to 104. The Git-launch reduction and the normalization cache are operator scope expansions recorded in [D005](docs/evidence/WO-156/decisions.md#wo-156-d005) and [D006](docs/evidence/WO-156/decisions.md#wo-156-d006) and bound in the planning log after [VER-001](docs/verifications/WO-156/VER-001.md) measured the hoist alone at 2.7 s against the order's 2 s bound.

**What a reviewer should know.** [VER-002](docs/verifications/WO-156/VER-002.md) met the timing and failed the order on two accepted-input regressions in the first batching repair: an unused legacy `work-order-map.md` symlink was rejected by the prefetch, and six individually readable receipts overflowed Git's shared 16 MiB output buffer in one batch. Both are fixed at source, each has a fixture that failed against the VER-002 bytes, and VER-003 reproduced both probes as accepted and passed all five criteria ([D009](docs/evidence/WO-156/decisions.md#wo-156-d009), [D010](docs/evidence/WO-156/decisions.md#wo-156-d010)). The 2 s bound is measured on the operator's host only, and the regressions bound stat calls, Git launches and normalization calls rather than wall-clock; the planning receipt that filed this order records both as reopening observations. `main` moved by WO-155 (`v0.46.1`) during the order; the review integrated it with one roadmap conflict and no source change, so the target is `v0.46.2` ([D011](docs/evidence/WO-156/decisions.md#wo-156-d011)).
