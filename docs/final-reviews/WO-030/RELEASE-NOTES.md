## Release overview

DotLn `v0.7.0` is the minor release above the published `v0.6.0`. The control plane now holds zero, one, or many in-flight work orders as independent lifecycles with attributable history. Each newly activated order owns one append-only JSONL segment at `docs/control/orders/WO-NNN.jsonl`; every order that was activated in the historical `docs/control/resume.jsonl`, including WO-030 itself, finishes there, so no recorded event moves and the control event schema stays `1`. Two orders can progress in two worktrees at the same time: a transition advances only its own order, the `wo-NNN` branch selects that order without a flag, `--work-order WO-NNN` selects explicitly on `main`, `status --json` keeps every selected-order field it had and adds an `orders[]` overview, and `docs/control/current.md` lists every in-flight order followed by the latest closed one. Merging one order into `main` cannot erase or reinterpret another's evidence: worktree finish, release close, release-note attribution, and the generated work-order index read committed segments and prove append-only byte prefixes per file, demonstrated in a real-Git fixture with three branches, serial merges, one order finished and released while a sibling stays open, and a third branch created before the first merge. Audience: the operator running the first paired wave of work orders, and every lifecycle peer that consumes control state. No exported runtime package changes; the walking skeleton and its component versions are unchanged. The order's two operator-authorized ideation breakouts ride along as documentation only: a candidate for whole-or-split work orders under one umbrella, and a candidate UIFA responsibility set for security, identity, logs, and traceability.

## Read before upgrading

- **New activations create `docs/control/orders/WO-NNN.jsonl`; historical events stay where they are.** `docs/control/resume.jsonl` is read first with its original global ordinals and is never rewritten; an order activated there keeps appending there until it closes, and reactivating a closed identity keeps its original file. A segment whose file name disagrees with its activation, that holds an event with another order's id, or that is empty refuses at fold with the path and ordinal, and no transition appends after such a refusal.
- **Every entry in `docs/control/orders/` must be a `WO-NNN.jsonl` segment.** Any other file or subdirectory there, including a Finder-created `.DS_Store`, makes every `resume` command, read-only `status` included, refuse with the offending path until it is removed. Git-revision views are unaffected because `.DS_Store` is ignored.
- **Selection is navigation, not lifecycle state.** In a `wo-NNN` worktree the branch selects `WO-NNN`; `--work-order WO-NNN` overrides it and is required on `main` when more than one order is open, where bare human `status` lists them while `status --json` and every transition refuse until the flag names one. An unknown id refuses and lists the open orders. On a `wo-NNN` branch, `activate` refuses a different id unless the flag names it. A `wo-NNN` branch whose order is not yet activated cannot run bare `status`; use `--work-order` on another order.
- **`status --json` adds `orders[]`; the selected-order fields are unchanged.** Each entry carries `workOrder`, `phase`, `latestVerdict`, `recordedAt`, and `elapsed`. Lifecycle peers still read only the JSON contract and never parse `current.md`.
- **`docs/control/current.md` changed shape.** It now renders one section per non-closed order, headed by the order id, followed by the latest closed one, chosen by Git integration order and never by wall-clock time. Regenerate a conflicted projection with `npm run resume -- next --work-order` naming a closed order and with `npm run work-orders -- index`; never union-merge, rewrite, or move control events.
- **`npm run resume --silent -- times` rows for segment events carry `segment` and a file-local ordinal.** Legacy rows and a legacy-only observation are byte-identical to the `v0.6.0` output.
- **`next` on a closed order names the other in-flight orders** and reports "between work orders" only when none remain; `release close` reports the same distinction after a merged close.
- **`worktree finish` now also requires the named order to be closed in the committed control state of `origin/main`.** A closed subject whose integrated order was reopened on `main` is preserved rather than removed.
- **The generated work-order index records each release tag's control segments** in its tag snapshot, and `index --check` refuses when a recorded tag's segment inventory differs from the tagged source; older snapshots without the field are accepted. Every non-closed order now appears under Active, and the `Now` line lists all of them.
- **Package TypeScript configs pin `"types": ["node"]`.** This is inert under the pinned TypeScript 5.4.5 because `@types/node` is the only installed `@types` package; it silences implicit-type errors the executor observed under TypeScript 7.0.2, which this repository does not install.

## Substantive changes

- **Control fold (`scripts/lib/control.mjs`).** `scanControl` keeps one state per `workOrderId`, so an activation or transition for one order cannot reset or capture another's phase, verdict, failure source, attestation, effort drift, or checkpoint; `fold` over a single order's events is unchanged and its phase table is unchanged. `foldSegments(legacy, segments)` returns one state per order plus the legacy fold and the file that owns each order, refusing an invalid segment name, an empty segment, a foreign `workOrderId`, a non-activation first event, and an order that already belongs to another file, each with the path and ordinal.
- **Control store (`scripts/lib/control-store.mjs`, new).** One reader for the working tree and for any committed revision or tag, reading blobs only and never a symlink target or a projection; `eventsForOrder`; `addedSegmentEvents`, the per-segment byte-prefix append-only proof; `branchWorkOrder`; `openOrders`; `latestClosedOrder` by Git first-parent integration order; and `selectWorkOrder` with the branch, flag, single-open-order, latest-closed, and refusal rules.
- **Resume (`scripts/resume.mjs`).** `--work-order` parsing, selection before every action, appends routed to the file that owns the order's activation, checkpoints unchanged and still per order, `orders[]` in `status --json`, the multi-order `current.md`, `next` naming in-flight orders, and `times` labeling segment rows.
- **Control time (`scripts/lib/control-time.mjs`).** Recovery refusals name the segment and ordinal for segment events and keep the line form for legacy events; segment rows carry `segment` and a local ordinal.
- **Worktree (`scripts/worktree.mjs`).** `finish` reads the subject's committed segments through the JSON contract, requires the named order closed there and in `origin/main`, and no longer parses a single log path; `start` is unchanged and activates on the new branch.
- **Release (`scripts/release.mjs`).** Control events at a revision come from every segment with segment and ordinal; the append-only proof between first-parent revisions runs per segment; `parseControlStateAt` and the surface check select the named order; close messages name remaining in-flight orders.
- **Work-order index (`scripts/work-orders.mjs`, `scripts/lib/release-records.mjs`).** Every non-closed order is Active; close-time and inferred no-release attribution run per segment so a sibling merge cannot shift another order's close ordinal; each tag's `controlSegments` are recorded, validated, and reported.
- **Tests.** `scripts/test-control-segments.mjs` covers synthetic interleaving, storage ownership, corrupt-segment refusals across all thirteen command forms with every control byte preserved, per-segment byte-prefix proofs, reactivation, the committed `v0.6.0` fold comparison, and the byte-identical `times` observation through a Git stub restricted to the recorded refs; `scripts/test-concurrent-control.mjs` drives a real-Git fixture with three worktrees, serial merges, finish and release close while a sibling is open, a third old-base branch, per-release attribution, and the first-parent append-only proof; the resume, checkpoint, worktree, release, and index suites are updated, including a reopened-order finish refusal.
- **Documentation.** Architecture's session-lifecycle section with a dated segment-layout migration note; the execution guide's resume phrases, closeout, and discipline; the playbook's paired-wave procedure and serial-integration rule; the domain model's control-plane sentence; the roadmap's navigation and ladder wording; IR compatibility's storage-axis note; the docs and root READMEs; the capability table's dated `control.concurrent-orders` row; the ledger's two dated sections; and the planning ladders, plan, and map.
- **Ideation breakouts (documentation only).** The roadmap's candidate for whole-or-split work orders under one umbrella with permanent whole-route exclusion once a child starts; the UIFA candidate for security, authentication, authorization, operational logs, and traceability responsibilities with the five adopted names unchanged; the audit document's cross-reference; ledger entries; and publication rows at `vision`.
- **Executor evidence (`docs/evidence/WO-030/`).** The captured `v0.6.0` fold of the 153-event activation prefix with input and implementation hashes, the byte-exact pre-change `times` observation, the fixture transcripts, and the script line-count table.
