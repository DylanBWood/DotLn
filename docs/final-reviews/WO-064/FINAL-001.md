## Review finding boarded up: target hooks run under the operator (D010)

The push is `git -C <repo> push --no-follow-tags origin <commit>:refs/heads/<branch>`, run from the target's Git root with no `core.hooksPath` override and no `--no-verify`. I probed this in session scratch with a repository, a linked worktree on `fix/x` and an executable `pre-push` in the main repository's `.git/hooks`. The same push shape exited 0 and the hook ran. With `-c core.hooksPath=/dev/null` it exited 0 and the hook did not run. So publish executes whatever hook the target's shared Git directory holds, in the operator's process, with the operator's Git and `gh` credentials, after every refusal has passed.

That matters only if a writer can place a hook, and that part is not established. The evidence for it: the writer runs `git commit -F <message>` itself inside a linked worktree whose objects and refs live in that same shared directory (`source-change-command.ts`). The host's post-exit checks cover the worktree's diff surfaces and residue, not the shared directory's hooks or config (`source-change-worktree.ts`). Product 03 states that "the sandbox is not the containment boundary: C-W6 and X-W6 observed sibling writes". The evidence against: no probe has written that directory's hooks from a sandboxed writer profile, and I ran none. I therefore do not fail the order: no criterion or stated claim is false, and every refusal still precedes the push. I also did not patch it, because disabling hooks also skips a target's legitimate operator-installed checks, a policy choice no verifier has judged. D010 names the probe, the interim hardening and a planted-hook fixture as the follow-up, with priority "before the first target publication of a model-written episode".
