## Release overview

This release makes how DotLn's published text reads a setting the operator chooses, surface by surface, instead of a correction made after the fact. A committed control file, `docs/control/reader-profiles.json`, holds one profile for each of five publication surfaces: pull-request title, pull-request body, commit subject, release notes and Release page. Each profile is a position on five dimensions (audience, density, identifiers, machine detail and voice), and each position has two illustrating sentences. A new command, `npm run reader`, compiles the committed profile to guidance and names the nearest example, shows three complete versions of a surface side by side for one real release, and scores how findable a release's answers are for a fresh reader. The two commands that already print a draft, `worktree publish` and `release prepare`, now print the guidance for the surfaces they write beside it. The release is for the operator who sets the style, for the reviewer and planner who write the surfaces, and for anyone who reads what DotLn publishes.

Nothing is refused or rewritten because of a profile. The guidance changes order, vocabulary and depth; the facts, limits, required sections and the no-attribution rule stay where product 08 puts them.

## Read before upgrading

- **Every surface starts as `balanced`.** No operator choice was recorded, so each surface writes for a contributor, at account density, with identifiers where they help, machine detail summarized and a plain voice ([D001](../../evidence/WO-191/decisions.md#wo-191-d001), [D013](../../evidence/WO-191/decisions.md#wo-191-d013)). To change one, run `npm run reader -- preview` with the surface name, edit the control file in a planning pass, and commit; the profile in force for a release is the file at that release's tag.
- **The document gate now judges the editorial files.** `npm run test:docs` refuses a profile with an unknown surface, dimension or position or a missing surface, an example whose fact anchors differ from the catalog, an examples library whose recorded sameness comparison no longer matches the example bytes, and a score row whose tag object, text hash, profile revision or quotation positions disagree with the tag it names.
- **Known limit: a missing tag object fails the gate with a raw error.** When a scored release's annotated tag object is absent from the local object store, as after a pruned tag deletion or in a `--no-tags` or shallow clone, the `reader-profiles` row fails with Git's own `bad file` error for the missing object and names no release or remedy. Boarded for the next order that edits the reader library ([D010](../../evidence/WO-191/decisions.md#wo-191-d010), FUP-8b8eb522d1d136c0).
- **Known limit: a `null` answer entry is refused with a raw TypeError.** `score --record` refuses a result whose answer entry is not an object before appending anything, but its message names neither the release nor the expected `{question, quote}` shape ([D011](../../evidence/WO-191/decisions.md#wo-191-d011), FUP-a4b2cdfb03ddbd2e).
- **Scores measure findability on the Release page only.** A row records whether a fresh reader quoted a sentence for each of four questions and how far into the text it sat; it judges neither the answer, nor the other four surfaces, nor the operator's taste, and it never gates a publication. Ten baseline rows exist, all with a `null` profile revision because the control file did not exist at those tags ([D003](../../evidence/WO-191/decisions.md#wo-191-d003)).
- **A reader run costs pinned-model tokens and is bounded.** `plan start` asks for one fresh reader only when a changed profile has three or more unscored releases, or when the operator asks; the planner's role sentence says the same. The baseline reader spent 11,174 output tokens over 138,259 bytes of prompt.
- **The examples are historical samples.** The fifteen variants rewrite v0.73.1's five published surfaces; they are not a new validation of that release. Their front matter discloses two inconsistencies in the published sources, and the record release notes' relative links are pinned to their original tagged destinations.
- **Component versions.** Application v0.74.2 is a patch over v0.74.1. Skeleton advances from 0.57.1 to 0.57.2 for the two role sentences; the console's pin and the lockfile follow; the root `package.json` adds only the `reader` script. No dependency is added.

## Substantive changes

**The control file and its check.** `docs/control/reader-profiles.json` (schema version 1) names the five surfaces and one position per dimension for each. `scripts/lib/reader-profiles.mjs` validates it with exact keys at every level, so an unknown or missing surface, dimension or position, a wrong-case position, an extra top-level key or another schema version is refused by name with the known list. A profile revision is the SHA-256 of the validated choices in canonical surface and dimension order, so key order and whitespace do not make a new setting while any changed choice does.

**The command.** `npm run reader -- profile` followed by a surface name prints the guidance the committed profile compiles to (one sentence per dimension, one preservation sentence) and the path of the nearest example, with distance counted in differing positions and ties favoring `balanced`, then `reader`, then `record`. `preview` with a surface name prints the three variants side by side with their positions, paths and source notes. Both refuse an unknown surface with the list of known ones. `score` prints one canonical prompt covering up to ten unscored releases as the immutable human text of their annotated tags; `score --record` with the reader's result file validates every quotation and the reader's three metadata keys before appending one row per release, binds each row to the tag object, text hash and tagged profile revision, and appends nothing for a release already scored; `score --correction` with the surface name and `--capture-hash` followed by the capture's `sha256:` digest records an operator correction against the current revision without copying the capture. `check` runs the profile, example and score validations and is the document gate's `reader-profiles` row; the eleven fixtures in `scripts/test-reader.mjs` are its `reader-fixtures` row.

**The two prints.** `worktree publish` prints the `prTitle` and `prBody` guidance after `Proposed N:` and before the product-gate block; `release prepare` prints the `releaseNotes` guidance after its outcome, except in the internal `--integration` call whose output becomes the integration receipt ([D007](../../evidence/WO-191/decisions.md#wo-191-d007)). A missing or malformed profile prints one `unavailable` line instead of refusing.

**Plan start and the planner.** `plan start` returns a `readerScores` block beside `failures`, outside the 1 KB failures block: answers found and median position by profile revision, typed corrections per surface, the current revision, the unscored count and whether a reader is due. The planner's role gains one sentence that runs the reader only when due or at the operator's word and records corrections only through the typed command; the reviewer's role gains one sentence that reads the profile for each surface it writes.

**The examples library.** `docs/publication/examples/` holds, for v0.73.1, three complete variants of each surface with JSON front matter naming their positions and literal fact anchors, a fact catalog, a two-sentence illustration for every position of every dimension, and an independent reviewer's per-surface sameness verdict bound to the examples' hashes.

Known limitations:

- Coverage is one macOS host with Node 26; the examples' two sub-agent workers and the reviewer comparison ran at launch-selected settings without effective readback.
