# WO-191

How DotLn's published text reads is now a committed setting instead of a correction after the fact. `docs/control/reader-profiles.json` holds one profile per publication surface (pull-request title and body, commit subject, release notes and Release page), each a position on five dimensions: audience, density, identifiers, machine detail and voice. `npm run reader -- profile` followed by a surface name compiles the committed profile to a few lines of guidance and names the nearest example; `preview` with the same name shows three complete versions of that surface for the real release v0.73.1, written as `record` (as published), `balanced` and `reader`, side by side with their positions. `worktree publish` prints the title and body guidance beside the merged-subject series it already shows, and `release prepare` prints the release-note guidance. Nothing refuses or rewrites text because of a profile: the guidance is advisory, and facts, limits, required sections and the no-attribution rule stay governed by product 08 ([D001](../../evidence/WO-191/decisions.md#wo-191-d001)).

**Choosing.** Every surface is `balanced` (contributor, account, identifiers where they help, machine detail summarized, plain voice) because no operator choice was recorded; the final review presented the three versions of each surface, and the fallback stands ([D013](../../evidence/WO-191/decisions.md#wo-191-d013)). A later change is one edit to the control file in a planning pass after `preview`. The document gate refuses a profile with an unknown surface, dimension or position or a missing surface, and refuses an examples library whose fact anchors or recorded sameness comparison no longer match the example bytes.

**Scoring.** `npm run reader -- score` prints one prompt covering up to ten releases not yet scored, each as the immutable human text of its annotated tag; a fresh reader with only that text answers four fixed questions per release (what changed for me, must I act, what is not covered, where is the evidence) by quoting one sentence or saying none answers. `score --record` with the reader's result file refuses a quotation that is not in the text, naming the release and question, binds each row to the tag object, the text hash and the profile revision read from that tag, and appends nothing for a release already scored. `plan start` reports answers found and median position by profile revision and asks for one reader only when a changed profile has three unscored releases. The baseline run covers v0.74.1 back to v0.69.1 with a `claude-opus-5-5` reader at launch-selected `xhigh`: all 40 answers carry a quotation found in the text, the median answer sits 0.70 of the way into its page, and all ten profile revisions are `null` because the control file did not exist at those tags ([D003](../../evidence/WO-191/decisions.md#wo-191-d003)). A score measures where a fresh agent finds an answer on the Release page; it judges neither the answer, nor the other four surfaces, nor the operator's taste, and it never gates a publication.

**Read before merging.** Two minor defects in the score path are boarded, not fixed. The document check fails with a raw Git error, naming no release or remedy, when a scored release's tag object is missing locally, as after a pruned tag deletion or in a `--no-tags` or shallow clone ([D010](../../evidence/WO-191/decisions.md#wo-191-d010), FUP-8b8eb522d1d136c0). `score --record` refuses a result whose answer entry is `null` with a raw TypeError rather than a named message, and appends nothing ([D011](../../evidence/WO-191/decisions.md#wo-191-d011), FUP-a4b2cdfb03ddbd2e). The examples are historical samples of v0.73.1, not a new validation of that release; their front matter discloses two inconsistencies in the published sources, and the record release notes' relative links are pinned to the tagged commit. Release-page scores make no claim about titles, bodies, commit subjects or release notes. The reviewer and planner roles each gain one sentence (read the profile for each surface you write; run the reader only when due or asked), and their cold-start roots stay under their ceilings.

**Validation.** [VER-001](../../verifications/WO-191/VER-001.md) passed on eleven refused mutations of the real control file, real-corpus scoring probes (an invented quotation refused by name, an identical repeat appending none, a due batch selecting its own revision), a byte-for-byte reproduction of the baseline prompt from the committed command, and WO-188's body-profile check over all nine body, note and page variants; it boarded the two follow-ups above. This review found `main` at the order's base, so integration changed no judged byte ([D012](../../evidence/WO-191/decisions.md#wo-191-d012)); it ran the publication, harness and release-surface checks, `npm run test:docs` at 34 of 34 suites, and `npm test -- --review`, which composed 39 passing suites at the unchanged code identity `aea7bae9…` from the executor's fresh row (39 suites, 91 fresh tasks, 1,428.3 s) plus the always-fresh format preflight. The presented examples, the criterion judgments and the gate figures are in [FINAL-001](FINAL-001.md).

Application v0.74.2, a patch over v0.74.1. Skeleton advances from 0.57.1 to 0.57.2 for the two role sentences, with the console pin and the lockfile following; the root `package.json` adds only the `reader` script, and no dependency is added.
