## Release overview

DotLn's control plane no longer knows where your documents live — it asks. Every script that reads or writes a work order, verification, final review, evidence file, release record, planning register, publication page, lineage index or control segment now resolves that path through one loader, `scripts/lib/config.mjs`, and one optional file at the launchpad root, `dotln.config.json`. Declare `{"version":1,"roots":{"docs":"vault"}}` and the whole lifecycle moves with it: `activate`, `implementation-ready`, `verify`, `verification-result`, `final-review`, `final-review-result`, `worktree start` and `worktree finish` all write under the roots you named. Declare nothing, and you get today's layout byte for byte — this repository ships no such file, and the eighteen default roots resolve to exactly the literals that used to be hardcoded. This release is for anyone who wants to run DotLn against a repository that is not this one, and it is the prerequisite the compiled starter export and the target-repository work depend on.

## Read before upgrading

**Nothing changes unless you add a file.** The absence of `dotln.config.json` is the same contract as `version: 1` with no declarations. `status --json`, `current.md`, the generated work-order index, `times`, `usage` and a release manifest derived over the real log are byte-identical to the previous release, verified by running both script editions against the same committed control history, refs and tags in a matched clone.

**The working directory never selects a launchpad.** Discovery is `DOTLN_LAUNCHPAD` first, then the nearest enclosing directory of the running `scripts/` checkout that holds a `dotln.config.json` or is a Git top level, then that checkout itself. This is deliberate: a copied script tree is routinely driven from an unrelated directory, and a working-directory ascent would let one checkout's session write into another's documents. If you run a copied tree against a launchpad, set `DOTLN_LAUNCHPAD` explicitly; it must name a directory that exists.

**Roots are relative, contained and validated positively.** A root must be a non-empty relative POSIX path inside the launchpad. Absolute paths, backslashes, and any segment that is empty, `.` or `..` are refused by name. Unknown keys in any section refuse, and a malformed file names its own path in the error rather than failing somewhere later.

**Children follow their parent unless you move them too.** `orders` defaults under `control` and `refutations` under `planning`. Moving `control` moves `orders` with it; declare `orders` separately only if you want them apart.

**`repositories`, `build` and `release` are validated, not consumed here.** `repositories` is required to be an object keyed by repository id whose values are objects, and nothing more — WO-071 owns its semantics. `build` carries `loadout`, `profile` and `overlay`; `release` carries the `readmeBlock`, `componentVersions`, `corpus` and `publicationCheck` toggles. Version 1 exposes both; the orders that own them will consume them.

**One lane is out of scope, by decision.** The compiled packages under `packages/` still resolve their own Git-ignored local harness lane at `docs/control/local/…` and are not part of this loader's subject. When a whole lifecycle was driven into a configured launchpad, that lane was the single write that did not follow the configured roots. WO-070 owns the kit's side of it.

**The schema has its own version axis.** `dotln.config.json`'s `version` is independent of the application release, the IR schema, the artifact and configuration identity, the compiler package and every doctrine or capability version. A launchpad can move its documents without touching any of them, and a future root or section advances this number alone.

## Substantive changes

**One loader, one root derivation.** `scripts/lib/config.mjs` exports `loadConfig`, `findLaunchpad`, `docRelative`, `docPath`, `defaultDocRelative`, `rootPattern`, `defaultRoots` and a single `TOOL_ROOT`. `TOOL_ROOT` is now the only place in the control plane that derives a directory from its own module URL, and it owns kit paths — `packages/`, `node_modules/`, script fixtures — while every document root comes from the launchpad. Before this change, `"docs/control` appeared 29 times across `scripts/`, `"docs/work-orders` 18, `"docs/final-reviews` 13, `"docs/verifications` 6, `"docs/publication` 5, `"docs/evidence` 4, `"docs/releases` 3 and `"docs/planning` 3, and eleven scripts derived the repository root in four different ways.

**A test that keeps it that way.** `scripts/test-configuration-root.mjs` walks every non-test `.mjs` file under `scripts/` except the loader itself and refuses a path-shaped `docs/…` literal, a `docs\/` fragment inside a regular expression, and four shapes of second root derivation — including the two-step `fileURLToPath(new URL("./", import.meta.url))` followed by a `resolve(…, "../..")`, which is the shape that actually escaped review the first time. Prose that mentions a root inside a sentence is treated as documentation, and that narrowing is stated in the test's own comment rather than left for a reader to infer.

**Configuration caching that stays honest.** A parsed configuration is shared per launchpad, but each lookup stats the file, so a launchpad that gains, loses or edits its configuration mid-process is picked up rather than served from a stale cache.

**Control storage follows the configured roots.** `controlPaths(root)` resolves the legacy `resume.jsonl` segment, the per-order segment directory and the segment filename for one launchpad, and the fold, the readers, the work-order index and the current-state projection all take their storage from it. The generated index and `current.md` now name their actual segment paths in their own prose instead of the literal defaults, so a configured launchpad's generated documents describe themselves correctly.

**Ignored-material classification is anchored, not pattern-matched.** The intake and `control/local` lanes are resolved from the launchpad's roots and compared by path anchoring, replacing the regular expressions that assumed `docs/`. The remedies quoted back to an operator name the configured path.

## Progressive polish

Product 07 gains §Where the control plane finds its documents — the discovery order, `DOTLN_LAUNCHPAD`, all eighteen root names, the nesting rule, positive validation and the `packages/` lane limit. Product 10 gains the launchpad configuration schema axis. The roadmap and the README release block record the `v0.37.2` retiming. The evidence-source inventories, the receipt path matchers, the follow-up register validator, the planning subject builder, the release-note and manifest readers, the licence-surface rules and the worktree-integration projections all take a launchpad argument instead of a constant; peers that hold no launchpad keep a default-layout name so fixtures and cross-process comparisons are unaffected. The new suite joins the existing machinery table as `configuration-root`, and the harness fixture's copy list gains the loader so libraries that now import it resolve inside the fixture.
