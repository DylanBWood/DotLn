## The verification sequence

Four of them share one root cause worth naming, because it is the thing that makes this order hard: replacing a literal with a default-returning accessor looks like the refactor and is not it. F1 left `lineage.mjs` and three planning consumers reading `defaultDocRelative`-derived constants at call time, so a declared launchpad broke with `ENOENT` on a path it had never been asked to use. F2 collected references under the configured roots and then validated them against the default ones, inside a single function. F3 kept a two-step `here`/`resolve(here, "../..")` derivation that the guard's three inline patterns could not see, and sent a report into the tool checkout instead of the launchpad. Each of those passes a green literal-root guard. The verifier found them by driving matched default and configured fixtures rather than by counting removed literals, which is the only method that could have found them, and it said so.

## The defect I met, and what I did with it

`planHarnessPrune` resolves each registered worktree's target-receipt directory with `docRelative(launchpad, …)` and then, in the loop directly beneath, resolved that lane's `installation.json` with `docRelative(root, …)` while joining it under `launchpad`. One worktree's configured control root was being used to name a path inside another worktree. In today's repository both resolve identically, because no launchpad ships a configuration and the defaults are the historical literals; under a launchpad that moved its control root the mismatch would not have failed loudly, it would have made `stat(path)` miss and silently skipped every target lane, dropping runtime pins from the prune plan. I scanned for the shape rather than assuming it was alone — every `join`/`safeChild`/`cpSync` call in the changed scripts whose base root and whose `docRelative`/`docPath` root are different variables — and this was the only instance in non-fixture code.

I fixed it: one token, `root` to `launchpad`, inside a path the order already owns, in a block whose surrounding `try` already catches configuration errors into `pinsUnknown`, so the change cannot introduce a new failure mode. It is recorded as [WO-069-D017](../../evidence/WO-069/decisions.md#wo-069-d017) with the rejected alternatives, and the gate above was run after it. The one surviving instance of the same shape is in fixture construction — `copilot-qualification.mjs` computes relative names with `docRelative(repository, …)` and writes them into a freshly created fixture root that declares no configuration of its own — and I nominated that separately in D017's follow-up instead of widening this diff, because a copy that preserves relative structure is a defensible design choice rather than an inconsistency, and changing it is design work for the order that owns fixture layout.

## Judgment and handoff

This order is a prerequisite, not a feature: it makes a launchpad's document layout data instead of code, which is what the export kit and the target-repository children of WO-033 consume. What earns the pass is the pairing — a separate tool checkout drives a whole lifecycle into a configured launchpad, while the defaults reproduce the activation base byte for byte across seven outputs and the entire suite table — because either half alone would be worthless. A refactor that only preserved the defaults would have shipped nothing; one that only moved roots would have broken the plane it runs on.

Rule beating is the trap this order is most exposed to, and it was tested rather than assumed at every level: VER-001 found three consumers that satisfied the guard and broke the behaviour, VER-002 mutated the repaired guard until it failed, and I mutated it again independently.
