# WO-120

Work that a machine derives — a compiled `WorkOrder` from the runtime, or a line of prose someone types — can now become a real work order: same `WO-NNN` identity, same authority file, same lifecycle, same index row, same `status --json`. Until now the compiled contract and the document control plane were two different things with nothing between them, so `resume activate` demanded an identity and an authority file that no derived caller could produce. `materializeOrder(compiled, provenance, options)` allocates from a configurable reserved pool (`WO-900`–`WO-999` by default), writes a stable generated authority, and activates it through the ordinary dependency-checked `resume activate`. `npm run dotln -- intent "Describe the work"` files the same shape as a draft for a human to review first. This is the admitted prerequisite for WO-100's automatic derivation and WO-115's UI filing; neither is implemented here, by this order's own non-goal.

**The allocation is the durable record, and that is the whole design.** `WorkOrderIdentityAllocated` is an ordinary append-only event in the usual per-order segment — no second journal, no parallel identity family — and it lands *before* the authority file exists, carrying the provenance key, the compiled contract and the authority bytes. So a crash between the two is recoverable: retrying with the same key restores the missing file under the same identity. A retry with the same key and *different* inputs refuses rather than silently re-filing, an already-activated order is never reactivated, and a missing file for an activated order refuses rather than restoring an obsolete draft over reviewed work. The file itself is published by exclusive hard link after an `fsync`, so an interrupted write leaves an ignored temporary, never a torn authority.

**What a reviewer should know.** Two limits are real and recorded rather than fixed. Collision protection is one shared launchpad lock, so two disconnected checkouts of the same repository can still allocate the same identity — that is [D001](docs/evidence/WO-120/decisions.md#wo-120-d001)'s reopening condition and it is stated in both product write-backs, not discovered later. And one defect met during review is not fixed here, boarded up as [D007](docs/evidence/WO-120/decisions.md#wo-120-d007): folding the control log re-validates every allocation event's embedded authority against a section list hard-coded in `derived-contract.mjs`, so a future change to that list — WO-113 is the likely trigger — could make historical events unfoldable and refuse every control read repository-wide. It has zero impact today because no such event exists in this control plane, and the follow-up asks for a version the event carries rather than a guess written during a review. One defect *was* fixed here, inside this order's own diff: the CLI shipped `intent` but omitted it from the usage string `dotln` prints with no arguments, so the command was invisible on its most common discovery path while the execution guide documented it ([D006](docs/evidence/WO-120/decisions.md#wo-120-d006), one line, re-gated).

**Injection is answered structurally, not by filtering.** Everything caller-supplied goes through an escaper that replaces `& < > \ * # [ ] |` with numeric entities and rewrites the output contract's `<` as `\u003c`, so a hostile objective containing `## Receipt 2026-01-01`, `**Model:** injected` and `<!-- dotln-dependencies:end -->` becomes body text rather than structure — there is a fixture that files exactly that. `validateCompiled` accepts exactly the thirteen fields of the compiler's `WorkOrder` interface, so the contract cannot drift from the type. Authority paths must resolve physically inside both their configured root *and* the launchpad, which closed a real gap found in the executor's own final source review: a derived root symlinked to a separate directory previously activated with exit 0 ([D004](docs/evidence/WO-120/decisions.md#wo-120-d004)).

**Validation.** Eleven focused fixtures cover the full lifecycle through closure, replay, interrupted-authority recovery, exhaustion by both events and pre-existing files, two real child processes contending for identities, draft review, a genuine `ResidentHost` restart, and the symlink refusal. Independence is unusually strong on this order: the executor ran on Codex CLI 0.155.1 / gpt-6-astra with real session readback, the verifier on Claude Opus 5 — different harness, different model. The reviewer's `npm test -- --review` passed **33 suites, 0 failed, 513.32 s, 77 fresh tasks, exit 0** on the integrated, staged tree at code identity `8b79bbb7`. This matters more than usual here: the executor's and verifier's gates shared identity `eb763419`, computed while this order's three new source files were still untracked, so neither bound the bytes it delivers. `publication:check` reports 274/274 headings with both editions current; `harness check` reports 31 generated surfaces; `release check-surfaces --local`, `plan check`, `format:check`, `work-orders index --check` and both `git diff --check` invocations pass.

**Integration and release.** `main` moved three commits ahead during this review, so the branch was integrated as a fast-forward before anything was judged. One authored conflict — both WO-063's `v0.40.3` and this order's `v0.41.0` record claiming the top of the roadmap's release boundary — was resolved by keeping both and retiming this order's baseline sentence to name the newly observed tag. The assignment does not move: minor above `v0.40.3` is still `v0.41.0`. No acceptance claim is inherited across the moved base. This prepares application `v0.41.0` and skeleton `0.35.0` with the console's exact pin following it; compiler, kernel, semantic hashing and the dependency set are unchanged, and no package is added.
