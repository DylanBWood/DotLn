## Release overview

Derived work now has a durable identity. A compiled `WorkOrder` produced by the runtime, or a line of prose typed at the CLI, can become a real work order with the same `WO-NNN` identity, authority file, lifecycle, index row and `status --json` projection as one written by hand. Before this release the compiled contract and the document control plane were two unconnected contracts: `resume activate` required an identity and an authority path that no derived caller could produce, so machine-originated work had nowhere to land. `materializeOrder(compiled, provenance, options)` allocates an identity from a configurable reserved pool, writes a stable generated authority under the configured derived root, and activates it through the ordinary dependency-checked `resume activate`. `npm run dotln -- intent "Describe the work"` files the same shape as a draft, with review placeholders where prose supplies no executable contract, and does not activate it. This is for the consumers that were blocked on it — WO-100's automatic derivation and WO-115's UI filing — neither of which is implemented here.

## Read before upgrading

Four things are worth knowing. First, `WO-900`–`WO-999` is now a reserved allocation pool by default, configurable as `derivedOrders.first` and `derivedOrders.last` in `dotln.config.json`; existing authorities that already occupy identities in the pool are skipped, never renumbered or overwritten, and a reversed or malformed range refuses naming the configuration path. Second, `dotln status --json` with a store directory gains an optional `derivedOrders` key read from the selected launchpad's control fold; it is omitted entirely when the list is empty, so no existing consumer sees a new key, and `DOTLN_LAUNCHPAD` selects the launchpad when the working directory is not it. Third, an authority file must now resolve physically inside both its configured authority root and the launchpad before `resume activate` will accept it — this closed a real gap where a derived root symlinked to a separate directory activated successfully, and it is a tightening that could refuse an existing unusual layout. Fourth, allocation collision protection is one shared launchpad lock, not a distributed allocator: two disconnected checkouts of the same repository can allocate the same identity. The application moves to `v0.41.0` and skeleton to `0.35.0` with the console's exact pin following it; compiler, kernel, semantic hashing and the external dependency set are unchanged, and no package is added.

## Substantive changes

**Allocation is an event, and it lands before the file.** `WorkOrderIdentityAllocated` is an append-only event in the ordinary per-order control segment — not a second journal and not a parallel identity family — carrying the stable public provenance key, the assigned `workOrderId`, the compiled contract and the authority bytes. Because it is durable before the authority file exists, an interrupted materialization is recoverable: retrying with the same provenance key restores the missing file under the same identity, and no other caller can ever reuse that identity in the meantime. A replay of the same sources reproduces the same allocation map.

**Retries are bound to their original request.** The same provenance key with identical inputs reuses the identity and never reactivates an already activated order. The same key with changed inputs refuses and tells you to use a new key. An edited draft refuses automatic activation and requires an explicit human-reviewed `resume activate`. A missing file for an order that is already activated refuses rather than restoring an obsolete generated draft over potentially reviewed work.

**Generated authorities have a fixed shape and typed dependencies.** Objective, Design, Acceptance criteria, Non-goals, Surfaces and Operator-review assumptions, with a typed dependency block and a `**Derived provenance:**` line. Everything caller-supplied is escaped into numeric character entities — ampersand, angle brackets, backslash, asterisk, hash, square brackets and pipe — and the output contract additionally rewrites its less-than characters as the six-character escape `\u003c`, so hostile prose containing headings, bold metadata fields or a dependency end-marker becomes body text rather than structure. WO-113 still owns the broader migration of historical work-order files; only generated authorities opt into this check.

**The catalog spans both roots.** The work-order index scans the configured `workOrders` and `derivedWorkOrders` roots, never follows a symlink while discovering authorities, keeps correct relative links for nested or relocated derived roots, and distinguishes an allocated draft (phase `none`, displayed as `draft`, excluded from open orders) from active work.

**Writes are crash-safe.** A generated authority is written to a staging file, `fsync`ed, published by exclusive hard link and followed by a directory `fsync`, so an interrupted write leaves an ignored temporary rather than a torn authority file.

## Progressive polish

`dotln`'s usage string now lists the `intent` command, which it had omitted — the command shipped but was invisible on the most common discovery path, `dotln` with no arguments, while the execution guide documented it. The execution guide gains a `Derived work and intent` section covering the command, the `materializeOrder` contract and its option defaults, the allocation event and its recovery and refusal rules, the shared-launchpad limit, and the new configuration keys; the roadmap records the reserved pool and the derived-work design under work-order navigation and identity. Neither changes observable semantics, saved-data interpretation, compatibility or any operator action.

## Evidence and compatibility

This prepares application `v0.41.0` as a minor release over the `v0.40.3` tag, under the classification the order declared at activation. Verification and final review ran on different harnesses and different models from the executor: implementation on Codex CLI 0.155.1 / gpt-6-astra with real session readback, verification and review on Claude Code 2.1.278 / claude-opus-5. That row matters more than usual: the executor's and verifier's gates shared code identity `eb763419`, computed while this order's three new source files were still untracked, so neither bound the bytes being released. `publication:check` passes with 274/274 headings and both editions current at 30 and 45 linked sections, `harness check` reports 31 generated surfaces, and `release check-surfaces --local`, `plan check`, `format:check`, `work-orders index --check` and both `git diff --check` invocations pass. Eleven focused fixtures in `scripts/test-derived-orders.mjs` cover the full lifecycle through closure, replay, interrupted-authority recovery, exhaustion from both control events and pre-existing files, two real child processes contending for identities, draft filing with hostile Markdown, a genuine resident restart, and the symlinked-root refusal.

`main` advanced three commits while this order was in flight, so the branch was integrated as a fast-forward before review judged anything, and no acceptance claim was carried across the moved base. The single authored conflict was two release-boundary records competing for the same position in the roadmap; both were kept and this order's baseline sentence was retimed to name the newly observed `v0.40.3` tag. The assignment itself did not change, because the next minor above `v0.40.3` is still `v0.41.0`.

Known limitations, each on the record. Collision protection is scoped to one shared launchpad and is not a cross-checkout distributed guarantee, recorded in [D001](../../evidence/WO-120/decisions.md#wo-120-d001). Folding the control log re-validates every allocation event's embedded authority against a section list hard-coded in `derived-contract.mjs`, so a future change to that list could make historical events unfoldable and refuse control reads repository-wide; this has no effect today because no such event exists in this control plane, and it carries a named follow-up in [D007](../../evidence/WO-120/decisions.md#wo-120-d007). The registered-public-repository branch of the authority renderer is verified but has no committed fixture. An out-of-shape human edit to a filed draft fails the whole index rather than one row, with a recoverable refusal that names the path. The `dotln intent` bridge resolves scripts relative to its own build output, so it works from this kit and not from a skeleton package published without `scripts/`; the packages are private and `prepublishOnly` refuses publication, so nothing is broken today. Committed authority and control records are public-material contracts, and callers must not supply private paths, secrets or employer material — a documented duty on callers, not an enforced screen.
