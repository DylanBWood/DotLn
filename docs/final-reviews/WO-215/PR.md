# WO-215

After `release close WO-NNN --publish` has published the tag and its Release, the helper now refreshes DotLn-Enterprise-Starter on its own. In a launchpad whose sibling declaration names an export sibling with a recorded checkout, it runs the export update for the released commit into a disposable worktree of that checkout (or, while the starter's `main` holds no `KIT-MANIFEST.json`, the first export of that commit), verifies the result the way an export verifies itself, commits it once, pushes that commit as a fast-forward of the starter's `main` through the hookless bare lane bound to core's origin owner and the sibling's declared name, fast-forwards the checkout, and holds WO-078's five-field receipt in main's ignored pending lane for the next `worktree start` to carry into a reviewed change. Nobody runs `launchpad export --update` by hand after a core release any more; the hand route keeps its behavior for other destinations.

**Checks before any write, and what each outcome means.** Before it touches the checkout or the remote, the refresh requires main's `HEAD` to be the published tag's commit, the recorded checkout to be a physical Git top level other than main, on `main`, with no tracked or untracked non-ignored change, its origin push URL (read before any rewrite) to name core's origin host and owner and the sibling's id, and after a hookless fetch into a host-owned bare lane its `main` to equal `origin/main` or be behind it (a behind checkout is fast-forwarded; ahead or diverged refuses; a remote without `main` refuses). A starter manifest that already names the released commit makes the row `current` with nothing pushed; one naming a descendant makes it `skipped`; one naming an unrelated commit refuses. The update runs through `planKitUpdate` and `applyKitUpdate` with the receipt held back (any refused plan row refuses), or `exportKit` into an empty scratch directory whose committable tree is copied over the initial commit (paths the export writes take its bytes, others are kept, both listed in the row; a file-against-directory collision refuses). The worktree then passes the export's own emit with every predicted surface equal (the operating contract by its marked block), its own `harness check` and `launchpad verify`, and its staged change set must be exactly the plan's changed rows plus `KIT-MANIFEST.json` and `CLAUDE.md` (a first export: exactly the export's tree, deleting nothing), with every staged blob and mode compared against the verified bytes. The commit uses a fixed message, hooks off and the host's identity; the push goes only to `refs/heads/main` of the bound URL with no tags and no force. Every row lands in `release-close.json` under `starterRefresh` and the summary prints one `Starter refresh` line per sibling naming its outcome, neither naming the checkout's path. A refused row adds a `starter-refresh` blocker with the same retry command, exits nonzero and keeps the dispatch's writer; the publication outcome, tag and Release are unchanged by any refresh outcome. A disposable worktree, its scratch directory and its branch are owned by an ignored cleanup record until every object is gone, so a cleanup failure after a successful push is finished by the retry before it reports `current`. Target orders, lower-version closes, closes without `--publish` and launchpads with no export sibling (every exported instance, the operator's fork) refresh nothing; `--publish --dry-run` judges the head main would fast-forward to, runs the checks with the fetch and prints `preview` or the outcome a real close would reach, writing no checkout file and pushing nothing. The checkout is recorded once with `worktree clone DotLn-Enterprise-Starter /path/to/starter-checkout`, which now admits a declared export sibling's id beside a registered repository's; the path stays in the ignored clone map.

**The receipt and the next order.** After a successful push the receipt is written, unchanged in shape and file name, into main's ignored pending lane, never into main's tracked tree, and a `current` row writes one only when no committed or pending receipt records the starter's manifest hash. The next `worktree start` reads the lane before it creates anything (a malformed pending receipt refuses the start with no worktree and no branch), freezes each receipt's path and bytes after the fast-forward, copies them into the new worktree's evidence root on both the self and the target route, regenerates the registry there, removes the pending files and prints one line naming the carried receipts. A registry failure keeps the worktree and the pending files and prints a retry program bound to the start's main, worktree, branch, base and authority hash, which finishes the same sequence without creating a second branch. The registry preamble now says receipts also arrive this way.

**Read before merging.** The first live refresh is this order's own release close, and it is the starter's first export: the public starter holds one empty-tree initial commit and no manifest (re-observed read-only at the base). Before `resume: release close`, the release-close session records the starter checkout from main with `worktree clone DotLn-Enterprise-Starter /path/to/starter-checkout`, the operator naming the path or asking a role to create the clone ([D002](../../evidence/WO-215/decisions.md#wo-215-d002--publish-only-the-verified-starter-commit-through-the-declared-binding)); a `--publish --dry-run` then previews the refresh checks before main's fast-forward.
