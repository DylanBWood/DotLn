# WO-068

DotLn has had a compiled presence policy since v0.19.0 and nothing that executes it. This adds the process: `dotln resident --store DIR --policy ID` folds one launchpad log, records every wall-clock sample as a `ClockSampled` event, drives WO-067's statechart, and dispatches one declared bounded script per phase when the policy allows. Because the clock is an input rather than an ambient read, the whole thing replays byte-identically through WO-047's explicit projector — the fixture proves it with `Date.now` poisoned to throw. `dotln presence away|back` records the operator edge, and `--once` runs a single complete cycle so an outside scheduler can drive it, which matters because neither harness exposes a scheduler of its own (WO-044 rows C-U3, X-U3).

The safety properties are the point, not the loop. A dispatch is appended and fsynced before the process spawns, with a deterministic identity over policy, phase, cadence, due time and arm generation, so a restart that finds a dispatched-but-unobserved episode records `ScriptEpisodeLost` and re-arms rather than dispatching that id twice. One host per store holds an exclusive lock; a second refuses; a dead owner is reclaimed only after a full positive replay. A `script` actor runs exact argv in a declared worktree with a cleared environment under a macOS sandbox that denies network, bounded in time and output, and its result reduces to a digest and a first line. Success means exit zero **and** a declared expected stdout SHA-256 — a script cannot certify itself. `cli-worker`, `human-handoff` and `local-model` stay unavailable with their WO-110/WO-122 reasons and the catalog never substitutes one kind for another.

**Two things a reviewer needs to act on.**

**This branch should not be merged until a planning dispatch clears B1.** Criterion 7 requires a dated `runtime.resident` row in the capability table, and `runtime.resident` is a capability id no planning pass has judged. The continuation gate rejects that by design — an appended section may only reassess known capabilities — so `npm run test:docs` is red here (`plan`, `plan-refutation-current`, both reporting `planning pass needs a receipt matching the current subject`). Removing the WO-068 section makes `npm run plan -- check` exit 0, which isolates it to that one write-back; renaming its heading to the accepted `dated reassessment` form only moves the failure to `new capability id runtime.resident`. No executor repair can discharge this: the only moves are deleting the row, which violates the criterion, or authoring a planning receipt, which is the planner's dispatch. It is a defect in the order as filed rather than in its execution, and merging as-is would turn `npm run test:docs` red on `main`.

**"A killed resident costs nothing" has one exception, and it is not covered by a fixture.** The resident takes a short append lock on every transaction, several times per tick. `WorkerStore.acquire` removes its `host-lock-recovery` guard only in a `finally`, and unlike `host.lock` that guard carries no owner pid, so it cannot be liveness-checked. A SIGKILL landing inside that 4–17 ms window leaves the guard behind and every later `dotln resident` and `dotln presence` against that store refuses until a human removes the directory. That is WO-048's inspect-before-reclaim contract behaving as specified, no event is lost or truncated, and the runbook documents the refusal — but the crash fixture waits for the guard to clear before sending SIGKILL, so the window has no adversarial coverage. Stamping the guard with an owner pid, or taking it off the per-transaction hot path, would close it.

Two further non-blocking findings are recorded: a `scope.budget` ceiling is silently discarded when its key collides with `scope.changeSize` (bounded by the authority envelope, which is checked independently in the same expression, so no authority escape is possible), and the NoOp dedupe keys on the reason string alone, so a later absence arm that refuses for the same reason leaves no log record.
