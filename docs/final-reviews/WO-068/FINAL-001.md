## B1 — blocking for merge — the capability write-back the order mandates leaves the planning gate red, and no executor repair can clear it

- **Criterion:** 7 (met as specified; this is its consequence, not its failure).
- **Observed:** criterion 7 requires "the capability table's dated `runtime.resident` row". `runtime.resident` is a **new** capability id — it appears nowhere in the repository before this branch. `checkPlanContinuation` (`scripts/lib/plan-continuation.mjs:298-308`) calls `reassessments` whenever the subject's capability inputs change, and `reassessments` enforces two rules on the appended region: the heading must match `^## (WO-\d{3}) dated reassessment \((\d{4}-\d{2}-\d{2})\)$` (`:70-79`), and every capability id in the section must already be known to the judged planning subject — `requireSamePlan(knownIds.has(id), \`new capability id ${id}\`)` (`:94`).
- **Effect:** `npm run test:docs` is **15 passed, 2 failed** on this branch: `plan` and `plan-refutation-current`, both reporting `planning pass needs a receipt matching the current subject`.
- **Reproduction, isolated three ways.** With the WO-068 capability section removed, `npm run plan -- check` exits 0 and emits its receipt — so nothing else on this branch contributes. With the section present as written, it fails on the heading rule, because the executor wrote `## WO-068 dated addition (2026-09-16)` while the checker accepts only `dated reassessment`. With the heading renamed to `dated reassessment`, it fails **differently and more fundamentally**: `new capability id runtime.resident`.
- **Why this is not an execution defect and does not route to repair.** The second failure is the gate working as designed: an appended section may only *reassess* capabilities a planning pass already judged; introducing a genuinely new capability id is a planning-subject change that requires a fresh receipt. An executor repair has only two moves, and both are wrong — delete the row, which violates criterion 7, or author a planning receipt, which is the planner's dispatch and not the executor's. So a `fail` verdict would route this to a phase that cannot discharge it. I am recording it here instead.
- **Why I did not rename the heading myself.** It would have been a one-word edit inside a criterion-7 named path, and the three most recent precedent sections do use `dated reassessment`. I deliberately left it. The heading is not the defect; it is the executor's honest label for what this genuinely is — an *addition*. Renaming it would relabel a new capability as a reassessment, hide the first failure behind a less legible second one, and make a planner-owned decision inside a reviewer dispatch.
- **What clears it:** a planning dispatch that admits `runtime.resident` into the judged subject — `planning: refute` or the next pass — after which the section is reconciled to the form that pass chooses. Until then this branch should not be merged, because merging turns `npm run test:docs` red on `main`.
- **Nomination for the planner, beyond this order.** The order's own criterion 7 instructed an action the repository gate rejects, so this is a defect in the filed order rather than in its execution. Any future order whose write-back duty names a *new* capability key will reproduce it. The durable repair is either to admit new capability ids through the planning pass that files the order, or to teach `reassessments` a dated-addition form for ids the filing order itself introduces.
- **Not pre-existing.** On `main` the capability inputs are unchanged from the judged receipt, so `reassessments` is never called and the suites pass. VER-001 did not run `npm run test:docs` (it ran `publication:check` and `harness check`), which is why this surfaces here.

### F1 — major — a SIGKILL inside the append-lock recovery window leaves a store that refuses until a human removes a directory (non-blocking; disclosed; planner nomination)

Confirmed independently. `WorkerStore.acquire` creates `host-lock-recovery` at `worker-store.ts:140-147` and removes it only in the `finally` at `:265-270`. Unlike `host.lock`, whose owner pid is liveness-checked at `:252-257`, the guard carries no owner, so it cannot be reclaimed the way a dead owner's lock is — an abandoned guard refuses permanently.

What WO-068 changes is exposure, not mechanism. `ResidentStore.transaction` (`resident-store.ts:101-132`) runs a full `acquire()`/`release()` cycle on the `.resident-append` store for **every** transaction — several per tick, and again on each 20 ms poll that observes a change while an episode is in flight. VER-001 measured the window at 4.0–17.3 ms per transaction and reproduced the bricked store directly.

I agree this does not fail criterion 2. It implements WO-048's inspect-before-reclaim contract, which the order cites as a dependency and instructs the executor to follow; no event is lost or truncated; and `packages/skeleton/README.md` discloses it ("Torn logs or interrupted lock-recovery guards refuse for inspection without truncation"). But it does make the order's own Design sentence — "the log is the state, so a killed resident costs nothing" — read wider than the delivered behaviour, and the fixture avoids the window by construction: `resident.test.ts:595-599` waits for both `host.lock` and `host-lock-recovery` to clear before it sends SIGKILL. ### F2 — confirmed, severity lower than recorded — a `scope.budget` ceiling is discarded when its key collides with `scope.changeSize`

Confirmed at source. `resident-state.ts:134-138` builds `{ ...phase.scope.budget, ...phase.scope.changeSize }`; spread is last-wins, so a `budget` entry named `files` or `lines` is overwritten by the looser `changeSize` value rather than combined by minimum. It is reachable: `compiler/src/types.ts:370-375` gives `changeSize` fixed `files`/`lines` keys while `budget` is an open `Readonly<Record<string, number>>`, and `presence-schema.ts:277` admits arbitrary budget keys through `quantities`.

I record a lower severity than VER-001's "major", and the reason is in the same expression rather than in a separate control. The `some` at `:141-149` tests each reservation against **both** `limits[resource]` and `phase.effectiveEnvelope.resourceLimits[resource]`, and a missing envelope entry yields `0`. So the defect can only loosen the scope ceiling to the `changeSize` value; it can never admit a reservation the compiled authority envelope refuses. The exposure is exactly: an author who sets `budget.files` or `budget.lines` *tighter* than both `changeSize` and `resourceLimits` silently gets the looser number. The shipped fixture's budget is `{tokens: 200}`, so no collision is covered by any test. Real defect, correctly non-blocking, and in code the order did not require at all — criterion 3's effect check is separate and correct.
