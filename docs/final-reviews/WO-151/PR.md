# WO-151

The Entropy Reducer has existed as a compiled review loadout since 2026-09-04 and has been run exactly once, because running it meant performing five steps by hand against APIs that no script called. `npm run entropy` is that missing dispatch host. One command freezes `HEAD` into a scratch copy, compiles the reviewer's WorkOrder and authority envelope for that exact repository and base, hands the canonical prompt to one fresh worker, binds what comes back with the loadout's own validators, and files a numbered immutable receipt. A second command sends only the blinded reproduction subjects the compiled selection rule chooses to a second fresh worker that has seen none of the first one's reasoning. A third records the operator's accept, defer or dismiss, and an accepted finding becomes a candidate row the follow-up register already harvests. The loadout, its residue, actor pin, authority envelope and Program are inputs here and are byte-identical to `main`; `Program.All` stays deferred and this host drives the compiled manual plan, exactly as the refutation host drives its one-shot order.

**The point was never the receipts — it was that nothing routed a finding anywhere.** 121 orders closed between the first review and this one with no second review, and the execution guide's promise that a planning pass "may" consume surviving findings had nothing to consume. Two things close that loop. `npm run entropy -- subject` reads the receipt chain and names one of three actions: finish a pending dispatch, consume a filed review that carries a refutation and no disposition, or pay for a fresh episode — consume before you produce, because an episode is 993 s and USD 9.50 at the pinned actor and a review nobody disposed is not a reason to buy another. And an operator scope expansion, authorized mid-dispatch and bound in the planning log as a `PlanExecutionAmended` row citing [D007](docs/evidence/WO-151/decisions.md#wo-151-d007), adds `planning: entropy reducer` as a clause of the existing planner role: that pass's subject is the review, and its surviving findings are decided in that same pass rather than queued for a later one. No role, no role skill, no scheduler, no cadence; nothing runs unless the operator types the phrase.

**Who reviewed is recorded as a fact, and the command execution is the interesting part.** The receipt reads `entropy-reducer@1` only when a launched `claude-cli-print` episode carried the compiled model, effort and harness on the command line; every other route — another transport, another model, a background worker, even one whose effort the operator attests — reads `substitute reviewer` with its recorded values and the reason, and `effectiveModel` and `effectiveEffort` are `unknown` everywhere, because no harness reports them and a launch selection is not a readback. This is also the one inspection profile in the repository that gives a model commands, and that is deliberate: the first review ran with no shell, recorded seven denied calls and measured one of its seven findings. The live row measures what the change bought — REVIEW-002 recorded **zero denied tool calls and four of four findings measured**. Claude confines the file tools to the frozen copy with `--restricted` and denies everything outside the named tools without a prompt; Codex adds a real `workspace-write` sandbox. Claude does not path-confine a shell command, so the security document and the receipts say so in those words rather than claiming enforcement that does not exist, and each episode records the subject's tracked-status hash and the frozen copy's inventory on either side.

**What a reviewer should know before approving.** Three limits are recorded rather than papered over. The explicit-commit route exists because an executor may not commit before final review and cannot hold a working tree still for a 993 s episode, so on that route the subject is bound by the named commit's tree object in both repositories and the working tree's own drift is recorded as `trackedStatusByteIdentical: false` instead of being hidden ([D002](docs/evidence/WO-151/decisions.md#wo-151-d002), [D009](docs/evidence/WO-151/decisions.md#wo-151-d009)) — the independent verifier judged that adaptation on its merits and accepted it, and so do I. One defect met in review is boarded up, not fixed: the confinement witness is coarser than the receipt's wording, because `git status --porcelain --untracked-files=no` does not see a new untracked file and the scratch delta is a net path count rather than a changed-path set ([D020](docs/evidence/WO-151/decisions.md#wo-151-d020)). Widening it would make the default route refuse its own receipts whenever the dispatching session writes an evidence file mid-episode, which is a decision about what the subject is and not a reviewer's cleanup. And the host keeps one pending dispatch per kind: a second `review` or `refute` is refused by path, before the 250 MB clone, naming the open episode and both recovery commands — that refusal is the independent verifier's first finding, repaired and regression-tested.

**Two defects were met and fixed in this review, both one line, both re-gated.** With every new file staged, `npm test -- --review` went red where no earlier gate could have: `kernel` failed because `docs/control/entropy-reducer.jsonl` is now tracked and no registry classified it as a non-`EventEnvelope` protocol, and `runner-fixtures` failed because the runner's own CLI-selection fixture stubs every document-suite script and had none for `scripts/entropy.mjs`. Both were invisible earlier for stated reasons — the control log was untracked, so `git ls-files` did not list it, and `runner-fixtures` was not in the suite set those runs selected — which is why the verifier's green `npm test` is true of what it ran and does not bind these two rows. The registrations and the four declined alternatives, including failing the review over two registry rows, are [D021](docs/evidence/WO-151/decisions.md#wo-151-d021).
