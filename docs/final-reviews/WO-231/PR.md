# WO-231

A registered target order's final review now lints the commits its pull request will carry. `final-review-result pass` lints from the subject's merge base with the clone's remote-tracking ref for the registered base branch to the subject whenever the activation base is an ancestor of that merge base, and from the activation base otherwise; the choice is the rule the publish already applied inside `describedTargetBase`, moved into one small helper, `targetBase`, that the review lint and the publish both call. A refusal now opens with the range it read: the number of commits linted, the described base, the subject, the activation base when the two differ, and the offending commit, before the format, identifier or attribution finding. When the clone holds no remote-tracking ref for the base branch, the lint reads from the activation base as before and the refusal says the ref was absent. Nothing recorded changes: `FinalReviewCompleted` still binds `targetSubject.baseCommit` to the activation base, the target gate binds the same reviewed commit, and the publish's own lint of the published commits from the lane-fetched merge base is unchanged. Review fetches nothing.

Why it matters: on 2026-10-24 the operator's fork met a verified target order whose `final-review-result pass` was refused with `subject.length: 90 of 72 characters` on a commit already merged on the target's base branch. The lint read 17 commits from the activation base, 16 of them the target's own merged history with subjects of 78 and 90 characters, while the pull request carries one commit whose subject measures 61. Nothing in the order, the launchpad or the fork could repair those commits, and WO-230 (v0.96.1) had moved every publish-side read to the described base but left this one on the activation base ([the order](../../work-orders/WO-231-final-review-lint-from-the-described-base.md), [D001](../../evidence/WO-231/decisions.md#wo-231-d001--describe-the-same-base-at-review-and-publication)).

What a reviewer should weigh. The review reads the ref the clone already holds and does not fetch, so a stale ref lints more commits than the forge will show and can still refuse a merged subject; the range sentence shows which base needs refreshing, and the publish fetches through the lane and lints the same commits again ([D002](../../evidence/WO-231/decisions.md#wo-231-d002--keep-review-local-and-preserve-the-conservative-fallback)). The order's Objective said the reviewer's `worktree integrate` had fetched that ref; it does not, since it fetches the launchpad's `origin main` in the launchpad worktree, and the clone's ref moves only at a target close, a target planning publication or a manual fetch. VER-001 corrected the rationale, and the no-fetch decision stands on its own evidence ([D006](../../evidence/WO-231/decisions.md#wo-231-d006--ver-001-boards-the-unnamed-tracking-ref-and-corrects-the-no-fetch-rationale)). Two follow-ups are boarded with reproductions. When the ref is present but stale, on unrelated history or peeling to no commit, the refusal names neither the ref, its commit nor the remedy, and reports the tree case as absent (F1, FUP-e4fa2bbf7c3968ec). A ref moved locally onto the subject empties the described range, so the review passes over no commit and the publish's lint then refuses the commit and opens no pull request, leaving a closed order that needs a new commit (F2, FUP-378c5638bf515e52; [D005](../../evidence/WO-231/decisions.md#wo-231-d005--ver-001-boards-a-review-range-a-moved-tracking-ref-can-empty)). Both belong to the next order that edits the lint; neither breaks a criterion, and `main`'s always-activation range is the behaviour this order replaces on purpose ([D008](../../evidence/WO-231/decisions.md#wo-231-d008--final-review-pass-at-the-integrated-identity-ver-001s-two-follow-ups-stay-boarded-and-the-register-rows-are-disposed)).

Validation: the executor's complete review passed 36 required suites and 102 fresh tasks at code identity `734504dc897e7648c6b214c024892bc2898126f0c5bbc3250c51948ddfd0df60` after one failed attempt on the runner's exact case inventory, repaired as [D004](../../evidence/WO-231/decisions.md#wo-231-d004--extend-the-existing-exact-inventory-for-this-orders-five-cases) ([handoff](../../evidence/WO-231/handoff.md), [controls](../../evidence/WO-231/controls.json)); two independent Codex workers found the same evidence gap in the controls record, fixed before handoff ([self-review](../../evidence/WO-231/self-review.md)). [VER-001](../../verifications/WO-231/VER-001.md) passed all five criteria, ran six probes beyond the fixture (origin online, a stale ref, a ref moved onto the subject with its control, a ref peeling to a tree, and unrelated history), and ran the shipped helper read-only against the fork's real target worktree, where it selects the merge base and lints one commit against 17. [FINAL-001](FINAL-001.md) integrated `main` and took in nothing, reran the nine review-lint cases and the six probes at the integrated tree, ran the affected checks, and passed with no finding of its own ([D007](../../evidence/WO-231/decisions.md#wo-231-d007--integrate-main-at-the-activation-base-with-nothing-taken-in)).

Limits a reviewer should weigh: no live forge was used, the fixture's local forge standing in as the order's evidence gate directs; the fork's one commit was not run through the outward lint with the fork's own configuration; the criss-cross merge-base case and a base branch not named `main` are untested; and a stale tracking ref keeps today's refusal until the operator fetches the base branch in the target clone.
