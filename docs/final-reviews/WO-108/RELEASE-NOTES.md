## Release overview

DotLn `v0.13.1` is an internal tooling/evidence patch above the published `v0.13.0`. It adds a deterministic, dependency-free mutation-evidence runner under `corpus/mutation/` and records the first measured campaign against the shipped kernel, compiler and skeleton test suites: a complete conservative census of 2,901 single-site candidates at the pinned base, a 32-site campaign selected before any verdict, and an append-only kill matrix in which the suites detected 18 of 29 conclusive compiled mutants (62.1 %) and missed 11, with two compile kills and one timeout kept out of that denominator. Every survivor is a numbered finding with its exact patch, the acceptance claim to investigate and a one-command reproduction; nothing is fixed and no assertion is added to any shipped suite. Audience: engineers deciding where the suites need distinguishing inputs before more assertions, and operators reading the repository's evidence corpus. The exported runtime, package versions, dependency declarations and schemas do not change.

## Read before upgrading

- **`npm test` now ends with the mutation runner's self-tests.** `npm run test:mutation` runs 21 synthetic tests in about ten seconds; they build small workspaces with the locked TypeScript under the system temporary directory, spawn real compiler and test subprocesses, and remove only scratch roots they created and re-validated. The four locked development packages must be provisioned. `npm run evidence:mutation` followed by the runner's own arguments is the runner itself; its campaign and reproduction modes are not part of `npm test`.
- **The campaign is evidence about 32 selected sites, not suite coverage.** The 62.1 % detection figure describes the selected sample, which is weighted toward guard neutering, and says nothing about the 2,869 unmeasured candidates. A survivor may be equivalent or outside exercised inputs and is not a proven defect. Read the findings as investigations for a later evidence-hardening order.
- **The manifests are pinned to base `3dc19b7`.** The runner refuses toolchain or source drift against its committed policy, site list and census; a campaign on a later base regenerates its own manifests and claim inventory rather than extending this matrix. Runs are single-writer: the runner detects an observed matrix change before appending but is not a concurrent-writer lock.
- **Component versions and contracts are unchanged:** `@dotln/kernel` `0.2.1`, `@dotln/compiler` `0.6.0`, `@dotln/skeleton` `0.12.0`, event-envelope schema `1`, compiled-loadout contract `1`; package source, tests and the lockfile are byte-identical to `v0.13.0`.

## Substantive changes

- **Evidence corpus: mutation lane.** `corpus/mutation/enumerate.mjs` tokenizes the 55 kernel, compiler and skeleton sources conservatively (comments, regexes and whole templates opaque; uncertain syntax omitted or refused) and enumerates twelve single-site operator classes plus the eight historical WO-008 compiler probes as exact-text seeds; `selectCampaign` draws the 32-site campaign from the census alone. `mutate.mjs` snapshots every tracked base file from Git, populates a provenance-validated scratch root with local workspace links and a private fixture Git directory that reads committed objects through an alternate, forces a fresh build, runs the three package suites under a 120-second per-mutant bound in a detached process group, and records one of four verdicts or refuses. The matrix is append-only with a validated resumable prefix and a 45-minute session budget; `--check` re-derives census, selection, matrix consistency, findings and transcript totals read-only; `--reproduce` and `--reproduce-survivors` rebuild a survivor without appending; `--report` regenerates the findings.
- **Measured campaign at base `3dc19b7`.** 32 of 32 sites measured in one session between two green 281-test baselines: 18 killed by test with named killing tests, 11 survived, 2 killed by compile (enumeration noise), 1 test-phase timeout (`M00030`, the v3 Beacon sparse-storage premise guard, undetermined at the bound). Historical probes 3, 4 and 8 (missing active capabilities, duplicate ids, zeroed prompt-token costs) are now caught; probes 1, 2, 5, 6 and 7 (forced tag compatibility, neutered tie guard, unreachable socket budget, deduplicated pipeline facets, emptied update laws) still survive, and six current-code guards join them: equipped-sense validation, Beacon age reevaluation, `VerificationOpened` stream selection, failing-evidence admission, decoded-Beacon replay comparison and JSDoc traversal. `findings-WO-108.md` carries each survivor's patch and reproduction; the campaign transcript, executor gate, preflight, self-test, survivor-reproduction, artifact-audit and scope captures live under `corpus/manifests/runs/`.
- **Runner self-tests and root wiring.** 21 tests prove the instrument's behavior with real subprocesses: a real `error TS2322` compile kill, a named test kill, a planted survivor, all eight historical shapes as known-survivable cases, red-baseline refusal that leaves no matrix, missing-suite refusal, a compiled infinite-loop timeout, descendant termination, scratch-provenance refusals, Git-applicable rendered patches, and append-only resume with partial-tail, duplicate, wrong-policy and mutated-field refusals. `package.json` adds `test:mutation` and `evidence:mutation` and appends the self-tests to `test`.
- **Documentation.** The corpus entry point and product 03's corpus policy distinguish generated evidence corpora (`corpus/fixtures`, `harness`, `manifests`, `mutation`) from policy-governed incident material, closing the layout follow-up WO-101 left; the work order records the operator's dated scope amendment and release assignment; the planning map, ledger and root README release block describe the source as preparing `v0.13.1`; the roadmap's release-boundary section records the activation completion with its base and classification.
- **Pattern library candidate: implementation and delayed consequences.** From an operator-opened ideation breakout, product 05 gains a candidate extension of the intervention question into execution: a justified recommendation can be implemented in a way that activates a hidden process or consumes a scarce resource later, so selected work should preserve its intended outcome, inspect what the concrete method changes for affected consumers, and use the smallest proportionate check for credible delayed effects, with any observation's owner, signal, duration, budget and stop condition explicit. The 5S section and product 03's suggestion pipeline point to it, the ledger preserves the entry, and the publication index labels it `vision`. It selects no IR type, runtime monitor, universal approval step or new work order.
