## Release overview

Since 2026-09-03 the only local-inference evidence in this repository was a crash: the one permitted server launch took the runner down before any model loaded, and every later plan for local models waited on that `n=0`. This release replaces it with a measured row. On this machine, the installed LM Studio build started from its CLI, loaded an already-present Qwen3.6 27B Q4_K_M artifact, and answered a noninteractive client: three byte-identical answers at temperature 0 with a fixed seed, a structured answer that validates against its schema, one tool-call round trip, a cancellation that stopped generation within 164 ms, a client timeout and a clean recovery. A two-minute, ten-request load run the operator added during the work stayed nominal on thermal state, memory pressure and swap. The recorded outcome is still `inconclusive`, on purpose: nothing confined the runner's outbound traffic, the template and sampling defaults the runtime actually applied were not read back, and interrupted requests yield no token rate. This release is for the operator and for whoever writes the local transport next, who now get real request and response shapes and an honest list of what is still unknown.

## Read before upgrading

Nothing about how DotLn runs changes, and no operator action is required. No package source, component version, dependency, harness setting, hook, event schema or authority rule moves, and nothing is removed. No model was downloaded, no runner setting was edited, and the runner was left unloaded and stopped. Read three limits before quoting the packet. `inconclusive` does not mean the runner failed; it means the readiness contract asks for more than successful inference, so WO-138's `ready` prerequisite stays unsatisfied while WO-110 may proceed on the `unavailable` route its own text admits. Binding the server to loopback controls incoming connections only, and a socket snapshot showing only loopback sockets at one instant is not a no-egress guarantee. The load run is a short bounded observation of whole-host signals, not maximum capacity, sustained-load tolerance or hardware safety; the native thermal API can report nominal when the state is unsupported or unknown.

## Substantive changes

The readiness packet is the release. [The narrative](../../discovery/local-runner-2026-09-18.md) and [the JSON packet](../../discovery/local-runner-2026-09-18.json) record 22 steps with their labels, nine protocol rows with requests, outputs, latencies and server statistics, the load run with 130 health samples, and provenance: LM Studio `0.4.24+1`, CLI commit `ff50809`, llama.cpp runtime `2.38.0`, Apple M3 Max with 48 GiB, the weight file and vision projector identified by SHA-256 and byte size, Apache-2.0 license, context 4096 and parallelism 1.

What the measurements show. The three fixed-prompt answers are one 55-byte string with empty reasoning, at 1.3–2.0 s and about 18.9 tokens/s. The schema answer parses and validates in independent client code. The model called `add` with exactly `a=2, b=3`, received `5` bound to its call id and answered `5`. The cancellation saw a first token at 731 ms, observed the model `generating`, aborted at 904 ms, and the runner was idle with nothing queued 164 ms after the abort. The nine completed load requests returned exactly 128 tokens each in 7.3–8.1 s at 17.8–18.7 tokens/s; the tenth was cut by the two-minute traffic limit, and the run stopped for that reason. Two things a transport author needs came out of the failures, which are kept: without `reasoning_effort: none` a short token cap is spent entirely on reasoning and the answer is empty, and the variant key the model list displays (`…@q4_k_m`) is rejected by the load command while the plain model key works.

What keeps it `inconclusive`. Three blockers are named: no attributable boundary denied the runner outbound traffic, so WO-027's deferral condition is not discharged; the runtime's applied prompt template and its other sampling defaults were not read back; and cancelled or timed-out requests return no usage or rate from the HTTP API, the model log or the server log. The next useful experiment is a boundary applied to the runner's actual lifetime, with loopback allowed and an external control denied.

The apparatus is two experimental clients under `scripts/probes/`, `local-runner-smoke.mjs` and `local-runner-load.mjs`, with fourteen deterministic tests against loopback doubles that now run inside `npm test`. Live inference needs a literal `--live` flag and the script as the process entry, refuses to start while a product gate process is visible on the host, and is never reachable from a test. The load client refuses limits above two minutes, ten requests or a fifteen-second request deadline, and stops on a non-nominal thermal state, non-normal memory pressure, 128 MiB of swap growth, unavailable monitoring, a visible gate, a failed request or a runner that does not return to idle.

Product 06's local-model candidate, the environment discovery record and the idea ledger each gain a dated entry pointing at the packet.

Known limitations, each of which the packet labels and does not fill. The live smoke rows were produced by a client revision that predates the audit corrections, and the packet records no client content hash; the request shapes are proven identical and the assessment recomputes to the same result. Two narrow defects in the experimental clients are reproduced and recorded, and neither touches a recorded row: the smoke client's live path observes runner state with a blocking call, so a deadline that elapses during that observation would be labelled a cancellation; and the load client, when run without an idle observer, can report its own two-minute limit as a request failure. Both still stop conservatively, and both belong to the separate implementation order that product 07 requires before these clients are promoted. Raw server and model logs were deliberately not retained, so the 53 ms cancel-to-release interval and the recovery request's 18.2 tokens/s cannot be re-checked from the repository. Operator time was not measured; the 61-minute implementation phase bounds it by inference only. Determinism is n=3 within one warm runner lifetime, not across restarts or prompts. Nothing here is a statement about model quality or a capability level.
