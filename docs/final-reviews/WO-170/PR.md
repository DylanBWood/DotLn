# WO-170

An order's hook journals and usage file live in its worktree and leave with it. For a closed order, `npm run meta` on `main` then read nothing and reported it as observed. Its correction count read 0 from no journal at all, and WO-166's tokens read unavailable, although its pull request recorded them. Only WO-043 and WO-126 had a committed snapshot, each a copy of the whole meter of about 100 KB. The 2026-09-27 cost table carried fourteen systems-trap series for five orders, and twelve were null or a false zero.

This pull request lands WO-170. The meter now keeps what an order's sessions observed, reads what it cannot observe as unavailable, and adds a count of the operator's directions, with a limit stated below.

- **A bounded snapshot, written where the journals are.** `release prepare` writes `docs/evidence/WO-NNN/meta.json` from the collection that renders this meter block. It holds the order's own row within 8 KB: metrics, journal corrections with their source, directions, usage totals by role, the observed dispatch values and declared supports. It writes only in a checkout holding a session journal of the order, and only while the order is open; otherwise it prints why. `meta --write …/meta.json` writes the same row ([D001](../../evidence/WO-170/decisions.md#wo-170-d001--one-collection-serves-the-meter-block-and-the-snapshot), [D002](../../evidence/WO-170/decisions.md#wo-170-d002--the-snapshot-is-the-orders-own-row-bounded-written-where-its-journals-are)).
- **After the close, the snapshot or unavailable.** For a closed order, journal values come from its snapshot. They never come from a later session's journal, such as release close on `main`. A correction count from no journal is `null` with source `unavailable`, never 0 ([D003](../../evidence/WO-170/decisions.md#wo-170-d003--after-the-close-journal-values-come-from-the-snapshot-or-read-unavailable)).
- **Usage by role, with its source.** Each role's usage comes from this checkout's observations, then the snapshot, then the retained usage copies `worktree finish` keeps. Each source is named, and one unknown dispatch keeps the total unknown. The latest recorded observation of a dispatch wins whatever order the copies are read in ([D004](../../evidence/WO-170/decisions.md#wo-170-d004--usage-by-role-this-checkout-then-the-snapshot-then-the-retained-copy), [D017](../../evidence/WO-170/decisions.md#wo-170-d017--repair-the-last-recorded-observation-of-a-dispatch-wins-whatever-the-read-order)).
- **One recovery.** 77 closed orders with a retained usage copy in the operator's main checkout now have a snapshot of their usage totals by role (2,262 rows, largest 3,550 bytes). 76 name their copy's SHA-256 in `usageCopies`. WO-067's copy also holds five planning rows and is listed as uncarried. The 37 closed orders without a copy are listed in [recovery.json](../../evidence/WO-170/recovery.json) ([D007](../../evidence/WO-170/decisions.md#wo-170-d007--the-one-recovery-77-retained-copies-37-closed-orders-without-one)).
- **Operator directions.** `operatorDirections` counts committed decision records whose dispatch begins with `scope expand:`, `operator override:`, `analysis:` or `conversation only:` (or, before the docs check, `operator`), plus `OperatorOverrideRecorded`, `RecordCorrected` and `CriterionWaived` events. It is a table column, a shifting-the-burden indicator, and a line for every closed order ([D005](../../evidence/WO-170/decisions.md#wo-170-d005--what-counts-as-an-operator-direction)).
- **The prune reads digests only from `usageCopies`** ([D008](../../evidence/WO-170/decisions.md#wo-170-d008--the-prune-reads-digests-only-from-usagecopies)).

**What a reviewer should know.**

- **The direction count follows agent-written labels, so it is a lower bound** ([D019](../../evidence/WO-170/decisions.md#wo-170-d019--final-review-passes-and-records-that-the-direction-count-reads-agent-written-labels)). The dispatched agent writes a decision's `dispatch` field, as a control prefix plus a paraphrase, and `resume:` is an admitted prefix. A step the operator took inside a `resume:` dispatch is filed as `resume: …; operator …` and not counted. On `main`, 71 of 871 dispatches count, and 165 others in 44 orders name the operator after `resume:`. WO-115 reads 0 although two of its decisions record an operator scope expansion. The order specified this rule, so its criteria are met. The follow-up asks planning to count the steps themselves before any pass relies on the series.
- **Directions on `main` for the five orders closed on 2026-09-25 and 2026-09-26:** WO-070 0, WO-115 0, WO-165 0, WO-085 2, WO-166 2.
- **A snapshot stops at its `release prepare`.** Usage recorded after it, typically the rest of the final review, stays in the retained copy, which the snapshot outranks for that role. A prepare-written snapshot cannot name the copy `worktree finish` makes later, so later orders' lanes stay retained ([D004](../../evidence/WO-170/decisions.md#wo-170-d004--usage-by-role-this-checkout-then-the-snapshot-then-the-retained-copy), `FUP-dc6c139003bd4b89`).
- **WO-043's and WO-126's whole-meter snapshots are replaced by their own bounded rows**, with their metrics kept and the recovered usage added. Their other orders' rows remain in Git history, and the baselines are untouched.
- **The prune can release the recovered lanes after the merge** (inference from D008 and WO-171's usage rule). Once `main` carries these snapshots, the usage rule no longer keeps the 76 lanes whose copies they name. An apply may then remove those lanes under its other rules, and their per-dispatch usage rows survive only as the committed totals by role.
- **Journal values of orders closed before this one are not recovered** (a non-goal), except WO-043, WO-049 and WO-126, which keep their earlier whole-meter metrics under a label that says their corrections are not journal counts.
