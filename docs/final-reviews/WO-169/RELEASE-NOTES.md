## Release overview

A deferred follow-up now reaches the order that opens its seam. `npm run plan -- followups --touching` lists the pending register rows that name a changed or given file or an order. `implementation-ready` and `repair-complete` print one advisory with the count of those rows and the rule for handling them, and the final review disposes each listed row. The register can be exported whole with `followups --export` and disposed in one command with an array passed to `followups --apply`. `worktree integrate` now generates only after authored conflicts are staged.

## Read before upgrading

No action is required. A completion may now print one more advisory, naming how many pending follow-up rows mention a file the change touches or the order itself; it never refuses a completion, and a stale register is reported as unavailable. `npm test -- --review` now selects the configuration-root suite for any changed path under `scripts/`, which adds about 2.8 s to that gate. The first pass of `worktree integrate` that meets an authored conflict no longer prints `Regenerated:` lines, the affected checks or the instruction to complete the draft decision; resolve and stage the conflicts, then run `--continue`, which prints them. `followups --export` accepts a destination only under the system temporary directory or the ignored local control lane; a Claude Code host scratchpad outside the temporary directory is refused.

## Substantive changes

`followups --touching`, given paths or `WO-NNN` identifiers, matches a pending row whose source title or summary, decision `followup` or `reopenWhen`, or latest disposition names a path, a trailing part of it or an order identifier not followed by a digit. With no argument it reads the worktree's committed, deleted, renamed and untracked changes against its merge base with `main` and the active order, or the order `--work-order` names. Pages keep the feed's 8 KB bound and a cursor bound to the register revision and the terms. `followups --export FILE [--all]` writes one JSON document with each selected row's identity, status, kind, source, title, the decision's whole text or the candidate's summary, and the whole disposition history, and prints only the counts, revision and path. It judges the destination by its physical path and replaces an existing file only when an export wrote it. `followups --apply` accepts a JSON array of ordinary requests that share one `expectedRevision`: they apply in order under one lock, the register is written once, and one invalid request writes nothing and names its index. `worktree integrate` holds generation while an unmerged path or an untracked stash collision remains, and writes the decision stub's release message as one line with one full stop.

## Progressive polish

## Evidence and compatibility

Application `v0.52.4` is a patch over `v0.52.3`. No package source, component version, dependency, register schema, control-event schema or role skill changed, and no evidence edition is re-minted. Independent verification passed all eight criteria. The final review ran the export, the batch apply and `--touching` live on the register, disposed the sixteen rows its own run returned, and ran the review gate on the staged tree (34 passed, 0 failed, 398.07 s, exit 0). Known limits are recorded with follow-ups: the match is textual and misses a row that names its seam in other words or links a file relatively; without `main` the advisory's command refuses; an export can create a missing reserved lane file; an explicit query of hundreds of terms overflows the page; untracked scripts select no machinery suite until staged; and two older defects of the integrate helper remain.
