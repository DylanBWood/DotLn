## Release overview

The walking skeleton is now an instance of the kernel loop instead of a script that happens to call kernel functions. One pure, typed reactor makes every decision the 13-step Repo Gardener scenario makes; the live host owns only the fakes, the append loop, and effect execution, and replay is the kernel's own `replay()` over the same reactor and the same log. The v0.2.0 claim "same log, same decisions" is therefore a structural property that the test suite checks over complete `Decision` values and semantic projections rather than an agreement between two hand-written scripts. Every derived skeleton event now carries a canonical `causationId`, and pulse- or command-scoped events carry a `correlationId`, so the audit projections can group records by recorded lineage instead of guessing from adjacency. The same order promoted an operator-opened ideation batch into documentation: the platform's reusable mechanisms are now labeled apart from the author's personal-implementation doctrine (ADR-0006), presence becomes a policy input with no built-in direction (ADR-0007), a public sources-and-inspirations register and an interim legal posture note exist, and the README leads with the product thesis. Audience: anyone reading the skeleton as the reference for how a DotLn host, reactor, and replay fit together, the WO-008 composition compiler that needs one decider to swap a compiled loadout into, and the audit follow-on that will prefer canonical links. This is DotLn `v0.3.6`, a compatible patch above `v0.3.5`, carrying `@dotln/kernel` `0.2.0` unchanged and `@dotln/skeleton` `0.3.2`.

## Read before upgrading

- **`replayScenario` takes only the log.** The unused `fixture` parameter is gone; callers pass `replayScenario(log)`. Its result no longer carries `adapterEffects`, `adapterDispatches`, or `recoveredCommands`, which replay cannot reconstruct; those three fields moved to `LiveScenarioResult`, the type `runScenario` returns.
- **`ScenarioResult.traces` is replaced by `decisions`.** The result exposes the complete `Decision` sequence over `RuntimeState`, one per event, instead of a list of recorded traces; read `decisions[i].trace` where a trace was consumed before.
- **`renderGlyphScene` takes folded `RuntimeState`, not an event list.** The six glyph slots derive from state flags (`presence`, `pulseSeen`, `inspectionCompleted`, `deletionRefused`, `verificationCompleted && verified`, `queuedPulseNoOp`). The rendered scene for the shipped scenario is byte-identical to before.
- **The demo log gains link fields only.** Every event id, type, order, and payload byte is unchanged; 17 events gain `causationId` and 11 gain `correlationId`. Stripping both fields from the new log reproduces the old log exactly. Consumers that compared logs byte for byte across versions must account for those two fields.
- **One audit association changes.** The verification record's association reads `explicit-event-link` instead of `derived-single-request-in-scope`, because the producer now records the link the fold used to infer. The structural-refusal record keeps its labeled `derived-same-episode-time-adjacency` fallback; the audit fold itself is byte-unchanged in this release.
- **The CLI banner reads `v0.3.2`.** That is the only byte that changes in default CLI output; the `--audit` form additionally shows the new link fields and correlation groups.

## Substantive changes

- **Skeleton reactor.** New `packages/skeleton/src/reactor.ts` exports `seiriReactor`, typed as the kernel's `Reactor` over `RuntimeState`, together with the predicate registry, the loadout, `compileWorkOrder`, and the runtime state shape. It is the only place in the skeleton that calls `evaluateCadence`, `authorize`, `decideProgram`, and `guardQueuedPulse`, and it imports only `@dotln/kernel`. The reactor folds every event type into state and, where the scenario requires it, returns intents, schedules, continuations, and a trace; the grant, the deletion refusal, the return-time revocation, and the queued-pulse guard are all reactor decisions.
- **Live host and replay share one computation.** `runScenario` drives a `LiveReactorDriver` that appends each event and steps it through the kernel's `replay()` one event at a time, executes the resulting intents against the fake executor, verifier, and scheduler, and records decisions through the existing `DecisionRecorded` slots. `replayScenario` is `replay(initialState(), decodeLog(log), seiriReactor, seiriPredicates)` plus a state projection, with no event-type branching of its own. The crash-recovery path restores state by replaying the persisted log through the same reactor before redispatching pending commands.
- **Canonical links.** Consequential events name their cause: pulses point at the away event, the work order at its pulse, the persisted command at the emitted work order, the result at the persisted or redispatched command, the deletion attempt at the result, the refusal and the recorded decision at the attempt, episode termination at the refusal, the verification request at termination, its completion at the request, and the no-op and cancellation at the queued pulse. Correlation ids name the first pulse for the work-order and grant events, the command id from persistence through verification, and the queued pulse for its no-op and cancellation. The four exogenous events (task creation, loadout, both presence changes) carry no cause.
- **Evidence.** The identity test compares the complete decision sequence plus timeline, glyph scene, work order, candidates, verified flag, and schedule ids live versus replayed, pins the decision count to the event count, the grant trace, the revocation branch, the five recorded-decision sources, and the exact candidate list. Six payload tampers each fail a named child test that must break when a decision input changes. A negative fixture drives `verified=false` and `○ unverified` in live, replay, and glyph state. The CLI has exact stdout and empty-stderr coverage for both public forms. A source-reading test proves that the four deciders live only in the reactor, that replay contains no branching, and that `scenario.ts` is smaller than before.
- **Platform and personal-implementation doctrine (documentation).** ADR-0006 separates reusable platform mechanisms from the author's personal-instance doctrine and accepts a future owner-sovereign profile as legitimate instance content; the README, vision, principles, domain model, architecture, interfaces, pattern library, roadmap, assurance design, IR compatibility, and `προτείνω` documents now label material claims as platform contract, personal profile, or another owner's option. ADR-0007 makes presence a policy input with four separately inspectable outputs and supersedes the earlier categorical "absence never grows authority" clauses without rewriting them.
- **Running worlds, commander-mediated tactics, and object behavior (documentation).** `προτείνω` records autonomous modeled continuity, unsanitized addressed speech as intervention data, a candidate commander-mediated tactical loop, and capability-based behavior attachment for non-cognitive objects as a replayable temporal rule; every new section is a candidate and its unresolved choices are listed.
- **Sources, legal posture, and front door (documentation).** New `docs/lineage/inspirations.md` is the best-known public influence register with five knowledge states and an exact-expression review register; new `docs/LEGAL.md` records the observed no-license state, the decision gates, and the package-publication gap without selecting a license; ADR-0001 gains a dated amendment that internal authorship uncertainty does not erase known external provenance; the README leads with the operator-authored executable-shelf quotation and a compact product thesis, uses one fitted-gear comparison, and states the core bet as convergence toward felt judgment rather than exhaustive formalization.
- **Intake lifecycle and local settings (documentation).** The docs index, playbook, and execution guide now say that backup archives only its own checkout and that reconciling a worktree-staged intake note into main is manual; WO-018 carries a dated scope clarification for the exact-path treatment of the main checkout's local harness settings.
