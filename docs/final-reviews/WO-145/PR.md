# WO-145

DotLn's executor can now be asked, once per order, to name one place where a small experiment might make the order's own work or a recurring repository step cheaper in seconds, tokens or commands, to run it inside a fixed budget or decline it with a reason, and to record what it cost and what it changed. The support is off by default and grants nothing an order does not already carry. Whether such experiments pay is the open question; this branch installs the instrument, records the first trial, names the two others and fixes the rule that will read the three of them before any of it can be argued from the result.

**One support, one record kind.** `tinkerer-economy` is declared through the existing Contributor support switches and equipped with the same `contributorConfiguredProgram` and `harnessInstallation` calls as every other optional support. Equipped, it adds exactly one paragraph to the executor's role text in both harness trees: 1,173 bytes, for an equipped cold start of 23,347 bytes against the 24,576-byte ceiling. Off, every one of the twelve generated role files hashes byte-for-byte to its `v0.33.2` bytes, and the fixture that holds those hashes was taken from the tag, not from the current build. The decisions generator now validates `kind: experiment` records: question, at least two alternatives, the deciding observation, a budget of at most 900 s, a measured cost with the commands that produced it, an effect with commands and a summary, an outcome of `adopted`, `kept-current` or `inconclusive`, a regression flag, history fields and a reopening condition. It refuses a record without a measured cost or with an effect that names no command, keeps unknown token and per-order values as `null` rather than inventing zeros, and admits a negative saving so a regression can be written down. No kernel, compiler, schema, gate or hook behavior changes.

**The first trial.** The order's own execution was trial one, run by hand before the support existed. It asked whether the two decision-focused tests in `scripts/test-process-debt.mjs` could stand in for the full file during development iteration: one full run passed 79 tests in 59.0 s, three focused runs passed 2 tests each in 0.27 s at worst, and the pre-registered rule (adopt only if every run passes and the slowest focused run is under half the full run) adopted the focused command for iteration while keeping the full file at integration. The experiment took 163.5 s of its 900 s budget. Its saving per future order is unknown and is recorded as `null`, not estimated; its token cost, 497,138, is a transcript counter over the measurement window and therefore an upper bound.

**What decides the support's fate.** [D001](../../evidence/WO-145/decisions.md#wo-145-d001) records the operator's three trials, WO-145, WO-110 and WO-099, where each record will appear, how the later two equip the support, and the reading fixed before they run: propose default equipment only if at least one adopted saving over the next ten orders exceeds the whole trial's experiment cost with no recorded regression; otherwise stay optional; withdraw if all three decline or are inconclusive. Product 05 records economy as the first of the thirteen aspects of quality the source register attributes to _Zen and the Art of Motorcycle Maintenance_, each other aspect needing its own measure before selection, with the adaptive modifier still open.

The release baseline hashes, the equipped-only executor change and the cold-start bytes were each reproduced independently at final review, and [VER-001](../../verifications/WO-145/VER-001.md) passed all five criteria under a different model from the executor's. This is a minor release, `v0.34.0` above `v0.33.2`, with skeleton `0.30.0` and the console pin; no dependency is added and no suppression enters the diff.

**What a reviewer should know before merging.** When the support is equipped, non-executor role files are not literally byte-identical: their generated `Origin` comment changes because its semantic hash describes the whole loadout, and the test strips that one line before comparing the prose; the executor recorded this in [D003](../../evidence/WO-145/decisions.md#wo-145-d003) and verification and final review both judged it the honest result rather than a defect. The two later trials are both packages orders, so the order's scripts-or-documents requirement rests on WO-145 itself, and the reading cannot be computed from records whose per-order effects are all `null`; both points are carried to the planning pass that applies the reading. A decline that ran nothing cannot be recorded, because the order's own design asks every record for the commands that show cost and effect. The bootstrap trial shows the record, not behavior arising from equipment alone. The executor's equipped Adjacent Repair also removed the stale "live model verification" claim from the README's not-yet sentence and the everyday outline, recorded in [D004](../../evidence/WO-145/decisions.md#wo-145-d004), because WO-056 had landed that evidence in the same release block. Final review changed no source and no document.
