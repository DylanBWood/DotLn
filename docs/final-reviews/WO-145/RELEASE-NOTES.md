## Release overview

DotLn's executor can now carry an optional instruction to run one small economy experiment per work order: name one place where a different working method might make the order's own work or a recurring repository step cheaper, state the question and the observation that would decide it, run it inside a 900 s budget or decline it with a reason, and record the measured cost and effect in a validated decision record. The support is off by default and grants no authority an order does not already have. This release installs the instrument, records the first trial, names the two further trial orders and fixes the rule that will read the three together, so that whether the experiments pay is decided by the record rather than by argument. It is for anyone running DotLn's Contributor loadout who wants the executor to question its method occasionally, and for anyone who wants that questioning bounded and accounted for.

## Read before upgrading

**Nothing changes unless you equip the support.** With `tinkerer-economy` off, which is the default, every generated role file is byte-identical to `v0.33.2`; a fixture hashed from that tag holds the twelve hashes and a test compares the default build against them. No kernel, compiler, schema, gate or hook behavior changes. The regenerated hooks and manifest carry only the new skeleton version and its snapshot key.

**Equipping it changes generated provenance in every role file.** The `Origin` comment's semantic hash describes the whole equipped loadout, so it changes in non-executor files too, although their prose does not. This is the compiler stating truthfully what was built; the test strips that one line before comparing non-executor prose, and the deviation is recorded with its reopening condition.

**The decisions generator is stricter for one record kind.** A `kind: experiment` decision without a measured cost, without commands for its cost and effect, with a budget above 900 s, or with a cost above its budget now fails `npm run meta` and the document gate. Unknown token or per-order values must be written as `null`; a string such as `"unknown"` is refused. Existing records of other kinds are unaffected.

**Trial orders equip the support explicitly.** WO-110 and WO-099 equip it through `contributorConfiguredProgram({ "tinkerer-economy": true })` or `harnessInstallation({ supports: { "tinkerer-economy": true } })` for their run and restore default equipment at handoff. No order is equipped by default until the three-trial reading says so.

## Substantive changes

**The `tinkerer-economy` executor support.** Declared beside the other optional executor supports and lowered to one paragraph of role text: before implementation on `next` or `fix`, name at most one economy opportunity within existing authority, pre-register its question, alternatives, deciding observation and budget, run or decline inside 900 s including preparation and recording, write one experiment record, and never start a second. Equipped, it adds 1,173 bytes to the executor skill for a cold start of 23,347 bytes against the 24,576-byte ceiling, identical in the Claude and Codex trees. It adds no gate, hook, agent, schedule or adaptive pressure.

**Experiment records in the decisions generator.** `readDecisions` validates the new kind's question, alternatives, observation, execution, outcome, budget, cost, effect, regression flag, history and reopening condition, with the refusals listed above; a decline requires a reason and the `kept-current` outcome, and a negative per-order saving is admitted so a regression can be recorded. A fixture exercises all three outcomes, a reasoned decline, index generation and readback, and 23 refusal shapes.

**The first trial, recorded.** WO-145's own execution asked whether the two decision-focused tests in `scripts/test-process-debt.mjs` could replace the full file during development iteration. One full run passed 79 tests in 59.0 s; three focused runs passed 2 tests each in at most 0.27 s; the pre-registered rule adopted the focused command for iteration only, with the full file retained at integration. The experiment used 163.5 s of its budget. Its saving per future order is unknown and recorded as `null`; its token figure is a transcript counter over the window and an upper bound.

**The trials and the reading, fixed in advance.** The operator chose WO-145, WO-110 and WO-099. After the third record the planning pass totals experiment cost and each adopted recurring saving; default equipment is proposed only if one adopted saving over the next ten orders exceeds the whole trial's cost with no recorded regression, otherwise the support stays optional, and it is withdrawn if all three decline or are inconclusive. Product 05 lists the thirteen aspects of quality the source register attributes to _Zen and the Art of Motorcycle Maintenance_, with economy first and the adaptive modifier still open.

Known limitations, each owned. The bootstrap trial enacted the support's instructions by hand before the support existed, so it shows the record, not behavior arising from equipment alone. Both later trials are packages orders, so the order's scripts-or-documents requirement rests on WO-145 itself. The reading needs per-order savings that the first record leaves `null`; if the later records do the same, the reading cannot be computed and the support defaults to staying optional. A decline that ran nothing cannot be recorded, because every record must carry the commands that show its cost and effect. The recorded token cost is an upper bound, not an allocation. Nothing here shows that the support pays for itself; that is the question the three trials exist to answer.
