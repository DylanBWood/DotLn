# WO-192 — One session drives an order through its whole lifecycle (v0.104.0)

Running a DotLn order today means typing one phrase per phase into a separate terminal and carrying each handoff by hand: at least four sessions for an order that passes first time, more for every repair, with a recorded 6.94 implied operator phrases per order and a third of within-order wall clock spent in the gaps since 2026-10-08. This pull request adds `drive: WO-NNN`: one phrase that carries an order from its current phase to a pull request ready to merge and, typed again after the merge, through release close. The session that receives it only routes. Every phase is done by a fresh worker that is handed nothing but its lifecycle phrase, runs in the order's own worktree, keeps its own writer, role, selected effort and sub-agent budget, and records its own completion.

**The router routes and nothing else.** `drive: WO-NNN` selects a new `router` role in the main checkout. Its whole procedure is to read canonical status through `node scripts/drive.mjs status WO-NNN`, run `node scripts/drive.mjs WO-NNN` once, and report each transition in one line. The driver chooses at most one action from the status's new `route` object, launches the generated phase worker as a separate native CLI session with exactly its phrase, waits, rereads status and repeats. It reads no order, diff, report or worker narrative, forwards nothing from one worker to the next, and holds no writer. Generated hooks refuse a router spawn whose prompt is not exactly a lifecycle phrase given to the agent type that phrase names, any router edit, and any shell command beyond the live gate's read list, its driver and its usage command; a host denial of the driver latches a router-only refusal until a new drive phrase. The router stops with one line and a next step for the operator's merge, a routed finding, an off-ramp or typed correction, `analysis:` or `operator override:`, a refused dispatch, three verification failures, two final-review failures, two incomplete endings in one phase, or an exhausted budget.

**Where the work happens.** For the launchpad's own order the worker runs in that order's worktree; for a registered target's order it runs in the target worktree WO-072 created, under the bundle WO-049 emitted there, and may write its paired launchpad records through the new `order-worktree` grant, which resolves both roots from the registries by physical identity so an alias spelling keeps the grant and another order is refused. The measured Claude host did not load the target worktree's hooks for an in-process worker ([host probe](../../evidence/WO-192/host-probe.json)), so the order's named fallback was selected ([D001](../../evidence/WO-192/decisions.md#wo-192-d001--use-separate-phase-sessions-on-the-measured-host)): each phase is a separate print or exec session, and the driven budget joins their admissions through a shared counter rather than pretending that moving work saves tokens. Release close runs in main only after the launchpad merge and, for a target, the target branch's arrival at its remote base; a drive of a closed order fetches both bases first, because a hosted merge reaches neither clone by itself, and a merge is read as close reads it: ancestry plus the order's passing final review in its own control record on the base.

**One actor per lifecycle worker.** A lifecycle worker definition is an actor of its own: its session record, role and selected effort are keyed by host session and agent, `harness writer --show` names the holding agent, and the new `SubagentStop` hook releases its reservation. Every other spawned agent works inside its spawner's session, under its role, grants and writer, because the host ends a helper with nothing to release; a driven worker's helper is read-only in both worktrees and writes only its own session scratch. A spawn counts against the agent whose tool call made it: `subagentCap` applies per spawner and a new `drivenSessionCeiling` (default four times the cap) bounds the whole drive, with unresolved joins still reported as minima and unobserved descendants as unknown. The generated roots' fan-out sentence states both bounds.

**Generated definitions, runner and front page.** The compiler emits every agent definition from one worker specification, so `dotln-executor`, `dotln-verifier`, `dotln-reviewer` and `dotln-release-close` carry the same pins as `dotln-worker` and preload their role skills, and `harness check` refuses a hand edit to any definition's model, effort or skill. The runner now runs the synthetic lifecycle fixtures as the `resume` product preflight, which blocks later product suites on failure, keeps the two legacy record comparisons in the document gate as `resume-docs`, and strips a driven worker's context from every suite environment. The front-page checker admits an operator-authorized change to `README.md` only through a validated execution amendment bound to this order and path; the What runs today and Why this exists passages are the operator's authored text ([D073](../../evidence/WO-192/decisions.md#wo-192-d073--implement-the-operators-validation-order-correction-and-front-page-rewrite-now)).

On Codex CLI 0.166.0 the same drive reached the passing final review (attempt 49), and its release close was then declined by the host in every run with no reason reported; the drive stops with `dispatch-refused` and does not retry. Codex exposes neither effective model nor effort in its stream, so those receipts carry the supplied pins as operator-attested values. The whole record is in the [native qualification](../../evidence/WO-192/native-qualification.md); on 2026-10-26 both hosts had performed all five roles on an earlier version of this code.
