## Release overview

DotLn `v0.12.0` is the minor release above the published `v0.11.0`. It makes independent verification a first-class, host-admitted mechanism. A blinded verifier episode receives a compiled capsule that contains only the acceptance criteria, the pinned diff, an explicit host-read repository snapshot and the host's own witnesses, and it returns claim-typed evaluations and typed findings through the same disposable worker transports that WO-009 introduced. A blocking finding compiles a focused repair WorkOrder; a fresh repairer episode proposes replacement contents for the finding's likely surface only; the host applies the proposal, derives which criteria the changed source bytes affect, marks their evidence stale, and dispatches another blinded verifier over the changed subject. The acceptance evidence matrix is a read-only replay of the event log and is visible in both `dotln status` formats at any point. The implementer never certifies itself: implementer-authored events, forged roles or results, old revisions, unsupported evidence and expired grants are refused rather than folded. Audience: operators who want machine-checkable acceptance evidence with visible staleness after a repair, and engineers extending the verification contract. Everything witnessed in this release is synthetic and deterministic; live model verification, source-writing repairers, independent code review and post-PR loops remain planned.

## Read before upgrading

- **`dotln status` gains `acceptanceEvidenceMatrices`.** The JSON form adds the array as a new top-level key, empty for stores without a verification stream, and the human form appends an `acceptance` block per workstream with one row per criterion. A consumer that compares the JSON byte for byte must expect the new key.
- **`WorkOrderTransport` is generic over the request.** `dispatch(request, now)` now returns the request-specific validated result: an existing inspection request still yields `WorkerResult`, and a `kind: "evidence-worker"` request yields a verification or repair result. An adapter written against the original inspection-only signature remains assignable, which the worker suite proves at compile time. `WorkerStore.saveResult` and `loadResult` are generic the same way, and `WorkerTransportName` admits `fake`, which the CLI launch shapes refuse.
- **The shared reactor gains a verification branch.** A `RuntimeState` whose optional `verification` field is set is folded by the verification branch of `seiriReactor`; every existing Seiri runtime leaves the field unset and is unchanged. Only host-actor events with `verificationResultVersion: 1` can update acceptance.
- **New CLI command and a new evidence gate.** `dotln verify-demo --store DIR` runs the synthetic planted-defect loop with the deterministic transport; `--transport claude-cli-print|codex-cli-exec --model M --effort E` uses the WO-009 launch shapes under the existing `DOTLN_LIVE_WORKERS=1` opt-in. `npm test` now ends with `scripts/verification-evidence.mjs --check`, which re-derives the four recorded loop artifacts under `docs/evidence/WO-010/` from a fresh run and refuses any byte difference.
- **The store path must be canonical.** The worker host refuses a store whose resolved path differs from the path given. On macOS a store under `/tmp` is refused because `/tmp` is a symlink to `/private/tmp`; use a repository-relative directory under the gitignored `.runtime/` root, as the runbook now does, or `/private/tmp`.
- **Component versions and artifact identity.** `@dotln/compiler` is `0.5.0` and `@dotln/skeleton` is `0.11.0`; `@dotln/kernel` stays `0.2.1`, the event-envelope schema stays `1` and the compiled-loadout contract stays `1`. `artifactIdentity.compilerPackageVersion` now reads `0.5.0` while every semantic hash and component definition hash is unchanged. The artifact-identity evidence helper writes and checks its current edition under `docs/evidence/WO-010/artifact-identity/`; the WO-029 and WO-022 receipts are retained as historical bytes and are no longer regenerated or byte-checked, and both evidence READMEs carry a dated migration note saying so.

## Substantive changes

- **Compiler: blinded verification capsules (`@dotln/compiler` 0.5.0).** `AcceptanceCriterion`, `VerificationEvidence`, `Evaluation`, `VerificationFinding`, `VerificationSubject` and `VerificationTask` are pinned types. `compileVerificationTask` builds a `verification-v1` capsule by positive construction, copying only named fields at every nested boundary, so implementer narrative, transcripts and result objects have no compiled path. It refuses criteria whose surfaces are outside the repository snapshot, an incomplete or non-blocking finding, and a repair surface outside the finding's criterion, and it pins the compiler package version and an FNV-1a equality key over the rest of the capsule. `assertVerificationTask` recompiles and refuses drift. `changedVerificationSurfaces` diffs exact source bytes, and `affectedVerificationCriteria` selects every criterion whose declared dependencies intersect the change, or all criteria when a changed surface is undeclared.
- **Skeleton: verification protocol and transports.** `parseEvidenceResult` validates the closed result schemas: exact key sets for the envelope, the evaluations and the findings; a claim type and evidence source that match the criterion; a pass only when every required check is witnessed passing and no adverse witness for that check exists anywhere in the subject; a failure only with a failing witness and a complete finding whose observed and expected values match an adverse host witness; and repair proposals only for the finding's likely surfaces, only for files already in the snapshot, and only with a substantive change. Both CLI adapters carry the new request through the WO-009 launch shapes with a request-specific JSON schema and prompt, and the deterministic `FakeVerificationTransport` is first-class.
- **Skeleton: the verification branch of the shared reactor.** `VerificationOpened` starts the workstream with baseline and candidate snapshots, criteria, the implementer episode, a host authority envelope and a repair bound. Dispatch compiles a capsule and emits the kernel intent through `Program.Invoke`, the durable `CommandPersisted` outbox and `VerificationContinuation`. Acceptance admits only a host-actor `CommandResult` with `verificationResultVersion: 1`, the pending command, a producing episode that this workstream started and that is not an implementer episode, a live lease, a current grant and an unchanged subject; anything else is recorded as a refused result. Evaluations enter the matrix with host-derived provenance, the producing episode, the subject revision and a stale flag. A repair proposal moves the workstream to `apply-repair`; `VerificationSubjectSubmitted` must match the proposal byte for byte and must change source, and it marks affected rows stale while preserving old evaluations and unaffected rows. `requiresHuman`, a failure without a blocking finding and an exhausted repair bound leave the workstream at `attention`, never at a verified completion.
- **Skeleton: host, demo and status.** `VerificationDriver` and `VerificationHost` mirror the WO-009 host with the same heartbeat, lease, deadline, single-writer store and immutable completed-result cache, plus a dry-run admission check that quarantines a rejected result before it is fed to the log. `runVerificationDemo` creates a synthetic file-selection repository, witnesses its baseline with real file reads and a real Node subprocess over the pinned interpreter, plants a policy defect, mounts each episode in a clean detached worktree, admits only validated JSON policy data as a repair, and recovers the crash windows around a saved result, an applied repair and an admitted result without repeating an effect. `projectAcceptanceEvidenceMatrices` is a pure replay that `dotln status` folds, and `dotln verify-demo` drives the loop from the command line.
- **Tests.** Three compiler tests cover pure blinded compilation under a throwing clock and random source, focused repair compilation with its refusals, and the repair radius. Fifteen skeleton tests cover the end-to-end loop through both CLI doubles with three physically distinct episodes and worktrees and identical kernel replay; implementer events and repair results that cannot certify; thirteen result mutations plus the live-source and unavailable-runner cases; two findings producing two plans and a zero repair bound stopping at `attention`; mid-repair `dotln status` showing stale rows without changing the store; crash recovery after a saved result, a committed repair and an admitted result; a human disposition holding a proposal; killed workers recovering in a fresh leased episode; model refusal, forged passes and incomplete results retaining pending work; and expired authority, lease and revocation quarantining acceptance under a pure replay. The WO-016 reactor-import guard admits the pure protocol and projection leaves and forbids Node built-ins in them.
- **Documentation and evidence.** The domain model pins the payloads, the capsule, the admission conditions, the staleness semantics and the matrix contract; the architecture ports gain the `VerificationAdapter` realization; the roadmap assigns `v0.12.0` and records the receipt; IR compatibility adds the `verification-v1` axis; the planning map, publication index, both audience routes and their source locks, the staleness demonstration, the root README release block, both package READMEs, the work order's activation header and the ledger's dated section are updated. Executor evidence under `docs/evidence/WO-010/` carries the recorded loop, the mid-repair and final projections, the CLI smoke receipt and the current artifact-identity edition.
