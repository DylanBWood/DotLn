# WO-048 — Malformed worker state stops recovery before it reclaims a lock or dispatches

A disposable worker host is most dangerous at the moment it recovers, because that is when it acts on bytes nobody has looked at. Until now `WorkerStore.acquire` read `host.lock` as `JSON.parse(readFileSync(lock)) as { pid: number }` and checked only that the pid was a positive safe integer, saved result receipts were validated when written but not when read back, and a leftover `.pending` staging file was unlinked and the run continued. WO-009 had proved the torn-log and abandoned-guard refusals; nothing fed a malformed receipt, a truncated capsule or a success-shaped stale staging file into recovery. This change decodes every on-disk value the worker and verification hosts trust, before any of them can change state: the log through `decodeLog`, each `CommandPersisted` command and saved capsule through `assertVerificationTask`, the three worker lease payloads, each `cmd_….result.json` through a wrapper decoder that requires exactly `requestKey` and `result`, a lowercase 64-hex key, an envelope with exactly its six fields and a completed status, and the lock as an object with exactly `pid`. Every refusal names the offending path and the shape that failed, and the store is byte-identical afterwards, so an operator can inspect what actually went wrong.

The second half is ordering. `WorkerHost` and `VerificationHost` gained a `preflight` that builds exactly the request the dispatch path builds and loads the cached result through it, and `run` now consumes that result instead of constructing its own — so a bad receipt is found before `CommandRedispatchRequested` or a lease expiry is appended, rather than after. `acquire` takes an optional read-only callback that runs inside the acquisition guard, and it then requires that every receipt it found on disk was actually loaded during that callback: a receipt whose original request context nobody can reconstruct is refused, not ignored. The three recovery callers supply that context from their own pinned fixture, model and mounts. The relocation is behaviour-preserving for a reason worth stating, because no test can show it: `workerRequestKey` strips `episodeId` before hashing, so cache identity is attempt-independent, and only `WorkerAttemptStarted` inserts into the episode map in `projectWorkerStatus`, so neither the moved gate event nor `expireLeases` can shift the attempt number the preflight computes.

What is proven: a 33-shape malformed corpus covering all six families the order names — truncated JSON, a success-shaped receipt for another command, a wrong result version, a missing envelope field, a foreign key, a non-object — plus lease tails, dangling symlinks and already-locked host calls, at 75 assertions, each checking the refusal text, that no dispatch happened, that no result was accepted, and that a full recursive snapshot of the directory including symlink targets and file bytes is unchanged; an executable read-path manifest whose deep-equal fails when a read is added, with planted ordinary, aliased and namespace reads demonstrating the tripwire; twelve further malformed shapes from the verifier outside that corpus, ten refusing by path and two correctly proceeding; and the WO-009 rows 2, 4 and 6, the torn-log, dead-host and durable-prefix fixtures and the WO-010 loop passing with no existing test or fixture file changed at all.

The application target is v0.21.1 with skeleton 0.18.1; kernel 0.4.0, compiler 0.11.1 and console 0.1.6 are WO-046's and unmoved, there is no new dependency, and the lockfile diff is the single skeleton workspace version. The order was verified at base 83e734f and staged v0.20.1 / 0.17.1; WO-046 merged to main as v0.21.0 / 0.18.0 during final review, so the review integrated that base and retimed the same patch intent to v0.21.1 / 0.18.1 under the order's existing classification, which D002 had named as its own reopening condition and D003 now records. The merge produced twenty conflicts and none in a source file — the two orders touch disjoint trees — and `release check-surfaces --local` agrees with the retimed result at every axis. Integration also required two evidence editions to be regenerated: a fresh operator-run live feedback audit as `WO-048/002`, because the declared feedback source set genuinely moved, and a fresh WO-048 authority edition, because regenerating the bundle at 0.18.1 moved the recorded bundle diff. VER-001 passed every criterion with no blocking finding and seven observations, all judged in the final review; `npm test -- --review` then passed once on the integrated tree at 27 suites, 0 failed, 662.64 s.

Read before merging. A leftover `.pending` no longer self-heals: `saveResult` used to unlink it and proceed, and now refuses permanently until someone inspects it, so a crash between the staging write and the `linkSync` wedges that command's store instead of recovering on the next run. That is the order's recorded choice — inspection belongs to the operator — and it is documented in the skeleton README, which also carries the new obligation on any custom caller of `WorkerStore.acquire` to supply request context for its receipts. Two known gaps are recorded rather than repaired, because repairing either widens the order: a refusal raised inside the acquisition preflight is prefixed with the log path before the offending receipt's path, so both are named but the leading one is the wrong file; and the inventory tripwire derives its API name from the call text, so a module-local rebinding such as `const bytes = readFileSync` escapes it, which admits no unguarded read in the present source but is the one literal gap against the criterion's wording. The reviewer's attestation records effort `unknown` because this harness exposes no effective-effort readback. Finally, a disclosure: `.claude/hooks`, `.claude/skills` and `.claude/settings.json` are outside this sandbox's write permissions, so the operator ran the merge and `harness emit` directly; the reviewer verified the result — the hook bundle differs from main only in the `skeletonVersion` literal, the runtime snapshot pin and each file's content hash — rather than performing the regeneration.
