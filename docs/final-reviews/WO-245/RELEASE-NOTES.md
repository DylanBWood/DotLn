## Release overview

An instance owner opens their repository and sees their own front page. The kit's complete guide now ships as `docs/KIT.md`, a manifest-listed kit file that every update carries, and the `README.md` the kit seeds is one short page the owner may replace the day they clone, which no later kit update, starter refresh or Git merge touches again while the seed's pinned digest holds. A launchpad may also prepare and close a release with a front page that carries no release block. This release is for instance owners and the forks of DotLn-Enterprise-Starter; core's own front page and its rule are unchanged.

## Read before upgrading

- The starter refresh that carries this release migrates DotLn-Enterprise-Starter's unedited long `README.md` to the short seed once. A fork that already edited `README.md` may meet one merge conflict on it when it takes the refreshed starter: keep the instance's page. Later guide changes arrive in `docs/KIT.md` and leave the front page alone.
- The guide's sections moved whole: anything that read the instance README's §First steps, §Releases in this instance, §Kit files and instance files or §Taking upstream updates now reads them in `docs/KIT.md`; the exported `docs/README.md` points there, and the recovery phrase for an older instance names the refreshed starter's kit guide, read with `git show upstream/main:docs/KIT.md`.
- The README release block is optional in a kit root: with neither marker present, `release prepare` writes no claim and records `not carried` in its decision, and the close's release-block check passes as `not carried`. If either marker is present, the block must remain exactly one ordered block holding only the generated version line, as before. Core's page keeps its requirement.
- The starter refresh no longer refuses on a customized, missing or non-regular `README.md`: it keeps the page, reports the reason in the close row's new `keptSeeds` field and publishes the kit files. `CLAUDE.md`, `.gitignore` and the other seeds keep their refusals.
- The seed template's SHA-256 is pinned in the `launchpad-docs` case; a later release that changes the seed names the one rewrite of unedited starter copies in its decisions and in its own Read before upgrading.
- `scripts/kit/README.client.md` keeps its file name although it is now the short seed; the long guide's bytes live in `docs/KIT.md`.

## Substantive changes

**The kit guide.** `docs/KIT.md` holds the text of the former instance README with its opening rewritten for a reader arriving from the instance's own front page, its release block removed, and its §Kit files and instance files naming the guide among the kit files and `README.md` among the instance files written once; §Taking upstream updates states the README migration, the kept reasons, the pin and the one conflict; §Releases in this instance states the optional block. The file is listed in `KIT-MANIFEST.json`, carried by every update, declared in the `launchpad` suite's sources and the `launchpad-planning` machinery sources, and read by the export, planning and update cases that read the guide before.

**The front page.** The seed is the display name, one paragraph, the pointer to the guide, the release block with its `v0.1.0` claim and one invitation; the `docs/README.md` seed names `docs/KIT.md`. The `launchpad-docs` case pins the seed's digest, asserts the exported manifest's hash of the guide, its eleven headings and absent block, and the seed's title, link, exact block and absence from the manifest.

**The refresh rule.** `planStarterSeeds` returns rewrites and kept entries: `README.md` is rewritten while it equals a proven prior rendering, otherwise kept as customized, missing or not a regular seed file; the refusal for a customized seed names the other seeds only; the starter refresh carries `keptSeeds` on the real and dry-run rows. The update fixture proves the one migration from a long-guide prior export, the four kept variants through refresh and preview, the unchanged refusals for the ancestor and `CLAUDE.md` variants and the kit-only loop's verification refusals.

**The kit-root release.** `planReleasePreparation` judges whether the page carries a claim (any marker present, or a root that is not a kit root): without one it assigns or retimes the heading alone, writes no README edit and records `readmeClaim: "not carried"`; `releaseBlockRule`, shared by `release prepare`, the close and `check-surfaces`, passes a markerless kit root as `not carried` and keeps the malformed-marker, one-marker, two-block and prose refusals; the instance-history case replaces its README before the update, keeps the bytes through the update and the instance document gate, and prepares a release.

**Documentation.** Product 03 §Platform and instance boundary states the ownership boundary as built, with the refresh rule, the pin, the one conflict and the optional block.
