## Release overview

Application v0.85.0 lets an exported instance's registered target order run from `worktree start` through its own draft route, the final publish and release close with the kit carrying what used to be hand steps. The generated hook admits the recorded target worktree's `git push`, `gh pr` and publish-helper commands for the dispatched order from main's committed registration and operator grant, at the phases the lifecycle makes them legal, with host deny rules still applying. `worktree publish WO-NNN --target-worktree --draft` is legal at `verified`, and the closed-phase publish reuses its branch and pull request, so one order opens one pull request. Release close deletes declared regenerable output in the target worktree and in the clone's base checkout, judges the base by the fetched tree's ignore rules, refuses undeclared ignored material with the registration remedy, and can tag and release the target under a declared policy. The starter refresh pushes core's release tag name onto the refresh commit and creates the sibling's Release, so a fork previews `--from vX.Y.Z`.

Under three operator scope expansions and a recovery contract recorded in the order, the gate process also changes for every order: completion consumes recorded rows and runs no gate, final review reuses a passing complete review row at an unchanged code identity, the executor starts one complete run that leads with failed and changed suites, and the probe wrapper gives a complete run a six-hour outer bound instead of ending it at its 900-second deadline.

The visible changes:
- Trust: `registeredTargetAdmission` in the harness host admits a `git -C` push from the recorded target worktree of `wo-NNN` or the recorded draft branch to `origin`, `gh pr create|view|ready|edit` bound to the registered repository, and the `worktree publish --target-worktree` helper, only for the dispatched order's single recorded target worktree on its order branch, only when main's committed `dotln.config.json` registers the repository and main's committed grants carry an operator grant with `repo.push` and `pr.open`, and only at `verified` (the draft forms) or `closed` with a passing final review (the publish forms); a lease is admitted only as `--force-with-lease` naming the draft branch and the recorded draft head; a bare force, another remote, another branch, the base branch, a shell operator, a `$(pwd)` path, a foreign executable spelled as the helper, or an emitted `permissions.deny` match admits nothing.
- The literal fallback: a registration's `hostRules: "literal"` makes `worktree start` write that order's exact rules into the main checkout's untracked `.claude/settings.local.json` and `.codex/rules/dotln-WO-NNN.rules`, with ownership in an ignored per-order sidecar under the control root's `local/host-rules/`; release close removes only what the start added and keeps pre-existing operator rules; `harness check` names a stale sidecar with its `worktree host-rules --remove` or `--rewrite` remedy; the rewrite requires the committed opt-in and matching target registration before touching a rule. The fallback is off until an instance turns it on.
- Launch lines: `worktree start` of a target order prints `codex --add-dir` with the target worktree and the Copilot `--allow-tool` forms for the order's commands, and nothing for a launchpad order.
- The draft: the draft form writes a commit object from the target worktree's working tree through a temporary index, leaving HEAD, the index and `git status` unchanged, pushes it from the isolated lane to the declared branch, opens a draft pull request and records `PullRequestOpened` with `draft`, `branch` and `headSha`; a draft at `active` or `ready-to-verify` refuses naming the phase, a second draft at the same tree reports already published, a draft at a new tree updates the same pull request, and the closed-phase publish pushes the reviewed commit with `--force-with-lease` against the recorded draft head, updates the title and body, marks the pull request ready and records the reuse; another `--branch` refuses.
- The close: a class or registration declares `disposable` paths, composed into one sorted set that nothing removes a class entry from; the close deletes ignored files under them in the target worktree and in the base checkout, judges every untracked base file (already ignored or newly ignored) by the fetched base commit's `.gitignore` blobs in a scratch repository that neither the operator's global excludes nor an init template can widen, refuses an undeclared ignored file naming each top-level path once with the remedy, keeps the ordinary refusal for a file the fetched tree does not ignore, refuses an unreadable ignored base directory or unreadable declared target output before deleting anything, moves the base only after the target is judged, deletes the draft ref with the worktree, and lists the deleted roots with their file counts in the receipt beside the gate's `baseCheckoutWrites` advisory, which reads as unavailable when its record cannot be read. The ignore judgment reads the same 16 MiB path list as its candidate scan, so a populated base tree such as an installed `node_modules` is judged rather than failing the close.
- The target release: `release: { "policy": "declared" }` with `release.close` in the authority profile and the order's `**Target release classification:** patch | minor | major` header makes `release close --publish` tag the merged base with the next `v*` tag above the tags that base reaches (`v0.1.0` when none), push it as an annotated tag through the lane and create the target's GitHub Release from the order's title and objective; `--dry-run` previews; a retry reports current; a tag at another commit refuses; after a Release failure the retry keeps the recorded tag commit even when the base advanced or the remote tag moved or vanished. Without the policy the close stays no-release.
- The starter: after the refresh push, core's release tag name is pushed as an annotated tag onto the refresh commit and the sibling's Release is created with a one-line body naming core's Release; a retry reports both current; a tag at another commit refuses unless it is an ancestor whose committed kit manifest names this exact core commit and tag; `launchpad preview --from` with that tag resolves it from a fresh instance.
- The gate process: `implementation-ready`, `repair-complete`, `verification-result` and `final-review-result` consume the newest passing `npm run test:docs` row this worktree recorded at the current code identity whose tree hash is the working tree's, and run no gate; `final-review-result pass` consumes the newest passing complete review row at the integrated identity whichever role recorded it, with every required suite's tasks passing in the row, and refuses only when none exists or a newer run there failed; a complete run leads with suites whose latest execution failed, whose inputs changed after the newest gate row, or which this branch changed; an exclusive suite at the head of the queue waits for the lanes to drain; a focused product selection judges only the build-phase generated artifacts and marks its structural companion row partial; a selection compiles a stale runtime before capturing its subject and never installs the harness; the bounded wrapper gives a complete selection a six-hour outer bound and keeps 900 seconds for focused, document, machinery and listing ones.
- Role text: the executor starts one complete run and never a focused sequence before it, the verifier consumes the executor's complete row, the reviewer reproduces blocking claims first and reuses the complete row at an unchanged identity, every role writes its report after the complete run and runs `npm run test:docs` once after the last document edit, and the release-close profile says regenerable output under a declared path is deleted and never moved to scratch or offered back; the WO-221 role oracle pins both economy settings and links the WO-216 oracle by hash.
