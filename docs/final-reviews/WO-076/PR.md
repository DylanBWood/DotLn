# WO-076

An instance now owns its build without editing kit files. `node scripts/harness.mjs emit` reads the JSON overlay that the configuration's `build.overlay` names (by the kit's convention `build/overlay.json`) and composes it over the kit's Contributor build: replace the identity, equip or unequip the existing support switches, narrow the authority envelope, add `operator` or `host-policy` grants whose provenance the manifest records, or declare `build: none` and keep only the hand-written floor. `harness check` verifies the result, overlay bytes included. Before this change `harness emit` admitted one loadout, the configuration's `build` section was read by no script, and a fork that wanted a different build had to edit kit files that `harness update` cannot then update. The three-repository route's WO-118 depends on this.

**How an overlay composes.** The overlay is decoded positively against a closed version-1 schema: `version`, `build`, `identity`, `unequip`, `equip`, `narrow` and `grants`, each with a declared shape. A file that is missing, unreadable, outside the launchpad, not JSON, or that holds an unknown key or a wrong type refuses both `emit` and `check` before any write, naming the configured path and the key or condition. Composition happens in the skeleton's `contributorProgram`: narrowings apply to the kit's saved base before compilation and the ceiling is the kit's immutable envelope, so allowing an effect the kit does not allow, raising a resource limit or extending expiry without a grant refuses with `AUTHORITY WIDENING` and writes nothing. Grants apply after narrowing through the compiler, beside the kit's own temporary-write grant, and every profile's manifest records each grant with its `grantedBy`. The manifest gains `overlay: { path, sha256 }` of the exact bytes read, so a later edit to the overlay is drift that `check` reports. With no overlay declared the emitted content is unchanged; the compiler release re-pins the runtime snapshot, so hashes and version strings move while the semantic hash and the installed path list do not ([D004](../../evidence/WO-076/decisions.md#wo-076-d004)). `build: none` removes every owned generated surface, keeps the hand-written floor of `CLAUDE.md` alone and a manifest with no profiles so `check` keeps a subject. The compiler (0.27.0) now admits a permission facet with no static deny matcher, so the generic envelope hook survives when every static deny has an explicit grant.

**Read before merging.** Narrowing is pre-grant: a `narrow.deniedEffects` entry that the kit's temporary-write grant re-admits (the three `outside.write` effects) is accepted and silently not applied, and `narrow.allowedEffects` cannot remove a kit-granted effect ([D008](../../evidence/WO-076/decisions.md#wo-076-d008), FUP-d5d0ef5cf034102e). On the real core floor, `build: none` leaves the five Start-here `Read[role]` directives pointing at skills the same emit removed, and no sentence says that no compiled refusal, hook or verification governs the instance ([D007](../../evidence/WO-076/decisions.md#wo-076-d007), FUP-d72bf62d3c82ca3f; the carried FUP-44639ec9a751d8d1 is left by [D003](../../evidence/WO-076/decisions.md#wo-076-d003)). An identity string that contains a harness block marker is accepted, and the emitted `CLAUDE.md` then fails `check` until it is repaired by hand ([D009](../../evidence/WO-076/decisions.md#wo-076-d009), FUP-620f25409f65f4aa). New in this review: the `build: none` manifest, whose profile list is empty by design, reads as `runtime-unavailable` to the runtime reader every control-plane command consults, so such an instance is told to run the bootstrap on every `resume` and `plan` command, and `worktree finish`, `worktree settle` and release preparation refuse after a rebuild ([D011](../../evidence/WO-076/decisions.md#wo-076-d011), FUP-9d397b57910ae6ed). `emit --profile` now removes the other profiles' owned files too, consistent with ownership; a full emit restores them. The overlay path is only ever the configuration's `build.overlay`; nothing loads `build/overlay.json` implicitly. Registration and classes stay in `dotln.config.json`.
