## Source review

The kernel change is close to the smallest one that achieves the objective. `defaultEnvironmentProjection` lifts the two `stateField` reads verbatim out of `replay`'s loop and exports them, so the documented contract becomes a named, testable function rather than an inline convention, and `replay`'s loop becomes a three-line branch. The guard is the detail worth reading twice: `if (projectEnvironment !== undefined && !Number.isFinite(rngState)) throw` keys on **supplied-versus-omitted, not on projector identity**, which is what preserves the legacy path's raw-`NaN` behaviour byte for byte while making the new path strict. That asymmetry is deliberate, recorded in D001, documented in both 02 and the kernel README, and it is what VER-001's O4 and VER-002's O5 record; it is unreachable from the skeleton, where `draw()` returns a uint32. Environment key order is unchanged because the env literal is still built in `replay`, so a projector cannot reorder or override `now` and `predicates` — VER-001 proved that positively by feeding a projector that returns `now`, `predicates`, `extra` and a `__proto__` key and observing `env.now` stay at 10.

The skeleton side is ten one-line call-site changes and one exported function. After integration that function is `return kernelStateFromRuntime(state)`. I want to be precise about why that is the right resolution rather than a tidy-up. Before it, the repository had two functions with identical bodies reading the same two fields for the same purpose: WO-050's, used by the *live* `seiriReactor` calls in `beacon-observe.ts` and `verification-host.ts`, and WO-047's, used by the *replay* calls. Live/replay identity is the property criterion 1 asserts and the property `LiveReactorDriver` relies on structurally. Two independently maintained copies of the kernel-facing layout can drift, and a drift between exactly those two copies *is* a live/replay divergence — the failure this order exists to prevent. Delegating makes it unrepresentable. It is behaviour-preserving by inspection (same two reads, same key order) and by execution (the fourth sweep mode above).

The tests are stronger than the criteria require in one place and weaker in another, and both are worth the reviewer's honesty. Stronger: `assertProjectionIdentity` wraps `runScenario` and `replayScenario` themselves, so **every existing scenario test** in the file now silently asserts three-way projector identity on its own log rather than relying on a separate identity test — a good pattern, because it cannot be forgotten by a future test author. Weaker: the AC3 encapsulation pin is a grep whose exempt region is carved by two `indexOf` string anchors, so an alias, a destructure, a computed key or a reordering of the two functions evades it, and repeating an anchor string in a comment moves the window. That is VER-001's O1/O2 and VER-002's O2/O3, and I confirmed the property holds today with my own census rather than through the test. The criterion asks for a grep test; a grep test is what it got.
