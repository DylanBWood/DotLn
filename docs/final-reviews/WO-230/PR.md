# WO-230

A registered target order's pull request now describes the change the forge shows. When the order's subject has taken in base-branch commits after its activation base, both session publish forms (`worktree publish WO-NNN --target-worktree` and its `--draft` form at `verified`) fetch the target's base branch through the publication lane, read the merge base of the subject and that branch, and compute the Change table, the base-tree exemption and the no-change check from it whenever the activation base is an ancestor of it; the Change section's closing sentence then names the described base and adds that the order was activated at its activation base, which the described base descends from. When the two bases are equal, every byte of the table, the exemptions and the body is unchanged. A subject that does not descend from the activation base still refuses with today's text; a fetch failure refuses before any push, names the remote and the public forge selector without a path, and keeps the prepared work so a plain retry reuses the same commit. The activation base stays the base of every record, event, registry entry and verification; nothing rebinds it. Separately, `npm run plan -- check` no longer advises renaming the order's own evidence, verification and final-review files, which reach a target only as moved kit records the lint exempts by design; a target-side path carrying a launchpad identifier or a review word is advised as before.

Why it matters: on 2026-10-24 the operator's fork met a verified target order whose draft publish was refused before any push, because the table described 515 files from an activation base the base branch had since passed, 17 of them earlier orders' moved records whose identifiers the lint refuses, while a diff from the base branch's head lists 83; the same fork's plan gate printed eleven advisories, eight of them on the kit's own evidence files. The fork's final review chose a core fix taken through a kit update, and this order is that fix ([the order](../../work-orders/WO-230-target-publish-against-the-base-branch.md), [D001](../../evidence/WO-230/decisions.md#wo-230-d001--keep-the-activation-evidence-and-describe-the-fetched-merge-base), [D002](../../evidence/WO-230/decisions.md#wo-230-d002--keep-episode-publication-and-planning-time-admission-unchanged)).

What a reviewer should weigh. The described base is the merge base, not the draft commit's parent: the parent equals the merge base when the branch sits at the base branch's head, but names the previous published commit when the branch carries one, and the fixture's final publish shows six changed paths against the merge base and four against the parent, the parent losing the reviewed target change ([D007](../../evidence/WO-230/decisions.md#wo-230-d007--supply-the-final-publish-fixtures-required-decision-record)). The base branch is fetched through the lane, as release close fetches it, so a stale local tracking ref cannot choose a base the forge no longer agrees with, and the publish already needs the remote for its push. A same-tree draft retry whose history is longer than one commit over the activation base now recomposes, lints and edits the pull-request body, because its merge base can advance; the direct-child shortcut stays, since that history has no intermediate ancestor the base branch could newly hold ([D005](../../evidence/WO-230/decisions.md#wo-230-d005--refresh-a-published-draft-when-its-merge-base-can-advance)). An unchanged tree now pays the fetch before its "no change to draft" refusal and leaves its prepared commit and one `DraftPrepared` row behind with nothing pushed; the fetch-first order is the objective's, the refusal text is unchanged, and the next preparation overwrites the ref. The episode form (`observeTarget`) keeps the request's base by design, and no base advance event or correctable `baseCommit` is added; both are recorded known issues with reopening conditions ([D002](../../evidence/WO-230/decisions.md#wo-230-d002--keep-episode-publication-and-planning-time-admission-unchanged)). The byte comparison of the console's workstream page moved from the product suite to the document suite, so a product test no longer reads a generated input its identity excludes ([D006](../../evidence/WO-230/decisions.md#wo-230-d006--keep-generated-document-parity-in-the-document-suite)).

Validation: the executor's complete review passed 39 suites and 105 fresh tasks at code identity `201d143894c00d9beaa6b4c24297b4e79d8110d0baba3d89a77ccaa594c10aaf` after two failed complete attempts, each repaired on the record ([handoff](../../evidence/WO-230/handoff.md), [D006](../../evidence/WO-230/decisions.md#wo-230-d006--keep-generated-document-parity-in-the-document-suite), [D007](../../evidence/WO-230/decisions.md#wo-230-d007--supply-the-final-publish-fixtures-required-decision-record)); two independent Codex workers each found the same same-tree retry defect, fixed as D005 ([self-review](../../evidence/WO-230/self-review.md)). [VER-001](../../verifications/WO-230/VER-001.md) passed all seven criteria and probed three states the fixtures held constant: a base branch advanced past the subject's merge base (the table comes from the merge base, not the fetched head), an unrelated fetched base branch (the activation base is kept under today's text) and an unchanged tree with the remote down, then up. [FINAL-001](FINAL-001.md) integrated `main` and took in nothing, read the whole diff, reran the six new publish cases, the body case and the plan-refutation suite at the integrated tree, ran the affected and edition checks, and passed with no finding of its own. The paired base controls are in [controls.json](../../evidence/WO-230/controls.json).

Limits a reviewer should weigh: no live forge was used, the fixture's local forge standing in as the order's evidence gate directs, and that the forge diffs a pull request from the merge base is the design premise rather than something re-derived here; the criss-cross case, several commits from `git merge-base --all`, is untested, the single merge base Git returns being used when the activation base is its ancestor and the activation base otherwise; a fetch that fails while a push to the same remote would succeed is newly refused, with the prepared work kept; and the fork's three target-side fixture names that carry a platform order id are refused by the lint at their first publish unless renamed, which the filing pass's answer block tells the fork. Planning receipt 054's five known issues are judged in FINAL-001, and none has occurred.
