# WO-152

A mission check on the `claude-cli-print` transport returns a verdict again. Until now it could not: `missionReferenceIds` built the `contract-clause` reference list by concatenating the pinned contract's clause ids, the story contract's and the observed contract's, and those lists are identical whenever the contract has not changed mid-episode — the ordinary case. `missionCheckResultSchema` spreads that list straight into the emitted `reference` enum, so every clause id appeared twice, and the Claude CLI rejects a `--json-schema` whose enum repeats an item. Every print-transport mission check ended `transport-failed` after about 1.28 s, before any model call, which left WO-100's resident and WO-111's unattended hour with the Codex transport as the only one that works. The repair is one first-seen-order `Set` inside that branch: the pinned ids first, the story contract's next, the observed contract's last, each exactly once. `validateMissionCheckResult` tests membership with `includes` and is untouched, so a result accepted before this change is still accepted; the `thesis` and `exclusion` branches project one list each and are untouched too.

**The regression walks the schema rather than naming it.** It collects every `enum` the emitted schema carries by path, asserts the walk reached seven of them so a broken walk cannot pass vacuously, and then asserts the literal expected id lists for all three finding kinds across three subjects: an unchanged contract, a contract renumbered after the pin so the observed side drops `contract:criterion:2` and adds `contract:criterion:3`, and a subject carrying a story contract with one clause id of its own. Both validator directions are asserted — a pinned-only clause id is still a supported reference, an id no contract supplies is still refused. Two negative controls back it: removing the `Set` makes the exact six-id assertion fail with every id twice, and removing the story-contract source makes the eight-id union assertion fail and nothing else in the file.

**The evidence cost more than the fix, and all of it is on the record.** One live `claude-cli-print` mission check against a real bound store returned a validated `drift` verdict — exit 0, model `claude-haiku-4-5-20251001`, CLI 2.1.278, 14 changed paths, 0 omitted — which is the whole point of the order: the same path exited 1 with no stdout before the deduplication. Because `packages/skeleton/package.json` is a registered evidence source, the component bump also owed a re-mint of the authority and feedback editions with a live self-host episode. The first execution declined that on measured grounds — both edition checks passed, because `evidenceSourceContent` normalizes component release labels — and [VER-001](docs/verifications/WO-152/VER-001.md) failed the order for it: the measurement was sound, but a required criterion is amended by the operator, not waived by the executor. The repair minted both editions and ran the episode, which took three live attempts; two refused with `invalid-result` and the append-only store keeps all three, at a recorded 1,740,588 tokens and USD 4.2364 across 631,183 ms. The re-mints are identity-only and measured as such: `authority.json` is byte-identical to WO-149's, and the new `feedback.json` differs from it in exactly one field, `subject`.

**What a reviewer should know.** Two refused live episodes recorded only the code `invalid-result`; `WorkerInterrupted` carries no detail, the CLI prints only the code and raw output is discarded, so neither refusal can be diagnosed from the store. That is a real diagnosability gap, and it is boarded rather than fixed here because its fix touches declared feedback sources and would stale the editions this order just minted — [D009](docs/evidence/WO-152/decisions.md#wo-152-d009), follow-up `FUP-ed431cc1c8ca9a52`. It is not a schema refusal: `decodeResult` reaches `invalid-result` only after the CLI has exited 0 with `structured_output` present, and these attempts ran 186–226 s and cost a full model turn each. Final review added the story-contract case to the regression, which the planning pass's independent refutation had asked for and no earlier phase dispositioned ([D010](docs/evidence/WO-152/decisions.md#wo-152-d010)), and left this order's two deferred adjacent-queue items carrying the literal target `planning` rather than their public follow-up ids, because queue mutation is refused outside the executor phase ([D011](docs/evidence/WO-152/decisions.md#wo-152-d011)). One more thing a reviewer reading the control log should know: this order's final-review event records the reviewer's effort as `unknown`, and that is wrong — the observed value is `xhigh`, which the reviewer asserted absent without checking either `CLAUDE_EFFORT` or the persisted `modelSettings` entry. The event is not re-recorded, because a recorded transition is never repeated to repair a record; the error, the observed value and the stale harness discovery probe it exposed are in [D012](docs/evidence/WO-152/decisions.md#wo-152-d012).
