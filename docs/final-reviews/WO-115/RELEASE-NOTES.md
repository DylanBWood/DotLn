## Release overview

This release gives DotLn's resident a command surface a UI can consume. Until now the terminal was the only way to run a lifecycle phrase, activate an intent or step the operator's presence; the actor board and the status host could only read. The resident now serves `console-commands-v1`, a typed list of exactly the twenty-three commands that exist as terminal implementations, over a loopback socket bound to the local user. Each command runs the terminal's own entrypoint under the terminal's own compiled authority and returns the terminal's exact result bytes, so a UI can do what the terminal can and nothing the terminal cannot. The text console invokes them, and a browser shell can use the same client.

The intended audience is the operator and anyone building a console host: this is the contract the fork's shell and this repository's text host both consume, and the prerequisite for authoring in a UI without a second workflow state machine.

## Read before upgrading

No terminal command changes meaning, and no Beacon, status projection or evidence format changes.

- Every `dotln resident` run now creates an owner-only `console` directory inside its store, listens on a random `127.0.0.1` port with a token held in a mode-0600 descriptor, and removes that descriptor on orderly stop. A pre-existing `console` path in a store that is not an owner-only directory refuses the resident's start with a named error; move or remove it.
- `SIGHUP` now stops `dotln resident` in order, like `SIGINT` and `SIGTERM`, so a closed terminal interrupts the console commands it started.
- The resident's private log gains two unregistered event types, `ConsoleCommandInvoked` and `ConsoleCommandObserved`, with actor `console`; result bytes are content-addressed under the store's `console/results` directory. Retain that directory with the store if replay matters.
- The contract includes `release.close` and `worktree.publish`. A client holding the token can push a work-order branch, open its pull request or publish a release exactly as the terminal's `resume: release close` phrase can, under the same `lifecycle.run` classification and the same compiled envelope. Do not copy the token into a repository, URL or public status view.
- `console status --watch` now reads the status file every 250 ms beside its filesystem watcher, so a missed directory notification cannot leave the text host stale; the read stops when the watcher closes or errors.
- `@dotln/console` gains a `./client` export whose two functions import no Node API; `readConsoleConnection` stays in the package root for Node hosts.

## Substantive changes

**The contract.** `packages/skeleton/src/console-commands.ts` maps each command ID to a Node entrypoint and its leading arguments: the eight `resume` actions, `release close`, the five `worktree` actions, `harness emit` and `check`, the skeleton's `--compiled-diff`, `dotln intent`, `presence away`, `presence back` and `status`, `console status`, and `resident-bind --portfolio`. The remaining arguments go to that terminal parser, which owns every usage refusal. There is no effect column: the resident writes each request as the command an operator would type, classifies it with the terminal permission hook's classifier and decides it with the hooks' decider against the resident's compiled program envelope. Text the classifier cannot classify is refused, because the console has no host-permission layer to defer to. Saved-build selection, equip preview and portfolio declaration have no terminal command and are documented exclusions.

**The loopback.** The server listens on `127.0.0.1`, requires a bearer token that lives in an owner-only descriptor, refuses a `Host` other than `127.0.0.1` with its port and a non-local `Origin`, and caps bodies at 1 MiB. Caller, route and request checks answer on arrival; commands run one at a time. Every decoded request's response opens at once and carries a keep-alive byte every 30 s while it waits and while its command runs. A caller that disconnects interrupts its command's process group as Ctrl-C would; a caller that leaves while queued, or a request still queued when the resident stops, is refused with a recorded reason. Every console-originated refusal has the lifecycle CLIs' shape: exit 1, empty stdout and one `error:` line.

**Receipts and replay.** Each decoded request records its invocation and its result with actor `console`: the command name (verbatim only within a safe charset, otherwise by digest), an argument hash, the classified effect and the authorization outcome, then the exit code and the SHA-256 and length of the stdout and stderr bytes. Replay reproduces every result from the receipts and the content-addressed bytes without rerunning an effect, rejects an orphan or duplicate result and names an invocation whose result was never recorded. Console receipts use a transaction that leaves the resident host's change baseline alone, so a served presence change is seen as promptly as a terminal one.

**The clients.** `console commands --store` lists the contract and `console invoke --store` runs a command, writing the terminal's bytes unchanged and exiting with its code; when no resident console is reachable the text host prints one `console refused:` line. `invokeConsoleCommand` and `readConsoleContract` are exported from `@dotln/console/client` with no Node import, for a browser shell whose local host supplies the connection.

**Gate reliability, landed once.** The runtime status watcher gains a bounded read fallback with a regression under suppressed notifications and stops it on error as well as close; the resident crash-child fixture skips console setup; the worktree-integration fixture bases its origin `main` on the source's committed revision so the working-tree overlays and the committed leaves they import come from one revision; and the scheduler test asserts skeleton's shared scheduling after a same-source comparison recorded in product 07.

**Known limitations.**

- Lifecycle, intent, bind and emit success paths are not executed by the fixtures; their parity rests on the identical entrypoint, arguments, working directory and environment and on the refusal pairs ([D009](docs/evidence/WO-115/decisions.md#wo-115-d009--takeover-correction-of-the-fixtures-and-evidence-claims)).
- A second OS account was not exercised; the local-user boundary rests on the owner-only directory and descriptor and the token refusals.
- Queued requests stay in memory until their lane turn, so a resident killed before admission loses them; ordinary disconnect and orderly shutdown keep their receipts.
- There is no streaming; `--watch` remains a terminal command. Process-group interruption assumes a POSIX host.
- The historical cause of FINAL-001's two deadline failures is unknown; they did not recur in the seven complete gates that followed, and the settled register rows carry reopening conditions for a recurrence.
