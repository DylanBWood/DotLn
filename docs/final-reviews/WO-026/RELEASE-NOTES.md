## Release overview

DotLn `v0.5.2` is the patch above the published `v0.5.1`. It answers "which work orders are open, which are closed, and what closed them" from evidence instead of from a hand-maintained table. A generated index at `docs/work-orders/README.md` presents the active, open, closed, and historical work orders from three labeled sources: each work order's own header, the append-only control log reduced through the one shared event fold the lifecycle scripts use, and the local annotated release tags whose manifests name each order. Work-order files never move: their paths remain the stable addresses that immutable verification reports, final reviews, control events, and tag manifests already cite. `npm test` proves the index fresh, and the index records the tag objects it was generated from, so tagging a reviewed commit cannot make that release's own tests fail. The human planning map keeps only what cannot be computed: recommendation, rationale, tracks, and activation preflight. Audience: the operator choosing and preflighting the next work order, the planning session that must not relitigate evidence state by hand, and every session that reads the control plane. The order's operator-authorized ideation breakout also adds, as documentation only, a candidate end-user workstream application: arriving at the desk, carrying one outcome from request to return, replacing a successful but costly workflow one evidenced slice at a time, and coordinating one outcome across repositories. The component packages are unchanged: `@dotln/compiler` `0.2.0`, `@dotln/kernel` `0.2.1`, and `@dotln/skeleton` `0.5.0`, with no `src/` change and no dependency added.

## Read before upgrading

- **`npm test` now fails when the generated index is stale.** The chain runs `node scripts/work-orders.mjs index --check`, which regenerates `docs/work-orders/README.md` to memory from the current headers and control log and names the first differing line. Regenerate with `npm run work-orders -- index` after every lifecycle transition and before running evidence; no lifecycle command regenerates it for you, and the immutable checkpoint a transition mints therefore predates the refresh that projects it.
- **The index is generated; do not edit its cells by hand.** It carries one recorded tag-snapshot line naming each local release tag and its immutable tag-object id. `--check` requires every recorded tag to exist with the same object and refuses otherwise; release tags created after the snapshot are reported as newer evidence and do not fail the check until an explicit regeneration includes them. Right after this release is tagged, the committed index still records the snapshot through `v0.5.1` and reports `v0.5.2` as newer evidence; that is by design, and the next work order's executor regenerates it.
- **The control-log fold moved to `scripts/lib/control.mjs`.** `scripts/resume.mjs` re-exports `fold`, `parseControlEvents`, and `CONTROL_LOG_SCHEMA_VERSION`, so existing imports keep working; new consumers should import the library directly, and `foldWorkOrders` there is the per-order projection the index uses. The fold's behavior, error text, and event ordinals are unchanged. The release fixture that perturbs the schema export now edits the library file.
- **Release-record helpers moved to `scripts/lib/release-records.mjs`.** `release list`'s fallback attribution, used only when the first-parent walk between two releases finds no passing final review and no changed release notes, now lists every order a manifest names (its `workOrder.id` and its `docs/final-reviews/WO-NNN/` changed paths) instead of `workOrder.id` alone. On the current fifteen tags the output is byte-identical. Tag objects are now read under the explicit `refs/tags/` prefix, so a branch sharing a tag's name cannot shadow it.
- **The planning map no longer carries evidence, dependency, or model/effort columns.** Read the index for those; read `docs/planning/work-order-map.md` for recommendation, rationale, tracks, and preflight. The dated activation comparison beside it explains every difference from the retired hand-written cells.
- **Read the index's labels as it defines them.** Closed means a passing final review in the control log, not proof of merge or remote publication; release disposition comes from local annotated tags only, and `unreleased` is the honest state between a close and its tag; dependency status is a literal token view of the Depends on paragraph, so recommended, independent, and reverse references need human interpretation; `WO-001` and `WO-002` are time-indexed history and never enter the closed set; a version-shaped token that is not a strict application version renders `malformed` rather than being guessed.
- **The workstream application document is a candidate.** It describes no shipped interface, deployment, host, provider, schema, or command, adds no acceptance criterion to any order, and allocates no release rung.

## Substantive changes

- **Planning tooling: the generated work-order index.** `scripts/work-orders.mjs` (package script `work-orders`) renders `docs/work-orders/README.md` with `index` and checks it with `index --check`. Each row carries id, title, version, phase and computed dependency status, latest verification and final review with verdicts taken from events, release disposition with its attribution kind (`manifest workOrder.id`, `manifest changedFiles`, `historical record`, `no-release close`, or `unreleased`), Model, Effort, hard dependency tokens with satisfaction against the control-closed set, and path. Rows are sorted by id with a locale-independent comparison, cells are escaped so no header can inject table structure, output is byte-deterministic, and the file is written through an exclusive temporary file and rename.
- **Control plane: one shared fold, projected per order.** `scripts/lib/control.mjs` holds the event parser, the schema version, and the single event-type switch; `fold` is unchanged behavior, and `foldWorkOrders` observes the same scan to project every order's latest state, final-review verdict, and close ordinal while retaining global ordinals for refusals. An unknown event type or an invalid `recordedAt` refuses with its ordinal exactly as before.
- **Release records: shared tag, manifest, and attribution helpers.** `scripts/lib/release-records.mjs` provides version parsing and comparison, local tag enumeration with tagger time, annotation and manifest extraction, the `v0.2.0` historical record, `manifestWorkOrders`, and `localReleaseRecords`, which validates every release-shaped local tag's manifest and enforces a recorded snapshot when one is supplied. `release.mjs` and the index consume the same helpers.
- **Reproducible checks under a growing tag set.** The operator selected a recorded tag-object snapshot during execution after the executor identified that an implicit tag refresh would make a reviewed source fail its own tests the moment it was tagged. `index` observes the current local release tags and records them; `--check` validates the recorded set, regenerates against current headers and control, and reports additional tags as newer evidence. No command fetches tags or mutates Git.
- **Tests.** `scripts/test-work-orders.sh` creates a guarded temporary root and runs `scripts/test-work-orders.mjs`, whose eleven groups build synthetic repositories with a synthetic control log and simulated annotated tags and prove the derived states, complete and sorted rows, deterministic bytes, first-differing-line diagnostics, read-only checking, snapshot refresh and refusal, later-tag time handling, malformed and missing metadata, historical attribution, Markdown escaping, path and symlink guards, and CLI argument refusal.
- **Planning documentation.** The map is reduced to human judgment; a dated activation comparison explains every discrepancy between the generated cells and the retired hand-written ones; a reference audit records that 242 pre-existing concrete work-order references resolve to all 36 retained paths and discloses the one historical dangling pointer; the fixture transcript records the suite's output.
- **Product and process documentation for navigation.** The roadmap's §Work-order navigation and identity carries a dated migration adopting the evidence view while metadata standardization, a registry, a scheduler, and automatic recommendation remain candidates; the playbook's planning step and the execution guide's dispatch section direct readers to the index for evidence and to the map for recommendation and describe the refresh duty and snapshot rule; the docs map names the stable addresses and the generated index; the ledger records the adopted and superseded ideas.
- **Ideation breakout (documentation only).** `docs/product/12-workstream-application.md` records the candidate desk-to-delivery journey, the interaction table from start to return, incremental parity checks against both existing workflow generations, one outcome coordinating separate repository changes with partial delivery kept visible, what the repository does not yet implement, and the open product choices; the vision and interfaces documents link it as a candidate; the ledger records the three adopted product directions and the preserved pilot choices; the publication index gains its seven `vision` rows.
- **Work-order record.** The WO-026 authority completes its activation target as `v0.5.2` under the operator's release-assignment default, restates criterion 1 to permit exactly its own bounded edits, and appends the operator-authorized ideation receipt, the operator-authorized tag-snapshot amendment, and the executor's implementation evidence receipt.
