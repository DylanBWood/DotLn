# WO-242 — Plan-first mode: a plan, a conversation and the complete proposed diff before any implementation, with the operator's approval recorded as a typed event the hook and helpers enforce (v0.120.0)

An operator who elects `features.plan-first` in `dotln.config.json` and says `resume: next` now reads before anything is built. The executor drafts the change in an owned scratch candidate, never in the implementation worktree, and writes three documents under the order's `plan-first/` directory in its documentation root: `plan.md` (where the change goes, why, the contracts it expects, the decisions and alternatives, the questions only the operator can settle), `conversation.md` (the exchange, persisting across sessions under dated headings naming the writer) and `proposal.md` (each file's intended change and the candidate's complete diff against the base, binary changes included). It records `PlanProposed`, prints the three paths and stops. The operator answers in the terminal or in `conversation.md`; the next turn answers every new entry, paraphrases terminal words into the conversation with their capture digest, announces any transformation before carrying a passage onto a screened surface, regenerates the plan and the proposal, and records a new proposal when either changed. Ordinary words of approval are captured and recorded as `PlanApproved` for that exact revision, and only then is the candidate applied. With the election absent or false every surface is byte-identical to the base ([D011](../../evidence/WO-242/decisions.md#wo-242-d011)).

The wait is held by the hook and the helpers, not by role text alone. While the order is active, plan-first is elected and no approval stands for the current proposal, which includes the time before the first proposal, an executor write is admitted only under the plan-first directory, the order's evidence directory, ignored intake, the owned candidate and session scratch; the refusal names `conversation.md` and the `plan-approved` command. The same freshness judgment refuses `implementation-ready`, the candidate apply and the source-change apply, so every route the helpers control is held in process on a host with no hook. When approval state cannot be read the hook fails closed for writes and still admits reads, opaque commands and null discards for diagnosis ([D019](../../evidence/WO-242/decisions.md#wo-242-d019), [D020](../../evidence/WO-242/decisions.md#wo-242-d020)). The installed target hook holds the same wait for a target order and admits the owned candidate ([D012](../../evidence/WO-242/decisions.md#wo-242-d012)). An approval is bound to the base commit, the three documents' digests and the candidate's diff digest; a later proposal, a changed document or a moved base clears it and the next briefing names what changed. A second approval of the same proposal, an approval without a capture or with a hash that does not match, and a proposal whose diff omits a changed file or carries two outer diff blocks are refused; a literal marker inside the diff is payload, framed on Git's LF boundaries ([D016](../../evidence/WO-242/decisions.md#wo-242-d016), [D017](../../evidence/WO-242/decisions.md#wo-242-d017)).

The clean room sits at the boundary. `node scripts/terms.mjs --plan-first WO-NNN` and `node scripts/outward-lint.mjs --plan-first WO-NNN` screen `plan.md`, `proposal.md` and a carried passage on standard input, refusing `refuse:` terms and, for a target surface, launchpad identifiers, and listing `review:` terms; `plan-proposed` and `plan-approved` run that screen before recording. A private target's `conversation.md` is never rewritten and screened only when a passage leaves it; a self order's public conversation is a publication input that `npm run publication:check` refuses by entry and line without printing the term. A driven order stops at `awaiting-plan-approval` after the proposal and the router launches the next executor only after approval; the Codex continuation treats the wait as an intentional turn boundary. The executor root carries the plan-first steps only when the election is on, so the installed root with it off is the base's byte for byte; the elected root measures 47,593 bytes against the 51,226-byte acceptance recorded under the standing route, with no reviewed duty trimmed ([D009](../../evidence/WO-242/decisions.md#wo-242-d009), [D014](../../evidence/WO-242/decisions.md#wo-242-d014)).
