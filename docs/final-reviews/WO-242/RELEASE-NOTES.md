## Release overview

Plan-first mode lets an operator read a plan, a running conversation and the complete proposed diff before any implementation, and have the executor build only after their approval is recorded. It is for a teammate who knows the product and the codebase but not agents, and for anyone who wants to read before anything is built. The mode is an instance election and is off by default; with it off, nothing in this release changes what runs.

## Read before upgrading

Elect the mode with `"features": { "plan-first": true }` in `dotln.config.json`; the kit's example configuration now shows it off with a note. With it on, `resume: next` on an active order produces `plan.md`, `conversation.md` and `proposal.md` under `evidence/WO-NNN/plan-first/` in the order's documentation root, records `PlanProposed` and stops; answer in the terminal or in the conversation document, and approve in ordinary words. The hook refuses an executor's source write, and `implementation-ready` and the candidate apply are refused in process, until `PlanApproved` stands for the current proposal; a later proposal, a changed document or a moved base clears the approval, and so does the executor's own integration of `main` before its complete run, after which the operator is asked to approve the unchanged proposal again. On Codex, direct tool writes stay a role duty under host permissions; the lifecycle and apply helpers enforce the wait in process on every host. A private target's conversation is never rewritten and is screened only when a passage leaves it; a self order's public conversation is screened by `npm run publication:check`, which refuses a `refuse:` term by entry and line without printing it. Two new `resume` actions, `plan-proposed` and `plan-approved`, and the `node scripts/plan-first.mjs draft|diff|apply|screen WO-NNN` helper are executor commands the role records from the operator's direction. An exported instance receives these with its next kit update; nothing is required of an instance that keeps the mode off.

## Substantive changes

Lifecycle: `PlanProposed` and `PlanApproved` fold inside `active` without a new phase, carrying the base commit, the three documents' digests, the candidate's diff digest and the approval's capture hash; `status --json` and `current.md` project `planFirst` and list `plan-approved` while a proposal awaits; `implementation-ready` requires a standing approval and releases the pinned candidate. Hook and helpers: one freshness judgment, shared by the launchpad hook, the installed target hook, the readiness check, the candidate apply and the source-change apply, admits only the plan-first directory, the order's evidence directory, ignored intake, the owned candidate and session scratch while a proposal awaits, fails closed for writes when approval state is unavailable, and leaves reads, opaque commands and null discards available for diagnosis. Candidate and documents: the executor drafts in an owned scratch clone pinned until the order completes or is withdrawn, the proposal carries the complete binary-capable diff between marker comments framed on Git's LF boundaries, and `plan-proposed` refuses a missing document, an invalid or disagreeing marker, a proposal whose diff does not match the candidate, or a duplicated outer block. Screens: `terms --plan-first` and `outward-lint --plan-first` screen the two regenerated documents and a carried passage, and an announced transformation is written to the conversation before the transformed text is carried. Router and continuation: a drive stops at `awaiting-plan-approval` after the proposal and resumes only after approval, and the Codex continuation treats that stop as intentional. Role and guide: the executor root carries the plan-first steps only when elected, so the installed root with it off is byte-identical to the base; the kit guide's §Plan-first mode, product 07, product 12 and the feature registry state the mode as built.

## Progressive polish

The real regeneration fixture now runs under exclusive admission so its fixed child deadlines are judged under the conditions they assume; the launchpad export test asserts the example's disabled election and its note by meaning rather than a boolean; the feature advisory check takes an explicit inventory so a queued consumer can still be exercised after the real one landed; the console fixtures follow the WO-242 feedback edition; and the generated hooks, manifest and Codex continuation are re-emitted from the changed sources.
