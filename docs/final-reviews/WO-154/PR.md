# WO-154

Every feedback self-host edition used to copy the full text of every file the live verifier judged, twice, into the tracked tree: about 2.1 MB per edition on today's subject, 105 MB of the repository's 185 MB, growing with every close. And because staleness followed every registered source rather than what the verifier judged, an order that bumped a component beside an unrelated edit paid a live self-host episode of two to five minutes and USD 1.5 to 3.3 for an audit whose subject had not changed in any way that mattered. This pull request lands WO-154: a feedback edition now records the judged files by Git blob reference and rebuilds their bodies when a check or reader needs them, and it goes stale only when the judged behavior or the regenerated report changes. The two editions minted here are 178 KB and 189 KB against 2.2 MB by value.

**Editions by reference.** `feedback-evidence --record-selfhost` projects every `{path, contents}` files entry of the verifier stream (the opening's subject and baseline, and the persisted capsule) to `{path, blobHash, bytes}`, with the Git blob identity of the UTF-8 bytes read so the reference is stable before the commit exists; the two synthesized `.feedback-source/` package projections name the repository blob they derive from. It writes only after the references rebuild the store's stream byte for byte. `--check` resolves each body from a hash-matching working-tree file, the edition's own report and `pins/` snapshot, or one `git cat-file --batch` for the rest (56 times faster than one process per reference, [D002](docs/evidence/WO-154/decisions.md#wo-154-d002--economy-experiment-how---check-resolves-blob-references)), verifies that the rebuilt subject hashes to the recorded revision, and names each unresolvable reference by path. A content-addressed `pins/` snapshot beside the edition keeps the raw bytes of every label-bearing judged file, so a version bump before the first commit cannot strand a reference ([D007](docs/evidence/WO-154/decisions.md#wo-154-d007--a-pins-snapshot-keeps-a-pins-only-change-from-stranding-a-reference)).

**A behavior key, not a registered-source key.** The schema 2 record carries a behavioral identity over the 51 files the verifier judged with component release labels normalized, a pins record of the labels themselves, and a reference to the live audit. The regenerated report is compared with the live one apart from `subject` and `policyHash`, and the recorded compiled program is compared with the current lowering apart from its compiler label, which closes the hole a bare `policyHash` exemption would open. A pins-only change keeps the audit with no action; `feedback-evidence --carry` mints a deterministic edition naming the live audit it carries; a judged-file change is refused, and the WO-147 D010 regression proves that a forged identity is refused twice more by the live audit's own per-file comparison. The executor's census corrected the order's premise: 16 of 81 historical re-mints were label-only on the judged files, not most, and each was owed because a registered source the verifier never judged changed beside it ([D001](docs/evidence/WO-154/decisions.md#wo-154-d001--goal-alignment-a-corrected-premise-and-the-design)).

**A recorded compiler release is metadata.** [VER-001](docs/verifications/WO-154/VER-001.md) found that once a compiler release-label change was built, every replay layer recompiled the recorded program at the current label and refused it, so neither check nor carry survived the very bump the order promised to make free. The repair ([D011](docs/evidence/WO-154/decisions.md#wo-154-d011--ver-001-f1-repair-a-compiler-release-is-recorded-metadata-at-every-replay-layer)) makes `assertCompiledFeedback` and `assertVerificationTask` lower a recorded program or capsule at the release it names and refuse every other difference, lets the verification reactor adopt a persisted command whose capsule differs from the dispatched one only in that label, and has `--check` name the deterministic carry when a compiler release moved the policy hash the console binds. That is the compatibility decision WO-050 D002 and WO-133 D004 had reserved; the operator confirmed WO-154 makes it, the WO-050 byte oracle keeps its bytes behind a hash-chained successor manifest that records why four historical refusals now replay to completion, and the oracle streams its digest because a full historical replay is longer than any string the runtime can build ([D014](docs/evidence/WO-154/decisions.md#wo-154-d014--wo-154-is-the-compatibility-scope-wo-050-d002-reserved), [D015](docs/evidence/WO-154/decisions.md#wo-154-d015--wo-133-d004s-rejected-option-is-now-the-contract)).
