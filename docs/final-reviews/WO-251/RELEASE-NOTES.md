## Release overview

A session in a DotLn instance no longer takes over the operator's desktop or the operator's own signed-in browser. Desktop control (the Claude desktop app's computer-use tools and a linked cloud session's remote-device tools) and the operator's own browser sessions (Claude in Chrome and the desktop app's browser pane) are refused unless the instance elects `features.desktop-control` in `dotln.config.json`, and an election only makes them admissible: the operator must still ask in the session. A web surface is verified in a browser the session launches, through the Playwright MCP's snapshot of the DOM and accessibility tree and a screenshot read as an image, or through the project's own browser tests. The permission hook and Claude Code's own `permissions.deny` both enforce it, every role's text states it, and the kit's refusal count is now derived from its list. This release is for instance owners and every session that runs in an instance; it changes no session's ordinary tools.

## Read before upgrading

- After updating the kit, run `node scripts/harness.mjs emit`: the regenerated `.claude/settings.json` carries sixteen deny entries for the desktop and operator-browser servers and skills, and the hook refuses the same tools with `DOTLN_DESKTOP_CONTROL_REFUSED`. A session that used desktop control, Claude in Chrome or the desktop app's browser pane before this release is refused until the instance elects the feature; `node scripts/harness.mjs check` reports a settings file that disagrees with the configuration.
- To admit those tools, add `"features": { "desktop-control": true }` or `{ "desktop-control": { "on": true, "note": "the operator's reason" } }` to `dotln.config.json` and re-emit. The election admits the tools; the operator's explicit request in the session is still required before a session uses them. Turning the election off takes effect at the next judgment, before any re-emit.
- `dotln.config.json` gains a `features` section with one known id, `desktop-control`. An unknown feature id, or a value that is neither a boolean nor `{ on, note }`, refuses every command that loads the configuration, naming the id or field, and the hook refuses the desktop tools with that cause.
- The hook and the host rules match a listed skill by its exact name (`anthropic-skills:computer-use`, `anthropic-skills:chrome-browser`, `anthropic-skills:built-in-browser`, `claude-in-chrome`) with or without arguments; an alias, display name or plugin form of the same skill is outside both layers' names, while the desktop and operator-browser tools themselves stay refused under every probed name (D017 boards the repair).
- Codex tool calls are unhooked: under Codex the rule is the sentence every role skill carries, and the worker transport's disabled features are unchanged. Copilot reuses the Claude registration.
- The kit template's new browser paragraph sits in the instance-owned floor of `CLAUDE.md`, which a kit update changes only through opted-in instance actions; an existing instance receives the rule through its regenerated role skills and the generated harness block, and may copy the paragraph into its own floor. The template's provenance and navigation paragraphs were shortened without losing a duty.
- Component versions: `@dotln/compiler` 0.36.0 and `@dotln/skeleton` 0.77.0, with the harness-host compatibility pin at 0.41.0; the console keeps 0.5.0 with its internal pins updated. No external dependency changes.

**The hook.** `harnessToolEffects` gains a `desktop` effect for eight host namespaces, and `isDesktopControlTool` classifies them by prefix and `Skill` by its selection. `desktopControlResponse` reads the election with `readFeatures` at judgment time, refuses with the key, the Playwright route and the request requirement when it is off or unreadable (with the validator's bounded cause), records the judgment without letting an observation failure change it, and when the election is on returns one advisory per session after the existing descendant-cap and router-launch guards. The refusal is judged before the moved-working-directory stand-down and before the outside-write judgment, so it holds from a nested or outside directory. A Playwright MCP tool keeps its existing classification advisory.

**The host settings.** `desktopControlDenyRules` derives sixteen `permissions.deny` entries from the same inventories, the namespace prefix followed by `*` for each namespace and, for each skill, `Skill(name)` with `Skill(name *)`; the settings emission includes them unless the program's `desktopControl` is `true`. `harness emit` reads the election from `dotln.config.json` and passes it through the instance overlay; `emitHarness` and `checkHarness` read it for their root; the compiler reads no configuration. `harness check` exits 1 with `harness drift` when the settings and the configuration disagree.

**The configuration.** `features` joins the section keys with `validateFeatures`: a boolean or `{ on, note }` per known id, unknown ids and keys refused by name, absence read as off; `readFeatures` resolves the election.

**The roles and the refusal count.** `browserVerificationGuidance` is inserted second in every contributor and target role's procedure, so all fourteen installed role skills carry it. `HARNESS_REFUSALS` holds seven rows, each with its id, source order and clause, and the refusals sentence is rendered from them, so `CLAUDE.md` reads `DotLn has 7 refusals (WO-135, WO-139, WO-144, WO-234, WO-251)`. A new role oracle, `wo251-role-baseline.json`, chains to the WO-247 oracle and pins every root; the startup-cost consumer now requires a measured ceiling breach to name its optimization follow-up in the register instead of failing.

**The kit and the documents.** The kit template states the browser route and the election; the example configuration elects `false`; the kit guide's §What runs here, and what does not opens with the election's shapes, the re-emit and the check, the Codex note and the route; product 07 §Discipline states the seventh refusal, the election, the request requirement and the route; the feature inventory lists the election and marks the `features` section as implemented with WO-241's registry still planned.

**Tests.** Four `harness-fixtures` cases judge the hook through its generated process (refused off, admitted on with one advisory, the `Skill` forms, Playwright unchanged, moved cwd, unavailable journal, the descendant and router guards) and drive the fixture's own CLI through emit and check under three elections; a `configuration-root` case walks valid, absent and invalid elections; two `compiler` cases assert the deny entries by election and the rendered sentence's count and clauses; the WO-146 profile-hash case asserts the eight desktop entries separately and keeps its historical pin; the template and the disabled-harness removal helper are declared sources of `harness-fixtures`, and the register of the process-debt suite.
