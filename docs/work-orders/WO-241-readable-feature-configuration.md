**Cites (read these sections):** `scripts/lib/config.mjs` (schema, defaults and loadConfig); `scripts/lib/harness.mjs` (decodeBuildOverlay and emit/check); `packages/skeleton/src/loadouts/contributor.ts` and `executor-supports.ts`; `scripts/kit/CLAUDE.template.md` §Clean Room and §Secrets; `scripts/kit/README.client.md` overlay contract; product 03's launchpad export paragraphs; product 07 §Operator-opened planning pass; [feature inventory](../product/feature-configuration.md).

**Objective:** An operator can read one primary configuration, understand which optional features and operator preferences are enabled, and see why an invariant cannot be disabled. Core and an authorized private instance can select different loadouts without silently changing authority or sharing private source.

**Observed gap (2026-10-30 at `4090d70d`):** `dotln.config.json` exists, but core's file holds only version, historical orders and contribution author. `build.overlay` selects a separate JSON file; ten optional support IDs and `build: none` already work. There is no unified human inventory or effective view of selected features and their origins. The portable Contributor identity hard-codes employer separation, while the starter's handwritten floor speaks of the repository owner's rights; its Secrets paragraph also prohibits private hostnames indiscriminately. Neither boolean support switches nor `build: none` expresses destination-aware private collaboration. This is a policy/loadout distinction, not permission to weaken core's locked floor.

**Design:** use the existing versioned JSON configuration and overlay lowering. Keep keys small, descriptive and explicitly documented; JSON's lack of comments is handled by a readable inventory, descriptions in the inspector and a minimal example. Classify each entry as required platform invariant, optional platform capability, or instance/operator preference. Inventory columns name default, current selection, implementing reader, consequences of off, dependencies, authority impact and whether it is available or only planned. Future orders may add and retire entries with their consumer changes. Unknown/conflicting keys refuse before emit mutates anything. Existing configurations and overlays keep their effective behavior; no migration rewrites them silently.

Reject a second YAML/TOML configuration or two independently authoritative feature lists (axis: drift). Reject treating core's operator habits as universal rules. Reject a `cleanRoom: false` or repository-visibility-as-permission switch: core's employer/secret floor remains mandatory, and an instance's private destination policy requires explicit recorded repository authority. Separate credentials and unauthorized disclosure from authorized ordinary project links. Credentials remain excluded everywhere; allowed private links stay solely in the authorized private target. A public request remains a manually written generic statement. Changing GitHub visibility never automatically broadens policy.

**Acceptance criteria (all required):**

1. One primary configuration and the effective view explain selected features, defaults, dependencies and non-disableable invariants. The inventory names real consumers and labels planned choices unimplemented. Every configurable selection has a tested effect.
2. Existing missing-file, explicit-file and overlay configurations retain their behavior; unknown keys, duplicate/conflicting choices and unsafe widening refuse before mutation. `build: none` retains its existing meaning and does not remove the handwritten floor.
3. Portable choices and core operator choices are distinguishable. The core profile retains its existing employer/secret prohibition. An explicitly authorized private-instance profile accepts ordinary local project links without exporting them, while credentials, ungranted destinations and attempts to broaden core's floor refuse. Both generated instructions and active mechanisms agree; no visibility-only inference grants authority.
4. Starter exports and both update routes preserve instance-owned choices and custom scripts. An inherited floor is never silently weakened by an update. The current-reference sweep in step 6 removes the retired deployment narrative without altering historical records or unrelated technical terminology.
5. Product and starter guidance and the inventory state the built choices. Required deterministic re-mints, oracle checks and any triggered live feedback episode pass. `npm run publication:check`, `npm test`, `npm test -- --review` and `npm run test:docs` pass; `git diff --check` is clean.
