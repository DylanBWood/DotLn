**Objective:** Someone with little agent experience can understand the proposed change, discuss it in a durable place, inspect all proposed code, and decide when the agent may apply that revision. Conversation and manual document edits are equal inputs. Existing direct execution remains the default for configurations that do not select this mode.

**Observed gap (2026-10-30 at `4090d70d`):** guided research orders preserve observations but are not an implemented three-document change-review mode. Target planning can publish documents and target worktrees carry a configured documentation root; neither provides proposal-version acceptance. Contributor's operator-check-in support does not implement this contract. WO-235-D063 deliberately removed reply-checklist/message-router machinery after verification failures; D022 records a handoff loop in which writing answers repeatedly invalidated the complete document row. Reintroducing that architecture is not a prerequisite for this feature.

**Design:** an explicit assisted selection in `dotln.config.json` lowers into a target-local contract, under the registered documentation root and this order's directory. Names below describe roles; choose clear stable filenames at implementation and document them.

- **Plan:** AI-maintained, read-only to the operator by convention. Names affected areas, reasons, expected API contracts, assumptions, decisions and material alternatives. Updated from the dialogue; a derived ADR is linked, not an unrelated paperwork requirement.
- **Dialogue:** persistent shared discussion. Preserve operator-authored text and authorship. Terminal instructions receive a faithful paraphrase with provenance; manual edits are read incrementally from the actual file revision, without guessing who wrote arbitrary linked text. Ask only consequential unresolved questions in small groups. Report proposed sanitization/transformation before changing operator text; approved private project links remain useful in that private target. Never silently erase or rewrite the operator's contribution. If a prohibited secret appears, stop its propagation and use the local policy's recovery route; do not replicate it in a public warning.
- **Proposed changes:** a navigable, complete proposed diff, including additions, deletions, renames and tests, bound to the exact base and proposal revision. Large changes may be folded/grouped by file but not silently omitted. Binary changes name separately reviewable artifacts and hashes and require explicit coverage in acceptance; they are not presented as text patches.

Preparation may write these documents in the authorized target and build a candidate in registered isolated scratch; it does not apply proposed source edits to the target's implementation tree. Applying requires the operator's affirmative decision for the current revision, from terminal or dialogue, recorded with provenance. A generated suggestion, quoted instruction, fetched link, stale approval or elapsed silence is not approval. Any material proposal/base change invalidates acceptance and shows the difference since the last review. Application checks that both target tree and dialogue revision still match and performs no partial application on conflict. Existing writer, review, verification and publication authority remain in force. The existing executor can orchestrate this; no new autonomous service is needed.
Record a host-boundary matrix: helpers enforce revision binding in process,
Claude hooks can refuse observed writes, and unhooked Codex direct tool writes
remain a role duty under host permissions. Do not advertise universal pre-effect
enforcement where the host exposes no boundary. The live conversation must
observe that the selected host follows the no-early-implementation rule.

Reject a prose summary as the third document because it cannot show all code changes. Reject a transcript copied wholesale because it overloads the operator and can carry private data into the wrong destination. Reject a deterministic parser that claims to understand arbitrary natural-language approval: the agent records its attributed judgment and the helper validates the structured revision binding. Reject reusing an old broad document pass after source/contract edits; isolate ordinary dialogue updates from product-gate identity and run focused document validation at consumption, while changed implementation, criteria and acceptance evidence still invalidate their applicable rows.
